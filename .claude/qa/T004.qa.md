## Manual QA — T004

**Prerequisites:** Docker Desktop installed and running (confirm with `docker ps` — it should return an empty table, not a pipe-connection error).

1. From the repo root, copy the env template and fill in real values:
   `cp .env.example .env`
   Edit `.env` and replace `SA_PASSWORD=<strong-password-here>` with a real value meeting SQL Server's complexity rule (8+ chars, upper+lower+digit+symbol) — e.g. `SA_PASSWORD=Sc5!TrainingPass`. That's the only variable this ticket's infra actually reads — you invent it yourself, it's not issued by anything.
   `JWT_SECRET` and `USER_DB_CONNECTION` only guard the `api-gateway`/`user-service` *stub* containers (no real app code until T011/T015+) — leave them as placeholders and don't start those two services in step 2 below.
   Expect: file saved, no errors.

2. Bring the infra-only services up (skip the app-service stubs, which will fail to build since T001-era Dockerfiles may be incomplete):
   `docker compose up -d sqlserver sqlserver-init mongodb kafka redis kafka-ui`
   (No separate `zookeeper` service — Kafka runs standalone in KRaft mode; see note below.)
   Expect: command returns, no immediate error about "no configuration file provided" (this confirms `COMPOSE_FILE`/`.env` resolution worked) or `variable is not set`.

3. `docker compose ps`
   Expect: `sqlserver`, `mongodb`, `kafka`, `redis`, `kafka-ui` all eventually show **STATUS: healthy** (may take up to ~60s due to `start_period`). `sqlserver-init` should show **Exited (0)** — that's success for a one-shot job, not a failure.

4. If `sqlserver-init` shows a non-zero exit code:
   `docker compose logs sqlserver-init`
   Expect on success: sqlcmd output creating 8 databases, no `Login failed` or password-policy error. If you see a password-complexity error, your `SA_PASSWORD` in `.env` doesn't meet SQL Server's policy — fix and re-run `docker compose up -d sqlserver-init`.

5. **AC2 — SQL Server on 1433:**
   `docker exec -it sqlserver /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P "<your-SA_PASSWORD>" -C -Q "SELECT name FROM sys.databases"`
   Expect: a list including `UserServiceDb`, `DiscoveryServiceDb`, `ConnectionServiceDb`, `ChatServiceDb`, `RatingServiceDb`, `NotificationServiceDb`, `ReportServiceDb`, `AdminServiceDb`.

6. **AC3 — MongoDB on 27017:**
   `docker exec -it mongodb mongosh --eval "db.adminCommand('ping')"`
   Expect: `{ ok: 1 }`.

7. **AC4 — Kafka on 9092:**
   `docker exec -it kafka kafka-topics.sh --bootstrap-server localhost:9092 --list`
   Expect: command returns (empty list is fine — no topics created yet by design, per the ticket).

8. **AC5 — Redis on 6379:**
   `docker exec -it redis redis-cli ping`
   Expect: `PONG`.

9. **AC6 — Kafka UI on 9000:**
   Open `http://localhost:9000` in a browser.
   Expect: page loads and shows a cluster named `local`. **Then specifically check**: click into the cluster and confirm the broker count/status shows as reachable, not an error banner or "0 brokers." If it shows an error here, that's the advertised-listener issue flagged below — expected/known, not a new regression, but worth confirming so it's not silently assumed fixed.

**Cleanup:** `docker compose down` (stops and removes containers, keeps `sqlserver-data`/`mongodb-data` named volumes so your test databases survive a restart). Only add `-v` (`docker compose down -v`) if you want to wipe the databases too — e.g. before re-testing `sqlserver-init`'s database-creation script from a clean state.

**Known minor issues from review (not blockers, but worth watching for during the steps above):**
1. `kafka-ui`'s internal topic browser will likely show a broken/errored cluster view — `kafka-ui` bootstraps via the container address `kafka:9092`, but the broker's advertised listener is pinned to `localhost:9092` (needed for AC4, host reachability). Once `kafka-ui` gets that address back in a metadata response, it tries to reconnect to itself, not the broker. Already tracked for a proper fix in T009 (dual listener). Confirm this during step 9 rather than assuming it's fine.
2. `SA_PASSWORD`'s guard clause (`${SA_PASSWORD:?...}`) only checks that the variable is set — not that it meets SQL Server's complexity policy. A weak password (e.g. `password`) will crash-loop the `sqlserver` container with a native SQL Server error instead of a clear message. Use a real complex password in step 1.
3. The Spring-service JDBC URLs added for discovery/connection/rating/admin in `docker-compose.override.yml` have no username/password fields at all. Out of scope for T004, but flagged so it isn't assumed already solved — those services will need real credentials wired in before they can connect to SQL Server.

**Issues actually hit while running this checklist, and fixed in the code (2026-08-15):**
4. **Zookeeper healthcheck false-negative:** ZooKeeper 3.5+ disables its "four-letter word" diagnostic commands (like `ruok`) by default except an explicit whitelist. The `zookeeper` service's healthcheck sent `ruok`, but the image's default whitelist only allowed `mntr`/`srvr` — so ZooKeeper silently refused to answer and Docker marked it unhealthy even though it was running fine. This is now moot (see #5), but the general lesson stands: a healthcheck relying on a diagnostic command needs that command explicitly whitelisted via `ZOO_4LW_COMMANDS_WHITELIST`.
5. **Kafka is KRaft-only as of Kafka 4.0:** `bitnami/kafka:latest` pulled today tracks Kafka 4.0, which removed Zookeeper support entirely — the container crash-looped demanding `KAFKA_CFG_PROCESS_ROLES`/`KAFKA_CFG_NODE_ID`. The `zookeeper` service and Kafka's `KAFKA_CFG_ZOOKEEPER_CONNECT` env var have been **removed from `docker-compose.yml`**; Kafka now runs standalone in KRaft mode (`KAFKA_CFG_PROCESS_ROLES=controller,broker`, a single-node metadata quorum of one — see the comment block above the `kafka` service). Step 2's command above already reflects this — do not add `zookeeper` back to it.
