## Manual QA — T006

**Prerequisites:** SQL Server instance running (via `/docker-up` or `docker compose up sqlserver`).

1. Confirm SQL Server is reachable:
   ```
   docker exec -it <sqlserver-container> /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P '<password>' -C -Q "SELECT @@VERSION"
   ```
   Expect: version string printed, no connection error.

2. **Rating Service — ratings unique index.** Create `RatingServiceDb`, apply the migration
   (`mvn -pl rating-service flyway:migrate` once datasource is configured, or apply the `.sql`
   file manually via sqlcmd), then:
   ```sql
   INSERT INTO ratings (rater_id, rated_id, connection_id) VALUES (1, 2, 100);
   INSERT INTO ratings (rater_id, rated_id, connection_id) VALUES (1, 2, 100);
   ```
   Expect: second INSERT fails with `Violation of UNIQUE KEY constraint 'idx_ratings_connection_id_rater_id'`.
   A different `rater_id` (e.g. 3) with the same `connection_id` must succeed.

3. **User Service — otp_attempts.Phone unique.** Run `dotnet ef database update` against
   `UserServiceDb`, then:
   ```sql
   INSERT INTO otp_attempts (Phone, AttemptCount) VALUES ('+15551234567', 1);
   INSERT INTO otp_attempts (Phone, AttemptCount) VALUES ('+15551234567', 1);
   ```
   Expect: second INSERT fails with a unique-index violation on `IX_otp_attempts_Phone`.

4. **User Service — EF model/snapshot agreement.** Run:
   ```
   dotnet ef migrations add ProbeNoOp --project src/services/user-service
   ```
   Expect: EF reports "no changes" and refuses to create a new migration (proves
   `AppDbContext.cs`, the migration, the Designer file, and the snapshot are all in
   agreement). If EF instead generates a new migration touching `otp_attempts`/`Phone`,
   that's a mismatch — delete the generated migration and re-diff the four files.

5. **Connection Service — filtered unique index (PENDING only).** Apply the migration to
   `ConnectionServiceDb`, then:
   ```sql
   INSERT INTO connection_requests (requester_id, recipient_id, status, expires_at) VALUES (1, 2, 'PENDING', DATEADD(HOUR, 1, SYSUTCDATETIME()));
   INSERT INTO connection_requests (requester_id, recipient_id, status, expires_at) VALUES (1, 2, 'PENDING', DATEADD(HOUR, 1, SYSUTCDATETIME()));
   ```
   Expect: second INSERT fails on `idx_connection_requests_unique_pending`. Then:
   ```sql
   UPDATE connection_requests SET status = 'EXPIRED' WHERE requester_id=1 AND recipient_id=2;
   INSERT INTO connection_requests (requester_id, recipient_id, status, expires_at) VALUES (1, 2, 'PENDING', DATEADD(HOUR, 1, SYSUTCDATETIME()));
   ```
   Expect: this third INSERT succeeds (proves the filter correctly ignores non-PENDING history).

6. **Discovery Service — geospatial column + spatial index.** Apply the migration to
   `DiscoveryServiceDb` via a tool that preserves `GO` batch separation (sqlcmd, or Flyway
   once wired up — a raw JDBC single-statement executor that ignores `GO` will fail here), then:
   ```sql
   SELECT name, type_desc FROM sys.indexes WHERE object_id = OBJECT_ID('scan_sessions') AND type_desc = 'SPATIAL';
   ```
   Expect: one row, `idx_scan_sessions_destination`, `type_desc = 'SPATIAL'`. Then:
   ```sql
   INSERT INTO scan_sessions (user_id, destination_lat, destination_lng) VALUES (1, 40.7128, -74.0060);
   SELECT destination.STAsText() FROM scan_sessions WHERE user_id = 1;
   ```
   Expect: returns `POINT (-74.006 40.7128)` with no error (proves all required `SET`
   options were in effect when the PERSISTED computed column was populated — if any were
   missing, this INSERT itself fails with error 1934, not just index creation).

**Cleanup:** `docker compose down` (or drop the four test databases if reusing a shared instance).
