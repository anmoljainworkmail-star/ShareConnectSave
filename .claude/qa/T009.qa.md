## Manual QA — T009

**Prerequisites:** Docker Desktop running. A `.env` (or exported shell vars) providing `SA_PASSWORD`, `JWT_SECRET`, and `USER_DB_CONNECTION` — `docker-compose.override.yml` requires these even to start just the Kafka pieces, since Compose parses the whole file. Dummy values are fine for this QA pass (e.g. `SA_PASSWORD=Test1234!Test`, `JWT_SECRET=localtestonly1234567890`, `USER_DB_CONNECTION=dummy`).

1. From `src/infra`, run:
   `docker compose up -d kafka`
   Expect: `Container kafka Started` with no errors. If Compose instead prints `required variable ... is missing a value`, you're missing one of the prerequisite env vars above — set it and retry.

2. `docker inspect kafka --format="{{.State.Health.Status}}"`
   Expect: eventually prints `healthy` (may show `starting` for ~60-70s first — poll every 5s). Failure looks like: stays `unhealthy` or the container exits.

3. Confirm host-side reachability (T004's original requirement — must still work after the listener change): from a terminal **on the host** (not `docker exec`), confirm TCP port 9092 is reachable, e.g. `Test-NetConnection localhost -Port 9092` (PowerShell) or any `telnet localhost 9092`.
   Expect: connection succeeds. Failure (`Connection refused`) would mean the advertised-listener fix regressed host access.

4. Confirm the internal listener is NOT exposed to the host: `docker port kafka`
   Expect: only `9092/tcp -> 0.0.0.0:9092` listed. `29092` should **not** appear. If it does, the internal listener has been accidentally published — that's a regression to flag.

5. Run topic init: `docker compose up kafka-init`
   Expect: log lines `Ensuring Kafka topic exists: <name>` followed by `Created topic <name>.` for all 7 topics (`user.verified`, `connection.accepted`, `connection.expired`, `chat.closed`, `rating.submitted`, `trust.score.updated`, `report.filed`), then `Kafka topic initialization complete — 7 topics ensured.`, and the container exits. Then check: `docker inspect kafka-init --format="{{.State.ExitCode}}"` → expect `0`.

6. Re-run to confirm idempotency (AC3): `docker compose rm -f kafka-init` then `docker compose up kafka-init` again.
   Expect: same 7 `Ensuring...` lines, but **no** `Created topic` lines this time, no errors, exit code `0` again. Failure looks like: a `TopicExistsException`/stack trace and a non-zero exit code.

7. Start Kafka UI: `docker compose up -d kafka-ui`, then open `http://localhost:9000` in a browser (or `curl http://localhost:9000/api/clusters`).
   Expect: cluster `local` shows `"status":"online"`, `brokerCount: 1`, `topicCount: 7`. In the browser UI, the Topics list shows exactly the 7 topic names above, each with 3 partitions. Failure looks like: `"status":"initializing"` stuck indefinitely, `brokerCount: 0`, or an error banner in the UI (this is the old bug T004 flagged — if you see it, the listener fix isn't actually applied).

**Cleanup:** `docker compose down` (removes containers and the `shareconnectsave-net` network; no named volumes were created by these three services so there's nothing to `-v`).
