## Manual QA — T011

**Prerequisites:** .NET 9 SDK installed. No Docker/Compose stack needs to be running — no downstream stub actually exists yet at this phase, so this QA only verifies the gateway's own routing/404 behavior standalone.

1. Open a terminal in `C:\Users\anmol.jain\Downloads\ShareConnectSave\src\services\api-gateway` and run:
   `dotnet run`
   Expect: console output showing `Now listening on: http://localhost:8080` (from `Properties/launchSettings.json`'s `applicationUrl`), no startup exceptions.

2. In a second terminal, run:
   `curl -i http://localhost:8080/nonexistent-route`
   Expect: `HTTP/1.1 404 Not Found` with an empty or minimal body — confirms AC2 (unknown routes return 404, no custom fallback swallowing them).

3. Run:
   `curl -i http://localhost:8080/user/anything`
   Expect: the request WILL NOT succeed right now — either a hang followed by a connection-refused/timeout style failure, or (if YARP surfaces it before the OS does) an `HTTP/1.1 502 Bad Gateway`. This is expected and correct: no `user-service` container is running at this phase (no Dockerfile exists for any service yet), so YARP is correctly matching the route (`user-route`, `appsettings.json:12-20`) and correctly failing to reach an unreachable destination — it does NOT return 404 for this one, which is the key distinction from step 2.

4. Repeat step 3 for one more prefix, e.g. `curl -i http://localhost:8080/admin/anything`, to confirm the same 502/connection-failure behavior (not 404) — proving the route/cluster table covers more than just the first entry.

**Cleanup:** In the first terminal, press `Ctrl+C` to stop `dotnet run`. No containers or persistent state were created.
