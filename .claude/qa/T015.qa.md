## Manual QA — T015

**Prerequisites:** Docker Desktop running; repo root `.env` copied from `.env.example` with real values for `SA_PASSWORD`, `USER_DB_CONNECTION` (matching the `sa` password), `JWT_SECRET`; `dotnet` 9 SDK and `dotnet-ef` tool installed (`dotnet tool install --global dotnet-ef` if not already).

1. From the repo root, start the infra stack:
   `docker compose up -d sqlserver sqlserver-init`
   Expect: `docker compose ps` shows `sqlserver` as `healthy` and `sqlserver-init` as `Exited (0)` within ~60s (respect the `start_period: 40s` health window).

2. Export the same connection string `dotnet ef` needs, matching `.env`'s `USER_DB_CONNECTION` value but pointed at `localhost` instead of the Docker service name `sqlserver` (since you're running `dotnet ef` on the host, not inside the compose network):
   PowerShell: `$env:ConnectionStrings__UserDb = "Server=localhost;Database=UserServiceDb;User Id=sa;Password=<your SA_PASSWORD>;TrustServerCertificate=True"`
   Expect: no output (just sets the variable in the current shell).

3. From `src/services/user-service`, run:
   `dotnet ef database update`
   Expect: console shows `Applying migration '20260820070019_InitialSchema'.` then `Done.` — no exception, no "ConnectionStrings__UserDb is not set" error.

4. Verify tables landed (using `sqlcmd` if installed, or any SQL client):
   `sqlcmd -S localhost -U sa -P <your SA_PASSWORD> -d UserServiceDb -Q "SELECT name FROM sys.tables"`
   Expect: three rows — `users`, `otp_attempts`, `identity_verifications`.

5. Bring up the full `user-service` container (which reads `ConnectionStrings__UserDb` from `docker-compose.override.yml`'s merged env, pointed at the in-network `sqlserver` host):
   From the repo root: `docker compose up -d --build user-service`
   Expect: `docker compose ps user-service` eventually shows `healthy` (allow the `start_period: 40s`).

6. Hit the health endpoint from the host:
   `curl -i http://localhost:8081/health`
   Expect: `HTTP/1.1 200 OK` with an empty body.

7. Confirm the container actually connected to SQL Server (not just that `/health` is up, since `/health` doesn't ping the DB): check logs for a clean startup with no EF/SqlException noise:
   `docker compose logs user-service --tail=50`
   Expect: standard ASP.NET Core startup lines (`Now listening on: http://[::]:8080`, `Application started.`) — no `SqlException`, no `InvalidOperationException` about the connection string.

8. Negative-path check for the empty-connection-string gap flagged in review: temporarily unset the var and confirm the failure mode is at least a crash, not a silent hang:
   `docker compose run --rm -e ConnectionStrings__UserDb= user-service` (overrides just this run's env to blank)
   Expect (today, before the recommended fix): the container starts and then throws an ADO.NET-level exception on first DB access rather than the clean `InvalidOperationException` message — confirms the finding above rather than a regression to check for.

**Cleanup:** `docker compose down` (add `-v` only if you also want to drop the SQL Server data volume and start clean next time). Unset the shell var with `Remove-Item Env:ConnectionStrings__UserDb`.
