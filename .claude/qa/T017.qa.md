## Manual QA — T017

**Prerequisites:** user-service running locally (gateway or direct on its port — examples below assume direct port `5100`; swap in the gateway URL/port if routing through YARP). SQL Server reachable per `appsettings.json`/`.env`. A valid JWT for a signed-in test user with `X-User-Id` resolvable (or a gateway that injects it) — examples show the header being set directly against user-service for simplicity. `curl` and `sqlcmd` (or Azure Data Studio/SSMS) available. Twilio client should be the stub/sandbox implementation so no real SMS is sent — check console/log output for the code instead of a real phone.

1. Send an OTP to a brand-new phone number:
   ```
   curl -i -X POST http://localhost:5100/auth/otp/send \
     -H "Content-Type: application/json" \
     -H "X-User-Id: 1" \
     -d "{\"phone_number\":\"+919876543210\"}"
   ```
   Expect: `200 OK`, body `{"sent":true}`. Check service logs / `ITwilioClient` stub output for the 6-digit code sent.

2. Verify with the WRONG code (AC2):
   ```
   curl -i -X POST http://localhost:5100/auth/otp/verify \
     -H "Content-Type: application/json" \
     -H "X-User-Id: 1" \
     -d "{\"phone_number\":\"+919876543210\",\"code\":\"000000\"}"
   ```
   Expect: `400 Bad Request`, body:
   ```json
   {"code":"INVALID_OTP","message":"The code entered is incorrect or has expired.","traceId":"<guid>"}
   ```
   (adjust field names to match `ErrorResponse`'s actual JSON casing if different).

3. Verify with the CORRECT code (AC1) — use the code captured in step 1 (repeat step 1 first if step 2 already consumed the window, since one wrong guess doesn't invalidate the code itself):
   ```
   curl -i -X POST http://localhost:5100/auth/otp/verify \
     -H "Content-Type: application/json" \
     -H "X-User-Id: 1" \
     -d "{\"phone_number\":\"+919876543210\",\"code\":\"<correct-code>\"}"
   ```
   Expect: `200 OK`, body `{"phone_verified":true,"status":"<pending|active>"}` depending on whether the profile is otherwise complete.

4. Observe lockout (AC3) — using a fresh, second phone number so step 3's success doesn't interfere. Send OTP once, then fire 5 wrong-code verifies in a row:
   ```
   curl -X POST http://localhost:5100/auth/otp/send -H "Content-Type: application/json" -H "X-User-Id: 1" -d "{\"phone_number\":\"+919876543211\"}"
   for i in 1 2 3 4 5; do
     curl -i -X POST http://localhost:5100/auth/otp/verify -H "Content-Type: application/json" -H "X-User-Id: 1" -d "{\"phone_number\":\"+919876543211\",\"code\":\"111111\"}"
   done
   ```
   Expect: calls 1–4 return `400 INVALID_OTP`. Call 5 (the one that hits `MaxAttempts=5`) returns `429 Too Many Requests` immediately, body:
   ```json
   {"code":"OTP_LOCKED","message":"Too many failed attempts. Try again after <ISO-8601 timestamp ~15 min from now>.","traceId":"<guid>"}
   ```
   A 6th call while still locked should also return `429 OTP_LOCKED` (guard clause at top of `VerifyOtpAsync`), with the same `LockedUntil`.

5. Inspect the row directly in SQL to confirm state matches the API:
   ```sql
   SELECT Id, Phone, AttemptCount, WindowStartedAt, LockedUntil, CodeHash, CodeExpiresAt, RowVersion
   FROM otp_attempts
   WHERE Phone = '+919876543211';
   ```
   Expect: `AttemptCount = 5`, `LockedUntil` roughly 15 minutes ahead (per `OtpOptions.LockoutMinutes`), `RowVersion` a non-null 8-byte value that changed after each of the 5 writes.

6. Confirm the filtered unique index on `Users.Phone`:
   ```sql
   SELECT i.name, i.filter_definition, i.is_unique
   FROM sys.indexes i
   JOIN sys.tables t ON t.object_id = i.object_id
   WHERE t.name = 'users' AND i.name LIKE '%Phone%';
   ```
   Expect one unique index on `Phone` with `filter_definition = '([PhoneVerifiedAt] IS NOT NULL)'`.

7. Verify the phone-uniqueness conflict path (`PhoneAlreadyInUse`): using the phone number already verified in step 3 (`+919876543210`) but a DIFFERENT `X-User-Id` (e.g. a second seeded user, `X-User-Id: 2`) — send + verify with the correct code for that phone against user 2 (you'll need a fresh OTP send/code cycle for user 2 against that same phone):
   ```
   curl -X POST http://localhost:5100/auth/otp/send -H "Content-Type: application/json" -H "X-User-Id: 2" -d "{\"phone_number\":\"+919876543210\"}"
   curl -i -X POST http://localhost:5100/auth/otp/verify -H "Content-Type: application/json" -H "X-User-Id: 2" -d "{\"phone_number\":\"+919876543210\",\"code\":\"<code-just-sent>\"}"
   ```
   Expect: `409 Conflict`, body:
   ```json
   {"code":"PHONE_ALREADY_IN_USE","message":"This phone number is already verified on another account.","traceId":"<guid>"}
   ```

8. Best-effort concurrency spot-check for the T017 fix (not a guaranteed repro — the race window is narrow): fire two near-simultaneous wrong-code verifies against a brand-new, never-`/send`-to'd phone number, backgrounding the first:
   ```
   curl -s -X POST http://localhost:5100/auth/otp/verify -H "Content-Type: application/json" -H "X-User-Id: 1" -d "{\"phone_number\":\"+919876543212\",\"code\":\"222222\"}" &
   curl -s -X POST http://localhost:5100/auth/otp/verify -H "Content-Type: application/json" -H "X-User-Id: 1" -d "{\"phone_number\":\"+919876543212\",\"code\":\"333333\"}"
   wait
   ```
   Expect: BOTH requests return `400 INVALID_OTP` (never a `500`). Then check SQL:
   ```sql
   SELECT AttemptCount FROM otp_attempts WHERE Phone = '+919876543212';
   ```
   Expect: `AttemptCount = 2` (both failures counted, no lost update, no crash). If you only ever see `AttemptCount = 1` or an occasional `500`, the requests likely didn't actually overlap at the DB level — rerun a few times before treating that as a real failure.

**Cleanup:**
```sql
DELETE FROM otp_attempts WHERE Phone IN ('+919876543210','+919876543211','+919876543212');
UPDATE users SET Phone = NULL, PhoneVerifiedAt = NULL WHERE Phone IN ('+919876543210','+919876543211','+919876543212');
```
(Adjust/remove the `users` cleanup if your test users should keep their verified state for other manual testing.)
