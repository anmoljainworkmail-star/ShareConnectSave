## Manual QA — T018

**Prerequisites:** user-service running locally (`dotnet run` from `src/services/user-service`), `ConnectionStrings__UserDb` pointing at a reachable SQL Server with migrations applied (`dotnet ef database update`), and a valid access token for an existing user. Since api-gateway isn't required for these checks, call user-service directly on its own port (examples below use `http://localhost:5080` — substitute the actual port from `dotnet run`'s console output) and set the `X-User-Id` header manually (this is what the gateway would normally inject after JWT validation).

1. `curl -s http://localhost:5080/users/me -H "X-User-Id: 1"`
   Expect: `200 OK`, JSON body containing `id`, `name`, `email`, `phone`, `photo_url`, `gender`, `preferred_language`, `status`, `phone_verified`, `created_at`.

2. `curl -s -X PATCH http://localhost:5080/users/me -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"name\":\"Test User\",\"preferred_language\":\"en\"}"`
   Expect: `200 OK`, body `{"profile": {...}}` with **no** `access_token` key present at all (name-only change must not trigger a reissue).

3. `curl -s -X PATCH http://localhost:5080/users/me -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"status\":\"looking\"}"`
   Expect: `200 OK`, body includes `"access_token": "<jwt>"`. Decode the JWT payload (e.g. paste into jwt.io, or `echo <payload-segment> | base64 -d`) and confirm its `status` claim reads `"looking"` — not whatever status the token you authenticated with originally had.

4. `curl -s -X PATCH http://localhost:5080/users/me -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"gender\":\"bad-value\"}"`
   Expect: `400 Bad Request`, body `{"code":"INVALID_REQUEST","message":"gender must be one of: female, male, unspecified.","traceId":"<some-id>"}`.

5. `curl -s -X PATCH http://localhost:5080/users/me -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"status\":\"busy\"}"`
   Expect: `400 Bad Request`, body `{"code":"INVALID_REQUEST","message":"status must be one of: looking, unavailable.","traceId":"<some-id>"}`.

6. `curl -s -X POST http://localhost:5080/users/me/photo -H "X-User-Id: 1" -F "photo=@/path/to/local/test.jpg;type=image/jpeg"`
   Expect: `200 OK`, body's `photo_url` is a new URL ending in `.jpg` under `/uploads/photos/`.

7. `curl -s http://localhost:5080/users/me -H "X-User-Id: 1"`
   Expect: `200 OK`, `photo_url` matches the URL returned by step 6 (confirms AC5 — the update is durably reflected on the next read).

8. `curl -s http://localhost:5080/users/2` (no `X-User-Id` header needed — public endpoint; use a different user id than the one you're authenticated as)
   Expect: `200 OK`, body contains only `id`, `name`, `photo_url` — no `gender` or `phone` key anywhere in the JSON (confirms AC2).

9. **409 concurrency-conflict path — cannot be reliably reproduced via sequential manual `curl` commands**, because a real race requires two requests' database reads to overlap in time before either write completes, which single-threaded manual curl invocations (even fired quickly back-to-back) will not reliably achieve — the first request's full request/response round-trip (including its `SaveChangesAsync`) typically completes before a human can launch the second. To actually exercise this path, use one of:
   - A small script that fires two `PATCH`/`POST` requests concurrently (e.g. `curl ... & curl ... & wait` in bash, or two requests issued in parallel from a load-testing tool like `k6` or `autocannon`) against the same user id.
   - Alternatively, verify it deterministically at the code level: manually set a breakpoint (or add a temporary `Task.Delay`) inside `UserRepository.UpdateAsync` between the read and `SaveChangesAsync`, trigger two requests, and confirm the second raises `DbUpdateConcurrencyException` and the controller returns `409`.
   This is a structural/timing limitation of manual curl testing, not a gap in the fix itself — the code review already traced the code path proving the fix is correct.
