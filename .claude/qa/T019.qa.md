## Manual QA — T019

**Prerequisites:** `user-service` running locally (SQL Server up, migrations applied — `20260904172514_AddIdentityBadgeToUsers` included), you have a valid `X-User-Id` header value for an existing user row (or the gateway/JWT flow issuing one), and `IDENTITY_VERIFY_STUB=true` set in the service's environment for steps 1-4.

1. Create/confirm a test user with **no** `photo_url` set (fresh user via Google sign-in with no picture, or one that never called `POST /users/me/photo`).
   ```
   curl -i -X POST http://localhost:5000/users/me/verify-identity \
     -H "X-User-Id: 1" \
     -F "selfie=@C:/path/to/selfie.jpg"
   ```
   Expect: `422 Unprocessable Entity`, body:
   ```json
   {"code":"NO_BASE_PHOTO","message":"No base profile photo on file. Upload one via PATCH /users/me before verifying your identity.","traceId":"..."}
   ```

2. Upload a base photo for that user.
   ```
   curl -i -X POST http://localhost:5000/users/me/photo \
     -H "X-User-Id: 1" \
     -F "photo=@C:/path/to/base-photo.jpg"
   ```
   Expect: `200 OK`, body includes `"photo_url": "http://.../uploads/photos/..."`.

3. Retry verification now that a base photo exists (stub mode).
   ```
   curl -i -X POST http://localhost:5000/users/me/verify-identity \
     -H "X-User-Id: 1" \
     -F "selfie=@C:/path/to/any-selfie.jpg"
   ```
   Expect: `200 OK`, body is the user's profile with `"identity_badge": true`.

4. Confirm the badge persisted.
   ```
   curl -i http://localhost:5000/users/me -H "X-User-Id: 1"
   ```
   Expect: `200 OK`, `"identity_badge": true` in the response.

5. Confirm the public projection also carries the badge (for Discovery/T020 to eventually trust).
   ```
   curl -i http://localhost:5000/users/1
   ```
   Expect: `200 OK`, `"identity_badge": true` present alongside `id`/`name`/`photo_url` — no phone, gender, or other private fields.

6. Missing auth header — expected failure case.
   ```
   curl -i -X POST http://localhost:5000/users/me/verify-identity \
     -F "selfie=@C:/path/to/selfie.jpg"
   ```
   Expect: `401 Unauthorized`, body:
   ```json
   {"code":"MISSING_IDENTITY","message":"X-User-Id header is missing or invalid.","traceId":"..."}
   ```

7. Missing selfie file — expected failure case.
   ```
   curl -i -X POST http://localhost:5000/users/me/verify-identity -H "X-User-Id: 1"
   ```
   Expect: `400 Bad Request`, body:
   ```json
   {"code":"INVALID_REQUEST","message":"A selfie image file (multipart field \"selfie\") is required.","traceId":"..."}
   ```

8. Real-Azure mismatch path (requires `IDENTITY_VERIFY_STUB=false` or unset, plus real `AzureFace__Endpoint`/`AzureFace__Key` set): call the endpoint with a selfie of a visibly different person than the base photo.
   Expect: `422 Unprocessable Entity`:
   ```json
   {"code":"IDENTITY_MISMATCH","message":"Selfie does not match the profile photo on file.","traceId":"..."}
   ```
   Confirm the response body contains **no** confidence score or Azure-specific field.

**Cleanup:** Reset the test user's `identity_badge` to `false` and delete the `identity_verifications` rows created during testing (`DELETE FROM identity_verifications WHERE user_id = 1; UPDATE users SET IdentityBadge = 0 WHERE Id = 1;`), or drop/recreate the local dev database if it's disposable.
