## Manual QA — T020

**Prerequisites:** Docker Desktop running; `.env` populated from `.env.example` (in particular `USER_DB_CONNECTION`, `KAFKA_BOOTSTRAP=kafka:29092`, `IDENTITY_VERIFY_STUB=true`); run from the repo root.

1. `docker compose up -d --build` (repo root, with `.env` present).
   Expect: `sqlserver`, `kafka`, `kafka-ui`, `kafka-init`, and `user-service` all reach `healthy`/exit-0. `docker compose ps` shows `user-service` as `Up (healthy)`.
2. Open Kafka UI at `http://localhost:9000`, go to Topics → `user.verified`.
   Expect: topic exists (created by `kafka-init`), 3 partitions, currently 0 messages.
3. Drive a real user through onboarding to flip `IsOnboardingComplete`. Using any HTTP client against `http://localhost:8081` (user-service's exposed port) or through the gateway if running:
   a. `POST /auth/google` with a valid Google ID token (or whatever your local Google OAuth test setup provides) → creates the user, returns a JWT.
   b. `POST /auth/otp/send` with `{"phone_number":"+919876543210"}` and the JWT from (a) in `Authorization: Bearer ...` → 200, code goes to Twilio (or your Twilio test credentials).
   c. `PATCH /users/me` with name, gender (not `"Unspecified"`), preferred language, and photo URL/upload, until the profile is complete.
   d. `POST /auth/otp/verify` with `{"phone_number":"+919876543210","code":"<the 6-digit code from step b>"}`.
   Expect: 200 response with `"phone_verified": true, "onboarding_complete": true, "access_token": "<new JWT>"`.
4. Back in Kafka UI → Topics → `user.verified` → Messages tab.
   Expect: exactly one new message, key = the numeric user id (e.g. `"1"`), value is JSON containing `event_id` (a UUID), `user_id` (matching the key), `gender` (lowercase — `"female"`/`"male"`), `verified_at` (an ISO 8601 UTC timestamp close to step 3d's execution time).
5. Repeat step 3d again (same user, request a fresh OTP first via step 3b, then verify).
   Expect: 200 response again, but this time `"access_token"` is absent from the JSON body (onboarding state didn't change again) — and back in Kafka UI, still only **one** message total on the topic (no duplicate publish).
6. Kafka-unavailable check: `docker compose stop kafka`. Then repeat steps 3b–3d for a *second, different* phone number/new user (register a new Google account or reuse another test account) all the way through to `POST /auth/otp/verify`.
   Expect: the HTTP response still comes back 200 with `"onboarding_complete": true` — the request does not hang or 500, even though Kafka is stopped. Check `docker compose logs user-service` for a line like `Failed to publish UserVerifiedEvent to Kafka topic user.verified for user 2: <reason>` appearing within roughly 30-60 seconds (delivery timeout), confirming the failure was logged, not silently dropped.
7. `docker compose start kafka`, wait for it to report healthy again (`docker compose ps`).
   Expect: no automatic re-publish of the message from step 6 — this is the known, ticket-approved gap (no outbox/backing store yet); this data point about a lost event is confirmed by the log line from step 6 only, not recoverable. No action needed here — just confirms the documented Phase 14 limitation is real and observable.

**Cleanup:** `docker compose down` (add `-v` if you also want to drop the SQL Server/Kafka volumes and start clean next time).
