## Manual QA — T021

**Prerequisites:** Docker Desktop running.

1. Confirm Docker Desktop is running, then from `src/infra`:
   ```
   docker compose up -d sqlserver sqlserver-init redis
   ```
   Wait for `docker compose ps` to show `sqlserver` and `redis` as `healthy` — `sqlserver-init` should show `Exited (0)`, not a nonzero exit code (that means the init script failed, e.g. because `DiscoveryServiceDb` couldn't be created).

2. Export the required env vars (bare `mvn spring-boot:run` needs these exported manually — this is exactly the profile gap flagged in this review, so don't skip it):
   ```
   set SPRING_PROFILES_ACTIVE=dev
   set DISCOVERY_DB_PASSWORD=<the sa password from your .env / docker-compose>
   ```
   Gotcha encountered this session: `DISCOVERY_DB_PORT` defaults to **14330**, not SQL Server's standard 1433 — this is intentional (matches `docker-compose.yml`'s host port remap for machines with a native SQL Server service already bound to 1433), so leave it unset unless your compose mapping differs.

3. Run the service from `src/services/discovery-service`:
   ```
   mvn spring-boot:run
   ```
   Expected: log lines showing Flyway applying `V001__discovery_service_initial_schema.sql`, then `Tomcat started on port 8080`. Failure mode to watch for: "Could not resolve placeholder 'DISCOVERY_DB_PASSWORD'" means step 2 was skipped; "Login failed for user" means the password doesn't match what `sqlserver-init` actually set.

4. Hit the health endpoint:
   ```
   curl http://localhost:8080/actuator/health
   ```
   Expected: exactly `{"status":"UP"}` — no nested `components` breakdown (that would mean `show-details` drifted from `never`).

5. Confirm Flyway only ran once / is idempotent on restart: stop the service (Ctrl+C) and run `mvn spring-boot:run` again. Expected: no "migration failed" or checksum-mismatch error, and the log should show Flyway reporting the schema is already at the current version rather than re-applying `V001`.

6. Sanity-check the profile gap called out in this review: run `mvn spring-boot:run` with `SPRING_PROFILES_ACTIVE=docker` instead of `dev` (leave `DISCOVERY_DB_PASSWORD` set). Expected today: startup fails on DataSource authentication (no username/password resolve under an unmatched profile) — this reproduces the finding above and should be treated as a known-broken path until the `docker` profile is added (see `.claude/notes/follow-ups.md`, affects T028), not re-reported as a new bug next time.

**Cleanup:** Stop the running `mvn spring-boot:run` process (Ctrl+C). Optionally `docker compose down` from `src/infra` if you don't need the infra running for anything else.
