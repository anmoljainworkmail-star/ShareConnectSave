## Manual QA — T022

**Prerequisites:** `docker-up` infra running (SQL Server, Redis reachable); discovery-service started with the `dev` Spring profile and `JAVA_HOME` pointed at the Temurin 21 install (`JAVA_HOME="C:/Users/anmol.jain/scoop/apps/temurin21-jdk/current"`), e.g. `JAVA_HOME=... SPRING_PROFILES_ACTIVE=dev ./mvnw spring-boot:run`; `redis-cli` available on PATH.

1. Start a scan:
   `curl -i -X POST http://localhost:8080/scan/start -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"destination_lat\":12.9,\"destination_lng\":77.6,\"destination_label\":\"Airport\",\"departure_time\":\"2026-09-12T10:00:00Z\"}"`
   Expect: `201 Created`, body `{"session_id": <n>, "mode": "gps"}`. Note `<n>`.

2. Send a location update:
   `curl -i -X PUT http://localhost:8080/scan/location -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"lat\":12.91,\"lng\":77.61}"`
   Expect: `204 No Content`.

3. Check Redis directly:
   `redis-cli -n 0 GET scan:<n>:location` — Expect: a JSON-ish serialized value present.
   `redis-cli -n 0 TTL scan:<n>:location` — Expect: an integer ≤ 30 (counting down).

4. Stop the scan:
   `curl -i -X POST http://localhost:8080/scan/stop -H "X-User-Id: 1"` — Expect: `204 No Content`.

5. Re-check Redis immediately:
   `redis-cli -n 0 GET scan:<n>:location` — Expect: `(nil)` — gone immediately, not after waiting out the TTL.

6. Boundary-input failure case — out-of-range latitude:
   `curl -i -X POST http://localhost:8080/scan/start -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"destination_lat\":999,\"destination_lng\":77.6}"`
   Expect: `400 Bad Request`, body shaped `{"code":"VALIDATION_ERROR","message":"<some bean-validation message>","traceId":"<id or empty>"}`.

7. Missing-header failure case (documenting a known, accepted gap — not a bug to chase in this ticket):
   `curl -i -X POST http://localhost:8080/scan/stop`
   Expect (today): `500 Internal Server Error`, body `{"code":"INTERNAL_ERROR","message":"An unexpected error occurred.","traceId":"..."}`. This is a pre-existing gap in `shared-java-lib`'s `GlobalExceptionHandler` (it has no handler for a missing required header), not something T022 introduced or is scoped to fix — logged as a follow-up instead.

8. **Concurrency fix verification** — start a fresh scan (repeat step 1, note new `<n>`), then in two separate terminals fire these as close together as you can (paste both, hit Enter on each within a second of each other):
   - Terminal A: `curl -i -X PUT http://localhost:8080/scan/location -H "X-User-Id: 1" -H "Content-Type: application/json" -d "{\"lat\":12.92,\"lng\":77.62}"`
   - Terminal B: `curl -i -X POST http://localhost:8080/scan/stop -H "X-User-Id: 1"`

   Expect one of two consistent outcomes, never a stuck/resurrected key:
   - B's `stop` completes with `204`, and A's `location` update either also returns `204` (it won the race and wrote before stop) **or** returns `404` with `{"code":"SCAN_SESSION_NOT_FOUND", ...}` (it lost the race, stop closed the session first).
   - Immediately after both requests return, run `redis-cli -n 0 GET scan:<n>:location` — Expect: `(nil)`, regardless of which of the two outcomes above occurred. This is the key evidence: the key is gone right after both requests settle, not merely after the 30s TTL elapses. Repeat this pair of curls a few times in a fresh session each time (network/OS scheduling makes exact interleaving non-deterministic) — every run should still end with `(nil)`.

**Cleanup:** `redis-cli -n 0 FLUSHDB` to clear any leftover scan keys from testing (dev Redis only — never run against a shared/prod instance).
