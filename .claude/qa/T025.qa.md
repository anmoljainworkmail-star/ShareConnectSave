## Manual QA — T025

**Prerequisites:** Full stack up via `/docker-up` (SQL Server, MongoDB, Kafka, Redis running); discovery-service started against that stack; `docker compose exec redis redis-cli` available for inspection; a valid JWT/gateway session (or direct service call with `X-User-Id`/`X-User-Gender` headers) for two test users, e.g. `42` (to be verified) and `99` (to remain unverified throughout).

1. Produce a well-formed `user.verified` message for user 42:
   `docker compose exec kafka kafka-console-producer.sh --topic user.verified --bootstrap-server kafka:29092` with:
   `{"event_id":"11111111-1111-1111-1111-111111111111","user_id":"42","gender":"female","verified_at":"2026-09-14T10:00:00Z"}`
   Expect: `redis-cli SISMEMBER scan:eligible_users 42` returns `1`.

2. **New guard — ineligible caller rejected:** with user 99 never having a `user.verified` event, call `curl -X POST http://localhost:<gateway-or-service-port>/scan/start -H "X-User-Id: 99" -H "X-User-Gender: female" -H "Content-Type: application/json" -d '{"destinationLat":1,"destinationLng":1,"destinationLabel":"x","departureTime":"2026-09-15T10:00:00Z"}'`
   Expect: HTTP `403`, body `{"code":"USER_NOT_ELIGIBLE_FOR_DISCOVERY","message":"User 99 is not eligible for discovery","traceId":"..."}`. Confirm no row was written for user 99 in `scan_sessions` (`SELECT * FROM scan_sessions WHERE user_id = 99` returns nothing) and `redis-cli SISMEMBER scan:active_sessions <any-id>` shows no new member.

3. **New guard — eligible caller allowed:** repeat the same `curl` call with `X-User-Id: 42` (verified in step 1).
   Expect: HTTP `201`, JSON body containing a `sessionId` and `"mode":"gps"`. Confirm `redis-cli SISMEMBER scan:active_sessions <sessionId>` returns `1` and a matching row exists in `scan_sessions`.

4. Produce a `trust.score.updated` suspension for user 42 (`request_limit: 0`):
   `{"event_id":"22222222-2222-2222-2222-222222222222","user_id":"42","new_score":10.0,"badge_level":"restricted","request_limit":0}`
   Expect: `redis-cli SISMEMBER scan:eligible_users 42` now returns `0`; `redis-cli HGETALL user:trust:42` shows the cached score/badge/limit.

5. **New guard — suspended caller now rejected:** call `POST /scan/start` again for user 42 (do not stop the session from step 3 first).
   Expect: HTTP `403` with `USER_NOT_ELIGIBLE_FOR_DISCOVERY`, confirming the guard reacts to the just-applied suspension on the caller's *next* request (not the currently-open session — this ticket does not force-close an already-open session on suspension, only blocks new ones).

6. Replay the exact same `trust.score.updated` message from step 4 again (same `event_id`).
   Expect: log line `Skipping already-processed trust.score.updated event 22222222-...` and no duplicate Redis writes (idempotency).

7. **Negative path** — malformed `trust.score.updated` missing `new_score`:
   `{"event_id":"33333333-3333-3333-3333-333333333333","user_id":"42","badge_level":"standard","request_limit":5}`
   Expect: log line `Received trust.score.updated event 33333333-... with a missing required field, skipping`; consumer stays alive (send a follow-up valid message and confirm it's processed); no `processed_events` row for this event_id.

8. **Negative path** — tombstone (null value) on `user.verified`.
   Expect: log line `Received null-value user.verified message, skipping`, no stack trace, consumer thread still alive.

**Cleanup:** `redis-cli SREM scan:eligible_users 42`, `redis-cli DEL user:trust:42`, `redis-cli SREM scan:active_sessions <sessionId-from-step-3>`, delete the test rows from `scan_sessions` and `processed_events` (or restart the container volumes) so this pass doesn't leave state that masks a future re-run.
