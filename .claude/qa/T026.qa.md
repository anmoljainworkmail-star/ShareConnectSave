## Manual QA — T026

**Prerequisites:** Docker infra stack running (`docker-up`), `discovery-service` running locally or in-container, `redis-cli` available against the same Redis instance discovery-service uses (logical DB 0), and a valid `X-User-Id` for a user already present in `scan:eligible_users` (or run `/scan/start` after seeding eligibility via a `user.verified` event).

1. Confirm Redis DB index convention.
   `redis-cli -n 0 PING`
   Expect: `PONG`

2. Start a scan session.
   `curl -X POST http://localhost:8081/scan/start -H "X-User-Id: 1001" -H "X-User-Gender: female" -H "Content-Type: application/json" -d "{\"destinationLat\":12.9,\"destinationLng\":77.6,\"destinationLabel\":\"Test\",\"departureTime\":\"2026-09-15T10:00:00Z\"}"`
   Expect: `201 Created` with a JSON body containing a numeric `sessionId`. Note this ID as `SID`.

3. Verify the session-location key does NOT exist yet (no location posted).
   `redis-cli -n 0 GET scan:SID:location`
   Expect: `(nil)`

4. Post a location update and check the key + TTL.
   `curl -X PUT http://localhost:8081/scan/location -H "X-User-Id: 1001" -H "Content-Type: application/json" -d "{\"lat\":12.9,\"lng\":77.6}"`
   then:
   `redis-cli -n 0 GET scan:SID:location`
   Expect: a JSON blob containing `lat`/`lng` (with a `@class` type hint from Jackson).
   `redis-cli -n 0 TTL scan:SID:location`
   Expect: an integer between 1 and 30 (session-location TTL).

5. Verify the session appears in the managed active-sessions Set with no TTL.
   `redis-cli -n 0 SISMEMBER scan:active_sessions SID`
   Expect: `1`
   `redis-cli -n 0 TTL scan:active_sessions`
   Expect: `-1` (no TTL — a persistent Set, not a cache entry).

6. Query nearby and verify the 10s nearby-result cache populates.
   `curl http://localhost:8081/scan/nearby -H "X-User-Id: 1001"`
   then immediately:
   `redis-cli -n 0 GET scan:SID:nearby`
   Expect: a JSON array (possibly empty `[]`) — not `(nil)`.
   `redis-cli -n 0 TTL scan:SID:nearby`
   Expect: an integer between 1 and 10.

7. Confirm the nearby cache actually gets *served*, not recomputed, within the 10s window.
   Wait 3 seconds, then repeat the same `curl http://localhost:8081/scan/nearby -H "X-User-Id: 1001"` call and check discovery-service's own logs.
   Expect: no new "No cached location" or filter-pipeline log lines for this call (the second call is served from the `scan:SID:nearby` cache-aside hit, not recomputed) — you should NOT see the per-candidate filter logic re-execute.

8. Confirm profile cache-aside populates on first candidate lookup (only meaningful if at least one eligible nearby candidate exists — otherwise skip to step 9).
   `redis-cli -n 0 KEYS "user:*:profile_cache"`
   Expect: at least one key per candidate returned in step 6's results.
   `redis-cli -n 0 TTL user:<candidateId>:profile_cache`
   Expect: an integer up to 300 (5 minutes, from `DISCOVERY_USER_PROFILE_TTL_MINUTES`).

9. Confirm blocklist cache-aside populates (fail-open is expected today, since User Service's `/blocks` endpoint doesn't exist yet).
   `redis-cli -n 0 GET user:1001:blocklist_cache`
   Expect: `[]` (an empty array, cached — not `(nil)`), since the upstream call fails open to an empty list per the current known User Service gap.
   `redis-cli -n 0 TTL user:1001:blocklist_cache`
   Expect: an integer up to 300.

10. Stop the scan and confirm explicit deletion (not left to TTL).
    `curl -X POST http://localhost:8081/scan/stop -H "X-User-Id: 1001"`
    then immediately:
    `redis-cli -n 0 GET scan:SID:location`
    Expect: `(nil)` immediately, not after waiting for the 30s TTL.
    `redis-cli -n 0 SISMEMBER scan:active_sessions SID`
    Expect: `0`
    `redis-cli -n 0 EXISTS scan:SID:gender scan:SID:women_only`
    Expect: `0` (both deleted).

11. Confirm no controller touches RedisTemplate directly (static check, no server needed).
    `grep -rn "RedisTemplate" src/services/discovery-service/src/main/java/com/shareconnectsave/discovery/scan/ScanController.java src/services/discovery-service/src/main/java/com/shareconnectsave/discovery/ble/BleTokenController.java`
    Expect: no output (no matches in either controller file).

12. Confirm TTLs are actually environment-overridable, not hardcoded.
    Restart discovery-service with `DISCOVERY_NEARBY_TTL_SECONDS=3`, repeat step 6, and re-check:
    `redis-cli -n 0 TTL scan:SID:nearby`
    Expect: a value at or below 3, not 10 — confirming the TTL is read from the env var, not a compiled-in literal.

**Cleanup:**
`redis-cli -n 0 FLUSHDB` (only against your local dev Redis instance — never run this against a shared or prod instance), then stop the scan session if still active and restart discovery-service without the overridden `DISCOVERY_NEARBY_TTL_SECONDS` env var to restore the default.
