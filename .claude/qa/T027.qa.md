## Manual QA — T027

**Prerequisites:** `docker-up` running (SQL Server, Redis, Kafka); discovery-service buildable via Maven.

1. `docker-up` to start SQL Server, Redis, Kafka.
   Expect: health summary shows all three healthy.
2. Run discovery-service (`mvn spring-boot:run`, `dev` profile). Confirm `GET /actuator/health` returns 200 with a `circuitBreakers` component showing `userService: CLOSED`.
   Expect: HTTP 200, JSON body contains `components.circuitBreakers.details.userService.status: "CLOSED"`.
3. Stop (or block via firewall/hosts-file) the user-service container so calls fail/timeout.
   Expect: user-service container stopped or unreachable from discovery-service's container network.
4. Drive 10 `/scan/nearby` calls for sessions with at least one nearby candidate (seed two active scan sessions close together first). Confirm: first ~5 failing calls behave as normal failures (slow/erroring), and by the 5th-out-of-10 failure, subsequent calls return near-instantly with either a cached profile or the `{"name":"Unknown","unavailable":true}` placeholder.
   Expect: calls 1-5 take noticeably longer (real attempted connection/timeout); calls 6+ return near-instantly with a card whose `unavailable` field is `true` (unless a warm cache still serves a real card).
5. Re-check `/actuator/health` — `circuitBreakers.userService` should now report `OPEN`.
   Expect: `components.circuitBreakers.details.userService.status: "OPEN"`.
6. Wait 30s, restart user-service, issue one more `/scan/nearby` call — confirm it succeeds with a real profile and `/actuator/health` transitions back toward `CLOSED` (may show `HALF_OPEN` momentarily depending on timing).
   Expect: the request after the 30s wait returns a real (non-placeholder) card; `/actuator/health` shows `HALF_OPEN` then `CLOSED` shortly after.
7. With user-service still down, hit an endpoint that triggers `getBlockList` for a user with a known blocked counterpart — confirm the blocked user *does* reappear in results during the outage, and decide with the tech lead whether that's acceptable before signing off on the blocklist fail-open follow-up.
   Expect: the previously-blocked candidate appears in `/scan/nearby` results while user-service is down (fail-open behavior) — flag to tech lead if this is not acceptable.
8. Check discovery-service logs during the outage window — confirm WARN-level lines appear for both profile and blocklist degradation, and confirm they contain only a numeric user id, no profile/gender/location content.
   Expect: `log.warn` lines from `DiscoveryCacheService.getProfile`/`getBlocklist` showing a numeric `userId` and exception type/message only — no PII.

**Cleanup:** Restart user-service if left stopped; `docker compose down` (or leave infra running if continuing to the next task).
