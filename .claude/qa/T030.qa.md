## Manual QA — T030

**Prerequisites:** connection-service running locally (via `/docker-up` + the service itself), reachable at e.g. `http://localhost:8082` (adjust port to your actual gateway/service mapping).

1. **Migration sanity check (if Flyway can't be run in this environment):** open `src/services/connection-service/src/main/resources/db/migration/V003__connection_requests_optimistic_lock.sql` and confirm by inspection: (a) filename follows `V003__...` convention after `V001`/`V002`, (b) the `ALTER TABLE ... ADD version BIGINT NOT NULL DEFAULT 0` is valid against a table that may already have rows (default backfills existing rows, satisfies NOT NULL). If Flyway *can* run: start the service against a dev DB and confirm `flyway_schema_history` gets a new row for V003 with no checksum conflict, and `sp_help connection_requests` (or `SELECT * FROM sys.columns WHERE object_id = OBJECT_ID('connection_requests')`) shows the new `version` column.

2. **Happy path — create, then accept:**
```
curl -i -X POST http://localhost:8082/connections \
  -H "X-User-Id: 101" -H "Content-Type: application/json" \
  -d '{"recipient_id": 202}'
```
Expect `201 Created`, body `{"connection_id": <id>}`. Then:
```
curl -i -X POST http://localhost:8082/connections/<id>/accept \
  -H "X-User-Id: 202"
```
Expect `200 OK`, body with `"status":"ACCEPTED"`.

3. **Self-connection rejection (new guard):**
```
curl -i -X POST http://localhost:8082/connections \
  -H "X-User-Id: 101" -H "Content-Type: application/json" \
  -d '{"recipient_id": 101}'
```
Expect `409 Conflict`, body `{"code":"SELF_CONNECTION_NOT_ALLOWED", "message":"...", "traceId":"..."}`.

4. **Non-recipient forbidden:**
```
curl -i -X POST http://localhost:8082/connections/<id>/accept \
  -H "X-User-Id: 999"
```
(where 999 is neither requester nor recipient) — expect `403 Forbidden`, `{"code":"FORBIDDEN_CONNECTION_ACTION", ...}`.

5. **Invalid state transition:** repeat step 2's accept call a second time against the same already-`ACCEPTED` connection id → expect `409 Conflict`, `{"code":"INVALID_STATE_TRANSITION", ...}`.

6. **Double-accept race (the actual concurrency fix) — fire two accepts at once:**
```
curl -i -X POST http://localhost:8082/connections/<id>/accept -H "X-User-Id: 202" &
curl -i -X POST http://localhost:8082/connections/<id>/accept -H "X-User-Id: 202" &
wait
```
Expect exactly one `200 OK` and one `409 Conflict` (either `INVALID_STATE_TRANSITION`, from the optimistic-lock path or the plain state-check, depending on timing — both are valid outcomes and both return the same code). Then confirm only **one** row exists in `outbox` for this connection's `connection.accepted` event (`SELECT COUNT(*) FROM outbox WHERE payload LIKE '%<connectionId>%'` — should be 1, not 2) and only one row in `saga_state` for `saga_id = <connectionId>`.

7. **Duplicate pending request (unique-index backstop):** fire two concurrent `POST /connections` with the same `X-User-Id: 101` and same `recipient_id: 303` — expect one `201 Created` and one `409 Conflict` with `{"code":"ACTIVE_CONNECTION_EXISTS", ...}`.

8. **Failure-path example (missing header — known pre-existing gap, not introduced by this fix):**
```
curl -i -X POST http://localhost:8082/connections \
  -H "Content-Type: application/json" -d '{"recipient_id": 202}'
```
Currently likely returns a raw `500 INTERNAL_ERROR` rather than a clean `400`, per the known follow-up noted in `ExceptionHandlingConfig.java:26-31` (tracked against T091). Confirm this is the pre-existing behavior, not a regression from T030's fixes.
