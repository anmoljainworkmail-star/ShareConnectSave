## Manual QA — T031

**Prerequisites:** SQL Server from the Docker Compose stack running and reachable (`/docker-up`), `connection-service` running locally with scheduling enabled. You do **not** need Kafka running to verify this ticket's own scope — see step 5 for why.

1. Using SSMS/`sqlcmd`/Azure Data Studio, insert or select an existing `connection_requests` row and force it into an overdue state:
   `UPDATE connection_requests SET status = 'PENDING', expires_at = DATEADD(MINUTE, -1, SYSUTCDATETIME()) WHERE id = <some existing PENDING id>;`
   Expect: the row shows `status = 'PENDING'`, `expires_at` in the past.
2. Wait up to 60 seconds (the scheduler's `fixedRate`).
   Expect: the connection-service application log prints `Expired 1 overdue connection request(s)` (or a higher count if multiple rows qualified) at INFO level.
3. Re-query the row:
   `SELECT status, updated_at FROM connection_requests WHERE id = <id>;`
   Expect: `status = 'EXPIRED'`, `updated_at` refreshed to a timestamp within the last minute.
4. Check the outbox table for the corresponding row:
   `SELECT TOP 1 topic, payload, status FROM outbox WHERE topic = 'connection.expired' ORDER BY created_at DESC;`
   Expect: one row with `topic = 'connection.expired'`, `status = 'PENDING'`, and `payload` containing `"connection_id":<id>` and `"requester_id":<the requester's id>` (snake_case keys, no timestamp field, no `recipient_id`).
5. **Cannot be completed in this environment:** verifying the event actually appears on the Kafka UI topic `connection.expired`. `OutboxRelay` (the component that reads `outbox` and calls `KafkaTemplate`) does not exist yet — it is T032, still `status: draft`. Until T032 ships, the row from step 4 will sit at `status = 'PENDING'` indefinitely; that is expected, not a bug, given T031's explicit scope. Re-run this step once T032 is implemented.
6. Re-run step 2 with an *empty* overdue set (no PENDING rows past `expires_at`) at least once.
   Expect: the log line from step 2 does NOT print (the `if (!overdueConnectionIds.isEmpty())` guard suppresses it), and no exception appears in the logs.

**Cleanup:** Reset any row you manually edited in step 1 back to its original `status`/`expires_at` if it was real test data you still need, or delete the test row and its `outbox` row:
`DELETE FROM outbox WHERE topic = 'connection.expired' AND payload LIKE '%<id>%'; DELETE FROM connection_requests WHERE id = <id>;`
