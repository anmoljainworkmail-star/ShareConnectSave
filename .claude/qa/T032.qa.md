## Manual QA — T032

**Prerequisites:** `/docker-up` has been run (Kafka, Kafka UI, SQL Server all healthy) and `connection-service` is running locally against that stack (`CONNECTION_DB_HOST`/`KAFKA_BROKERS` pointed at the compose stack's exposed ports).

1. Create a connection request: `POST /connections` (through the gateway or directly to connection-service) with a valid `requesterId` (JWT/header) and a `recipientId`.
   Expect: `201` with a `connectionId` in the response body.

2. Query the outbox table directly: `SELECT id, topic, status, payload FROM outbox WHERE topic = 'connection.requested' ORDER BY created_at DESC;` (against the `ConnectionServiceDb` on the SQL Server instance, e.g. via `sqlcmd -S localhost,14330 -d ConnectionServiceDb -U sa -P <password> -Q "..."`).
   Expect: one row, `status = 'PENDING'` immediately after the POST, flipping to `'PROCESSED'` within ~500ms-1s on re-query.

3. Open Kafka UI (default `http://localhost:8080` per the compose stack — adjust to whatever port `/docker-up`'s health summary reported) and browse the `connection.requested` topic.
   Expect: one message whose value JSON contains `event_id`, `connection_id`, `requester_id`, `recipient_id`, `requested_at`; `event_id` is a UUID string.

4. Compare that Kafka message's `event_id` against the outbox row's `id` column from step 2.
   Expect: the two values are byte-for-byte identical (confirms the outbox-row-id == payload-event_id fix end-to-end, not just in code).

5. As the recipient, `POST /connections/{connectionId}/accept`.
   Expect: `200`, and within ~500ms-1s a new row appears in `outbox` for `topic = 'connection.accepted'`, reaching `PROCESSED`; the corresponding Kafka UI message on `connection.accepted` has `connection_id`/`requester_id`/`recipient_id` as JSON *numbers* (not quoted strings) and an `accepted_at` ISO-8601 timestamp field present — confirms the schema fix (int64, not uuid-format string) is correct on the wire, not just in the schema file.

6. Let a PENDING request sit past its 10-minute expiry (or manually set `expires_at` in the past via `UPDATE connection_requests SET expires_at = SYSUTCDATETIME() WHERE id = <id>;` and wait for the next scheduler tick), and confirm a `connection.expired` message appears in Kafka UI with exactly `event_id`, `connection_id`, `requester_id` (no `recipient_id`, no timestamp field) — matching `connection.expired.schema.json`'s `additionalProperties: false` shape.

**Cleanup:** `DELETE FROM outbox; DELETE FROM connection_requests WHERE id IN (...);` on the test rows created above, or simply tear down and recreate the SQL Server container via `/docker-up` if using disposable dev data.
