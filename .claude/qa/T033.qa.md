## Manual QA — T033

**Prerequisites:** `docker-up` infra stack running (SQL Server, Kafka, Kafka UI at http://localhost:9000). `connection-service` running locally against that stack (`dev` profile) with an existing `PENDING` connection-request setup possible via `POST /connections`. Have at least one real numeric `X-User-Id` you can act as (any BIGINT works, no auth needed at this layer since the gateway isn't required for local service testing).

1. Open Kafka UI at `http://localhost:9000`, navigate to Topics, and open (or create if missing) `trust.score.updated`.
   Expect: topic exists with 3 partitions (per this platform's dev convention).

2. Using Kafka UI's "Produce Message" panel, send a message to `trust.score.updated` with key = your test user's id (as a string) and value:
   ```json
   {"event_id":"11111111-1111-1111-1111-111111111111","user_id":"<YOUR_TEST_USER_ID>","new_score":92.5,"badge_level":"trusted","request_limit":1}
   ```
   Expect: message appears in the topic view immediately.

3. Watch `connection-service`'s console/log output (DEBUG level is on in the `dev` profile per `application.yml`).
   Expect: no error or warning logged for this message (confirms it deserialized and passed all guard clauses). Note: today there is no explicit success log line, so absence of an error is your positive signal here.

4. As `<YOUR_TEST_USER_ID>`, call `POST /connections` against `connection-service` (e.g. via curl/Postman) with header `X-User-Id: <YOUR_TEST_USER_ID>` and a body naming any other user as `recipientId`, twice in a row (two different recipients, to avoid tripping the separate "active connection" guard).
   Expect: the first call returns `201 Created`. The second call returns `409 Conflict` with body `{"code":"REQUEST_LIMIT_EXCEEDED", "message":"User <id> already has 1 pending outbound requests", "traceId":"..."}` — this proves the cache genuinely picked up `request_limit: 1` from step 2 and T030's throttle enforced it.

5. Re-produce the *exact same* message from step 2 (identical `event_id`) in Kafka UI.
   Expect: `connection-service` logs `Skipping already-processed trust.score.updated event 11111111-1111-1111-1111-111111111111` at INFO level — proof of the idempotency guard working against a real redelivery.

6. Query the `connection-service` database's `processed_events` table (`SELECT * FROM processed_events WHERE event_id = '11111111-1111-1111-1111-111111111111'`).
   Expect: exactly one row — confirms step 5's redelivery did not insert a duplicate.

7. Produce a deliberately malformed message (missing `request_limit`) to the same topic:
   ```json
   {"event_id":"22222222-2222-2222-2222-222222222222","user_id":"<YOUR_TEST_USER_ID>","new_score":10.0,"badge_level":"restricted"}
   ```
   Expect: `connection-service` logs an ERROR line ("... with a missing required field, skipping ...") and does NOT insert a row into `processed_events` for this `event_id` (query it to confirm) — proves the guard clause skips cleanly without crashing the consumer or falsely marking a skipped event as processed.

**Cleanup:** Delete the two test rows from `processed_events` (`DELETE FROM processed_events WHERE event_id IN ('11111111-1111-1111-1111-111111111111','22222222-2222-2222-2222-222222222222')`) if you want a clean slate for repeat runs; the two test `PENDING` connection requests created in step 4 can be left to expire naturally via `ConnectionExpiryScheduler` (10 minutes) or deleted directly from `connection_requests` if you need the state cleared sooner.
