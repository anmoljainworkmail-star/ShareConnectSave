## Manual QA — T036

**Prerequisites:** `docker-up` infrastructure running (MongoDB + Redis reachable), chat-service built and running with `ConnectionStrings__ChatDb`, `SIGNALR_REDIS_CONNECTION`, and `MONGO_TTL_SECONDS` set. Two existing `chat_rooms` documents' ids on hand: one real chat room id (`<chatId>`) with `user_a_id=1001`, `user_b_id=1002`, and a gateway (or manually set `X-User-Id` header, since this is behind YARP in prod but can be hit directly in dev) for a third user id `9999` who is NOT a participant.

1. `curl -H "X-User-Id: 1001" "http://localhost:<port>/chats/<chatId>/messages"`
   Expect: `200 OK`, JSON array of message objects (empty array `[]` if none sent yet), each shaped `{ "id", "chat_id", "sender_id", "content", "sent_at" }`, ascending by `sent_at`.
2. `curl -X POST -H "X-User-Id: 9999" "http://localhost:<port>/chats/<chatId>/met"`
   Expect: `403 Forbidden`, body `{ "code": "NOT_A_PARTICIPANT", "message": "You are not a participant in this chat.", "traceId": "<some-id>" }`.
3. `curl -H "X-User-Id: 1001" "http://localhost:<port>/chats/not-a-valid-objectid/messages"`
   Expect: `404 Not Found`, body `{ "code": "CHAT_ROOM_NOT_FOUND", "message": "No chat room exists with this id.", "traceId": "<some-id>" }` — NOT a 500.
4. Using a SignalR client (e.g. `@microsoft/signalr` from a browser console, or a small test script) connect to `ws://localhost:<port>/hubs/chat` with header `X-User-Id: 9999` (non-participant), then invoke `connection.invoke("JoinRoom", "<chatId>")`.
   Expect: the invoke promise rejects with a `HubException` whose message is "You are not a participant in this chat." — the connection is NOT added to the SignalR group (verify no `ReceiveMessage` events arrive for this chat afterward in step 6).
5. Open two separate SignalR client connections both with `X-User-Id: 1001` and `X-User-Id: 1002` respectively (the two real participants). Both invoke `connection.invoke("JoinRoom", "<chatId>")`.
   Expect: both invoke promises resolve successfully (no exception).
6. From client 1001's connection, invoke `connection.invoke("SendMessage", "<chatId>", "hello from 1001")`.
   Expect: both client 1001 and client 1002's `"ReceiveMessage"` handlers fire with a payload `{ "id", "chat_id": "<chatId>", "sender_id": 1001, "content": "hello from 1001", "sent_at": "<ISO timestamp>" }` within a couple seconds.
7. Re-run step 1's curl against the same `<chatId>`.
   Expect: `200 OK`, the new message now appears in the array, confirming it was persisted to MongoDB (not just broadcast in memory) — the array is sorted ascending by `sent_at`.
8. `curl -X POST -H "X-User-Id: 1001" "http://localhost:<port>/chats/<chatId>/met"` then `curl -X POST -H "X-User-Id: 1002" "http://localhost:<port>/chats/<chatId>/met"`.
   Expect: first call returns `200 OK` with `{ "chat_id": "<chatId>", "both_users_met": false }`; second call returns `200 OK` with `{ "chat_id": "<chatId>", "both_users_met": true }`.
9. Repeat step 8's second call again (same user, after both already confirmed).
   Expect: this is NOT currently guarded against double-confirmation re-triggering (idempotent update, same result) — still `200 OK` with `both_users_met: true`, no error. (Informational: confirms `MarkUserMetSuccessfullyAsync`'s per-field `Set` update is safe to call twice.)

**Cleanup:** Close both SignalR connections (`connection.stop()`); no other teardown needed — MongoDB TTL index will expire the test messages automatically after `MONGO_TTL_SECONDS`.
