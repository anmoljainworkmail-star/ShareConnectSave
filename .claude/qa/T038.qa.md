## Manual QA — T038

**Prerequisites:**
- Full stack running via `/docker-up` (SQL Server, MongoDB, Kafka, Redis, Kafka UI, Jaeger) with chat-service built and running (`dotnet run` or its container).
- A way to publish to the `connection.accepted` topic: Kafka UI (http://localhost:<kafka-ui-port>, find topic `connection.accepted`, "Produce Message") or CLI (`docker exec -it kafka kafka-console-producer --topic connection.accepted --bootstrap-server localhost:9092`).
- Mongo shell/Compass access to `ChatServiceDb` (`docker exec -it mongodb mongosh ChatServiceDb`).
- Two SignalR test client sessions (e.g. two browser tabs, or a small test harness) connected to `/hubs/chat` with distinct `X-User-Id` headers matching the `requester_id`/`recipient_id` used below.

1. Connect both SignalR test clients (`user_id=1001` and `user_id=2002`) to `/hubs/chat` and confirm (via server logs) each joined its personal `user:{id}` group — look for no "no resolvable X-User-Id" warning in chat-service logs for either connection.
2. Publish one `connection.accepted` message to the `connection.accepted` topic with a fresh payload, e.g.:
   ```json
   {"event_id":"11111111-1111-1111-1111-111111111111","connection_id":5001,"requester_id":1001,"recipient_id":2002,"accepted_at":"2026-10-11T00:00:00Z"}
   ```
   Expect: message accepted by Kafka UI/producer CLI with no error.
3. Within one poll cycle, confirm in chat-service logs: `"Opened chat room {ChatId} for connection 5001 (users 1001, 2002)."`
   Expect: log line appears within a few seconds.
4. Confirm in Mongo: `db.chat_rooms.findOne({connection_id: "5001"})`
   Expect: exactly one document with `status: "OPEN"`.
5. Confirm both SignalR test clients received a `ChatOpened` event.
   Expect: `chat_id` matches step 4's `_id`, and `connection_id: "5001"` is present in the payload for both clients.
6. Confirm in Mongo: `db.processed_events.findOne({_id: "11111111-1111-1111-1111-111111111111"})`
   Expect: document now exists.
7. **Idempotency test** — republish the exact same message from step 2 (same `event_id`) a second time.
   Expect: message accepted by the producer with no error.
8. Confirm chat-service logs show: `"Skipping already-processed connection.accepted event 11111111-1111-1111-1111-111111111111."`
   Expect: no second "Opened chat room" line appears.
9. Confirm in Mongo: `db.chat_rooms.countDocuments({connection_id: "5001"})`
   Expect: still exactly `1`.
10. (Optional — exercises the app-level existing-room guard rather than the DB unique-index backstop, which only fires under a genuine concurrent race and is hard to force deterministically via manual QA) Publish a *different* `event_id` but the *same* `connection_id: 5001`, e.g. `"event_id":"22222222-2222-2222-2222-222222222222"` with the same `connection_id`/`requester_id`/`recipient_id`.
    Expect: chat-service logs show `"Chat room {ChatId} already exists for connection 5001, reusing."` and `chat_rooms` count for `connection_id: "5001"` remains `1`.

**Cleanup:**
```js
db.chat_rooms.deleteOne({connection_id: "5001"})
db.processed_events.deleteMany({_id: {$in: ["11111111-1111-1111-1111-111111111111","22222222-2222-2222-2222-222222222222"]}})
```
Disconnect the two test SignalR clients.
