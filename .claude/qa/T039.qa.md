## Manual QA — T039

**Prerequisites:** `.env` filled in from `.env.example`; a chat room already exists and is OPEN (i.e., a connection has already gone through `connection.accepted` per T038 — if none exists, drive a request through Connection Service to `accepted` first, or insert a test `chat_rooms` document directly via Mongo Compass pointed at `mongodb://localhost:<mapped-port>/ChatServiceDb` with `status: "OPEN"`, valid `connectionId`/`userAId`/`userBId`, and `createdAt` set).

1. Run `/docker-up` (or `docker compose -f src/infra/docker-compose.yml -f src/infra/docker-compose.override.yml up -d --build`) and wait for the health summary to show `chat-service`, `kafka`, and `kafka-ui` all healthy.
   Expect: all listed services report healthy; no restart loops in `docker compose ps`.

2. Open Kafka UI at `http://localhost:9000`, go to Topics, and confirm `chat.closed` exists (or will appear on first publish — Kafka UI can auto-create on first produce depending on broker config, check cluster settings if it isn't listed yet).
   Expect: topic list loads without error (confirms Kafka UI itself reached the broker over `kafka:29092`, same listener chat-service now uses).

3. **Grace-close path (met_successfully):** note the `_id` of your OPEN test chat room from Mongo Compass. Send `POST http://localhost:8084/chats/{that_id}/met` with header `X-User-Id: <userAId>`, then again with `X-User-Id: <userBId>` (both participants must confirm).
   Expect: first call returns `200` with `bothUsersMet: false`; second call returns `200` with `bothUsersMet: true`. In Mongo Compass, the room's `status` flips to `CLOSING` immediately, then — after the grace period (`CHAT_MET_GRACE_PERIOD_SECONDS`, default 300s; temporarily set this env var lower, e.g. `10`, in `.env` and restart chat-service via `docker compose restart chat-service` if you don't want to wait 5 minutes) — flips to `CLOSED` with `closedAt` set and `outboxPublishedAt` populated (no longer null).

4. In Kafka UI, open the `chat.closed` topic → Messages tab.
   Expect: a new message appears, keyed by the chat room's `_id` (partition key = `chat_id`, per the ticket's "Partition key: chat_id" spec). Message value is JSON containing `event_id` (a non-empty GUID), `chat_id` matching the room, `connection_id`/`user_a_id`/`user_b_id` matching the room's stored values, and `closed_reason: "met_successfully"`.

5. **Auto-close / timeout path:** temporarily set `CHAT_AUTO_CLOSE_THRESHOLD_HOURS=0` and `CHAT_AUTO_CLOSE_POLL_INTERVAL_SECONDS=10` in `.env` (2 hours isn't practical to wait out in a QA session), restart chat-service, and create/leave a second test room OPEN with `createdAt` in the past.
   Expect: within ~10s, Mongo shows that room's `status` go straight to `CLOSED` (no `CLOSING` intermediate — auto-close doesn't go through the grace-timer path), and a second `chat.closed` message appears in Kafka UI for that room's `chat_id` with `closed_reason: "timeout"`. Revert both env vars afterward.

6. **Negative/idempotency check:** re-send `POST /chats/{id}/met` for the room that's already `CLOSED` from step 3, for either user.
   Expect: `409 Conflict` with `CHAT_ALREADY_CLOSED` (per `ChatController.MarkMetSuccessfully`'s `ChatRoomClosed` branch) — and no second message for that `chat_id` appears in Kafka UI (confirms the `Status != CLOSED` filter guard in `ChatRoomRepository.CloseRoomAsync` is doing its job; only one `chat.closed` event per room close, not per close *attempt*).

**Cleanup:** `docker compose -f src/infra/docker-compose.yml -f src/infra/docker-compose.override.yml down` (add `-v` only if you want to wipe Mongo/SQL/Kafka volumes too); revert any temporary `.env` overrides from steps 3/5 back to their defaults (or delete the lines).
