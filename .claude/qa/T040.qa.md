## Manual QA — T040

**Prerequisites:** Docker Desktop running; repo checked out at `C:\Users\anmol.jain\Downloads\ShareConnectSave`; `.env` present in `src/infra/` (copied from `.env.example`) with any required secrets (e.g. `SA_PASSWORD`) filled in, since other services in the same compose file require it to start.

1. Open a terminal in `src/infra/` and run:
   `docker compose up -d mongodb redis kafka`
   Expect: all three containers report `Up` (not `Up (unhealthy)`) after their own `start_period` elapses — confirm with step 2 before proceeding.

2. Run:
   `docker compose ps mongodb redis kafka`
   Expect: the `STATUS` column shows `healthy` for all three (not `starting` or `unhealthy`). Do not proceed to step 3 until this is true — chat-service's `depends_on` (docker-compose.yml:377-383) will otherwise refuse to start it.

3. Run:
   `docker compose up -d --build chat-service`
   Expect: a build log showing the `build` stage (`dotnet restore`, then `dotnet publish`) complete successfully, followed by the `runtime` stage's `apt-get install curl` step, then container creation. No red `ERROR` lines. This is the first runtime confirmation of AC1 (static analysis only covered this until now).

4. Run:
   `docker compose ps chat-service`
   Expect: `STATUS` column shows `Up X seconds (health: starting)` immediately after creation, transitioning to `Up X seconds (healthy)` within roughly `start_period` (40s) + one `interval` (30s), i.e. within about 70 seconds. If it instead shows `(unhealthy)` after several retries, re-check step 2 — a common cause is Mongo/Redis being `Up` but not yet `healthy` when chat-service started, despite `depends_on` normally preventing this.

5. Run:
   `docker compose logs chat-service --tail=50`
   Expect: ASP.NET Core startup log lines (e.g. "Now listening on: http://[::]:8080", "Application started") with no unhandled exceptions, no `MongoDB.Driver` connection-refused errors, and no Kafka `Broker transport failure` errors repeating in a loop. This confirms the override.yml connection strings (lines 130-165) actually resolve at runtime, not just in static config.

6. From the host machine (not inside the container), run:
   `curl -f http://localhost:8084/health`
   Expect: HTTP 200 with a small JSON/plain-text health payload. This confirms the external port mapping (`8084:8080`, docker-compose.yml:385) and the app's own `/health` endpoint both work end-to-end — a stronger signal than the container-internal healthcheck alone. (AC2 confirmed.)

7. Run:
   `docker images shareconnectsave/chat-service:dev --format "{{.Size}}"`
   Expect: a value under `200MB`. If it's at or above, compare against `docker images` output for `api-gateway` as a baseline — the gap is most likely explained by Confluent.Kafka's native `librdkafka` dependency, which api-gateway does not reference. (Closes AC3 with a real measurement, since static analysis alone could not confirm this.)

**Cleanup:** `docker compose down` (from `src/infra/`) to stop and remove all containers started above; add `-v` only if you also want to discard MongoDB/Redis/Kafka volumes (not necessary for this QA pass, and discards other test data — use with care, only if you're sure).
