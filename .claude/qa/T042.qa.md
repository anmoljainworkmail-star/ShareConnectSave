## Manual QA — T042

**Prerequisites:** Infrastructure running via `/docker-up` (SQL Server reachable on `localhost:14330`, Kafka on `localhost:9092`, Kafka UI available). Rating Service started locally (`dev` profile) with `RATING_DB_PASSWORD` exported. Flyway must have applied both `V001__rating_service_initial_schema.sql` and `V002__rating_service_outbox_table.sql` (check service startup logs for "Successfully applied 2 migrations").

1. Submit a valid rating:
   ```
   curl -i -X POST http://localhost:<rating-service-port>/ratings \
     -H "Content-Type: application/json" \
     -H "X-User-Id: 101" \
     -d '{"connection_id": 5001, "rated_id": 202, "tags": ["Friendly", "On time"], "comment": "Great trip"}'
   ```
   Expect: `201 Created`, body `{"id": <number>, "connection_id": 5001, "rater_id": 101, "rated_id": 202, "tags": ["Friendly","On time"], "comment": "Great trip", "created_at": "<ISO timestamp>"}`.

2. Repeat the exact same request immediately.
   Expect: `409 Conflict`, body `{"code": "RATING_ALREADY_SUBMITTED", "message": "User 101 has already rated connection 5001", "traceId": "..."}`.

3. Fire the step-1 request concurrently twice in parallel (race condition check — the actual regression this fix addresses) against a **new** `connection_id` (e.g. 5002) the user hasn't rated yet:
   ```
   curl -s -X POST http://localhost:<port>/ratings -H "Content-Type: application/json" -H "X-User-Id: 101" -d '{"connection_id": 5002, "rated_id": 202, "tags": ["Friendly"]}' & \
   curl -s -X POST http://localhost:<port>/ratings -H "Content-Type: application/json" -H "X-User-Id: 101" -d '{"connection_id": 5002, "rated_id": 202, "tags": ["Friendly"]}' & \
   wait
   ```
   Expect: one response is `201 Created`, the other is `409 Conflict` with `RATING_ALREADY_SUBMITTED` (NOT a `500`) — this is the exact case the prior review blocked on.

4. Submit an invalid tag:
   ```
   curl -i -X POST http://localhost:<port>/ratings -H "Content-Type: application/json" -H "X-User-Id: 101" -d '{"connection_id": 5003, "rated_id": 202, "tags": ["Super nice"]}'
   ```
   Expect: `400 Bad Request`, body `{"code": "INVALID_RATING_TAG", "message": "'Super nice' is not a recognized rating tag", "traceId": "..."}`.

5. Submit a self-rating (should fail, not in the ticket's three named exceptions but present):
   ```
   curl -i -X POST http://localhost:<port>/ratings -H "Content-Type: application/json" -H "X-User-Id: 101" -d '{"connection_id": 5004, "rated_id": 101, "tags": ["Friendly"]}'
   ```
   Expect: `400 Bad Request`, `{"code": "SELF_RATING_NOT_ALLOWED", ...}`.

6. Submit with an empty tags array (boundary/bad-input case):
   ```
   curl -i -X POST http://localhost:<port>/ratings -H "Content-Type: application/json" -H "X-User-Id: 101" -d '{"connection_id": 5005, "rated_id": 202, "tags": []}'
   ```
   Expect: `400 Bad Request`, `{"code": "VALIDATION_ERROR", ...}`.

7. Observe the OutboxRelay publishing: open Kafka UI (default `http://localhost:<kafka-ui-port>`, topic `rating.submitted`) immediately after step 1's request. Within ~500ms a message should appear with key `5001` (the connection_id partition key) and a JSON value containing `"event_id"`, `"rating_id"`, `"rater_id":"101"`, `"rated_id":"202"`, `"tags":["Friendly","On time"]` — note ids are stringified, tags are Title Case, matching `contracts/kafka/rating.submitted.schema.json` exactly.

8. Confirm the outbox row flipped state: query `SELECT status, processed_at FROM outbox WHERE partition_key = '5001'` against RatingServiceDb (e.g. via a SQL client on `localhost:14330`). Expect `status = 'PROCESSED'` and `processed_at` populated (non-null), within a second or two of step 1's request.

9. (Documents the known, accepted gap — not a failing test) Submit a request with no `X-User-Id` header at all:
   ```
   curl -i -X POST http://localhost:<port>/ratings -H "Content-Type: application/json" -d '{"connection_id": 5006, "rated_id": 202, "tags": ["Friendly"]}'
   ```
   Expect (current, pre-existing platform behavior): `500 Internal Server Error`, `{"code": "INTERNAL_ERROR", ...}` — NOT the `401 Unauthorized` the OpenAPI contract describes. This is a shared-java-lib-wide gap across every service, not specific to T042; record it separately if the team wants it fixed, but it is not a T042 regression and should not block this ticket.

**Cleanup:** No teardown required beyond normal `/docker-up` stack lifecycle; the test ratings/outbox rows created above can be left in the dev database or cleared with `DELETE FROM ratings; DELETE FROM outbox;` against RatingServiceDb if a clean slate is wanted before the next ticket.
