## Manual QA — T044

**Prerequisites:** Infrastructure running via `/docker-up` (SQL Server on `localhost:14330`, Kafka + Kafka UI reachable). `RATING_DB_PASSWORD` exported.

1. Run `mvn -q compile` from `src/services/rating-service` — Expect: `BUILD SUCCESS`, no compile errors (this is the first real compile of this code in this environment — Maven was unavailable during review).
2. Start rating-service (`dev` profile). Check startup logs — Expect: "Successfully applied 3 migrations" (V001, V002, V003), and confirm `closed_chats`, `processed_events` tables and `trust_scores.report_count` column exist in RatingServiceDb.
3. Publish to `chat.closed` via Kafka UI, key `5001`: `{"event_id":"11111111-1111-1111-1111-111111111111","chat_id":"c-1","connection_id":"5001","user_a_id":"101","user_b_id":"202","closed_reason":"met_successfully"}` — Expect: row in `closed_chats` (connection_id=5001), row in `processed_events` (that event_id). Re-publish the identical message — Expect: log line "Skipping already-processed chat.closed event..." and still exactly one `closed_chats` row.
4. Submit 2-3 ratings via `POST /ratings` for the same `rated_id` (e.g. 202) against distinct, chat-closed connections — Expect: within ~2s of each, a `trust.score.updated` message on Kafka UI keyed `202`, with `new_score` (1.0-5.0), `badge_level` (string), `request_limit` (plain integer, never a string). Query `SELECT * FROM trust_scores WHERE user_id=202` — row matches.
5. Publish three `report.filed` events for the same `reported_id` (e.g. 303) with `report_count_for_target` = 1, 2, 3 — Expect: counts 1 and 2 produce no `trust.score.updated` but are recorded in `processed_events`; count 3 triggers `trust.score.updated` keyed `303` with `request_limit:0`, `badge_level:"restricted"`.
6. **Concurrency race:** pick a brand-new, never-before-seen user id (e.g. 909). Publish a `rating.submitted` event with `rated_id:"909"` and a `report.filed` event with `reported_id:"909"` (`report_count_for_target:3`) as close together as you can (two Kafka UI tabs, submit within ~1 second of each other). Expect: one of the two consumer transactions may log a rollback/error for a duplicate-insert constraint violation on `trust_scores` (this is expected, not a bug) — but after both have been redelivered and reprocessed, exactly ONE row exists in `trust_scores` for user 909 (`SELECT COUNT(*) FROM trust_scores WHERE user_id=909` = 1), and its final state reflects both inputs having been applied (check `report_count=3` and `request_limit=0`/`restricted`, confirming the report-driven suspension won).
7. Restart with `RATING_REPORT_SUSPENSION_THRESHOLD=1` exported and repeat step 5 with a single report at count 1 — Expect: immediate recalculation on the first report (confirms config is read from env, not hardcoded).

**Cleanup:** `DELETE FROM closed_chats; DELETE FROM processed_events; DELETE FROM trust_scores; DELETE FROM ratings; DELETE FROM outbox;` against RatingServiceDb.
