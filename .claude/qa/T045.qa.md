## Manual QA — T045

**Prerequisites:** Rating Service and Connection Service both running (via `/docker-up` + each service started, e.g. `mvnw spring-boot:run -Dspring-boot.run.profiles=dev` in each service directory), SQL Server reachable, and at least one Kafka-driven `trust_scores` row already created for a test user (e.g. by submitting a rating via T042's endpoint so T044's recalculation populates `trust_scores`). Have two test user ids ready: one with a `trust_scores` row (`USER_WITH_SCORE`), one with none (`USER_NO_SCORE`).

1. `curl -i http://localhost:<rating-service-port>/trust/<USER_WITH_SCORE>`
   Expect: `200 OK`, JSON body shaped `{"user_id":<id>,"trust_score":<decimal>,"request_limit":<int>,"is_trusted":<bool>,"rating_count":<int>}`. Confirm `request_limit` is a plain integer (e.g. `5`, `3`, `10`), never a string like `"STANDARD"`.

2. `curl -i http://localhost:<rating-service-port>/trust/<USER_NO_SCORE>`
   Expect: `404 Not Found`, JSON body `{"code":"TRUST_SCORE_NOT_FOUND","message":"No trust score found for user <id>","traceId":"<some id or empty string>"}` — not a 500, not an empty body.

3. In connection-service, trigger a `createConnection` call as `USER_NO_SCORE` (e.g. `curl -i -X POST http://localhost:<connection-service-port>/connections -H "Content-Type: application/json" -H "X-User-Id: <USER_NO_SCORE>" -d '{"recipientId": <someOtherUserId>}'`, adjusting header/body to match this service's actual gateway-identity contract).
   Expect: `201 Created` (or whatever this endpoint's normal success status is) — the request succeeds using `DEFAULT_REQUEST_LIMIT` (5), not a 500, because the 404 from step 2 resolves to a normal cached `TrustData(5, fromFallback=false)`, not a circuit-breaker failure.

4. Check connection-service logs after step 3 for a line containing `Cache-Aside miss for user <USER_NO_SCORE> resolved via Rating Service; caching requestLimit=5` (DEBUG level — ensure `logging.level.com.shareconnectsave.connection: DEBUG` is active, which the `dev` profile already sets).
   Expect: this line appears exactly once for that user. Repeat step 3's `createConnection` call (or any action calling `getLimit` for the same user) 2-3 more times and confirm the log line does **not** repeat — proving the value is now served from cache, not re-fetched every time.

5. Stop Rating Service (e.g. `docker stop <rating-service-container>` or kill its process) to simulate an outage.

6. Call `getLimit` indirectly for a *different*, not-yet-cached user — e.g. `createConnection` as `USER_WITH_SCORE_2` (a third test user never queried before) — at least `minimum-number-of-calls: 10` times in a row (per `application.yml`'s `resilience4j.circuitbreaker.instances.ratingService` config) to force the circuit past its failure-rate threshold and open.
   Expect: each call still returns success (fallback keeps `createConnection` working), and connection-service logs show `Rating Service unavailable for user <id> (...); falling back to default request limit (fail-open)` at WARN level for each attempt — confirming the exception is logged, not swallowed.

7. With the circuit now open, call `GET http://localhost:<connection-service-port>/actuator/health`
   Expect: JSON includes a `circuitBreakers` component showing the `ratingService` instance in `OPEN` state (per `management.health.circuitbreakers.enabled: true` and `show-details: always`).

8. Restart Rating Service, then repeat step 3/6's `createConnection` call for the same user used in step 6 after the circuit breaker's `wait-duration-in-open-state` (30s) has elapsed.
   Expect: the circuit moves to HALF_OPEN then CLOSED, and a fresh `getLimit()` call now fetches and caches the user's real limit from Rating Service (log line from step 4's pattern reappears for this user) instead of permanently sticking at the fallback default.

9. Restart connection-service entirely (simulating a pod restart) for a user who was already cached with a non-default limit (e.g. a low-trust user with `request_limit: 1` from a prior rating).
   Expect: immediately after restart, a fresh `createConnection` call for that user logs the cache-miss-resolved-via-Rating-Service line again and correctly enforces `request_limit: 1` (not silently reset to `5`) — the exact T033 gap this ticket closes.

10. Confirm the build itself: in a terminal, run:
    ```
    cd src/services/connection-service && ./mvnw -o clean compile
    ```
    Expect: `BUILD SUCCESS` with a line like `Compiling 42 source files...` (not "Nothing to compile" — that would mean a stale/cached result, not a real check). This was independently verified during this review cycle: both `connection-service` (42 source files) and `rating-service` (51 source files) built successfully from a clean state, confirming the `Mono` import defect from cycle 2 is fully resolved.

**Cleanup:** Restart Rating Service if still stopped from step 5. Clear any test `trust_scores`/`connection_requests` rows created for `USER_NO_SCORE`/test users if this was run against a shared dev database. Restart connection-service normally (not in the mid-circuit-open state) before resuming other testing.

**Non-blocking item carried forward (not required for this ticket, flagged for awareness only):** `InMemoryRequestLimitCache.getLimit()` has a benign cache-stampede race under concurrent cold-cache requests for the same user (two threads can both miss and both call Rating Service before either caches) — same classification cycle 2 gave it (RISK, not BLOCKER), re-confirmed present and still non-corrupting (both threads get the same correct value). Worth a future ticket if Rating Service load from stampedes ever becomes a real concern; Caffeine's `get(key, Function)` atomic-load-or-compute variant would close it.
