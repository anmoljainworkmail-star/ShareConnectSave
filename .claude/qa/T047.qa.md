## Manual QA — T047

**Prerequisites:** Docker Desktop running; a real Firebase project with a service-account JSON key file downloaded locally; a real Android/web device or emulator registered to receive a test push via that Firebase project (to get one real FCM device token) — if you don't have this available, skip step 4 and read its note instead.

1. Place the downloaded Firebase service-account JSON at `./secrets/fcm-service-account.json` relative to `src/infra/` (or set `FCM_CREDENTIALS_JSON_HOST_PATH` in your `.env` to point elsewhere).
   Expect: file exists and is valid JSON (a service-account key has `"type": "service_account"` near the top).
2. From `src/infra/`, run `docker compose up -d --build notification-service`.
   Expect: container starts and stays up (`docker compose ps` shows `notification-service` as `Up`, not restarting). Check `docker compose logs notification-service` — no `InvalidOperationException: FCM_CREDENTIALS_JSON is not configured` and no Firebase credential error.
3. Temporarily remove or blank the `FCM_CREDENTIALS_JSON_HOST_PATH`/mounted file and re-run `docker compose up notification-service`.
   Expect: container fails to start immediately with `InvalidOperationException: FCM_CREDENTIALS_JSON is not configured...` in the logs — this is the intended fail-fast behavior, not a bug. Restore the real credentials file afterward.
4. Smoke-test an actual send: since no HTTP endpoint exists yet to trigger `SendAsync` (by design — this ticket is plumbing only), do this via a short-lived local test harness. Calling `SendAsync` through the real `IUserServiceClient` is NOT sufficient on its own — User Service has no `fcm_token` field yet, so the real lookup always returns null (see note below). Instead, temporarily swap the DI registration to a throwaway stub returning your real device token (e.g. `builder.Services.AddScoped<IUserServiceClient>(_ => new FakeTokenClient("<your real FCM token>"));`) before `builder.Build()`, then call `app.Services.GetRequiredService<IFcmNotificationService>().SendAsync("<any-id>", "Test", "Hello from T047", new Dictionary<string,string>())` right after. **This step cannot be exercised as a normal user-facing flow today** — note this limitation explicitly in your QA record rather than skipping silently.
   Expect: the registered test device receives a push notification titled "Test" with body "Hello from T047"; logs show no error. Revert the temporary DI/Program.cs changes afterward — do not commit them.
5. Re-run with an intentionally invalid/expired token in place of the real one (same stub approach as step 4).
   Expect: the Firebase send throws (FCM rejects the invalid token) — this currently propagates as an unhandled exception out of the test harness call; that's expected given this ticket adds no HTTP boundary to catch it, not a new regression.

**Note on AC2:** "SendAsync with a real FCM token delivers a notification" cannot be demonstrated end-to-end through the real User Service lookup today, because User Service's `GET /users/{id}` does not yet serialize an `fcm_token` field. `UserServiceClient` correctly calls the real, verified endpoint and reads the right property name — it will start working automatically once a future ticket adds that field to User Service. Step 4 above verifies the Firebase SDK integration itself works via a stubbed client in the meantime.

**Cleanup:** `docker compose down notification-service`; revert any temporary `Program.cs`/stub changes made for step 4/5; do not commit the real service-account JSON or your personal FCM device token anywhere in the repo.
