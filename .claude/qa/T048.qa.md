## Manual QA — T048

**Prerequisites:** `docker-up` infrastructure running (shared Redis reachable), notification-service built and running with `SIGNALR_REDIS_CONNECTION` and `FCM_CREDENTIALS_JSON` set (the latter required for the service to start at all per T047's guard clause). A way to run a small script/console with network access to notification-service's port.

1. Using a Node script (browsers can't set arbitrary headers like X-User-Id directly — in production the gateway injects it) with `@microsoft/signalr`, connect to `http://localhost:<port>/hubs/notifications` passing `headers: { 'X-User-Id': '1001' }` in the connection options, then `await connection.start()`.
   Expect: connects with no error; `connection.connectionId` is a populated guid-like string.

2. Check notification-service container logs right after connecting.
   Expect: no "has no resolvable X-User-Id" warning for this connection — its absence is the positive signal that the group join succeeded (there's no explicit success log by design).

3. Repeat step 1 omitting X-User-Id (or set it to `"abc"`).
   Expect: connection still succeeds (no exception) — confirming graceful degradation — AND the log shows: `SignalR connection <connectionId> has no resolvable X-User-Id; it will not receive personal notifications.`

4. With the step-1 connection still open and a `connection.on('TestEvent', msg => console.log('received', msg))` handler registered before `start()`, temporarily add a throwaway (not committed) `app.MapGet("/test-push/{id}", ...)` endpoint that resolves `IHubContext<NotificationHub>` and calls `.Clients.Group("user:1001").SendAsync("TestEvent", "hello")`, then hit it.
   Expect: console logs `received hello`. If no way to add even a throwaway endpoint exists in this environment, skip and record explicitly that end-to-end group delivery was not verified in this pass — that verification should happen naturally once T049 adds a real publish call.

5. Cross-replica check: run a second notification-service instance on a different port against the same SIGNALR_REDIS_CONNECTION (via `docker compose up --scale notification-service=2` if networking supports it, or a manually started second process). Connect client A to replica 1 (X-User-Id: 1001); trigger the step-4 test-push endpoint on replica 2.
   Expect: client A (connected to replica 1) still receives TestEvent, proving the Redis backplane — not just in-process Clients.Group — delivers across processes. If a working two-replica setup isn't available here, say so explicitly rather than skipping silently; this is the one AC that can't be verified with a single instance.

**Cleanup:** `connection.stop()`, remove any temporary test-push endpoint before committing anything, scale notification-service back to 1 instance.
