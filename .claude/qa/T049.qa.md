## Manual QA — T049

**Prerequisites:** Docker Desktop running; `.env` populated from `.env.example` (including `SA_PASSWORD`, `INTERNAL_SERVICE_KEY`, FCM credentials); run `docker compose up` (or your project's `/docker-up`) from `src/infra` to bring up SQL Server, Kafka, Redis, Kafka UI, and all services including notification-service and user-service.

1. Confirm the Kafka fix actually takes effect: `docker compose logs notification-service | grep -i "connection.requested\|connection.accepted\|connection.expired\|GroupCoordinator\|subscribed"` (or just `docker compose logs -f notification-service` and watch startup).
   Expect: log lines showing the consumer group `notification-service` successfully joining and getting partitions assigned for `connection.requested`, `connection.accepted`, and `connection.expired` — not just "Broker connected" but an actual partition assignment / "Subscribed" message. This is the proof the override fix works, since before the fix the consumers connected to the wrong listener and silently never received messages.

2. Register an FCM token for a real user (replace `<JWT>` with a valid token for that user obtained via your normal login flow):
   ```
   curl -X PATCH http://localhost:<gateway-port>/users/me/fcm-token \
     -H "Authorization: Bearer <JWT>" \
     -H "Content-Type: application/json" \
     -d '{"fcmToken":"test-device-token-abc123"}'
   ```
   Expect: `204 No Content`.

3. Negative check — confirm a token cannot be set for another user (the DTO has no id field, so attempt a body with an extraneous `userId` field to confirm it's ignored, not honored):
   ```
   curl -X PATCH http://localhost:<gateway-port>/users/me/fcm-token \
     -H "Authorization: Bearer <JWT-for-user-A>" \
     -H "Content-Type: application/json" \
     -d '{"fcmToken":"hijack-attempt","userId":999}'
   ```
   Expect: `204 No Content`, and when you later check via the internal endpoint (step 6) that user A's own token — not user 999's — was updated. (An extra JSON field with no matching DTO property is simply ignored by model binding; this confirms there is no route/body-based id override path.)

4. Trigger a `connection.requested` event by going through the normal connection-request flow (User B sends User A a connection request via the Connection Service's public API) — or publish directly via Kafka UI (`http://localhost:<kafka-ui-port>`, topic `connection.requested`) with a JSON body matching `ConnectionRequestedEvent`'s shape if you want to isolate notification-service.
   Expect (if User A is connected to the SignalR hub): a SignalR push delivered to User A within ~1s. Expect (if User A is NOT connected to the hub): an FCM send attempt in notification-service's logs for User A's registered token.

5. Idempotency check — republish the exact same `connection.requested` message (same `EventId`) via Kafka UI's "produce" feature.
   Expect: notification-service logs "Skipping already-processed connection.accepted/requested event {EventId}" (per the relevant handler) and does NOT send a second SignalR push or FCM notification.

6. Confirm the internal FCM-token lookup end-to-end and that it is NOT reachable through the public gateway:
   ```
   curl -i http://localhost:<gateway-port>/users/internal/<userAId>/fcm-token
   ```
   Expect: `404 Not Found` (gateway does not route this path) — proving the internal endpoint is not exposed publicly.
   Then, from inside the Docker network (e.g. `docker compose exec notification-service curl -i -H "X-Internal-Service-Key: <value from .env>" http://user-service:8080/users/internal/<userAId>/fcm-token`):
   Expect: `200 OK` with body `{"fcm_token":"test-device-token-abc123"}` (the value set in step 2/3).
   Then repeat the same internal curl with a wrong/missing `X-Internal-Service-Key` header.
   Expect: `401 Unauthorized` with error envelope `{"code":"INVALID_INTERNAL_KEY","message":"Internal service authentication failed.","traceId":"..."}`.

7. Poison-pill check — publish a deliberately malformed message to `connection.requested` via Kafka UI (e.g. `{"garbage": true}` or plain invalid JSON like `not-json`).
   Expect: notification-service logs an error ("Failed to deserialize..." or "missing/invalid required field...") and the consumer continues polling normally — confirm by publishing a valid, well-formed message to the same topic immediately after and seeing it processed (SignalR push / FCM attempt) rather than the consumer being stuck.

**Cleanup:** `docker compose down` from `src/infra` (add `-v` only if you also want to wipe SQL Server/Mongo/Kafka volumes between test runs).
