## Manual QA — T052

**Prerequisites:**
- Infra running via `/docker-up` (MongoDB reachable at `mongodb://localhost:27018/ReportServiceDb`, Kafka reachable at `localhost:9092`, Kafka UI reachable at whatever URL `/docker-up` reported, typically `http://localhost:8080` or similar — check the health summary it printed).
- report-service running (`dev` profile), e.g. `mvnw spring-boot:run` from `src/services/report-service`, listening on its configured port (check `application.yml` / docker-compose for the exact port; assume `8086` below — substitute the real one from your `/docker-up` output).
- Have two distinct user-id strings on hand to use as reporter/reported, e.g. `USER_A` and `USER_B` (any string works for X-User-Id in dev since the gateway isn't in front of a bare `mvnw spring-boot:run`).

1. File a valid report.
   ```
   curl -i -X POST http://localhost:8086/reports \
     -H "Content-Type: application/json" \
     -H "X-User-Id: USER_A" \
     -d "{\"reported_id\": \"USER_B\", \"reason\": \"Harassment\", \"connection_id\": null, \"details\": \"Test report\"}"
   ```
   Expect: `HTTP/1.1 201`, JSON body shaped like:
   ```
   {"id":"<uuid>","reporter_id":"USER_A","reported_id":"USER_B","reason":"Harassment","connection_id":null,"details":"Test report","status":"open","created_at":"<ISO timestamp>"}
   ```

2. Confirm the report persisted to MongoDB (AC1).
   Connect to Mongo (e.g. `mongosh "mongodb://localhost:27018/ReportServiceDb"`) and run `db.reports.find().sort({createdAt:-1}).limit(1).pretty()`.
   Expect: one document with the `id` from step 1's response, `reason: "Harassment"`, `status: "OPEN"`, a non-null `eventPayload` field (a JSON string), and `outboxPublishedAt` either `null` (if the relay hasn't ticked yet) or a recent timestamp (if it has — the relay runs every 500ms, so by the time you check it should usually be set).

3. Confirm the `report.filed` event was actually published to Kafka (AC2).
   Either:
   - Kafka UI: open the Kafka UI URL from `/docker-up`, navigate to topic `report.filed`, view messages. Expect: a message keyed by `USER_B` (the `reportedId`) with a JSON value containing `"event_id"`, `"report_id"` (both equal to the `id` from step 1), `"reporter_id":"USER_A"`, `"reported_id":"USER_B"`, `"reason":"Harassment"`, `"report_count_for_target":1`.
   - Or CLI: `docker exec -it <kafka-container> kafka-console-consumer --bootstrap-server localhost:9092 --topic report.filed --from-beginning` and look for the same JSON payload.
   Also check report-service logs for no `"Failed to relay report.filed event"` error line around the time of the request — absence of that log line plus the Mongo `outboxPublishedAt` being set (step 2) is your proof the relay succeeded.

4. Confirm `report_count_for_target` increments correctly (AC3).
   Repeat step 1's curl with the SAME `reported_id` (`USER_B`) but a different reporter (`X-User-Id: USER_C`) and any valid reason.
   Expect: `201`, and in the Kafka message for this second event, `"report_count_for_target": 2`.

5. Invalid reason string — the bug this cycle fixed. Expect a clean 400, not a 500.
   ```
   curl -i -X POST http://localhost:8086/reports \
     -H "Content-Type: application/json" \
     -H "X-User-Id: USER_A" \
     -d "{\"reported_id\": \"USER_D\", \"reason\": \"banana\", \"connection_id\": null, \"details\": null}"
   ```
   Expect: `HTTP/1.1 400`, body:
   ```
   {"code":"INVALID_REPORT_REASON","message":"'banana' is not a recognized report reason","traceId":"<id or empty string>"}
   ```
   This must NOT be a 500 and must NOT contain a stack trace — if you see `HTTP/1.1 500` here, the cycle-1 bug has regressed.

6. Missing X-User-Id header — expected behavior is a known pre-existing gap (not something this cycle introduced or is expected to fix).
   ```
   curl -i -X POST http://localhost:8086/reports \
     -H "Content-Type: application/json" \
     -d "{\"reported_id\": \"USER_B\", \"reason\": \"Harassment\", \"connection_id\": null, \"details\": null}"
   ```
   Expect: `HTTP/1.1 500` with `{"code":"INTERNAL_ERROR","message":"An unexpected error occurred.","traceId":"..."}`. This is documented in `ExceptionHandlingConfig.java` as a known gap tracked against T091 — do not treat this as a new T052 defect.

7. Self-report guard sanity check (confirm untouched by the fix).
   ```
   curl -i -X POST http://localhost:8086/reports \
     -H "Content-Type: application/json" \
     -H "X-User-Id: USER_A" \
     -d "{\"reported_id\": \"USER_A\", \"reason\": \"Harassment\", \"connection_id\": null, \"details\": null}"
   ```
   Expect: `HTTP/1.1 409`, body `{"code":"SELF_REPORT_NOT_ALLOWED","message":"User USER_A cannot report themselves","traceId":"..."}`.

**Cleanup:** `db.reports.deleteMany({reportedId: {$in: ["USER_B","USER_D","USER_A"]}})` in `mongosh` against `ReportServiceDb` to remove test documents created above (Kafka topic messages are TTL/retention-governed and don't need manual cleanup).
