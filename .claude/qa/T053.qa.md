## Manual QA — T053

**Prerequisites:** `report-service` running locally (via `/docker-up` infra + `mvnw spring-boot:run` or the service's Docker image) with `REPORT_ESCALATION_THRESHOLD` left at its default (3). A Kafka UI reachable (default local dev URL `http://localhost:8080`, topic `report.filed`) or `kcat`/console-consumer access to the same topic. Three distinct `reporterId` UUIDs and one shared `reportedId` UUID to report against.

1. File report #1 against the shared target:
   ```
   curl -X POST http://localhost:<report-service-port>/reports \
     -H "X-User-Id: 11111111-1111-1111-1111-111111111111" \
     -H "Content-Type: application/json" \
     -d '{"reported_id":"99999999-9999-9999-9999-999999999999","reason":"Harassment"}'
   ```
   Expect: `201 Created`, JSON body with `"status":"open"`.

2. File report #2 against the same target (different reporter):
   ```
   curl -X POST http://localhost:<report-service-port>/reports \
     -H "X-User-Id: 22222222-2222-2222-2222-222222222222" \
     -H "Content-Type: application/json" \
     -d '{"reported_id":"99999999-9999-9999-9999-999999999999","reason":"Harassment"}'
   ```
   Expect: `201 Created`, `"status":"open"`.

3. File report #3 against the same target (third reporter) — this is the one that crosses the default threshold of 3:
   ```
   curl -X POST http://localhost:<report-service-port>/reports \
     -H "X-User-Id: 33333333-3333-3333-3333-333333333333" \
     -H "Content-Type: application/json" \
     -d '{"reported_id":"99999999-9999-9999-9999-999999999999","reason":"Harassment"}'
   ```
   Expect: `201 Created`. The JSON response (ReportResponse) still shows `"status":"open"` at this point — the response schema doesn't echo the escalation state; that's visible via steps 4-6 instead.

4. Confirm `escalated: true` landed on the Kafka event: open Kafka UI at `http://localhost:8080`, navigate to topic `report.filed`, find the message whose `report_id` matches report #3's `id` from step 3's response.
   Expect: message payload includes `"escalated": true` and `"report_count_for_target": 3`.
   (CLI alternative: `docker exec -it <kafka-container> kafka-console-consumer --bootstrap-server localhost:9092 --topic report.filed --from-beginning --max-messages 3` and inspect the JSON.)

5. Confirm the bulk status flip in MongoDB directly (or via the queue endpoint in step 6): connect to the `ReportServiceDb` database (`mongodb://localhost:27018/ReportServiceDb` for local dev) and query `db.reports.find({reportedId: "99999999-9999-9999-9999-999999999999"})`.
   Expect: all three report documents now show `"status": "ESCALATED"` and `"reportCountAtEscalation": 3`.

6. Call the admin queue endpoint as an admin:
   ```
   curl http://localhost:<report-service-port>/reports/queue \
     -H "X-User-Id: 44444444-4444-4444-4444-444444444444" \
     -H "X-User-Role: admin"
   ```
   Expect: `200 OK`, a JSON array containing exactly the 3 reports from steps 1-3 (and no `open`-status reports from any other target you may have filed in earlier testing).

7. Call the same endpoint as a non-admin (the failure case):
   ```
   curl -i http://localhost:<report-service-port>/reports/queue \
     -H "X-User-Id: 55555555-5555-5555-5555-555555555555" \
     -H "X-User-Role: user"
   ```
   Expect: `403 Forbidden`, body shaped like:
   ```json
   {"code":"ADMIN_ROLE_REQUIRED","message":"User 55555555-5555-5555-5555-555555555555 is not authorized to view the report escalation queue","traceId":"<some-id-or-empty-string>"}
   ```

8. (Optional, documents the known accepted gap — do not treat as a failure) Call the queue endpoint with `X-User-Role` omitted entirely:
   ```
   curl -i http://localhost:<report-service-port>/reports/queue \
     -H "X-User-Id: 66666666-6666-6666-6666-666666666666"
   ```
   Expect: `500 Internal Server Error` with a generic `INTERNAL_ERROR` envelope — this is the pre-existing, ticket-acknowledged `MissingRequestHeaderException` gap deferred to T091, not a new bug introduced by T053.

**Cleanup:** Drop the three test reports from `ReportServiceDb.reports` (`db.reports.deleteMany({reportedId: "99999999-9999-9999-9999-999999999999"})`) if you want a clean queue for the next manual test pass; no Kafka cleanup needed (dev topic is expected to accumulate test messages).
