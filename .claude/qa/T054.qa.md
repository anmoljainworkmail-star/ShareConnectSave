## Manual QA — T054

**Prerequisites:** report-service and its dependencies (MongoDB, Kafka, Zookeeper/KRaft) running via `/docker-up` or equivalent `docker compose up`. Report-service itself running with logs visible (`docker compose logs -f report-service` or console if running via `mvnw spring-boot:run`). A way to call `POST /reports` (Postman/curl) with a valid JWT for an authenticated user and a valid `reportedId`.

1. With Kafka healthy, call `POST /reports` with a valid body (`reportedId`, `reason`, optional `details`).
   Expect: HTTP `201` returned immediately (sub-second), containing the new report's id.

2. Watch report-service logs for the next ~1 second.
   Expect: no `DEAD_LETTER_REPORT_FILED` line, no retry/backoff log — the relay's next tick (within 500ms) publishes successfully on attempt 1 and the document is marked published with no visible retry noise.

3. Confirm the Mongo document was marked published: query the `reports` collection (`mongosh` or Compass) for that report's `_id` and check `outboxPublishedAt` is non-null.
   Expect: `outboxPublishedAt` is set to a timestamp shortly after `createdAt`.

4. Induce a Kafka outage: `docker compose stop kafka`.

5. Call `POST /reports` again with a new, valid body.
   Expect: HTTP `201` returned immediately, exactly as in step 1 — the response does not wait on Kafka at all (this is the core "retry is relay-internal, not request-blocking" guarantee).

6. Watch report-service logs for the next several ticks (several seconds).
   Expect: one `DEAD_LETTER_REPORT_FILED reportId=... reportedId=... attempts=3 eventPayload={...}` ERROR line per tick for the new report (every ~500ms, since Kafka is still down and each tick retries all 3 attempts then dead-letters again) — each line showing the full JSON payload, the reportedId, and an exception (connection refused / timeout) attached as the stack trace.

7. Query the `reports` collection for that same report's `_id`.
   Expect: `outboxPublishedAt` is still `null` — confirms a dead-lettered tick never marks the document published.

8. Bring Kafka back: `docker compose start kafka`. Wait a few seconds for the broker to finish starting and report-service's producer to reconnect.

9. Watch report-service logs.
   Expect: the `DEAD_LETTER_REPORT_FILED` lines stop appearing; within one or two ticks (~500ms-1s) a successful publish happens with no error log.

10. Re-query the `reports` collection for that report's `_id`.
    Expect: `outboxPublishedAt` is now set — confirms self-healing once Kafka recovers, with no manual intervention or replay step needed (the log line was a breadcrumb for a human, not a required action).

11. (Optional, harder to induce reliably) To specifically exercise the 200ms/400ms backoff-but-eventual-success path (AC1's "retried up to 3 times" on a transient blip, not a full outage): stop Kafka, call `POST /reports`, then restart Kafka within roughly 200-600ms of the next relay tick firing.
    Expect: occasionally you'll see a log line indicating a retry happened within a single tick before eventual success (no dedicated log line for "attempt 2 succeeded" exists in this implementation — the only observable signals are the dead-letter log on full failure and the Mongo `outboxPublishedAt` state; this step is best-effort only and may not reliably reproduce at a human's reaction speed — don't rely on seeing it directly).

**Cleanup:** `docker compose stop kafka` (if still running from a mid-test state) — ensure `docker compose up -d` or `/docker-up` is re-run afterward to restore the full stack; delete or ignore the test report documents created during this QA pass (no cleanup endpoint exists, they're harmless and will fall outside any manual review window).
