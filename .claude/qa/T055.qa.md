## Manual QA — T055

**Prerequisites:** Docker Desktop (or equivalent engine) running; repo checked out at the commit containing this ticket's changes; no other process bound to host ports 8087, 27017-equivalent Mongo mapping, or the Kafka port.

1. Run `docker compose -f src/infra/docker-compose.yml build --no-cache report-service`
   Expect: build completes with exit code 0, and the log shows the `shared-java-lib` install step (`./mvnw install -DskipTests -B` under `shared-java-lib`) running and succeeding *before* report-service's own `dependency:go-offline` step — confirms the build doesn't silently depend on a pre-existing local Maven cache or stale Docker layer cache.

2. Run `docker inspect --format={{.Size}} shareconnectsave/report-service:dev`
   Expect: a byte count under `314572800` (300MB). Should read close to the previously-verified `120918431` bytes (~115.3MB) — a large jump would indicate an accidental dependency bloat or a broken multi-stage split (e.g., JDK/Maven leaking into the runtime stage).

3. Run `docker compose -f src/infra/docker-compose.yml up -d` (full stack, not report-service in isolation)
   Expect: `mongodb` and `kafka` report `healthy` first, then `report-service` transitions from `starting` to `healthy` within the 60s `start_period`. Confirms the `depends_on: service_healthy` ordering actually holds under the full stack, not just when report-service is brought up alone.

4. Run `docker compose -f src/infra/docker-compose.yml ps report-service`
   Expect: `STATUS` column shows `Up ... (healthy)`.

5. Run `curl -f http://localhost:8087/actuator/health` from the host
   Expect: HTTP 200 with `{"status":"UP"}` — confirms the external port mapping (`8087:8080`) and the healthcheck's internal endpoint both actually resolve, not just that the container process is alive.

6. Run `docker compose -f src/infra/docker-compose.yml logs report-service | grep -i "profile"` (optional spot-check)
   Expect: log line showing `The following 1 profile is active: "docker"` — confirms `SPRING_PROFILES_ACTIVE=docker` was received, and (per the known no-op-profile follow-up) that startup still succeeds via the override env vars rather than failing to find a `docker` profile document.

**Cleanup:** `docker compose -f src/infra/docker-compose.yml down` (add `-v` only if you also want to wipe the Mongo/SQL Server/Kafka volumes — not needed just to undo this QA pass).
