## Manual QA — T059

**Prerequisites:** Full stack running via `docker-up` (SQL Server, MongoDB, Kafka, Redis). User Service, Connection Service, Rating Service, Admin Service, Discovery Service all up. A test user exists in "looking_for_companion"/active state with at least one pending or accepted connection request, and a known numeric id (call it `USER_ID`). Calls to admin-service use `X-User-Role: admin` and any `X-User-Id` (acting admin id, e.g. `999`).

1. `curl -i -X POST http://localhost:<admin-service-port>/admin/users/USER_ID/suspend -H "X-User-Id: 999" -H "X-User-Role: admin" -H "Content-Type: application/json" -d "{\"reason\": \"Repeated harassment reports\"}"`
   Expect: `200 OK`, body `{"userId": "USER_ID", "status": "suspended", "expiredConnectionCount": <N>, "updatedAt": "<ISO timestamp>"}` where N equals the number of that user's pending/accepted connections before the call.
2. Query User Service directly: `curl http://localhost:<user-service-port>/users/internal/USER_ID -H "X-Internal-Service-Key: dev-internal-key-123"`
   Expect: `account_status: "suspended"`, `suspended_at` populated with a recent timestamp.
3. Query Connection Service for that user's connections (via whatever read endpoint exists, or check the DB directly).
   Expect: every connection that was `pending`/`accepted` is now `expired`.
4. Within roughly 1-2 seconds (1 poll of the 500ms outbox relay + Kafka consumer poll), check Discovery's Redis cache: `redis-cli SISMEMBER scan:eligible_users USER_ID` (adjust key/command to the actual Redis data structure Discovery uses).
   Expect: `0` (not a member) — user removed from eligible scanning.
5. Repeat step 1 (retry the exact same suspend call).
   Expect: `200 OK` again, `expiredConnectionCount: 0` this time (idempotent — nothing left to expire), `status: "suspended"` unchanged.
6. Failure case — suspend with a non-existent user id: `curl -i -X POST http://localhost:<admin-service-port>/admin/users/999999999/suspend -H "X-User-Id: 999" -H "X-User-Role: admin" -H "Content-Type: application/json" -d "{\"reason\": \"test\"}"`
   Expect: `500 Internal Server Error` (known gap — see `.claude/notes/follow-ups.md` "From T059" item 2 — should ideally be a 404, but must NOT return a stack trace or leak internals), body `{"code": "INTERNAL_ERROR", "message": "An unexpected error occurred.", "traceId": ""}`.
7. Failure case — missing `X-User-Role` header on a direct Connection Service call (to confirm T104's own guard in isolation): `curl -i -X PUT http://localhost:<connection-service-port>/admin/connections/users/USER_ID/expire-active`
   Expect: `403 Forbidden` with the standard error envelope (no 500, no stack trace).

**Cleanup:** Reinstate the test user via `POST /admin/users/USER_ID/reinstate` (same headers) to restore it to "active" for reuse in other test runs; manually clear any leftover MongoDB `admin_outbox` test documents if you inspected them directly.
