## Manual QA — T063

**Prerequisites:** `docker compose up` for the full stack is NOT required for most of this — `user-service` and `api-gateway` can run standalone against a local SQL Server, but the simplest path is: infra stack up (`/docker-up` or `docker compose up -d sqlserver`), then `dotnet run` for `user-service` and `api-gateway`, then `ng serve` (or `ng build --configuration development` + serve dist) for the Angular app with `API_BASE_URL` pointing at the gateway (e.g. `http://localhost:5000`) and a real `GOOGLE_CLIENT_ID` configured for GSI to render.

1. Run: `curl -i -X POST http://localhost:5000/user/auth/google -H "Content-Type: application/json" -d "{\"id_token\":\"not-a-real-token\"}"`
   Expect: HTTP 401, body `{"code":"INVALID_GOOGLE_TOKEN","message":"Google ID token failed validation.","traceId":"<some-guid>"}`.
2. Run: `curl -i -X POST http://localhost:5000/user/auth/refresh -H "Content-Type: application/json" -d "{\"refresh_token\":\"\"}"`
   Expect: HTTP 401, body `{"code":"INVALID_REFRESH_TOKEN","message":"Refresh token is missing, invalid, or expired.","traceId":"<some-guid>"}`.
3. Run the same curl as step 2 but with `-d "{\"refresh_token\":\"garbage.not.a.jwt\"}"`.
   Expect: same 401 `INVALID_REFRESH_TOKEN` shape (malformed JWT, not just empty string, is handled identically).
4. Since a valid Google ID token cannot be fabricated in a script, get a real one through the UI: open `http://localhost:4200`, click the rendered Google Sign-In button, complete a real Google account sign-in.
   Expect: redirected to `/auth/otp`.
5. Open browser devtools → Application → Local Storage → your app's origin.
   Expect: both `scs_access_token` and `scs_refresh_token` keys are present with non-empty JWT-looking string values (three base64 segments separated by `.`).
6. On the OTP screen, enter a phone number and click "Send code".
   Expect: screen advances to the 6-digit code entry step (assumes OTP delivery/Twilio sandbox is configured — if not available in this environment, note that explicitly here and skip to step 8 using whatever test/bypass OTP mechanism `user-service`'s T017 setup documents).
7. Enter the received 6-digit code and click "Verify".
   Expect: navigation to `/` (app root); no errors shown.
8. **AC3, partial-failure recovery:** in devtools, overwrite `scs_access_token`'s value with a corrupted string (e.g. append `"xxx"` to it) — leave `scs_refresh_token` untouched. Trigger any authenticated API call (e.g. reload a screen that calls a protected endpoint, or manually fire one via devtools console using the app's HttpClient if no authenticated screen exists yet — note: as of this ticket, no protected feature screen exists to naturally trigger this, so this step may need to be exercised via a manual `fetch`/`XMLHttpRequest` against any `/user/...` authenticated route using the corrupted token).
   Expect: the request initially gets a 401 from the gateway, `AuthInterceptor` silently calls `/auth/refresh`, a new valid `scs_access_token` is written to localStorage, and the original request succeeds transparently — you should NOT be redirected to `/auth/login`.
9. **AC3, full failure / logout:** in devtools, corrupt or delete BOTH `scs_access_token` and `scs_refresh_token`. Trigger the same kind of authenticated API call again.
   Expect: the 401 triggers a refresh attempt, `/auth/refresh` itself fails (empty/invalid refresh token → 401 `INVALID_REFRESH_TOKEN`), and the app clears both tokens and navigates to `/auth/login`. Confirm via devtools that both localStorage keys are now gone.

**Cleanup:** clear `scs_access_token`/`scs_refresh_token` from localStorage manually if any test tokens remain; `docker compose down` if the infra stack was started for this session.
