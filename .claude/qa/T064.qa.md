## Manual QA — T064

**Prerequisites:** `docker-up` running the full stack (discovery-service, user-service, gateway) — needed for all steps below except the destroy$/navigate-away test, which can be verified purely client-side with network throttling/devtools.

1. Log in, land on Radar idle screen, enter a destination, tap Start Scan — Expect: button shows "Starting…", then view transitions to the active scan screen with the sweep animation running continuously. *(Requires backend.)*
2. While scanning, open DevTools Network tab and confirm a `PATCH /user/users/me` fired with `{status: "looking"}` right after `/scan/start` and `/scan/location` succeeded. *(Requires backend.)*
3. If any discovered users appear, tap a dot or chip — Expect: bottom sheet opens, photo loads via an authenticated XHR/fetch (check Network tab shows `Authorization` header on the photo request, not a bare `<img>` GET), falling back to initials if no photo. *(Requires backend.)*
4. Tap Stop Scan — Expect: view returns to idle, and Network tab shows `POST /discovery/scan/stop` plus `PATCH /user/users/me` with `{status: "unavailable"}`. *(Requires backend.)*
5. **Geolocation denied:** deny the browser's location permission when starting a scan — Expect: `startError` shows "Location permission is required to start a scan.", not a raw browser error string; `isStartingScan` resets so the button is clickable again.
6. **Offline → BLE badge+banner switch and recovery (re-test of polling fix):** start a scan successfully, then use DevTools → Network → "Offline" to simulate connectivity loss mid-scan — Expect: mode badge flips to "BLE · Nearby only" (amber), the amber banner appears below the HUD with the exact text "No internet · Bluetooth mode active · Range ~20m", and — critically — polling keeps running underneath (re-enable network after ~15-20s and confirm the badge flips back to "GPS" and polling is still alive, i.e. it never silently died). *(Requires backend to observe real poll behavior; can be simulated purely client-side for the badge/banner visual part.)*
7. **Navigate-away mid-start-scan (re-test of destroy$ fix):** tap Start Scan, then immediately navigate to another route (e.g. browser back button or another in-app link) before the request round-trip finishes — Expect: no console errors, and critically, confirm via Network/backend logs that `PATCH /users/me {status: looking}` was NOT sent after navigation (the chain was cancelled, not just ignored client-side). *(Requires backend to confirm the PATCH truly never fired, not just that the UI didn't show it.)*

**Cleanup:** Stop any scan left active (Stop Scan button, or re-run step 4) so the test user's `status` doesn't stay stuck at `looking` across test runs.
