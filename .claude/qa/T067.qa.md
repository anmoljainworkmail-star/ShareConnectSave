## Manual QA — T067

**Prerequisites:**
- Run `npm install` in `src/frontend`. `@microsoft/signalr` was added to `package.json` by hand.
- The frontend builds with `API_BASE_URL=http://localhost:8080` in the development configuration, so the API gateway must be on port 8080.
- Backend running: the infrastructure stack (SQL Server, MongoDB, Kafka, Redis; `/docker-up`) plus api-gateway, user-service, discovery-service, connection-service, notification-service and chat-service.
- Two verified user accounts, A (requester) and B (recipient), in two separate browser profiles or one normal window plus one incognito window. Both must have a profile and a GPS location, and both must be in each other's radius.
- Browser DevTools open on both (Network tab filtered to WS, plus Console).

1. In `src/frontend`, run `npm install`, then `npm start`. Open http://localhost:4200 in window A and again in window B (incognito).
   Expect: the app loads without a build error for `@microsoft/signalr`.
2. Sign in as A in window A and as B in window B. Open DevTools, Network, WS.
   Expect: each window opens a WebSocket to `.../notification/hubs/notifications?id=...&access_token=...` with status 101. (Dev-only: the Console also prints the token. That is minor item 2 in follow-ups.)
3. Window B: on the Radar, tap "Start scanning". Window A: do the same.
   Expect: each can see the other as a dot on the radar.
4. Window A: click B's dot, then "Send Request".
   Expect: the button briefly reads "Sending...", then "Request Sent" (disabled). In the Network tab there is exactly one `POST .../connection/connections` returning 201. Double-click Send quickly on another user: still only one POST.
5. Window B (on the Radar, not on the inbound page).
   Expect: a banner at the top, "New connection request / Someone nearby wants to connect with you.", with a "View" link. A two-tone chime plays (you may need to have clicked anywhere on the page once). If it stays silent, the banner is still the real notification.
6. Window B: click "View".
   Expect: the "New Request" bottom sheet at `/connections/inbound`, showing A's name, photo or initials, a verified badge if applicable, and the text "Expires in M:SS" counting down every second, with a shrinking ring around Accept.
7. Window B: click "Accept".
   Expect: one `POST .../connections/{id}/accept` returns 200. The app tries `/chat/{id}`. Until T068 ships, that route doesn't exist, so a toast reads "Request accepted. The chat screen is not available yet." instead. This is the expected current result for AC1's last step.
8. Window A (the requester).
   Expect: a green toast, "Request accepted. Opening chat...", then the same fallback toast, because `/chat/{id}` is not routed yet. When T068 is done, this step should open the chat.
9. Decline path: sign in with a third account C. Window A sends C a request. As C, open `/connections/inbound` and click "Decline".
   Expect: a toast "Request declined.", and the sheet closes back to the Radar. In window A the card for C stays "Request Sent". This is expected until the backend adds the decline push (follow-ups item 1).
10. Expiry path, on the recipient inbound page: send a new request from A to B, then wait out the 10-minute TTL (or ask the backend owner to shorten `expires_at`). Keep window B on `/connections/inbound`.
    Expect: the countdown reaches 0:00 and the sheet shows "This request has expired." with Accept disabled and a "Dismiss" button. Window A shows a toast "Request expired." when the server's expiry job runs. Window A's card for B still shows "Request Sent" (known gap, follow-ups item 9).
11. Reconnect path: in window B's DevTools, Network tab, set throttling to "Offline" for about 60 seconds. The Console shows reconnect attempts.
    Expect: the console shows reconnecting messages and no "give up" or "closed" state after the default ~42 s. Meanwhile, in window A, send a request to B.
12. Window B: set throttling back to "No throttling".
    Expect: within about 30 s the WebSocket reconnects (a new 101 entry), and a banner appears: "Pending connection requests: Someone is waiting for your reply." with a "View" link. The request sent while offline is not lost.
13. Edge case, expired token: in window B's DevTools, Application, Local Storage, delete the access-token entry but keep the refresh token, then reload the page.
    Expect: the app refreshes the token (one `POST .../user/auth/refresh`) and the WebSocket connects. If you instead remove both tokens, expect a redirect to `/auth/login` and the WebSocket to close.
14. Edge case, logout: log out in window B.
    Expect: the WebSocket closes (status shows as closed), and no further banners arrive for that user.

**Cleanup:** stop `ng serve` (Ctrl+C), close both browser windows, run the infrastructure stack's teardown (`docker compose down`), and clear the test requests from the connection-service database if you want a clean slate.
