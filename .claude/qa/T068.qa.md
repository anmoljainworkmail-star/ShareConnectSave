## Manual QA — T068

**Prerequisites:**
- Full stack running (`/docker-up` for SQL Server, Mongo, Kafka, Redis), plus gateway, user-service, connection-service, chat-service, notification-service and `ng serve`. Kafka and the outbox relay must be running so `connection.accepted` creates the chat room.
- Two verified test users, A and B, each with a profile name set.
- Two separate browser sessions: a normal window for A and an incognito window for B. Both signed in and on `/radar`.
- DevTools open on A's window (Network and Application tabs).

1. **Open a chat.** As A, send a connection request to B. As B, Accept it.
   Expect: both windows navigate to `/chat/<connectionId>`. The header shows the other person's name as the title and "You: <own name>" as the subtitle. The first line in the list reads "Chat opened. You have 2 hours." The input is enabled.

2. **Real-time messaging.** In A, type "hello" and press Enter.
   Expect: a violet gradient bubble, right-aligned, appears in A with no page refresh. In B, a pale violet bubble with an avatar appears within about a second. The input clears in A.

3. **Reply and scroll.** In B, reply "hi back". Send roughly 15 messages. Scroll up in A, have B send one, then send one from A.
   Expect: B's reply appears on A's left. The view follows new messages. While A is scrolled up, B's message does not jump the view down. A's own send jumps to the bottom.

4. **Timestamp gap.** Wait over 5 minutes (or skip) and send another message.
   Expect: a centered time label above the new message.

5. **Message not rendered as HTML.** Send `<b>x</b>` from A.
   Expect: it shows as literal text.

6. **Met dialog, Cancel.** In A, click Met Successfully. Then click "Not yet". Repeat and press Esc. Repeat and click the backdrop.
   Expect: a dialog titled "Did you meet <B's name>?" with "Not yet" and "Yes, Met!". It closes each time and A stays in the chat. Messaging still works. No POST to `/met` appears in the Network tab.

7. **Met dialog, Confirm.** In A, click Met Successfully, then "Yes, Met!".
   Expect: the button shows "Please wait...", and one POST to `/chat/chats/<id>/met` returns 200. Because `/rating` does not exist until T069, a toast "The chat has ended. The rating screen is not available yet." appears and A stays on the chat. This is expected until T069.

8. **Grace-period behaviour.** After step 7, look at B's window.
   Expect: B is not kicked out (room is CLOSING, not CLOSED). B can still send messages. If B also confirms Met, the same toast appears.

9. **Server-driven close.** Wait for the grace period to elapse (5 minutes by default).
   Expect: both windows try to navigate to `/rating/<connectionId>` and show the "not available yet" toast.

10. **Offline banner and disabled input.** With a fresh chat open (repeat steps 1-2 with a new pair), set A's DevTools Network to "Offline".
    Expect: within a few seconds an amber "Reconnecting..." bar appears under the header. The input is greyed with placeholder "Reconnecting...". The send button is disabled.

11. **Reconnect.** Set Network back to "No throttling". Have B send a message.
    Expect: the banner disappears, the input re-enables, and B's message arrives in A (room was rejoined).

12. **Reload on `/chat/:id`.** In A, press F5 while the chat is OPEN or CLOSING.
    Expect: "Opening your chat..." briefly, then the chat renders. The first line reads just "Chat opened." with no "You have 2 hours" claim. Earlier messages are not shown (no history by design). New messages from B still arrive.

13. **Closed while offline.** As A, set Network to Offline. As B, confirm Met and wait for the grace period so the room becomes CLOSED and the push is missed. Put A back online.
    Expect: on reconnect A calls `GET /chat/chats/by-connection/<id>`, sees `status: CLOSED`, and tries to go to `/rating/...`, giving the "not available yet" toast.

14. **Non-participant lookup returns 404.** Sign in as a third user C. In C's DevTools console, fetch `<apiBase>/chat/chats/by-connection/<A-B connectionId>` with C's `Authorization: Bearer <token>`. Then fetch with a connection id that does not exist.
    Expect: both return HTTP 404 with body `{ "code": "CHAT_ROOM_NOT_FOUND", "message": ..., "traceId": ... }`. The two responses are indistinguishable.

15. **Token expiry reconnect (partly exercisable).** Real expiry takes 60 minutes. To simulate: in A's Application tab, set `scs_access_token` to a token whose `exp` is in the past (signature will be invalid, so only the refresh call is the observable signal), or wait for natural expiry with the chat open. Set Network Offline for a few seconds, then back online.
    Expect: one `POST /user/auth/refresh` appears before the new hub connect, the banner clears, messaging resumes, and `scs_access_token` in storage has changed. Hub requests carry `?access_token=` in the URL. The duplicate-refresh case (both hubs reconnecting together) cannot be reliably exercised by hand.

16. **Service worker does not cache chat.** In the Application tab, open Cache Storage.
    Expect: no entries for `/chat/...` URLs.

**Cleanup:** Close both browser windows. Optionally clear `scs_access_token` and `scs_refresh_token` in each window's storage. Remove the test `chat_rooms` document and test connection if you want a clean slate. Stop the stack with `docker compose down`.
