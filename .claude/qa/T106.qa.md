## Manual QA — T106

**Prerequisites:** discovery-service running locally (via `/docker-up` + `mvn spring-boot:run`, or however this session normally starts it) with the SQL Server `scan_sessions` table reachable. Know the service's local port (check `application.yml` / `docker-compose.yml`, commonly `8080` container-internal / a mapped host port for discovery-service).

1. `curl -i http://localhost:<discovery-port>/admin/scan/stats -H "X-User-Role: admin"`
   Expect: `200 OK`, body `{"total_scans_today": <integer >= 0>}`.

2. `curl -i http://localhost:<discovery-port>/admin/scan/stats`  (no `X-User-Role` header at all)
   Expect: `403 Forbidden`, body `{"code":"FORBIDDEN","message":"Admin role required","traceId":""}`.

3. `curl -i http://localhost:<discovery-port>/admin/scan/stats -H "X-User-Role: user"`
   Expect: identical to step 2 — `403 Forbidden`, same `{"code":"FORBIDDEN","message":"Admin role required","traceId":""}` body. This proves the missing-header and wrong-role-present cases are handled identically.

4. `curl -i http://localhost:<discovery-port>/scan/nearby -H "X-User-Id: 1"`  (no `X-User-Role` header)
   Expect: normal existing behavior unaffected by this ticket — NOT a 403.

5. `curl -i http://localhost:<discovery-port>/actuator/health`  (no headers at all)
   Expect: `200 OK` with the usual health JSON — proves `SecurityConfig`'s `permitAll()` rule didn't accidentally lock down the rest of the service as a side effect of adding Spring Security for the first time.

6. Seed one scan session (`POST /scan/start` with a valid body/headers), then repeat step 1.
   Expect: `total_scans_today` increments by exactly 1 versus step 1's count.

**Cleanup:** no state was created except step 6's scan session, which is harmless local dev data; stop any active session via `POST /scan/stop` if desired, or leave it — no cleanup is required by T106 itself.
