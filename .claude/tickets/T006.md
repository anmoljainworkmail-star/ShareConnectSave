# T006 — SQL Server Database Schemas

## Why this ticket exists
Database schemas are the contract between migrations and services. Without them, services fail on startup and can't store or retrieve data. This ticket establishes clean, indexed schemas for every relational service so migrations can run safely and queries perform predictably. Each service owns its data — no cross-service joins.

## What to build

- Five SQL Server databases: `users_db`, `discovery_db`, `connections_db`, `ratings_db`, `reports_db`
- Flyway migration scripts for each Java service at `services/<service>/src/main/resources/db/migration/`
- EF Core migration scripts for each .NET service at `services/<service>/Migrations/`
- User Service schema: `users`, `otp_attempts`, `identity_verifications` tables with appropriate indexes
- Discovery Service schema: `scan_sessions`, `ble_tokens` tables with geospatial support
- Connection Service schema: `connection_requests` table with status lifecycle and TTL
- Rating Service schema: `ratings`, `trust_scores` tables with JSON support for tags
- Indexes on all foreign keys, status columns, and temporal columns (created_at, expires_at)
- Admin Service: no owned schema — reads from `users_db`, `ratings_db`, `reports_db` via HTTP

## Technical specification

Create Flyway migration scripts for each service that uses SQL Server. Each service gets its own database. Place migrations at `services/<service>/src/main/resources/db/migration/` (Java) or `services/<service>/Migrations/` (.NET EF Core).

**User Service DB (`users_db`):**
- `users` — id, google_id, phone, name, photo_url, gender, preferred_language, status, created_at
- `otp_attempts` — id, phone, attempt_count, locked_until
- `identity_verifications` — id, user_id, status, verified_at

**Discovery Service DB (`discovery_db`):**
- `scan_sessions` — id, user_id, destination_lat, destination_lng, destination_label, departure_time, started_at, ended_at
- `ble_tokens` — id, user_id, token_hash, expires_at

**Connection Service DB (`connections_db`):**
- `connection_requests` — id, requester_id, recipient_id, status, created_at, expires_at, updated_at

**Rating Service DB (`ratings_db`):**
- `ratings` — id, rater_id, rated_id, connection_id, tags (JSON array), created_at
- `trust_scores` — id, user_id, score, badge_level, request_limit, updated_at

**Report Service DB (`reports_db` in MongoDB — handled in T051)**

**Admin Service DB:** reads from `users_db`, `ratings_db`, `reports_db` — no own schema

## Acceptance criteria

- [ ] Migrations run cleanly on fresh SQL Server instance
- [ ] All tables have appropriate indexes (user_id FK, status, created_at)
- [ ] Geospatial columns on `scan_sessions` use SQL Server `geography` type for destination point

## Patterns demonstrated

**Database per Service** — Each microservice owns its relational data in a separate SQL Server database. No service reads another service's tables directly; they communicate via HTTP or Kafka. This teaches independent scaling, failure isolation, and the constraint that makes distributed systems work: data locality.

**Schema Migration (Flyway / EF Core)** — Migrations version schema changes the same way code versioning tracks features. This demonstrates infrastructure-as-code: schemas live in version control, deployments are repeatable, and rollback is possible.

**Idempotency in DDL** — Each migration runs exactly once. Flyway checksums prevent reruns; EF Core timestamps achieve the same. Demonstrates why "write once" is a safety property in distributed systems.

**Geospatial Indexing** — SQL Server `geography` type stores and indexes destinations. This teaches why domain types (not just numeric lat/lng) matter: native support for "distance between two points" and spatial indexing make queries fast without application-level math.

## Agent implementation notes

**Key files to create:**

Java services (Discovery, Connection, Rating):
- `services/{service}/src/main/resources/db/migration/V001__{service}_initial_schema.sql`

.NET services (User):
- `services/{service}/Migrations/{timestamp}_{service}_initial_schema.cs`
- Entity classes in `services/{service}/Models/`

(Admin Service owns no schema of its own — see "What to build" above. Chat and Notification aren't part of T006: Chat's data lives in MongoDB, handled by T007.)

**Patterns to use:**

1. **Flyway naming convention** (Java) — File names must be `V{version}__{description}.sql`. Version increments per migration (V001, V002, etc.). Flyway tracks checksums to prevent reruns.

2. **EF Core Migrations** (.NET) — Use `dotnet ef migrations add {description}` to generate boilerplate, then edit the migration class to ensure idempotency. Seed only reference data, never user data.

3. **Primary Keys** — Use `BIGINT IDENTITY(1,1) PRIMARY KEY` on all tables for auto-increment. Distributed systems need stable, sparse IDs (not UUIDs here — identity is fine for single-database records).

4. **Foreign Keys** — Add `REFERENCES` clauses and `ON DELETE CASCADE` or `ON DELETE RESTRICT` as appropriate. e.g., `user_id BIGINT NOT NULL FOREIGN KEY REFERENCES users(id)`.

5. **Temporal Columns** — `created_at DATETIME2 DEFAULT GETUTCDATE()`, `updated_at DATETIME2 DEFAULT GETUTCDATE()`, `expires_at DATETIME2 NULL`. Always UTC, never local time.

6. **Geospatial** — In `scan_sessions`, use `GEOGRAPHY::Point(destination_lat, destination_lng, 4326)` for the destination. Create a spatial index: `CREATE SPATIAL INDEX idx_destination ON scan_sessions(destination)`.

7. **JSON Columns** — In `ratings`, `tags` column is `NVARCHAR(MAX)` stored as JSON array. SQL Server 2016+ validates JSON syntax. No need for a separate `rating_tags` table.

8. **Indexes** — Add non-clustered indexes on:
   - `user_id` (every table that has it — for "find records for this user")
   - `status` (where status has multiple values — e.g., connection_requests.status)
   - `created_at`, `expires_at` (for time-based queries and TTL cleanup)
   - `phone` (users table — for OTP lookup by phone)

9. **Constraints** — Add `UNIQUE` where needed (e.g., `users.google_id` is unique; `users.phone` during verification). Add `NOT NULL` on columns that always have values.

**What NOT to do:**

- Don't create a shared schema across services. Each database is owned by one service only.
- Don't use `DATETIME` (precision issues). Use `DATETIME2` for all temporal columns.
- Don't hard-code service-specific logic (e.g., "status IN ('Verified', 'Pending')") into schema design. Keep schema agnostic; logic is in service code.
- Don't use UUID (UNIQUEIDENTIFIER) for primary keys in SQL Server unless there's a specific reason. Identity is simpler for single-database records.
- Don't assume migrations are idempotent without checking Flyway/EF Core tracking. Both frameworks prevent reruns, but only if you follow naming/versioning conventions.
- Don't create stored procedures for business logic. Keep those in service code — schema is just the shape of data.
- Don't forget that `discovery_db.scan_sessions.destination_lat/lng` are the **stated destination**, not the live location. This schema doesn't track real-time location — that's ephemeral, discarded after scan. Misunderstanding this breaks the privacy contract.
