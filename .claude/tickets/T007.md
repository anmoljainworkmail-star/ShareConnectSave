# T007 — MongoDB Setup

## Why this ticket exists

Chat and Report services need persistent data storage with specific schema structure and automatic lifecycle management. Without this ticket, the Chat Service has no place to store messages or room metadata, and the critical TTL index that auto-deletes messages after 2 hours (privacy hard requirement) won't exist. Reports Service has no place to file user complaints. Docker Compose won't initialize these databases on startup.

## What to build

- MongoDB initialization scripts in `/infra/mongo-init/` directory (mounted to mongo container in T004's docker-compose.yml)
- **chat_db** database:
  - `messages` collection — ephemeral message storage with TTL index on `sent_at` field (2 hours default, configurable via env var)
  - `chat_rooms` collection — room metadata and lifecycle tracking
  - Compound index on `(chat_id, sender_id)` for efficient message queries
  - Compound index on `(connection_id)` for room lookups
- **report_db** database:
  - `reports` collection — incident records with status tracking
  - Compound index on `(reported_id)` for admin queue queries
  - Compound index on `(filed_at)` for time-based sorting
- Init scripts must be idempotent (safe to run multiple times) and execute via Docker volume mount on container startup

## Technical specification

Create MongoDB initialization scripts in `/infra/mongo-init/`:

**`chat_db`:**
- Collection: `messages` — fields: `_id`, `chat_id`, `sender_id`, `content`, `sent_at`, TTL index on `sent_at` (2 hours default, configurable)
- Collection: `chat_rooms` — fields: `_id`, `connection_id`, `user_a_id`, `user_b_id`, `status`, `created_at`, `closed_at`

**`report_db`:**
- Collection: `reports` — fields: `_id`, `reporter_id`, `reported_id`, `reason`, `context` (free text), `filed_at`, `status`

Both collections include a `createIndexes` call in the init script.

## Acceptance criteria

- [ ] Init script runs on `docker compose up` via `mongo-init` volume mount
- [ ] TTL index on `messages.sent_at` is created and `expireAfterSeconds` is set
- [ ] Collections have compound indexes on `chat_id` and `user_id` fields

## Patterns demonstrated

**Database per Service** — Chat and Report services own their MongoDB data exclusively; no other service reads these databases directly. Init scripts make this boundary explicit.

**TTL Indexes (Automatic Lifecycle Management)** — MongoDB's TTL feature demonstrates how to enforce time-based data expiry at the database layer, not in application code. Hard enforces the privacy requirement: "no message history persists after chat closes."

**Infrastructure as Code** — Init scripts are versioned and reproducible; schema lives in the repo, not manual CLI commands. Demonstrates how to make local dev environments deterministic.

**Idempotency** — Scripts must handle re-runs gracefully (check if collection exists before creating; recreate indexes without error if they already exist). Aligns with the Idempotency system design principle.

## Agent implementation notes

**Files to create:**
- `/infra/mongo-init/01-init-chat.js` — initialize chat_db, messages and chat_rooms collections
- `/infra/mongo-init/02-init-report.js` — initialize report_db, reports collection

**Patterns to follow:**
- Use MongoDB shell JavaScript syntax (not the Node.js driver)
- Each script should connect to its target database and create collections + indexes
- TTL index: use `expireAfterSeconds: 7200` (2 hours in seconds) on `messages.sent_at`; make this configurable via environment variable passed at runtime
- Compound indexes: `messages` needs `(chat_id, 1)` and `(sender_id, 1)` separately for query patterns used by Chat Service
- `chat_rooms` needs index on `(connection_id, 1)` for room lookups
- `reports` needs index on `(reported_id, 1)` for admin queue scans

**What NOT to do:**
- Do not hardcode TTL expiry time — the 2-hour default must be overrideable via env var (services may adjust per business rules later)
- Do not assume the mongo container is already running or connected — scripts are invoked by Docker during startup
- Do not create user/auth credentials in these scripts (that's handled by docker-compose env vars)
- Do not drop collections on re-init; use `createCollection()` guard to check existence first

**Verify with T004:**
- Confirm `/infra/mongo-init/` volume mount exists in docker-compose.yml (should be `./infra/mongo-init:/docker-entrypoint-initdb.d`)
- Ensure MongoDB container is named `shareconnectsave-mongo` or use the name from T004's compose file
- Check that environment variable for TTL (e.g., `MONGO_TTL_SECONDS`) is defined in compose, default to 7200
