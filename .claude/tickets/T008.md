# T008 — Redis Setup

## Why this ticket exists
Redis is critical for two purposes in the local dev environment: caching scan results in Discovery Service (to hit the P95 < 500ms latency target) and providing the SignalR backplane so Chat and Notification service instances can share WebSocket state without round-tripping to a database. Without proper configuration and database separation, the dev stack will not scale horizontally and Redis memory will thrash. This ticket codifies the separation into infrastructure configuration so both use cases coexist cleanly.

## What to build
- `/infra/redis.conf` — Redis configuration file with memory limits, eviction policy, and database indices clearly separated by use case
- Update `/infra/README.md` to document which database index is reserved for which service (DB 0 for Discovery cache, DB 1 for SignalR backplane)
- Ensure docker-compose.yml (from T004) mounts this config file into the Redis container

## Technical specification
Redis is already in Docker Compose (T004). This task configures logical database separation:
- DB 0: Discovery Service (nearby scan cache)
- DB 1: SignalR backplane (Chat + Notification services)

Create `/infra/redis.conf` with:
- `maxmemory 256mb`
- `maxmemory-policy allkeys-lru`
- No persistence (dev) — `save ""`

Document the DB index convention in `/infra/README.md`.

## Acceptance criteria
- [ ] Redis starts with the config file mounted
- [ ] `redis-cli ping` returns PONG
- [ ] DB separation documented

## Patterns demonstrated
**Cache-Aside** — Discovery Service will load user profiles into DB 0 on cache miss, serving subsequent scans from cache to avoid redundant SQL Server calls and reduce latency below the P95 < 500 ms target.

**Logical Database Separation** — Using Redis logical databases (0 and 1) to isolate concerns (cache vs. backplane state) without requiring separate Redis instances, reducing operational complexity in dev.

**Bounded Resource Management (LRU Eviction)** — The `maxmemory-policy allkeys-lru` prevents unbounded memory growth during development by automatically evicting the least-recently-used keys when cache exceeds 256MB, protecting the dev machine from OOM crashes.

## Agent implementation notes
- **File to create:** `/infra/redis.conf` at project root, with the exact configuration listed in the spec above
- **File to update:** `/infra/README.md` — add a section documenting the database index convention (create the file if it doesn't exist)
- **Docker Compose integration:** The redis service in `docker-compose.yml` (from T004) should mount this config file using a volume: `./infra/redis.conf:/usr/local/etc/redis/redis.conf`
- **Verification:** After the ticket is implemented, confirm by running the local stack and executing `docker exec <redis-container-name> redis-cli ping` — should return `PONG`. Also verify with `docker exec <redis-container-name> redis-cli INFO server` to confirm the config was loaded.
- **Documentation:** The `/infra/README.md` entry should be clear enough that a developer can look it up without reading code:
  - DB 0: Discovery Service (scan result caching)
  - DB 1: SignalR backplane (Chat and Notification service state sharing)
- **What NOT to do:** Do not add RDB or AOF persistence (e.g., `save` or `appendonly yes`) — this is a dev-only Redis instance and should reset on restart. Do not set `maxmemory-policy` to `noeviction` — the dev cache will fill up and break discovery scans.
