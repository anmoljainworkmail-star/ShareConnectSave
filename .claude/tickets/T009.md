# T009 — Kafka Topics Init

## Why this ticket exists
Kafka topics are the event channels that connect all microservices. Before any service can emit events (user verification, connection acceptance, chat closure, ratings, trust score updates, reports), the topics those events flow through must exist in the broker. Without this, services will fail at runtime with "topic does not exist" errors. This script also ensures idempotency—ops teams can safely re-run initialization without breaking the system if a topic already exists.

## What to build
- **File:** `/infra/kafka-init.sh` — a POSIX shell script using Kafka's `kafka-topics.sh` command to create 7 topics
- **Topics to create (all with 3 partitions and replication factor 1):**
  - `user.verified`
  - `connection.accepted`
  - `connection.expired`
  - `chat.closed`
  - `rating.submitted`
  - `trust.score.updated`
  - `report.filed`
- **Docker Compose integration:** Add a `kafka-init` service to `docker-compose.yml` that:
  - Runs after Kafka is healthy
  - Executes the init script
  - Exits with code 0 on success

## Technical specification
Create an init script `/infra/kafka-init.sh` that creates all topics defined in T002:

```
user.verified          — partitions: 3, replication: 1
connection.accepted    — partitions: 3, replication: 1
connection.expired     — partitions: 3, replication: 1
chat.closed            — partitions: 3, replication: 1
rating.submitted       — partitions: 3, replication: 1
trust.score.updated    — partitions: 3, replication: 1
report.filed           — partitions: 3, replication: 1
```

Wire this script as a `kafka-init` service in Docker Compose that runs after Kafka is healthy.

## Acceptance criteria
- [ ] All 7 topics visible in Kafka UI after `docker compose up`
- [ ] Init service exits 0 after creating topics
- [ ] Topics are idempotent (re-running script on existing topics doesn't error)

## Patterns demonstrated
**Idempotent Operations** — The script uses Kafka's `--if-not-exists` flag to safely re-run without errors, teaching how to make infrastructure changes repeatable without manual cleanup.

**Infrastructure as Code** — Topic topology is version-controlled alongside the rest of the platform, so schema changes are tracked and deployable.

**Service Dependency Ordering** — The Docker Compose service uses health checks to ensure Kafka is ready before topic initialization attempts, preventing race conditions that cause flaky startup sequences.

## Agent implementation notes
- **Key files to create/modify:**
  - `/infra/kafka-init.sh` (new file, executable)
  - `docker-compose.yml` (add `kafka-init` service entry; modify existing Kafka service if needed to ensure health check is present)

- **Implementation guidance:**
  - The script will run inside a Docker container with Kafka CLI tools available. Use the same image already running Kafka in this stack — `bitnami/kafka:latest` (see `src/infra/docker-compose.yml`) — as the base for this service, not a Confluent/confluentinc image. `kafka-topics.sh` ships in that image already, and mixing broker vendors between the running broker and the init container risks CLI/protocol version mismatches for no benefit.
  - Use `kafka-topics.sh --bootstrap-server kafka:9092` (not localhost) because this runs inside the Docker network.
  - Use the `--if-not-exists` flag on the `--create` command to achieve idempotency. This prevents errors if the topic already exists.
  - Reference the `kafka-outbox` skill for guidance on Kafka topic patterns and naming conventions used in this project.
  - Ensure the `kafka-init` service has a `depends_on` clause that references the `kafka` service with a `condition: service_healthy` check.
  - Set exit code to 0 on success (default shell behavior if there are no errors).

- **What NOT to do:**
  - Do NOT hardcode `localhost` or `127.0.0.1`—use Docker service name (`kafka:9092`).
  - Do NOT use replication factor > 1 for dev/local environment (single-broker setup can't replicate).
  - Do NOT deviate from the partition count (3) or replication factor (1) specified above.
  - Do NOT add topics beyond the 7 listed—this ticket is scoped exactly to Phase 1 infrastructure.
  - Do NOT attempt to create the script if the Kafka service health check isn't already in place from T004.
