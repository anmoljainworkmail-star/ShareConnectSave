# T011 — YARP Gateway Project Setup

## Why this ticket exists
Right now the Angular PWA would have to know the address of every single microservice — user-service, discovery-service, connection-service, and the rest — and call each one directly. That means every future change (a service moving, a port changing, adding JWT checks, adding rate limits) has to be repeated eight times, once per service. This ticket puts one door in front of the whole system: the API Gateway. The client talks to exactly one address, and the gateway forwards the request to the right backend service. Without this ticket, there is no single entry point, which blocks every later security and traffic-control ticket in Phase 2 (JWT validation, rate limiting) since those only need to be built once — here — instead of duplicated across eight services.

## What to build
- New .NET 9 project: `api-gateway` (Minimal API host)
- NuGet package: `Yarp.ReverseProxy`
- `appsettings.json` reverse-proxy configuration with routes + clusters for all 8 downstream services:
  - `user-service` (container `user-service`, port 8081) — prefix `/user`
  - `discovery-service` (container `discovery-service`, port 8082) — prefix `/discovery`
  - `connection-service` (container `connection-service`, port 8083) — prefix `/connection`
  - `chat-service` (container `chat-service`, port 8084) — prefix `/chat`
  - `rating-service` (container `rating-service`, port 8085) — prefix `/rating`
  - `notification-service` (container `notification-service`, port 8086) — prefix `/notification`
  - `report-service` (container `report-service`, port 8087) — prefix `/report`
  - `admin-service` (container `admin-service`, port 8088) — prefix `/admin`
- Each route pattern: `/<service-prefix>/{**catch-all}`
- `Program.cs` wiring: `builder.Services.AddReverseProxy().LoadFromConfig(...)` and `app.MapReverseProxy()`
- Gateway itself runs as container `api-gateway` on port 8080 (per REQUIREMENTS.md service table)

## Patterns demonstrated
**API Gateway** — a single entry point handles cross-cutting concerns (routing here; JWT validation and rate limiting land in later tickets) so no downstream service has to duplicate that logic.

**Dependency Inversion (D in SOLID)** — the gateway routes by configuration (`appsettings.json` clusters/routes), not by hardcoded service URLs baked into code, so swapping a downstream address never requires a code change or redeploy of gateway logic.

**Open/Closed Principle (O in SOLID)** — adding a 9th downstream service later means adding a new route + cluster entry to config, not modifying existing routing code.

## Agent implementation notes
- **Key files to create:**
  - `src/api-gateway/ApiGateway.csproj` (.NET 9 Minimal API project)
  - `src/api-gateway/Program.cs`
  - `src/api-gateway/appsettings.json` (ReverseProxy `Routes` and `Clusters` sections)
  - `src/api-gateway/Dockerfile` (only if sibling services already have one at this path convention — check T001/T003 output for the established per-service folder/Dockerfile pattern and mirror it exactly)

- **Patterns to use:**
  - Follow the `dotnet-minimal-api` skill file for Minimal API host bootstrapping conventions (top-level `Program.cs`, `WebApplication.CreateBuilder`).
  - Use the config-driven YARP setup: `builder.Services.AddReverseProxy().LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));` then `app.MapReverseProxy();`. Do not build routes/clusters programmatically in code — config-driven is what makes this Open/Closed.
  - Route `Match.Path` values must be exactly `/<prefix>/{**catch-all}` (e.g. `/user/{**catch-all}`) and `Transforms` should strip or preserve the prefix consistently with how downstream stub services expect to receive paths — pick one approach and apply it uniformly across all 8 routes.
  - Cluster destination addresses must use Docker container names, not `localhost` (e.g. `http://user-service:8081`), since this runs inside the Compose network — same reasoning as T009's Kafka bootstrap server.
  - Gateway's own Kestrel listen port must be 8080 to match the container port table in REQUIREMENTS.md.

- **What NOT to do:**
  - Do NOT implement JWT validation or rate limiting in this ticket — those are separate, later Phase 2 tickets. This ticket is routing only.
  - Do NOT hardcode `localhost`/`127.0.0.1` for any downstream cluster destination — use the container names from the table above.
  - Do NOT add a 9th route for the gateway calling itself, and do NOT omit any of the 8 listed services.
  - Do NOT write routing logic in C# controllers/endpoints — YARP's config-driven proxy replaces the need for that entirely.
  - Do NOT deviate from the port numbers given in REQUIREMENTS.md's service table.
