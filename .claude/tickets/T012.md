# T012 — JWT Validation Middleware

## Why this ticket exists

Without centralized JWT validation, every backend service would need to independently verify tokens, validate signatures, and extract claims — a maintenance nightmare and a security risk if validation logic drifts. This ticket moves that responsibility to the API Gateway, the single entry point. Once validated here, downstream services trust the injected headers and focus only on business logic. This is the security boundary that protects the entire platform.

**Corrected during ticket review (before implementation) — read this before anything else:**
The gateway validates the **app's own JWT**, issued by `user-service` (T016) — never Google's raw
Sign-In token directly. Google's ID token only carries Google's own fields (`sub`, `email`, `name`,
`picture`); it has no concept of this app's `role` or `gender`, since those live in our own
`users` table, not Google's. `user-service` validates the Google token exactly once, at
`POST /auth/google`, then issues its own RS256-signed JWT carrying `sub` (our UUID), `role`,
`gender` — and exposes the matching public key at its own
`GET /.well-known/jwks.json`. That is the JWKS endpoint this middleware fetches and caches —
not `https://www.googleapis.com/.well-known/openid-configuration`. Google's raw token is only
ever handled inside `user-service`, never at the gateway, and never on any request after the
initial sign-in.

## What to build

A JWT Bearer authentication middleware for the YARP gateway that:
- Validates incoming JWT signatures against `user-service`'s own JWKS endpoint
  (`http://user-service:8080/.well-known/jwks.json`) — the RSA public key `user-service` uses
  to sign the app's own tokens, not Google's JWKS
- Checks token expiry and audience/issuer (this app's own configured values —
  `process.env.JWT_AUDIENCE` / `process.env.JWT_ISSUER` — not `GOOGLE_CLIENT_ID`)
- Extracts `sub` (user ID), `role`, and `gender` claims from valid tokens
- Injects three headers into the downstream request: `X-User-Id`, `X-User-Role`, `X-User-Gender`
- Strips the raw `Authorization` header before forwarding (services never see the JWT itself)
- Bypasses JWT validation entirely for public auth routes: `POST /auth/google`, `POST /auth/otp/send`, `POST /auth/otp/verify`

**Key files to create:**
- `src/services/api-gateway/Middleware/JwtValidationMiddleware.cs` — middleware that validates tokens and injects headers
- `src/services/api-gateway/Services/JwksService.cs` — caches `user-service`'s own JWKS endpoint (public key for validation)
- `src/services/api-gateway/Configuration/JwtOptions.cs` — configuration object for issuer/audience and JWKS endpoint URL
- Update `src/services/api-gateway/Program.cs` to register the middleware into the request pipeline

## Technical specification

Add JWT Bearer authentication middleware. This validates the **app's own JWT** — the one
`user-service` issues from `POST /auth/google` (T016) — not Google's raw Sign-In token.
Validate:
- Signature — fetched from `user-service`'s own JWKS endpoint
  (`http://user-service:8080/.well-known/jwks.json`, RS256/RSA public key), cached ~24h,
  not Google's JWKS endpoint
- Expiry
- Audience/issuer — this app's own configured values (`process.env.JWT_AUDIENCE`,
  `process.env.JWT_ISSUER`), not `GOOGLE_CLIENT_ID`

On valid JWT: extract `sub` (user ID), `role`, `gender` claims. Inject as headers before forwarding:
```
X-User-Id: <sub>
X-User-Role: <role>
X-User-Gender: <gender>
```

Strip the `Authorization` header before forwarding downstream (services must not receive the raw JWT).

Public routes (no JWT required): `POST /user/auth/google`, `POST /user/auth/otp/send`,
`POST /user/auth/otp/verify` — the **gateway-facing** paths, i.e. what the client actually
sends to the gateway, including the `/user` prefix from T011's YARP route table. This
middleware runs before `app.MapReverseProxy()`, so it sees the request before YARP's
`PathRemovePrefix` transform strips that prefix — `contracts/openapi/user-service.yaml`
documents these same endpoints without the prefix (`/auth/google`) because that file
describes what `user-service` itself receives *after* stripping, not what arrives at the
gateway. Comparing against the un-prefixed path would never match a real incoming request.
These are the only calls that ever involve Google's raw token, and that handling happens
inside `user-service` (T016), never at the gateway.

## Acceptance criteria

- [ ] Request with valid JWT → headers injected, Authorization stripped, proxied
- [ ] Request with expired/invalid JWT → 401 returned, not forwarded
- [ ] Public routes pass through without JWT

## Patterns demonstrated

- **API Gateway Pattern** — Centralize cross-cutting concerns (authentication) at a single entry point. Services trust injected headers and never re-validate the token; this prevents duplication, reduces attack surface, and ensures consistency.
- **Dependency Inversion (D)** — The middleware depends on `IConfiguration` and an abstraction for JWKS retrieval, not hardcoded Google URLs or client IDs. Easy to swap implementations for testing.
- **Middleware Chain** — ASP.NET Core's middleware pipeline is the backbone. JWT validation is one plug-in layer; rate limiting (T013) will be another. Non-blocking composition.
- **Caching for Resilience** — the JWKS endpoint (`user-service`'s own, in this project) is called infrequently and cached. Reduces latency, reduces dependency on `user-service`'s availability at request time, matches industry practice (signing keys rotate on a schedule, not per-request).

## Agent implementation notes

**Key implementation decisions (already made by spec, corrected during ticket review):**
- `user-service` is the token issuer (T016), not Google directly — use `user-service`'s own
  `/.well-known/jwks.json` endpoint as the source of truth for the RSA public key that
  validates the app's own JWT
- The audience/issuer claims must match this app's own configured values
  (`process.env.JWT_AUDIENCE` / `process.env.JWT_ISSUER`) — strict validation, no wildcards
- Strip `Authorization` header after validation; downstream services must use only the injected `X-User-*` headers
- Public routes bypass the middleware entirely; use a route-based bypass (e.g., endpoint metadata) not per-request checks

**What to do:**
- Use `Microsoft.IdentityModel.Protocols.OpenIdConnect` and related NuGet packages to handle JWKS and JWT validation (the same `Microsoft.IdentityModel.*` libraries work identically whether the JWKS document comes from Google or from `user-service` — only the URL and audience/issuer values differ)
- Implement `JwksService` to cache `user-service`'s JWKS for ~24 hours
- In the middleware, catch `SecurityTokenException` and return 401 Unauthorized with a clear error message
- Ensure the three headers (`X-User-Id`, `X-User-Role`, `X-User-Gender`) are always present on forwarded requests (or return 401 if a required claim is missing)
- Store the current principal/claims in `HttpContext.User` after validation (ASP.NET Core convention)

**What NOT to do:**
- Do not re-validate the JWT in downstream services; they must trust the injected headers
- Do not log or expose the raw JWT in error responses (only log the validation failure reason)
- Do not hardcode `user-service`'s JWKS endpoint URL as a literal string in code — read it from config (`process.env.JWKS_ENDPOINT` or similar), consistent with the "no hardcoded config" rule
- Do not validate against Google's JWKS endpoint (`https://www.googleapis.com/.well-known/openid-configuration`) — that only matters inside `user-service`'s own `POST /auth/google` handler (T016), never at the gateway
- Do not forget that `role` and `gender` may not be present in all tokens — handle missing claims gracefully (default to a safe value or 401)
- **T016 (`user-service`, the JWKS issuer this middleware depends on) has not been implemented yet.** There is nothing live at `http://user-service:8080/.well-known/jwks.json` to fetch during this ticket. Build `JwksService` and the middleware to the correct contract (fetch, cache, validate against RS256/JWKS shape `{ "keys": [...] }`), but acceptance criteria that require an actual valid/expired token round-trip cannot be exercised end-to-end until T016 exists — verify by static/code review and note this limitation explicitly, the same way T011's review handled "no downstream stub exists yet."
