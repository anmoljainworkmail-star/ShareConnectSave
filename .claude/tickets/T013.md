# T013 — Rate Limiting Middleware

## Why this ticket exists
The gateway is the single door every client request walks through, which makes it the only place that can stop abuse before it reaches any backend service. Without limits here, one misbehaving client (a buggy retry loop, a scraper, or someone brute-forcing OTP codes) could hammer `POST /connection/connections` or `POST /user/auth/otp/send` and either exhaust SMS provider budget or spam other users with connection requests. Every service would otherwise have to duplicate this protection itself — this ticket puts it in exactly one place so no downstream service ever needs to think about it.

**Path correction (found while implementing T012 — read before writing route-matching code):**
Every endpoint-specific path in this ticket must be the **gateway-facing** path — YARP's route
prefix (`/user`, `/connection`, etc., from T011's route table) plus the downstream service's own
path from its OpenAPI spec, e.g. `connection-service`'s own `POST /connections` (from
`contracts/openapi/connection-service.yaml`) is reached through the gateway at
`POST /connection/connections`, and `user-service`'s own `POST /auth/otp/send` is reached at
`POST /user/auth/otp/send`. T012's `JwtValidationMiddleware` originally used the un-prefixed,
service-local paths for its public-route bypass and it silently never matched any real
request — locking out login entirely — until caught and fixed during that ticket's
implementation. Any per-route policy binding in this ticket (`.RequireRateLimiting(...)` on
specific endpoints) must use the prefixed path for the same reason.

## What to build
- Register `Microsoft.AspNetCore.RateLimiting` in the gateway's request pipeline (the same YARP gateway project built in T012).
- Three named rate limiter policies:
  - `GlobalPolicy` — sliding window, 100 requests/minute, partitioned per client IP. Applied to all routes.
  - `ConnectionRequestPolicy` — fixed window, 10 requests/minute, partitioned per `X-User-Id` header. Applied only to `POST /connection/connections` (gateway-facing path — see the path-correction note above).
  - `OtpSendPolicy` — fixed window, 5 requests/10 minutes, partitioned per phone number (from request body). Applied only to `POST /user/auth/otp/send` (gateway-facing path).
- A shared `OnRejected` handler that writes the standard error envelope on every 429:
  ```json
  { "code": "RATE_LIMIT_EXCEEDED", "message": "...", "traceId": "..." }
  ```
- Response header `X-RateLimit-Remaining` populated on every response (429 and success) so clients can self-throttle.

## Technical specification
Use .NET 9 built-in rate limiting (`Microsoft.AspNetCore.RateLimiting`).

Policies:
- **Global:** 100 req/min per IP (sliding window)
- **Connection requests:** 10 req/min per `X-User-Id` on `POST /connections` (fixed window)
- **OTP:** 5 req/10min per phone number on `POST /auth/otp/send`

429 responses use the shared error envelope: `{ "code": "RATE_LIMIT_EXCEEDED", ... }`.

## Acceptance criteria
- [ ] Exceeding global limit returns 429
- [ ] Exceeding connection limit returns 429 with `RATE_LIMIT_EXCEEDED`
- [ ] Rate limit headers (`X-RateLimit-Remaining`) present on all responses

## Patterns demonstrated
**API Gateway (cross-cutting concern)** — rate limiting is enforced once at the gateway, so no individual microservice needs to reimplement or remember to apply it.

**Sliding vs. Fixed Window Rate Limiting** — the global policy uses a sliding window (smooths out burst-at-boundary abuse across the whole client base), while the connection and OTP policies use fixed windows (simpler to reason about per-key, acceptable when the key space is already narrow — one user or one phone number).

**Partitioned Rate Limiting** — each policy partitions its limit by a different key (IP, user ID, phone number), demonstrating that "rate limit" is not one global counter but a family of counters keyed to whatever dimension actually represents abuse risk for that endpoint.

**Shared Error Envelope / Consistent API Contract** — the 429 response reuses the same `{ code, message, traceId }` shape as every other error in the system, so clients parse errors one way regardless of which limiter or service produced them.

## Agent implementation notes
- **Key files to create/modify** (inside the gateway project created in T012, e.g. `src/api-gateway/`):
  - `Program.cs` — register `AddRateLimiter(...)` with the three named policies and the global `OnRejected` callback, and call `UseRateLimiter()` in the middleware pipeline (must run after routing but this is handled automatically by `UseRateLimiter`).
  - `RateLimiting/RateLimitPolicies.cs` (new) — define policy names as constants and factory methods building each `RateLimitPartition` (sliding window for global, fixed window for connection/OTP).
  - `RateLimiting/RateLimitRejectionHandler.cs` (new) — the shared `OnRejected` delegate that writes the `RATE_LIMIT_EXCEEDED` error envelope as JSON with status 429, reusing whatever `traceId`/`ProblemDetails` helper already exists from the gateway's error-handling middleware (check T012's error middleware before writing a new one — do not duplicate it).
  - `RateLimiting/RateLimitHeadersMiddleware.cs` (new, or extend existing middleware) — sets `X-RateLimit-Remaining` on the response. .NET's built-in limiter does not add this header automatically, so it must be read from `HttpContext.Features.Get<IRateLimitMetadata>()` or tracked manually alongside the limiter and written before the response starts.
  - Route registration (wherever YARP routes/reverse-proxy config or minimal API endpoints for `/connections` and `/auth/otp/send` are defined) — attach `.RequireRateLimiting(RateLimitPolicies.ConnectionRequestPolicy)` / `OtpSendPolicy` to those specific routes; leave the global policy as the pipeline-wide default limiter.
- **Partition key extraction:**
  - IP: `httpContext.Connection.RemoteIpAddress` (fall back to `X-Forwarded-For` only if the gateway sits behind a reverse proxy already configured to forward it — check T012 for `ForwardedHeaders` setup before adding this).
  - User ID: read the `X-User-Id` header (this header is injected by the gateway's JWT validation middleware per the architecture — confirm it's set before this middleware runs in the pipeline).
  - Phone number: the OTP endpoint's request body must be read to extract the phone number for partitioning; use a partition key resolver that buffers/reads the body without breaking the downstream model binder (enable buffering or read a already-bound DTO if minimal API model binding runs before the limiter — sequence this carefully, since rate limiting middleware runs before endpoint binding by default).
- **What NOT to do:**
  - Do NOT implement rate limiting logic manually with counters/dictionaries — use the built-in `Microsoft.AspNetCore.RateLimiting` package only, per the spec.
  - Do NOT apply `ConnectionRequestPolicy` or `OtpSendPolicy` globally — they must be scoped to their specific single endpoint only.
  - Do NOT invent a different error shape for 429s — reuse the exact `{ code, message, traceId }` envelope used elsewhere in the gateway.
  - Do NOT skip the `X-RateLimit-Remaining` header on successful (non-429) responses — the acceptance criteria requires it on all responses, not just rejections.
  - Do NOT partition the global policy by anything other than IP, and do NOT partition connection/OTP policies by IP instead of user ID / phone number — mixing these up defeats the purpose of per-identity throttling.
