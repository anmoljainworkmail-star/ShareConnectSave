# T014 — Gateway Docker Image

## Why this ticket exists
Right now the API Gateway only runs if a developer has the .NET 9 SDK installed locally and starts it by hand. Every other piece of local infrastructure (SQL Server, MongoDB, Kafka, Redis) is already brought up with one command via Docker Compose, and `docker-compose.yml` already has an `api-gateway` service stub pointing at a `Dockerfile` that doesn't exist yet — so `docker compose up` currently fails to build the gateway at all. Without this ticket, nobody can run the full platform end-to-end with one command, and the gateway can't be exercised the same way (same network, same container-name DNS resolution, same healthcheck-gated startup ordering) that every downstream service will depend on. This also produces the first .NET Dockerfile in the repo — later .NET services (User, Chat, Notification) will copy its shape, so getting the multi-stage build and healthcheck right here saves rework later.

## What to build
- **File:** `src/services/api-gateway/Dockerfile` — multi-stage build (`build` stage on the SDK image, `runtime` stage on the ASP.NET runtime image)
- **Build stage base image:** `mcr.microsoft.com/dotnet/sdk:9.0`
- **Runtime stage base image:** `mcr.microsoft.com/dotnet/aspnet:9.0`
- **Wiring:** confirm/align the existing `api-gateway` block in `src/infra/docker-compose.yml` with this Dockerfile (build context, exposed port `8080`, healthcheck)
- **Endpoint:** `GET /health` on the gateway must return `200 OK` — this is what the Compose healthcheck polls

## Patterns demonstrated
**Multi-Stage Build** — the `build` stage carries the full SDK (compilers, NuGet cache, ~800MB+) needed only to produce a compiled output; the `runtime` stage starts fresh from a much smaller ASP.NET runtime image and copies in only the published binaries. Nothing needed to *compile* the app ships in the image that *runs* it in production.

**Separation of Build-Time and Run-Time Concerns** — mirrors Single Responsibility at the infrastructure level: the SDK image's job is "produce artifacts," the runtime image's job is "execute artifacts." Collapsing them into one stage would work, but couples two different concerns into one artifact and bloats every deploy.

**API Gateway pattern** — this is the single entry point for all client traffic (per the system design table in CLAUDE.md); containerizing it first, before the services it routes to, reflects that everything else in the platform is reached through it.

**Healthcheck as a Dependency Gate** — matches the pattern already used by `sqlserver`, `mongodb`, `kafka`, and `redis` in `docker-compose.yml`: a container isn't considered "up" just because its process started — Compose (and later, any service with `depends_on: condition: service_healthy`) waits until `/health` actually answers `200`. Without this, a `docker compose up` race could let a dependent service start talking to a gateway that hasn't finished initializing.

## Agent implementation notes

**Key files to create/modify:**
- `src/services/api-gateway/Dockerfile` (new)
- `src/services/api-gateway/Program.cs` (verify/modify — see health endpoint note below)
- `src/infra/docker-compose.yml` (verify only — the `api-gateway` service block already exists at lines ~226-243 with `build.context: ../../src/services/api-gateway`, `dockerfile: Dockerfile`, port `8080:8080`, and a `curl`-based healthcheck already wired against `/health`. Do not duplicate this block — just make sure the Dockerfile you write satisfies it. Only touch this file if something in it is actually wrong.)

**Dockerfile shape to follow:**
```dockerfile
# build stage — full SDK, only needed to compile/publish
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src
COPY api-gateway.csproj ./
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app/publish --no-restore

# runtime stage — slim ASP.NET runtime only, no SDK/compiler ever ships
FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
EXPOSE 8080
ENTRYPOINT ["dotnet", "api-gateway.dll"]
```
Copy the `.csproj` and run `dotnet restore` *before* copying the rest of the source — this is a Docker layer-caching concern: as long as the `.csproj` doesn't change, Docker reuses the cached `restore` layer on rebuilds instead of re-downloading NuGet packages every time source code changes.

**Healthcheck endpoint — verify before assuming it exists:**
`src/services/api-gateway/Program.cs` currently only has `app.MapGet("/", () => "Hello World!");` — there is no `/health` route yet. T013 (the gateway project scaffold, which this depends on) is expected to add it, but if it hasn't landed by the time you implement this ticket, add a minimal one yourself so the acceptance criteria can pass:
```csharp
app.MapGet("/health", () => Results.Ok());
```
Keep it trivial — this is a liveness check only ("is the process up and serving HTTP"), not a deep check of downstream dependencies. Do not wire in checks against User Service, Redis, etc. here; that's out of scope for this ticket.

**`curl` must exist inside the runtime image:**
The Compose healthcheck (already in `docker-compose.yml`) runs `curl -f http://localhost:8080/health` *inside* the container. `mcr.microsoft.com/dotnet/aspnet:9.0` is Debian-based but does **not** ship `curl` by default — if you don't install it, the healthcheck will fail with "executable file not found" even though the app itself is fine. Add to the runtime stage:
```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*
```
The `rm -rf /var/lib/apt/lists/*` matters for the 200MB budget — it clears the apt package index Docker otherwise leaves behind in the layer.

**200MB image size budget — flag risk, don't silently swap the base image:**
`mcr.microsoft.com/dotnet/aspnet:9.0` (Debian-based) plus `curl` can land close to or over 200MB depending on the exact build. If `docker image ls` shows the built image over budget, do NOT unilaterally switch to `-alpine` — the spec pins the exact tag `mcr.microsoft.com/dotnet/aspnet:9.0`. Report the actual measured size in the PR/review notes and let the Tech Lead decide whether the alpine variant (`mcr.microsoft.com/dotnet/aspnet:9.0-alpine`, ~half the size, but musl libc — occasionally trips up native dependencies) is an acceptable substitution.

**What NOT to do:**
- Do not install the SDK in the runtime stage — that's the entire point of the multi-stage split; if `dotnet build` or `dotnet restore` ever run in the `runtime` stage, the split has failed.
- Do not `COPY . .` in the runtime stage — only copy `/app/publish` from the `build` stage. Copying the full source tree into the runtime image drags in `.git`, `bin/`, `obj/`, and everything else in the build context.
- Do not add a `.dockerignore`-less build — check whether `src/services/api-gateway/.dockerignore` exists; if not, add one excluding `bin/`, `obj/`, `.vs/` so the existing local build artifacts (already present in this checked-out working tree) aren't copied into the build context and don't shadow the container's own `dotnet publish` output.
- Do not hardcode `ASPNETCORE_URLS` or the port inside the Dockerfile via `ENV` — `docker-compose.yml` already sets `ASPNETCORE_URLS=http://+:8080` and `ASPNETCORE_ENVIRONMENT=Development` as environment variables on the service; duplicating them in the Dockerfile creates two sources of truth that can drift.
- Do not add a second `healthcheck:` block to `docker-compose.yml` — one already exists on the `api-gateway` service; adding another either errors or silently overrides it.

**Testing guidance for reviewer:**
- `cd src/infra && docker compose build api-gateway` — confirm it builds clean
- `docker compose up api-gateway` — confirm the container reaches `healthy` status (`docker compose ps` shows `(healthy)`, not `(unhealthy)` or stuck `(starting)`)
- `curl http://localhost:8080/health` from the host — confirm `200`
- `docker image inspect shareconnectsave/api-gateway:dev --format='{{.Size}}'` — confirm under `200000000` bytes (~200MB)
