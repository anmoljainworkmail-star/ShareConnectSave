# T015 — User Service Project + EF Core Setup

## Why this ticket exists
Right now User Service has database entities and a migration on disk, but no running application actually uses them — `Program.cs` is still the default "Hello World" template, nothing registers `AppDbContext` with the app, there is no way for other code to read or write a user/OTP/verification row through an interface, and there's no `/health` endpoint for Docker Compose (or anything else) to check that the service is alive. Every later User Service ticket — Google OAuth (T016), OTP verification (T017), profile CRUD (T018), identity verification (T019), the `user.verified` Kafka event (T020) — needs a working, DI-wired database access layer to build on. Without this ticket, none of those can start, and Discovery Service (which depends on `user.verified` firing) stays blocked indefinitely. This is also the first of 9 services to wire its "database per service" schema into actual running application code, so getting the repository boundary right here sets the pattern every other service copies.

## What to build
- Register `AppDbContext` in `Program.cs` via `AddDbContext`, reading the connection string from configuration (env var), never hardcoded
- `IUserRepository`, `IOtpRepository`, `IIdentityVerificationRepository` interfaces (one per aggregate — Interface Segregation, not one fat `IUserServiceRepository`)
- EF Core implementations: `UserRepository`, `OtpRepository`, `IdentityVerificationRepository`
- Register all three repository interfaces + implementations in DI (`builder.Services.AddScoped<...>()`)
- `GET /health` endpoint returning `200`
- Fix/complete the connection-string wiring gap described below so `dotnet ef database update` and the running container both actually connect
- One paragraph of documentation (in this ticket's PR description or a code comment in `AppDbContextFactory.cs`) stating the chosen approach for keeping Flyway (Java services) and EF Core (.NET services) migrations in sync with the T006 schema — they will not literally share migration files; document how schema drift between the two is prevented (e.g. "each service is source of truth for its own DB; column names/types are cross-checked manually against SPECS.md/REQUIREMENTS.md at review time, not auto-synced")

## Patterns demonstrated
**Interface Segregation** — `IUserRepository`, `IOtpRepository`, and `IIdentityVerificationRepository` are three separate interfaces, not one combined repository. A future consumer that only needs OTP lookups (e.g. a rate-limiting check) depends only on `IOtpRepository`, never forced to see user-profile or verification methods it has no business calling.

**Dependency Inversion** — application code (future controllers/services in T016-T019) will inject `IUserRepository`, never `UserRepository` or `AppDbContext` directly. This is what makes an in-memory fake repository possible for unit tests later, without spinning up SQL Server.

**Database per Service** — this is the first service to wire its T006 schema into real, running application code. `UserServiceDb` is touched only through this repository layer; no other service in the platform is allowed to query it directly, only via HTTP/Kafka.

**Liskov Substitution** — any future alternate implementation of these interfaces (an in-memory fake for tests, a caching decorator, etc.) must be swappable for the EF Core implementation without callers changing behavior or breaking.

**Health Endpoint as a Dependency Gate** — same pattern as the API Gateway (T014): Docker Compose's healthcheck for `user-service` polls `GET /health`; other services that eventually `depends_on: user-service condition: service_healthy` rely on this being a real signal that the process (and, per acceptance criteria, its DB connection) is actually ready.

**No Hardcoded Config** — connection string comes from an environment variable read through ASP.NET Core configuration binding, never a literal string in `appsettings.json` or code. This is what lets the same image run against different SQL Server instances (local dev, CI, later a real cloud DB) without a rebuild.

**EF implementation pattern:**
```csharp
namespace user_service.Repositories;

using Microsoft.EntityFrameworkCore;
using user_service.Infrastructure;
using user_service.Models;

public class UserRepository : IUserRepository
{
    private readonly AppDbContext _db;

    public UserRepository(AppDbContext db) => _db = db;

    public Task<User?> GetByIdAsync(long id) =>
        _db.Users.FirstOrDefaultAsync(u => u.Id == id);

    public Task<User?> GetByGoogleIdAsync(string googleId) =>
        _db.Users.FirstOrDefaultAsync(u => u.GoogleId == googleId);

    public async Task<User> AddAsync(User user)
    {
        _db.Users.Add(user);
        await _db.SaveChangesAsync();
        return user;
    }

    public async Task UpdateAsync(User user)
    {
        _db.Users.Update(user);
        await _db.SaveChangesAsync();
    }
}
```
