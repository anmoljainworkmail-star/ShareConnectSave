# T016 — Google OAuth + JWT Issuance

## Why this ticket exists

Right now nobody can sign in. Without this ticket there is no way to turn "I signed in with Google on my phone" into an identity our own backend understands and trusts — no user row gets created, no session token gets issued, and every other service (Discovery, Connection, Chat, ...) has nothing to check a request against. This ticket is also the other half of a contract the gateway already relies on: T012 (JWT Validation Middleware) is already built and configured to fetch a JWKS document from `user-service` and validate an RS256 JWT that carries `sub`, `role`, and `gender`. Until this ticket ships, that endpoint returns nothing and every authenticated request in the whole platform fails closed. T016 is the producer: it validates the user's Google sign-in once, looks them up (or creates them), and issues the app's own signed token — the one every other service will trust for the rest of the session.

## What to build

- `POST /auth/google` endpoint in `user-service` accepting `{ "id_token": "<google id token>" }`
- Google ID token validation against Google's token info endpoint
- Extraction of `sub`, `email`, `name`, `picture` from the validated Google token
- Upsert logic against the `users` table (create on first sign-in, match on subsequent sign-ins)
- New users get `status = incomplete` until phone verification (OTP) and gender are both set
- RSA keypair owned solely by `user-service`, used to sign a new JWT with claims: `sub` (our UUID, not Google's), `role = "user"`, `gender` (from profile if already set)
- `GET /.well-known/jwks.json` exposing only the public key, in standard JWKS shape (`{ "keys": [...] }`)
- Response: `{ "access_token": "...", "refresh_token": "...", "is_new_user": true/false }`
- 401 with error code `INVALID_GOOGLE_TOKEN` when Google's token fails validation

## Technical specification

`POST /auth/google`
Body: `{ "id_token": "<google id token>" }`

1. Validate the Google ID token using Google's token info endpoint.
2. Extract `sub`, `email`, `name`, `picture`.
3. Upsert user in `users` table.
4. Issue a signed JWT with claims: `sub` = user_id (our UUID), `role` = "user", `gender` (from profile if set).
   Sign with RS256 using an RSA private key held only by `user-service` — never a shared
   symmetric secret — and expose the matching public key at `GET /.well-known/jwks.json`
   (standard JWKS shape: `{ "keys": [...] }`) so the gateway (T012) can fetch and cache it
   to validate this token on every later request, without ever holding the private key
   itself.
5. Return: `{ "access_token": "...", "refresh_token": "...", "is_new_user": true/false }`

New users (`is_new_user: true`) must complete profile setup before discovery is enabled. Set `status = incomplete` until phone is verified and gender is set.

## Acceptance criteria

- [ ] Valid Google token → JWT issued, user upserted
- [ ] Invalid Google token → 401 with `INVALID_GOOGLE_TOKEN`
- [ ] Returned JWT validates against the gateway's JWKS config

## Patterns demonstrated

- **Asymmetric signing (RS256) over a shared secret** — `user-service` holds the RSA private key and never shares it with anyone, including the gateway. The gateway only ever fetches the public key via JWKS. This means only `user-service` can ever mint a valid token, but any number of services can verify one — a compromised gateway can validate tokens but can never forge one, which a shared HMAC secret would not protect against.
- **Single Responsibility (S)** — this endpoint's job is "prove who signed in and issue our own token." It does not implement OTP verification, profile completion, or trust scoring; those stay in their own handlers/services.
- **Dependency Inversion (D)** — the Google token validator and the user repository should be injected as abstractions (e.g. `IGoogleTokenValidator`, `IUserRepository`), not called as static/concrete classes, so tests can substitute fakes without hitting Google's network endpoint.
- **API Gateway / trust boundary** — this ticket is the producer half of the contract T012 consumes. Downstream services never see Google's token and never re-derive `role`/`gender`; they trust the headers the gateway injects after validating *this* token.

## Agent implementation notes

**Security-critical asymmetry — read this before writing any signing code:**
The RSA private key generated/held by `user-service` must never leave `user-service` — not logged, not returned in any response, not sent to the gateway, not checked into config that other services read. The gateway (T012) only ever consumes the **public** key, and only via the `GET /.well-known/jwks.json` endpoint this ticket builds. This is the entire reason RS256 was chosen over a shared symmetric secret (e.g. HS256): with HS256 the same secret both signs and verifies, so the gateway would need a copy of the signing secret and could theoretically mint valid tokens itself. With RS256, only `user-service` can produce a valid signature; every other service, including the gateway, can only verify one. If the implementation ever needs to hand the private key to another service or config store to "make validation work," that is a sign the wrong key ended up in the wrong place — stop and use the public key instead.

**Key files to create:**
- `src/services/user-service/Controllers/AuthController.cs` — `POST /auth/google` and `GET /.well-known/jwks.json`
- `src/services/user-service/Services/IGoogleTokenValidator.cs` + `GoogleTokenValidator.cs` — calls Google's token info endpoint, returns `sub`/`email`/`name`/`picture` or throws/returns invalid
- `src/services/user-service/Services/IJwtIssuer.cs` + `JwtIssuer.cs` — holds the RSA keypair, signs outgoing JWTs, exposes the public key in JWKS shape
- `src/services/user-service/Repositories/IUserRepository.cs` + implementation — upsert-by-Google-`sub` against the `users` table
- `src/services/user-service/Models/User.cs` — include `status` (`incomplete` | `active` | ...), `gender`, `google_sub`, `email`, `name`, `picture_url`
- Update `src/services/user-service/Program.cs` to register these services and map the endpoints

**Patterns to use:**
- Reference the `dotnet-mvc-controllers` skill for controller/attribute-routing conventions (`[ApiController]`, `[HttpPost("/auth/google")]`, `[HttpGet("/.well-known/jwks.json")]`, constructor-injected dependencies), request/response DTO conventions, and how this project structures MVC controller projects (see T011/T012 for the sibling gateway project's layout, which this project should mirror).
- Use `Microsoft.IdentityModel.Tokens` / `System.IdentityModel.Tokens.Jwt` for RS256 signing — the same library family the gateway already uses to validate, so the token shape lines up naturally.
- Generate or load the RSA keypair from a secret store or environment-provided key material (`process.env.*`, per this project's no-hardcoded-config rule) — never a literal string in source.
- Guard clause style for validation failures (early-return on invalid Google token → 401), consistent with this project's stated preference for early returns over nested conditionals.

**What NOT to do:**
- Do not validate the app's own future JWTs against Google's JWKS — Google's token is only ever handled inside this one endpoint, for this one exchange.
- Do not put business logic (OTP verification, trust score, discovery eligibility) in this ticket — only auth + JWT issuance + the `incomplete` status flag.
- Do not return the RSA private key, or any representation of it, in any response body, log line, or error message.
- Do not use a symmetric secret (HS256) "to keep it simple" — the whole point of this ticket is the RS256/JWKS asymmetry the gateway (T012) is already built against; a symmetric secret would silently break that contract and would additionally mean the gateway needs the same secret as the issuer, which defeats the security boundary.
- Do not skip the `is_new_user` / `status = incomplete` flag — Discovery Service (later tickets) depends on `status` to know which users are eligible to appear in scans.
- Do not forget `INVALID_GOOGLE_TOKEN` as the literal error code in the 401 response body — other services/tests will match on this string.
