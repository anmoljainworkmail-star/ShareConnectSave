# T017 — Phone OTP Verification

## Why this ticket exists
After Google sign-in (T016), users must verify they own their phone number before they can use the platform. This ticket implements the OTP send-and-verify flow, plus a brute-force lockout to stop attackers from guessing codes. Without this, anyone could sign in as someone else by guessing a random phone number. Onboarding breaks here — users can't move to profile setup without passing phone verification.

## What to build
Two new endpoints in the User Service that handle one-time password verification, plus database and environment configuration to support it:

- `POST /auth/otp/send` — Sends a 6-digit OTP code to a phone number via Twilio; idempotent (repeated calls to the same phone within the same session return the same code)
- `POST /auth/otp/verify` — Consumes the OTP code, verifies it against the stored code, increments or resets attempt counters, and on success marks the phone as verified and updates user status to `active` if their profile is complete
- `otp_attempts` table rows — Track failed verification attempts per phone number with a `locked_until` timestamp to enforce 15-minute lockouts
- Environment variables — `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER` (outbound sender) configured and injected into the service

Request/response shapes consistent with T013 (rate limiting) and T016 (JWT envelope); error responses follow the standard error envelope defined in T003.

## Technical specification
`POST /auth/otp/send` — sends OTP to phone number (use Twilio via `process.env.TWILIO_*`).
`POST /auth/otp/verify` — verifies OTP, marks phone as verified on user record.

Brute-force protection: after 5 failed attempts within 10 minutes, lock the phone number for 15 minutes. Track in `otp_attempts` table.

On successful verification: update user `status` to `active` if profile is also complete.

## Acceptance criteria
- [ ] Correct OTP → phone marked verified, user status updated
- [ ] Wrong OTP → 400 with `INVALID_OTP`, attempt count incremented
- [ ] After 5 failures → 429 with `OTP_LOCKED`, lockout time in response

## Patterns demonstrated
- **Idempotency** — OTP send must not generate a new code on every call; if the same phone requests within 5 minutes, return the same code already sent. This ensures a slow network or client retry doesn't break the user's attempt.
- **Brute-force Protection** — Tracking failed attempts in a dedicated table and locking after N failures in a time window demonstrates defensive security. This is a business-rule lockout layer separate from the gateway's request-rate limiter (T013).
- **Dependency Injection** — Twilio client injected into the OTP service, not instantiated inline. Allows swapping for a test double without changing the service code.
- **Saga Compensation** — If phone verification succeeds but the user's profile is incomplete, status stays `pending`; it advances to `active` only when both are true. Later, identity verification (T019) will add a third condition, showing how sagas chain conditions across async events.

## Agent implementation notes
- Create `OtpService.cs` (depends on `ITwilioClient` abstraction and `IOtpAttemptRepository`)
- Create or extend `User` entity to add `phone_verified_at` timestamp and ensure `status` field exists (from T006)
- Create `otp_attempts` table schema migration or seed if not already present (verify against T006)
- Endpoints must validate input (phone format, code format) before calling service
- OTP code generation: use 6-digit random numeric code (e.g., `Random.Next(0, 1000000)` zero-padded to 6 chars)
- Idempotency: on `POST /auth/otp/send`, check if a code already exists for this phone with `created_at > now - 5 minutes`. If yes, return the existing code; if no, generate new
- Lockout check: before accepting an attempt on `POST /auth/otp/verify`, query `otp_attempts` for this phone and check if `locked_until > now`. If true, return 429 immediately
- Failed attempt increment: on wrong OTP, increment `attempt_count` and also update `locked_until = now + 15 minutes` if `attempt_count == 5`
- Status update: on successful verify, update user `status = 'active'` only if both `phone_verified_at IS NOT NULL` and profile is complete (name, photo, language, gender all set)
- Error envelope: use the error shape from T003 (standard service error response). 400 for `INVALID_OTP`, 429 for `OTP_LOCKED`
- Do not hardcode Twilio credentials; all must come from `process.env.TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`
- Avoid: Do not re-send the OTP code in the 200 response (for security, only Twilio knows it). Do not store OTP codes in plain text in the database (hash them, e.g., SHA256). Do not use a static lockout duration — make it configurable via env var with a sensible default (15 minutes).
