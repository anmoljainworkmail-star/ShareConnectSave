# T018 — Profile CRUD

## Why this ticket exists
Right now a user can sign in with Google (T016) and get a JWT, but there is no way to view or edit their own profile, and no way for anyone else to look up a public profile card. Without this ticket, discovery and connection features have nothing to show — no name, no photo, no status toggle — and identity verification (T019) has no way to get a base photo to match against. This ticket is also the first place the platform's core privacy rule gets enforced in code: gender and phone number must never appear in a response to another user, only to the profile owner.

## What to build
- `GET /users/me` endpoint — returns the caller's full own profile (all fields, including gender and phone)
- `PATCH /users/me` endpoint — updates `name`, `preferred_language`, `gender`, `status`
- `POST /users/me/photo` endpoint — multipart file upload, stores the photo, sets `photo_url` on the user record
- `GET /users/:id` endpoint — returns a public profile projection (name, photo, rating, badges, destination) — gender and phone excluded by construction
- A distinct public-facing response DTO (e.g. `PublicUserProfileDto`) separate from the full profile DTO used by `/users/me`, so the gender/phone fields structurally cannot leak
- Validation for `gender` (`female | male | unspecified`) and `status` (`looking | unavailable`) on `PATCH`, returning 400 on invalid values

## Technical specification
- `GET /users/me` — returns own profile (all fields)
- `PATCH /users/me` — update name, preferred_language, gender, status (`looking` | `unavailable`)
- `POST /users/me/photo` — multipart upload. Stores photo, sets `photo_url`. Required before identity verification can be started. If Google provided a photo on sign-in, this is pre-populated but user can replace it.
- `GET /users/:id` — returns public profile (name, photo, rating, badges, destination — no gender, no phone)

## Acceptance criteria
- [ ] `PATCH` validates gender is one of `female | male | unspecified`
- [ ] `GET /users/:id` never returns gender or phone fields
- [ ] `PATCH` with invalid status value returns 400
- [ ] `POST /users/me/photo` sets `photo_url`, overwrites any Google-provided photo
- [ ] After `POST /users/me/photo`, `GET /users/me` reflects the new `photo_url`

## Patterns demonstrated
- **Single Responsibility (SOLID - S)** — the endpoint handlers only orchestrate request/response; validation and persistence are delegated to their own collaborators, not inlined into the route.
- **Interface Segregation (SOLID - I)** — the public profile shape and the owner's full profile shape are separate contracts (separate DTOs), so no caller is ever handed a type that carries fields it has no right to see.
- **Data minimization / privacy-by-construction** — sensitive fields (gender, phone) are excluded by the shape of the DTO returned to the public endpoint, not by a runtime `if` check that could be forgotten or bypassed later.
- **Dependency Inversion (SOLID - D)** — the endpoints depend on `IUserRepository` (abstraction), not a concrete `SqlUserRepository`, so persistence can be swapped or mocked in tests.

## Agent implementation notes
- Key files to create (paths from project root, adjust to actual `user-service` project layout):
  - `src/services/user-service/Controllers/UserProfileController.cs` — maps `GET /users/me`, `PATCH /users/me`, `POST /users/me/photo`, `GET /users/:id`
  - `src/services/user-service/Dtos/UserProfileDto.cs` — full profile shape, owner-only (includes gender, phone)
  - `src/services/user-service/Dtos/PublicUserProfileDto.cs` — public shape (name, photo, rating, badges, destination) — must NOT contain gender or phone fields at all
  - `src/services/user-service/Dtos/UpdateProfileRequest.cs` — PATCH request body with validation attributes/logic for `gender` and `status`
  - `src/services/user-service/Repositories/IUserRepository.cs` and its implementation — follow the `dotnet-mvc-controllers` skill's repository pattern conventions
  - `src/services/user-service/Services/ProfilePhotoStorageService.cs` (or similar) — handles the multipart file save and `photo_url` assignment, kept separate from the endpoint handler (Single Responsibility)
- Use attribute-routed controller actions per the `dotnet-mvc-controllers` skill file conventions (`[ApiController]`, `[HttpGet]`/`[HttpPatch]`/`[HttpPost]` attribute routing, validation pattern, error envelope shape).
- Reuse the JWT identity header injected by the gateway (from T012/T016) to resolve "me" — do not accept a user id from the client for `/users/me` routes.

- **Privacy-critical implementation note (do not skip):** `GET /users/:id` must never serialize `gender` or `phone` under any circumstance. Do NOT implement this by taking the full internal user entity/DTO and omitting or nulling out fields ad hoc (e.g. `dto.Gender = null` before returning) — that pattern is fragile and will silently leak the field again the moment someone adds a new sensitive field to the entity without remembering to scrub it here too. Instead, define `PublicUserProfileDto` as its own distinct type that structurally has no `Gender` or `Phone` property at all, and map into it explicitly (field-by-field or via an explicit mapper/projection). The absence of the field in the type itself is the safety guarantee, not a runtime check.
- Common mistakes to avoid for this task type:
  - Returning the same entity/DTO from both `/users/me` and `/users/:id` with conditional field suppression.
  - Trusting a client-supplied user id instead of the JWT-derived identity for `/users/me`.
  - Allowing `PATCH` to silently accept an invalid `gender` or `status` value instead of returning 400.
  - Forgetting that `photo_url` set by `POST /users/me/photo` must be immediately visible on the next `GET /users/me` call (no caching staleness).
