# T019 — Identity Verification Badge

## Why this ticket exists

Right now nothing stops an impostor from posing as someone else on the platform, and there is no signal a wary traveler can look for to tell a verified real person from an unverified one. This ticket builds the "Verified" badge: a user submits a selfie, the system compares it against their own profile photo, and — on a match — flips a flag that every other part of the product (matching, discovery, trust scoring) can rely on. The one hard rule from REQUIREMENTS.md is that verification can never start without something to compare against: if a user signed in with a Google account that has no profile picture (common for work/school accounts), they must upload a photo first via `PATCH /users/me` before this endpoint will do anything. Without this ticket, that rule has nowhere to live, and Discovery Service (T020) has no `identity_badge` field to trust when it starts tracking verified users.

## What to build

- `POST /users/me/verify-identity` endpoint in `user-service`, multipart form body with a `selfie` image file
- Pre-condition guard: read the caller's `photo_url` from their profile before touching any face-matching code
  - `photo_url` null → `422 NO_BASE_PHOTO`, message pointing the user at `PATCH /users/me` to upload a photo first
  - `photo_url` set → proceed
- Download the base photo referenced by `photo_url`
- Face comparison via Azure Face API, driven by `process.env.AZURE_FACE_*` config, with a stub fallback for dev
- `IDENTITY_VERIFY_STUB=true` env flag forces the stub to always return `verified: true` (no network call to Azure)
- On confidence > 0.8: insert `identity_verifications` row with `status = verified`, set `identity_badge = true` on the user
- On confidence <= 0.8 (or explicit mismatch): insert `identity_verifications` row with `status = failed`, return `422 IDENTITY_MISMATCH`
- Uses the existing `identity_verifications` table (id, user_id, status, verified_at) from T006 — no schema change in this ticket

## Technical specification

`POST /users/me/verify-identity`
Body: multipart form — `selfie` (image file)

Pre-condition check: user must have a `photo_url` set on their profile before this endpoint can be called.
- If `photo_url` is null (Google account had no photo and user hasn't uploaded one): return 422 with `NO_BASE_PHOTO` and a message directing them to upload a profile photo first via `PATCH /users/me`.
- If `photo_url` is set: proceed with face match.

Steps:
1. Download the base photo from `photo_url`.
2. Compare selfie against base photo using Azure Face API (`process.env.AZURE_FACE_*`) or fallback stub returning `verified: true` for dev.
3. On match (confidence > 0.8): create `identity_verifications` record with `status = verified`, set `identity_badge = true` on user.
4. On mismatch: record `status = failed`, return 422 with `IDENTITY_MISMATCH`.

## Acceptance criteria

- [ ] No `photo_url` on profile → 422 with `NO_BASE_PHOTO` before any face API call
- [ ] Matching faces → badge set on user, 200 returned
- [ ] Confidence below threshold → 422 with `IDENTITY_MISMATCH`
- [ ] Dev mode (env flag `IDENTITY_VERIFY_STUB=true`) always returns verified
- [ ] User who uploads photo via `PATCH /users/me` can then call this endpoint successfully

## Patterns demonstrated

- **Guard clause / fail fast** — the `photo_url` pre-condition check is a hard early-return before any external API call. This isn't just correctness (you can't face-match against nothing) — it's a cost and latency guard: Azure Face API calls are billed per call and add real network latency, so short-circuiting on a condition you can check with data already in hand avoids paying that cost for a request that can never succeed.
- **Single Responsibility (S)** — this endpoint's job is "prove the selfie matches the base photo and flip the badge." It does not implement photo upload (that's `PATCH /users/me`, a separate ticket) and does not touch trust scoring or discovery eligibility.
- **Dependency Inversion (D)** — the face-matching call should sit behind an abstraction (e.g. `IFaceMatchService`) with two implementations (Azure-backed, stub-backed), selected by config/env flag — not an `if (isDev)` branch sprinkled through the handler.
- **Open/Closed (O)** — swapping face-match providers later (e.g. away from Azure) should mean adding a new `IFaceMatchService` implementation, not editing this endpoint's logic.

## Agent implementation notes

**The precondition check must short-circuit before any Azure Face API call — this is the most important thing to get right in this ticket.** Read `photo_url` off the user's profile first. If it is null, return `422 NO_BASE_PHOTO` immediately and stop — do not download anything, do not construct a face-match request, do not touch `process.env.AZURE_FACE_*` at all in that code path. This is a guard clause both for correctness (you cannot compare against nothing) and for cost/latency: Azure Face API is a paid, network-bound external call, and every request that hits it for a user with no base photo is money and time spent on a call that was already known to fail before it started.

**Key files to create:**
- `src/services/user-service/Endpoints/IdentityVerificationEndpoints.cs` — `POST /users/me/verify-identity`
- `src/services/user-service/Services/IFaceMatchService.cs` + `AzureFaceMatchService.cs` + `StubFaceMatchService.cs` — abstraction over face comparison; stub returns `verified: true` unconditionally when `IDENTITY_VERIFY_STUB=true`
- `src/services/user-service/Repositories/IIdentityVerificationRepository.cs` + implementation — insert into `identity_verifications` (id, user_id, status, verified_at)
- Update `src/services/user-service/Repositories/IUserRepository.cs` usage (or equivalent) to read `photo_url` and to set `identity_badge = true` on match
- Update `src/services/user-service/Program.cs` to register `IFaceMatchService` (Azure vs stub based on `IDENTITY_VERIFY_STUB`) and map the new endpoint

**Patterns to use:**
- Reference the `dotnet-minimal-api` skill for endpoint registration, multipart form binding (`IFormFile` for `selfie`), and this project's request/response DTO conventions (see T016/T018 in this same service for sibling layout).
- Guard clause style throughout: precondition check, then match/mismatch branches — no nested conditionals.
- Config via `process.env.AZURE_FACE_*` (endpoint, key) and `IDENTITY_VERIFY_STUB` — never hardcode Azure credentials or a literal confidence threshold buried in unrelated code; keep the `0.8` threshold as a single named constant.

**What NOT to do:**
- Do not call the face-match service (Azure or stub) before the `photo_url` guard clause has passed — this defeats the entire point of the precondition check.
- Do not skip writing an `identity_verifications` row on the failed/mismatch path — the audit trail of failed attempts matters as much as the successful one.
- Do not conflate this ticket with photo upload — `PATCH /users/me` (setting `photo_url`) is out of scope here; this ticket only reads that field.
- Do not hardcode the `0.8` confidence threshold or Azure credentials as literal strings — use a named constant and `process.env.*` respectively, per this project's config rule.
- Do not return any detail of *why* a match failed (e.g. raw confidence score, Azure error internals) beyond the `IDENTITY_MISMATCH` error code — avoid leaking biometric matching internals to the client.
