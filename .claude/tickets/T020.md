# T020 — Kafka Producer: user.verified event on activation

## Why this ticket exists
Right now, when a user finishes verification (phone confirmed + profile complete), User Service marks them `active` in its own database and nothing else in the system finds out. Discovery Service — the part of the app that lets nearby travelers find each other — has no way of knowing this user exists, so a fully verified traveler would never show up in anyone's search results. This ticket makes User Service announce "this user is now verified" onto Kafka the moment that status flip happens, so any service that cares (starting with Discovery, in a later phase) can react. This is the very first cross-service event in the whole platform — every later saga and event chain builds on this same shape.

## What to build
- `IUserVerifiedEventPublisher` interface (Dependency Inversion — callers depend on the abstraction, not on `Confluent.Kafka` directly)
- `KafkaUserVerifiedEventPublisher` implementation using the `Confluent.Kafka` NuGet package
- Producer targets topic `user.verified`, using `user_id` as the Kafka partition key
- Event payload matches the existing `user.verified.schema.json` contract from T002 — key fields: `user_id`, `gender`, `verified_at` (plus `event_id` for the envelope, consistent with other events in this system)
- Hook the publish call into the existing status-transition code path (the logic in User Service that flips a user's status to `active` once phone verification + profile completion are both satisfied — built in T017/T018/T009)
- Fire-and-forget-with-retry wrapper: publish attempt runs off the request thread; on failure it logs an error and retries in the background, but never throws back into the HTTP request pipeline
- Structured logging on publish failure (service name, topic, user_id, exception) so failures are visible in local dev (Kafka UI / logs), since there is no outbox table backing this yet

## Technical specification
When a user's status transitions to `active` (phone verified + profile complete), publish a `user.verified` event to Kafka.

Use `Confluent.Kafka` NuGet. Message schema from T002. Produce to topic `user.verified` with `user_id` as the partition key.

## Acceptance criteria
- [ ] Status transition to `active` → event visible in Kafka UI
- [ ] Event matches `user.verified.schema.json` contract
- [ ] Kafka unavailable → log error, do not fail the HTTP request (fire-and-forget with retry in background)

## Patterns demonstrated
- **Dependency Inversion (SOLID - D)** — the status-transition code depends on `IUserVerifiedEventPublisher`, not on `Confluent.Kafka`'s `IProducer<>` directly. This is what lets the outbox-backed implementation swap in later (Phase 14) without touching call sites.
- **Event-Driven Architecture** — the event name (`user.verified`) is a fact about the past, not a command. User Service doesn't know or care that Discovery Service will eventually consume it.
- **Single Responsibility (SOLID - S)** — the publisher class only knows how to serialize and send this one event; it does not contain verification business logic, and the verification logic does not know about Kafka wire details.
- **Fire-and-forget with background retry** — demonstrates why a synchronous, in-request call to an external system (Kafka) is dangerous: if Kafka is briefly unreachable, the user's HTTP request (which just legitimately completed verification) must not fail because of it. This is a deliberately simpler stand-in for the full Outbox Pattern, which this ticket explicitly does not build (see scope boundary below).

## Agent implementation notes
- Key files to create (adjust root namespace/folder to match existing user-service layout from T017/T018):
  - `src/services/user-service/Events/IUserVerifiedEventPublisher.cs`
  - `src/services/user-service/Events/KafkaUserVerifiedEventPublisher.cs`
  - `src/services/user-service/Events/UserVerifiedEvent.cs` (DTO matching `user.verified.schema.json`)
  - Wire `IUserVerifiedEventPublisher` into DI in `Program.cs` (singleton — one long-lived `IProducer<>` per process is the standard Confluent.Kafka pattern)
  - Call the publisher from wherever the status-transition to `active` is finalized (the code from T017/T018/T009) — do not duplicate the "is this user now eligible for active" check; hook into the existing transition point
- Patterns to use: see `dotnet-minimal-api` skill for where cross-cutting service registration and endpoint wiring conventions live in this repo; see `kafka-outbox` skill for the event envelope shape (`event_id`, payload conventions) so this event is consistent with every other Kafka producer in the system, even though this ticket does not build a real outbox table.
- What NOT to do (common mistakes for this task type):
  - Do not call `producer.Produce(...)` synchronously and `await` or block on the delivery report inside the HTTP request path — that reintroduces the exact failure mode acceptance criterion #3 forbids.
  - Do not create a new `IProducer<>` per publish call — expensive, and defeats Kafka's internal batching/connection reuse.
  - Do not swallow the error silently — a failed publish must be logged with enough context (user_id, topic) to be debuggable, since there's no outbox table to later re-drive it from.
  - Do not gate the HTTP response on publish success/failure in any way (no partial 202, no warning field) — per SPECS.md, the HTTP request path is entirely unaffected by Kafka's availability.
- **Scope boundary — read before building:** SPECS.md's acceptance criteria for T020 ask only for fire-and-forget-with-retry, which is simpler than the full Outbox Pattern described in REQUIREMENTS.md's system design principles table. Implement ONLY the simpler fire-and-forget-with-retry approach here. Do NOT build an `outbox` table, an `OutboxRelay` background service, or consumer-side idempotency/`processed_events` handling in this ticket — that full machinery is explicitly Phase 14's job (T091–T096), and consumer-side idempotency is Discovery Service's job (Phase 4, T025). Building any of that now is over-engineering this ticket and will need to be reconciled/reworked when Phase 14 lands.
