# T021 — Spring Boot Project Setup

## Why this ticket exists
Discovery Service is the geospatial core of the platform — it will power the GPS radar and BLE offline fallback that let travelers find each other nearby. It's also the very first Java service in a codebase that has so far only had .NET services (User Service, API Gateway). Without this ticket, there is no runnable Spring Boot application at all: no way to connect to its own database, no way to talk to Redis for caching, no Flyway migration pipeline, and no consistent error-response shape matching the rest of the platform. Every later Discovery Service ticket (GPS query, BLE tokens, caching, circuit breaker) builds directly on top of what this ticket creates, and the four other Java services (Connection, Rating, Report, Admin) will copy this ticket's `application.yml` and virtual-threads setup as their own template.

## What to build
- Maven project `discovery-service` (Java 21, Spring Boot 3) with dependencies: Spring Web, Spring Data JPA, Spring Kafka, Spring Data Redis, Validation, Actuator, Lombok, MapStruct, Flyway, Resilience4j, plus the `shared-java-lib` module (from T003) for `ErrorResponse` / `GlobalExceptionHandler`
- `src/main/resources/application.yml` with `dev` and `prod` Spring profiles
- `DataSource` configuration reading `DISCOVERY_DB_HOST`, `DISCOVERY_DB_PORT`, `DISCOVERY_DB_NAME`, `DISCOVERY_DB_USERNAME`, `DISCOVERY_DB_PASSWORD` environment variables
- Redis configuration reading `REDIS_HOST` / `REDIS_PORT` (DB index 0, per T008's convention for Discovery Service caching)
- Flyway migration directory `classpath:db/migration` (empty baseline migration is fine — first real migration lands in a later ticket)
- `GET /actuator/health` endpoint returning `{ "status": "UP" }` when SQL Server and Redis are reachable
- `com.shareconnectsave.discovery.exception` package that pulls in `GlobalExceptionHandler` from `shared-java-lib` (no duplicate handler code)
- `spring.threads.virtual.enabled: true` in `application.yml`

- `spring.threads.virtual.enabled: true` in `application.yml` — Spring MVC's default
  thread-per-request model holds a Tomcat platform thread for a request's full
  duration, including idle time blocked on outbound HTTP (e.g. this service's
  WebClient call to User Service in T023/T027). Virtual threads (Java 21) unmount
  from the OS thread while blocked, so a burst of slow-but-live downstream calls
  can't exhaust the platform thread pool. This is every Java service's default
  going forward (Discovery, Connection, Rating, Report, Admin) — establish it here
  since T021 is the template the other four "Spring Boot Setup" tickets copy.
  Complements, not replaces, the Resilience4j circuit breaker (T027): virtual
  threads absorb a SLOW dependency, the circuit breaker absorbs a DOWN one.

## Patterns demonstrated
**Virtual Threads (Java 21 / Project Loom)** — frees the Tomcat platform thread while a request is blocked on outbound I/O (e.g. the future User Service call), instead of holding it for the request's entire duration; this is the "why" behind `spring.threads.virtual.enabled: true`.

**Circuit Breaker (system design principle, set up here / used in T027)** — Resilience4j is added as a dependency now so the later ticket that wraps calls to User Service has it available; virtual threads absorb a *slow* dependency, the circuit breaker absorbs a *down* one — the two are complementary, not redundant.

**Cache-Aside (set up here / used in later tickets)** — Spring Data Redis is wired to DB index 0 (per T008's convention) so a later ticket can load user profiles into Redis on cache miss and serve from cache afterward.

**Don't Repeat Yourself via shared library** — Discovery Service depends on `shared-java-lib` (T003) for `GlobalExceptionHandler` and `ErrorResponse` rather than writing its own error-translation code, keeping the HTTP error envelope (`code`, `message`, `traceId`) identical across all nine services.

**Single Responsibility (SOLID-S)** — this ticket only wires up infrastructure (DB, Redis, Kafka client libs, health check, error handling). No controllers, no domain logic — that is deliberately left to later tickets (T022+).

## Agent implementation notes
- Key files to create:
  - `/services/discovery-service/pom.xml` — Maven parent `spring-boot-starter-parent`, Java 21, dependency on `com.shareconnectsave:shared-java-lib` (from `/services/shared-java-lib`, see T003)
  - `/services/discovery-service/src/main/java/com/shareconnectsave/discovery/DiscoveryServiceApplication.java` — `@SpringBootApplication` entry point
  - `/services/discovery-service/src/main/resources/application.yml` — base config + `dev`/`prod` profile blocks (`---` document separators), all secrets/hosts via `${ENV_VAR}` placeholders per `java-spring-boot` skill's "always environment variables" convention
  - `/services/discovery-service/src/main/resources/db/migration/V1__baseline.sql` — empty or near-empty baseline migration so Flyway has something to run on first startup; do not invent domain tables here, that belongs to whichever ticket first needs a table
  - `/services/discovery-service/src/main/java/com/shareconnectsave/discovery/config/` — `DataSourceConfig` (if not using pure property-based config) and `RedisConfig`
  - `/services/discovery-service/src/main/java/com/shareconnectsave/discovery/exception/` — thin re-export/import of `shared-java-lib`'s `GlobalExceptionHandler`; do not copy its code into this package
- Follow the `java-spring-boot` skill's package-by-feature layout — even though this ticket has no feature packages yet, `config/` and `exception/` should already sit at the correct level (`com.shareconnectsave.discovery.*`) so later tickets slot `<feature>/` packages in alongside them without restructuring
- `application.yml` must read `DISCOVERY_DB_HOST`, `DISCOVERY_DB_PORT`, `DISCOVERY_DB_NAME`, `DISCOVERY_DB_USERNAME`, `DISCOVERY_DB_PASSWORD`, `REDIS_HOST`, `REDIS_PORT`, and `KAFKA_BROKERS` — no hardcoded connection strings, matching the skill's "always environment variables" rule and the user's own `process.env.*`-for-config preference
- Redis config: connect to logical DB index **0** (Discovery Service's reserved index per T008) — do not default to DB 0 implicitly, set it explicitly in `application.yml` so the convention is visible in code, not just in the T008 README
- `spring.threads.virtual.enabled: true` goes in the base (shared) section of `application.yml`, not inside a single profile — it must apply to both `dev` and `prod`
- Actuator: only expose `health` (and `info` if trivial) in `management.endpoints.web.exposure.include` — do not expose the full actuator surface (`*`) in `prod`
- What NOT to do:
  - Do not write any controller, entity, or repository for actual discovery logic — that starts in T022+. This ticket is infrastructure-only.
  - Do not add `shared-java-lib` business logic beyond what T003 already built — only declare the Maven dependency and wire the existing `GlobalExceptionHandler`
  - Do not use `RestTemplate` anywhere, even in placeholder code — the skill mandates `WebClient` for all future outbound HTTP
  - Do not use Lombok's `@Data` if you add any placeholder `@Entity` for the baseline migration test — use `@Getter @Builder @NoArgsConstructor @AllArgsConstructor` per the skill
  - Do not hardcode `localhost` or container IPs anywhere in `application.yml` — everything comes from environment variables, with sensible `dev`-profile defaults only where the skill's examples show a default (e.g. `port: ${REDIS_PORT:6379}`)
