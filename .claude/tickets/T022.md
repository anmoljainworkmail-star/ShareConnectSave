# T022 — Geospatial Schema + Scan Session

## Why this ticket exists
Right now Discovery Service has an empty database and no way to represent "a user is currently looking for a travel companion." Before any matching logic can exist (T023's nearby-search query), the platform needs a place to record that a scan started, what destination the user is heading toward, and — critically — a way to track that user's live GPS position without ever writing raw coordinates to a permanent database. This ticket builds that foundation: the `scan_sessions`/`ble_tokens` tables and JPA entities, plus the start/stop/location endpoints. The location-in-Redis-only design is not an implementation detail — it's a direct answer to the Location Privacy requirement (REQUIREMENTS.md): coordinates must be discarded the moment a scan ends, and a SQL row with a TTL can't guarantee that the way a Redis key with `EXPIRE 30` can.

## What to build
- Flyway migration in `discovery-service` creating `scan_sessions` and `ble_tokens` tables, matching the schema already defined in T006 (`scan_sessions`: id, user_id, destination_lat, destination_lng, destination_label, departure_time, started_at, ended_at, with `destination` as a SQL Server `geography` column; `ble_tokens`: id, user_id, token_hash, expires_at)
- JPA entities: `ScanSession`, `BleToken`
- `POST /scan/start` — reads `X-User-Id` header (set by API Gateway after JWT validation), body `{ destination_lat, destination_lng, destination_label, departure_time }`, creates a `scan_sessions` row, returns `{ session_id, mode: "gps" }`
- `POST /scan/stop` — closes the session (sets `ended_at`), deletes the corresponding Redis location key
- `PUT /scan/location` — body `{ lat, lng }`, writes to Redis key `scan:{session_id}:location` with a 30-second TTL — this endpoint must never touch the `scan_sessions` table or any other SQL table
- Repository interfaces: `ScanSessionRepository`, `BleTokenRepository` (Spring Data JPA)
- A `ScanSessionService` (or similarly named service class) that owns the start/stop/location business logic — controllers stay thin and delegate to it

## Technical specification
Flyway migration creates `scan_sessions` and `ble_tokens` tables (matching T006 schema).

JPA entities: `ScanSession`, `BleToken`.

`POST /scan/start` — authenticated (reads `X-User-Id` header)
Body: `{ "destination_lat", "destination_lng", "destination_label", "departure_time" }`
Creates a scan session, returns `{ "session_id", "mode": "gps" }`.

`POST /scan/stop` — closes the session, clears location from Redis.

During an active session, the client sends location updates:
`PUT /scan/location` — Body: `{ "lat", "lng" }` — stored in Redis only (key: `scan:{session_id}:location`, TTL 30s). Never written to SQL.

## Acceptance criteria
- [ ] `POST /scan/start` creates DB record, returns session_id
- [ ] `PUT /scan/location` writes to Redis, not SQL
- [ ] After `POST /scan/stop`, Redis key is deleted
- [ ] Location key TTL is 30 seconds (auto-expires if client goes silent)

## Patterns demonstrated
- **Single Responsibility (SOLID - S)** — `ScanSessionService` only owns scan lifecycle and Redis location bookkeeping; it does not compute matches or call other services (that's T023's job). Controllers only translate HTTP in/out and delegate.
- **Repository (GoF / DDD)** — `ScanSessionRepository` and `BleTokenRepository` hide the fact that scan sessions live in SQL Server behind a plain collection-like interface (`findById`, `save`), the same shape as `IUserRepository` in User Service.
- **Cache-Aside (partial precursor)** — this ticket only writes to Redis; it doesn't yet read from Redis to serve a query (that lands in T023). But the key design (`scan:{session_id}:location`, short TTL) is what T023's read side depends on, so getting the write-side contract right here matters.
- **Ephemeral storage as a privacy control** — plain English: Redis's `EXPIRE` command tells Redis "delete this key automatically after N seconds, no one has to remember to clean it up." Real-world analogy: it's like a whiteboard note that fades by itself after 30 seconds, instead of a filing cabinet entry someone has to remember to shred. Why it matters here: the requirement is that raw coordinates are *never* stored permanently. A SQL row requires a background job or manual cleanup to enforce "never permanent" — that's a promise that can be broken by a bug. A Redis key with a TTL enforces it structurally — even if the app crashes right after `PUT /scan/location`, the coordinate disappears on its own 30 seconds later. This is why the spec is explicit: location updates go to Redis only, never to SQL, even in a table with a TTL cleanup job.

- Use the `java-spring-boot` skill for Spring Data JPA entity/repository conventions, Spring Data Redis `RedisTemplate`/`StringRedisTemplate` usage for the TTL-bound key, and where controller/service wiring conventions live in this repo (mirrors the thin-controller rule already applied in User Service).
- `destination_lat`/`destination_lng` arrive from the client as plain doubles in the JSON body; the migration should still store the destination as a SQL Server `geography` point column (per T006's acceptance criterion), so map the two incoming doubles to a `POINT` value in the migration/entity mapping rather than adding separate flat lat/lng columns as the source of truth.
- Session id: use a UUID (or the DB-generated identity, whichever this codebase's existing entities use — check `ScanSessionRepository`'s sibling entities from T006/earlier services for the established id convention) and return it as `session_id` in the `/scan/start` response — do not leak the internal JPA `@Id` field name/casing into the JSON contract if it differs (`session_id` is snake_case per the spec, matching the rest of this API's JSON convention).
- Redis key construction (`scan:{session_id}:location`) should live in one place (e.g. a small constant/helper in `ScanSessionService`), not string-concatenated ad hoc in multiple methods — T023 will need to construct the same key shape to read it back, so keep this easy to reuse/import from.
- What NOT to do (common mistakes for this task type):
  - Do not write `lat`/`lng` from `PUT /scan/location` to any SQL table, not even as a "just in case" audit column — this directly violates the Location Privacy requirement and the ticket's explicit acceptance criterion.
  - Do not skip setting a TTL on the Redis `SET` call (e.g. using a plain `SET` instead of `SETEX`/`SET ... EX 30`) — without the TTL, a client that goes silent (app killed, network lost) leaves stale location data live indefinitely.
  - Do not forget to actually delete the Redis key in `/scan/stop` — relying solely on the 30-second TTL to expire it is not sufficient; the acceptance criterion requires the key gone immediately after stop, not up to 30 seconds later.
  - Do not build the GPS matching/nearby query, BLE token issuance/rotation logic, or the `user.verified` Kafka consumer in this ticket — those are T023 (and later tickets) and are explicitly out of scope here; this ticket is schema + session lifecycle only.
  - Do not call User Service, apply trust-score/gender filters, or touch `status` fields on the user profile from here — the REQUIREMENTS.md note about `PATCH /users/me` status flips is User Service's own concern triggered from the frontend, not something this ticket's endpoints call directly.
