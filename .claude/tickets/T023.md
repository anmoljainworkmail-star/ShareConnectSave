# T023 — GPS Discovery Query

## Why this ticket exists

Users need to find each other in real time. Without this endpoint, the entire discovery system sits idle. The GPS query is the highest-latency-sensitive path in the platform (P95 < 500ms target), so every part of it must be cached and fault-tolerant. If the User Service goes down, the query must degrade gracefully by falling back to cached profile data instead of failing completely. This ticket implements server-side filtering (distance, route overlap, departure time, block lists, gender) all in one atomic query so the frontend doesn't need to do work the backend can do faster and more securely.

## What to build

After this ticket, the Discovery Service will have:

- **Endpoint:** `GET /scan/nearby` in a `ScanController` that accepts optional filter parameters
- **Service layer:** `ScanQueryService` (or `NearbyUsersService`) implementing the 5-step query logic:
  1. Read caller's current location from Redis
  2. Fetch active scan sessions list from Redis
  3. Apply all server-side filter predicates (distance, route overlap, departure time, block list, gender)
  4. Fetch matching user profiles from User Service with Resilience4j circuit breaker
  5. Cache the final result set in Redis with 10 s TTL
- **Circuit breaker configuration:** `UserServiceClient` (or similar name) wrapping HTTP calls to User Service, with fallback to return cached profile data
- **Redis keys:**
  - `scan:{session_id}:location` — caller's current GPS coordinates
  - `scan:active_sessions` — Redis Set of all active session IDs
  - `scan:{session_id}:nearby` — cached query result (10 s TTL)
  - `user:blocklist:{user_id}` — cached block list (5 min TTL)
- **DTOs:** `UserCardResponse` (or minimal user profile representation) returned in array
- **Filter implementations:**
  - Distance calculation (haversine formula, comparing to configurable radius; default 1 km)
  - Route overlap via bearing similarity between destinations
  - Departure time window (±30 min)
  - Bidirectional block list check
  - Women-only mode filter (when caller gender = female and preference enabled, exclude non-female candidates)

## Technical specification

`GET /scan/nearby` — returns users within the active session's filter criteria.

Query logic (all server-side):
1. Read caller's current location from Redis (`scan:{session_id}:location`).
2. Read all active scan sessions from Redis (key: `scan:active_sessions` — a Redis Set of session IDs populated when sessions start/stop).
3. For each candidate session, apply filters:
   - Distance ≤ radius (default 1 km, configurable per session)
   - Route overlap ≥ threshold (compute bearing similarity between destinations)
   - Departure time within ±30 min
   - Not in caller's block list (fetched from User Service via WebClient, cached in Redis DB 0, TTL 5 min)
   - Candidate status = `looking`
   - Women-only mode: if caller has `X-User-Gender: female` and has women-only enabled, filter to `female` only
4. For each match: call User Service `GET /users/:id` (WebClient, Resilience4j circuit breaker, fallback: return cached profile or omit).
5. Cache full result set in Redis (key: `scan:{session_id}:nearby`, TTL 10s).

Return: array of user cards.

## Acceptance criteria

- [ ] Users outside radius are excluded
- [ ] Block list filtering works (bidirectional)
- [ ] Women-only filter excludes non-female users when enabled
- [ ] Result cached in Redis for 10 s
- [ ] User Service circuit breaker: if open, return cached profile data, log warning

## Patterns demonstrated

- **Cache-Aside Pattern** — result set and block list are loaded on miss and stored for 10 s / 5 min TTL; subsequent queries within the window hit Redis instead of recomputing, cutting latency.
- **Circuit Breaker Pattern** — wraps all User Service calls with Resilience4j; when the service is unhealthy, returns cached data or omits the match rather than failing the entire query.
- **Dependency Inversion (D in SOLID)** — `ScanQueryService` depends on `IUserServiceClient` interface, not a concrete WebClient; swapping implementations (real vs mock, cached vs live) requires no changes to query logic.
- **Single Responsibility (S in SOLID)** — `ScanQueryService` implements filtering logic only; location reads, Redis caching, and User Service calls are delegated to injected dependencies, keeping each class focused.
- **Geospatial Query Pattern** — demonstrates how to apply distance and bearing calculations server-side instead of shipping raw data and filtering in the frontend.

### Implementation guidance

1. **Redis reads for current location and active sessions:**
   - Use `RedisTemplate<String, String>` for location (store as "lat,lng" or similar simple format).
   - Use `RedisTemplate<String, Set<String>>` for `scan:active_sessions` to fetch all candidate session IDs.
   - Refer to `java-spring-boot` skill's Redis section for syntax.

2. **Filter implementation order (as written in spec):**
   - Distance first (cheapest check, excludes most candidates).
   - Route overlap second (bearing calculation).
   - Departure time window third.
   - Block list fourth (requires Redis lookup; cache it with 5 min TTL in Redis DB 0).
   - Status check fifth (should already be in candidate data).
   - Women-only last (check caller's `X-User-Gender` header and session preference).

3. **User Service circuit breaker (Resilience4j):**
   - Inject `@Bean CircuitBreaker circuitBreaker()` in a configuration class.
   - Wrap `WebClient` calls in `circuitBreaker.executeSupplier(() -> ...)` or use annotations (`@CircuitBreaker`).
   - On circuit open: log warning, return cached user profile if available, or skip that match.
   - Configuration: reasonable defaults are `failureThreshold: 50%, slowCallDurationThreshold: 2000ms, waitDuration: 30s`.
   - Refer to `java-spring-boot` skill's Resilience4j section.

4. **Bidirectional block list check:**
   - When evaluating a candidate, check:
     - Is candidate in caller's block list? (caller → candidate)
     - Is caller in candidate's block list? (candidate → caller)
   - Both must be false for the candidate to pass.
   - Cache block lists separately per user, keyed `user:blocklist:{user_id}`, TTL 5 min.

5. **Women-only mode filter:**
   - Read caller's gender from `X-User-Gender` header (injected by API Gateway, trusted).
   - Read session's women-only preference from Redis (e.g., `scan:{session_id}:women_only` boolean).
   - If both are true, apply predicate `candidate.gender == "female"` before returning.
   - Gender is never exposed in the response — only used as a filter predicate server-side.

6. **Caching the result:**
   - After all filters and User Service calls complete, serialize the `List<UserCardResponse>` to JSON.
   - Store in Redis key `scan:{session_id}:nearby` with TTL 10 seconds.
   - Next call within 10 s returns cached data.

### What NOT to do

- **Do not** make User Service calls synchronously without wrapping in circuit breaker.
- **Do not** hard-code filter thresholds; read them from application properties (e.g., `discovery.radius.km`, `discovery.route-overlap-threshold`).
- **Do not** expose gender, email, or other PII in `UserCardResponse`; return only display name, photo, trust score, and status.
- **Do not** skip the bidirectional block list check; checking only caller → candidate misses the other direction.
- **Do not** cache results longer than 10 s; stale data means users appear/disappear incorrectly.
- **Do not** allow missing location data to crash the query; log a warning and skip that session.
- **Do not** compute distance and bearing in the frontend; all filters are applied server-side for performance and security.
