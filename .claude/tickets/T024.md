# T024 — BLE Token Generation

## Why this ticket exists

When a user's internet connection drops during discovery, the app falls back to Bluetooth (BLE) to detect nearby users. Without this ticket, there's no way to generate or resolve those rotating tokens — users see "nearby devices detected" but can't identify who they are when connectivity returns. This ticket makes the handoff possible: device broadcasts a short-lived token offline, then trades it for the real profile once back online.

## What to build

- **Endpoint** `POST /scan/ble/token` — generates a new rotating BLE token for the current user, returns the raw token to broadcast over BLE
- **Endpoint** `POST /scan/ble/resolve` — accepts an array of raw tokens collected offline, returns the user profiles for valid (non-expired) tokens
- **Database table** `ble_tokens` — stores the HMAC-SHA256 hash of each token with a 5-minute expiry; raw token never stored
- **Java classes:**
  - `BleTokenController` — routes the two endpoints
  - `BleTokenService` — orchestrates generation (random bytes + HMAC hash), resolution (lookup by hash, filter expired), and cleanup
  - `BleToken` entity — JPA model for the `ble_tokens` table
  - `BleTokenRepository` — JPA repository for persistence
- **Cleanup task** — deletes expired tokens from the database (scheduled job or TTL mechanism)

## Technical specification

`POST /scan/ble/token` — generates a rotating BLE token for the current user.

1. Generate a random 16-byte token, store its HMAC-SHA256 hash in `ble_tokens` table with `expires_at = now + 5 minutes`.
2. Return the raw token (client broadcasts this over BLE).
3. Old tokens for this user (expired) are deleted.

`POST /scan/ble/resolve` — resolves a detected BLE token to a user profile (called when back online).
Body: `{ "tokens": ["<raw_token_1>", ...] }`
Returns: array of user card objects for resolved users (same shape as GPS nearby results).

## Acceptance criteria

- [ ] Token hash stored, raw token returned to client
- [ ] Token expires after 5 minutes (DB record AND functional — expired tokens not resolvable)
- [ ] Resolve endpoint returns profile data for valid tokens only
- [ ] Expired or unknown tokens silently omitted from resolve response

## Patterns demonstrated

- **HMAC-SHA256 Hashing for Security:** Token identity is never stored in plaintext on the server. Only the hash is persisted, mirroring the OTP hashing approach in User Service. This prevents server compromise from exposing user identity via a stolen token table.
- **Time-Based Token Rotation:** Tokens expire after exactly 5 minutes, reducing the window for token interception or replay attacks in offline mode.
- **Idempotency & Silent Failure:** The resolve endpoint silently omits expired or unknown tokens instead of raising errors. This teaches how distributed systems handle stale data gracefully — the client doesn't need to know why a token failed, just which ones succeeded.
- **Database per Service:** Discovery Service owns the `ble_tokens` table exclusively. No other service reads or writes tokens; they own their own data islands.

## Agent implementation notes

- **Token generation:** Generate 16 cryptographically random bytes using Java's `SecureRandom` or `UUID.randomUUID()` converted to bytes. Compute HMAC-SHA256 of the raw bytes. Store only the hash in the database; return the raw token to the client.
  
- **Expiry implementation:** Set `expires_at` to `Instant.now().plus(Duration.ofMinutes(5))`. Functional expiry is critical — the resolve endpoint must check `WHERE expires_at > NOW()` in its query; a record that exists but is expired must be filtered out, not returned.

- **Cleanup:** Use Spring's `@Scheduled` annotation with `@EnableScheduling` on a config class. Run every 1–2 minutes to delete rows where `expires_at < NOW()`. This prevents the table from growing unbounded.

- **Resolve endpoint:** Accept an array of raw tokens. For each:
  1. Hash it with the same HMAC-SHA256 key
  2. Query `ble_tokens` for a matching hash AND `expires_at > NOW()`
  3. Load the associated user profile (name, photo, destination, distance—same fields as GPS nearby results)
  4. Include only successful matches in the response; silently drop expired or unknown tokens

- **User authentication:** The `/token` endpoint requires an authenticated user (extract from JWT in the request context, same as GPS scan). The spec is silent on auth for `/resolve` — per the project's API Gateway pattern (CLAUDE.md: YARP validates JWT and injects identity headers for every request; no service re-implements this itself), assume `/resolve` goes through the same gateway JWT validation as every other endpoint unless the Tech Lead says otherwise during ticket review. Do not invent a no-auth exception for this endpoint.

- **Kafka/Outbox note:** This ticket does not publish or consume Kafka events. BLE tokens are purely a transient mechanism for offline discovery and have no event-driven dependencies. The `kafka-outbox` skill is listed because the Discovery Service as a whole uses Kafka (T025), but this specific ticket's endpoints do not trigger any Kafka publishes. Do not fabricate an outbox write.

  - `src/main/java/com/shareconnectsave/discovery/repository/BleTokenRepository.java`
  - `src/main/java/com/shareconnectsave/discovery/task/BleTokenCleanupTask.java`

- **What NOT to do:**
  - Do not store the raw token anywhere in the database.
  - Do not add a token history or audit log for BLE tokens (they are temporary by design).
  - Do not invent an auth exemption for the resolve endpoint that isn't in the spec — follow the standard gateway JWT validation unless the Tech Lead explicitly says otherwise.
  - Do not force resolve to return an error for unknown tokens; silently omit them.
