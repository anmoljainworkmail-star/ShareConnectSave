# T024 — BLE Token Generation (v2)

## Why this ticket exists

When a user's internet connection drops during discovery, the app falls back to Bluetooth
(BLE) to detect nearby users. GPS discovery only ever answers "who is near me *right now*,
at the exact moment I query it" — it has no memory. If two travelers spend a
connectivity-dead stretch (a subway tunnel, an elevator, a parking garage) near each other,
GPS discovery never runs during that window, and by the time signal returns, one or both
may already be gone. BLE converts that fleeting physical encounter into a durable,
resolvable record: log the rotating tokens heard over Bluetooth during the gap, then
exchange them for real candidate profiles once connectivity returns — feeding the exact
same "send a connection request" flow a GPS match would. BLE adds no functionality while
offline beyond this; the rest of the app stays fully non-functional without connectivity,
same as before. (Full rationale documented in REQUIREMENTS.md §4.)

## Why this ticket is being reworked (v1 → v2)

The initial implementation (v1, shipped and reviewed) had the server mint each 5-minute
token via `POST /scan/ble/token` — the client had to call the server to get a fresh
broadcastable value roughly every 5 minutes. This breaks exactly when the feature is
supposed to help most: if a device goes offline for longer than 5 minutes, its current
token expires mid-outage with **no way to refresh it while offline**, since refreshing
requires the same connectivity that's missing. A device that started scanning already
offline never had a token to broadcast in the first place. Both cases silently defeat the
whole point of an offline fallback.

v2 fixes this the way Apple/Google's Bluetooth Exposure Notification system solved the
identical problem: give the client a secret **seed** once, while it still has signal, and
let it derive a fresh rotating broadcast value from that seed **entirely offline**, on its
own clock, indefinitely — no server round-trip needed to keep rotating. The server only
needs to be involved again at *resolve* time.

## What to build

- **Endpoint** `POST /scan/ble/seed` — replaces `/scan/ble/token`. Registers a fresh random
  seed for the current user (client-generated or server-generated — either is
  cryptographically fine; server-generated is simpler to reason about and is the default
  here). Returns the raw seed once. Called once per scan session (or on seed expiry), not
  every 5 minutes.
- **Endpoint** `POST /scan/ble/resolve` — same external contract as v1 (`{"tokens": [...]}`
  in, array of user cards out), but the resolution mechanism changes completely (see below).
- **Database table** `ble_seeds` (new Flyway migration, e.g. `V002__ble_seeds.sql` — do
  **not** edit `V001__discovery_service_initial_schema.sql`; per this project's own
  convention, a shipped migration is checksummed and never edited after the fact). Drop the
  now-obsolete `ble_tokens` table in this same migration — nothing in it is worth
  preserving, tokens were already designed to be ephemeral.
  - Columns: `id`, `user_id`, `seed` (see Security note below — **not** hashed), `created_at`,
    `expires_at` (the seed's own lifetime — tied to a realistic scan-session length, not 5
    minutes; e.g. default several hours, configurable).
- **Java classes** (package-by-feature, mirrors existing `ble/` package):
  - `BleTokenController` — **Tech Lead decision: no separate `BleSeedController`.** Add a
    third route, `POST /scan/ble/seed`, directly onto the existing `BleTokenController`
    alongside `/token` (now retired/replaced by `/seed`) and `/resolve`. Rationale: both
    endpoints are steps in the same BLE discovery feature and this controller already owns
    that surface — no need to split it for one more route.
  - `BleTokenService` / `BleTokenServiceImpl` — gains an `issueSeed(Long userId)` method
    (replaces `issueToken`); `resolveTokens` is rewritten per the spec below.
  - `BleSeed` entity (new), `BleSeedRepository` (new) — replace `BleToken`/`BleTokenRepository`.

## Technical specification

### `POST /scan/ble/seed`

1. Generate 32 random bytes (`SecureRandom`) as the seed.
2. Persist it against the caller's `user_id` in `ble_seeds`, with `expires_at = now +
   ble.seed.ttl-minutes` (config, no hardcoded literal — see `ble.seed.ttl-minutes` below).
   Delete this same user's previously-expired seeds first (same "old tokens for this user
   are deleted" spirit as v1's per-user cleanup).
3. Return the raw seed to the client once. The client is responsible for deriving all
   future broadcast values locally from this point on — it should never need to call this
   endpoint again until the seed's own (long) lifetime runs out or a new scan session starts.

### Client-side derivation (out of scope for this backend ticket — documented here so T065
consumes the identical algorithm the server verifies against)

```
window = floor(unixEpochSeconds / ble.window.seconds)      // default window: 300s (5 min)
broadcastValue = HMAC-SHA256(seed, window)                  // truncate to fit a BLE
                                                             // advertisement payload —
                                                             // classic BLE advertising caps
                                                             // at 31 bytes total, so the
                                                             // full 32-byte HMAC output
                                                             // will not fit alongside the
                                                             // app's Service UUID; truncate
                                                             // to the first 16 bytes
                                                             // (128 bits — still
                                                             // astronomically collision-safe
                                                             // for this use case)
```

### `POST /scan/ble/resolve`

The server can no longer do a single indexed hash lookup (v1's approach) — it never sees a
broadcast value before this call, so nothing was pre-indexed against it. Instead:

1. Fetch the set of **candidate user ids** to check against — scoped to
   `scan:active_sessions` (the same Redis Set `ScanQueryServiceImpl`/`ScanCacheService`
   already use for GPS discovery), not every user who has ever registered a seed. This is a
   deliberate cost-bounding decision: without it, resolve cost grows with total registered
   users, not just people plausibly nearby right now.
2. Batch-fetch `ble_seeds` rows for those candidate user ids in one query (mirrors
   `ScanSessionRepository.findAllById`'s batching in `ScanQueryServiceImpl` — no
   per-candidate N+1 query).
3. For each submitted raw token, and for each candidate's seed, compute
   `HMAC-SHA256(seed, currentWindow)` **and** `HMAC-SHA256(seed, currentWindow - 1)`
   (tolerate a value generated just before a window boundary — clock skew / network delay
   between broadcast and resolve), truncated the same way the client truncates. Compare
   against the submitted token.
4. On a match, that candidate's `user_id` is resolved. Apply the same bidirectional
   block-list check already implemented in v1 (`isBlocked`, mirrors
   `ScanQueryServiceImpl`), then the same `UserServiceClient.getUserCard` circuit-breaker-
   guarded lookup, before adding a card to the results.
5. No match against any candidate/window → silently omitted from the response, same
   idempotent silent-failure behavior as v1 and GPS discovery's own block-list omission.

### New config (Options pattern, `BleProperties` — extend/replace v1's fields)

```yaml
ble:
  seed:
    ttl-minutes: ${BLE_SEED_TTL_MINUTES:240}   # long-lived — tied to a realistic scan
                                                 # session, NOT the rotation cadence
  window:
    seconds: ${BLE_WINDOW_SECONDS:300}          # rotation cadence — replaces v1's
                                                 # token ttl-minutes concept
  range:
    meters: ${BLE_RANGE_METERS:30}               # unchanged from v1
```
`ble.token.hmac-secret` (v1) stays conceptually — still needed, but now it signs/derives
from the seed rather than hashing a server-minted value; consider whether the same env var
name still makes sense or should be renamed for clarity (Tech Lead's call).

## Acceptance criteria

- [ ] Seed registered once per scan session via `/scan/ble/seed` — never a raw per-broadcast
      value round-tripped through the server
- [ ] Client can derive valid rotating broadcast values entirely offline for the seed's
      whole lifetime — no server call required to keep rotating (verify by confirming the
      resolve-side derivation is a pure function of `(seed, window)`, independently
      reproducible without a network call)
- [ ] Resolve endpoint correctly maps a submitted broadcast value back to the right user,
      scoped only to currently-active scan-session users
- [ ] Blocked/blocking candidates still silently omitted (carried over from v1's own fix)
- [ ] Unknown/non-matching values silently omitted — same idempotent silent-failure
      behavior as v1
- [ ] The seed itself is never broadcast, logged, or exposed to any device other than its
      owner's one-time registration response

## Patterns demonstrated

- **Rolling identifiers derived from a locally-held secret** (the actual concept behind
  Apple/Google's Exposure Notification system) — rotation without a server round-trip.
- **Cost-bounded verification via scoping, not indexing** — resolve trades an O(1) hash
  lookup for an O(active candidates) recomputation, deliberately bounded to
  `scan:active_sessions`, mirroring the same scoping principle GPS discovery already uses.
- **Idempotency & Silent Failure** (carried over from v1) — unknown, expired, or blocked
  candidates are all indistinguishable failure modes to the caller, by design.
- **Migration-never-edited convention** — the new `ble_seeds` table is a new Flyway file,
  not a rewrite of `V001`.

## Security note — read before approving

v1 stored **only a hash** of each ephemeral token — irreversible, worthless if
`ble_tokens` were ever read by an attacker. v2 requires the server to **retain the actual
seed** (not a hash of it) for the seed's whole lifetime, because resolving requires
recomputing `HMAC-SHA256(seed, window)` — which is impossible from a hash alone. This is a
materially larger blast radius if `ble_seeds` is ever compromised: an attacker with read
access gets every affected user's actual seed, and could derive that user's past and
future broadcast values for as long as the seed remains valid. This is an inherent
trade-off of the rolling-identifier approach (Apple/Google's system has the equivalent
exposure for a day's Temporary Exposure Key), not an implementation bug — but it's worth
your explicit sign-off before this ships, and worth considering whether `ble_seeds.seed`
should be encrypted at rest (application-level, not just relying on DB-level access
controls already in place for every other table).

## What NOT to do

- Do not store derived broadcast values in the database the way v1 stored token hashes —
  v2 has nothing to index in advance, since derived values are never sent to the server
  until resolve time.
- Do not let the seed leak into logs, error responses, or any endpoint other than the
  one-time `/scan/ble/seed` registration response.
- Do not silently widen resolve's candidate scope beyond active scan sessions without
  Tech Lead sign-off (cost-control decision, Open Question 1).
- Do not add a token/seed history or audit log (same "temporary by design" rule as v1).
