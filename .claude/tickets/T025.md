# T025 — Kafka Consumer: user.verified + trust.score.updated

## Why this ticket exists

Discovery scans must only show verified, active users. Without these two consumers, the discovery pool never reacts when users complete onboarding or when trust scores change. A newly verified user would not appear in nearby scans, and suspended users would remain visible indefinitely — breaking both the discovery experience and the safety guardrails that keep low-trust users from reaching others.

## What to build

Two `@KafkaListener` consumer methods in Discovery Service that maintain the Redis cache of eligible discoverers:

- **UserVerifiedEventListener**: Consumes `user.verified` topic. On receipt, add the user to Redis Set `scan:eligible_users` (the gate for discovery eligibility).
- **TrustScoreUpdatedEventListener**: Consumes `trust.score.updated` topic. On receipt, update cached trust metadata. If `request_limit = 0` (suspension signal), remove the user from `scan:eligible_users` immediately.

Both listeners:
- Belong to consumer group `discovery-service`
- Validate message receipt against `ProcessedEventsRepository` (idempotency check) before processing.
- Commit offsets only after successful processing.

## Technical specification

Two `@KafkaListener` consumers:

1. `user.verified` → add user to Redis Set `scan:eligible_users`. This is the gate — only verified users appear in discovery.
2. `trust.score.updated` → update cached trust data for the user. If `request_limit = 0`, remove from `scan:eligible_users` (suspended users cannot appear in scan).

Use consumer group: `discovery-service`.

## Acceptance criteria

- [ ] New verified user → appears in discovery within 1 Kafka poll cycle
- [ ] Trust suspended user → removed from `scan:eligible_users`
- [ ] Consumer group offset committed after processing

## Patterns demonstrated

- **Event-Driven Architecture**: Discovery Service reacts to user lifecycle events published by other services (User Service, Rating Service) without direct coupling or polling. Each event is a past-tense fact, not a command.
- **Idempotency**: Kafka guarantees at-least-once delivery. Maintains `processed_events` table keyed by `event_id` to safely skip duplicate messages. Ensures processing the same event twice produces the same result as processing it once.
- **Cache-Aside Pattern**: Redis Set `scan:eligible_users` acts as the working cache of who can be discovered. On first verification or trust update, the cache is kept in sync with source-of-truth (User Service, Rating Service), and subsequent queries hit Redis without round-trips.
- **Observer Pattern (via Kafka)**: Rating Service publishes suspension signals; Discovery Service subscribes and acts. Neither service knows about the other's internals — loose coupling, high cohesion.

## Agent implementation notes

**Key files to create:**
- `src/main/java/com/shareconnectsave/discovery/kafka/listener/UserVerifiedEventListener.java` — @KafkaListener for `user.verified`
- `src/main/java/com/shareconnectsave/discovery/kafka/listener/TrustScoreUpdatedEventListener.java` — @KafkaListener for `trust.score.updated`
- `src/main/java/com/shareconnectsave/discovery/kafka/event/UserVerifiedEvent.java` — POJO for user.verified deserialization
- `src/main/java/com/shareconnectsave/discovery/kafka/event/TrustScoreUpdatedEvent.java` — POJO for trust.score.updated deserialization

**Implementation guidance:**
- Follow the **java-spring-boot** skill for consumer setup: use `@KafkaListener(topics = "...", groupId = "discovery-service")` annotations.
- Follow the **kafka-outbox** skill section on idempotency: query `ProcessedEventsRepository.findByEventId(eventId)` before processing. If it exists, log and skip. If not, process, then insert a new row (event_id, processed_at).
- Deserialize message payloads as JSON using Spring's Jackson integration. Field names are `snake_case` per schema (e.g., `user_id`, `trust_score`, `request_limit`).
- For `user.verified`: add user to Redis Set `scan:eligible_users` with key format `scan:eligible_users` (no user-id suffix).
- For `trust.score.updated`: update cached trust metadata (e.g., a Redis Hash or a `UserTrustCache` class in Redis), then check `request_limit`. If it is 0, remove the user from `scan:eligible_users`.
- Ensure manual offset commit only after successful processing (Spring default `AckMode.BATCH` is acceptable if processing is transactional).
- Handle JSON deserialization errors gracefully — log and skip (not a recoverable failure).

**What NOT to do:**
- Do not write to SQL Service databases directly from the listener (Discovery Service's database is not the primary store for user verification or trust state).
- Do not call User Service or Rating Service synchronously from the consumer — that defeats event-driven design.
- Do not forget the idempotency check. At-least-once delivery means the same event can arrive twice.
- Do not omit error handling for malformed messages. Log and continue; don't crash the consumer.

## Known follow-ups

1. **Schema description mismatch**: `contracts/kafka/user.verified.schema.json` currently describes this event as "Published by User Service when a user completes identity verification," but the actual trigger is **onboarding completion** (`User.IsOnboardingComplete` flipping to true in `OtpService.VerifyOtpAsync`), not the optional identity-badge verification step. Before merging this ticket, correct the schema's `description` field to reflect the real trigger.

2. **user_id type clarification**: The schema declares `user_id` as `"type": "string", "format": "uuid"`, but the .NET User Service's `User.Id` is actually a `long` (BIGINT IDENTITY). The producer serializes it to a string for Kafka, but that string is never a UUID. Deserialize `user_id` as a plain string in your event POJOs (not as a UUID type), to match the actual data coming from User Service.

3. **Docker Compose bootstrap listener fix**: `docker-compose.override.yml` currently specifies `${KAFKA_BOOTSTRAP:-kafka:9092}` as the default for discovery-service, but this is the external listener. For a container-to-container Kafka client, use the internal listener `kafka:29092` (as already fixed for user-service in `docker-compose.yml`). Correct the default in `docker-compose.override.yml` for discovery-service before wiring up this consumer.
