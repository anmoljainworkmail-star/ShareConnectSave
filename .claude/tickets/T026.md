# T026 — Redis Caching Layer

## Why this ticket exists

Without a centralized cache service, every controller and service that needs to cache data—location scans, nearby-user results, user profiles, blocklists—will write its own Redis calls. This creates duplicate logic, inconsistent TTL expiration, and makes it impossible to enforce the privacy rule that location coordinates never persist permanently. This ticket centralizes all Redis interactions so every cache read and write follows the same rules: short TTLs for location data (30s, 10s), consistent fetch-on-miss behavior for profiles, and a single source of truth for which users are eligible to see each other.

## What to build

- `DiscoveryCacheService` class (Spring component) that wraps all Redis interactions
  - Methods: `cacheSessionLocation()`, `getSessionLocation()`, `cacheNearbyResults()`, `getNearbyResults()`, `cacheProfile()`, `getProfile()`, `cacheBlocklist()`, `getBlocklist()`, `addActiveSession()`, `removeActiveSession()`, `getActiveSessions()`, `addEligibleUser()`, `removeEligibleUser()`, `getEligibleUsers()`
  - All methods handle cache misses: if profile/blocklist not found in Redis, fetch from upstream (User Service via WebClient), store result with TTL, return it
- Configuration file (application.yml) with TTL values as configurable properties: `cache.ttls.session-location`, `cache.ttls.nearby-results`, `cache.ttls.profile`, `cache.ttls.blocklist`
- Integration: DiscoveryCacheService becomes the single dependency for all Controllers and Services that need Redis (T022, T023, T025 code paths refactor to use it instead of raw RedisTemplate calls if they landed first)

## Acceptance criteria

- [ ] All cache reads/writes go through `DiscoveryCacheService`, not raw `RedisTemplate` calls in controllers
- [ ] Cache miss on profile → WebClient fetch, store result
- [ ] All TTLs configurable via `application.yml`

## Patterns demonstrated

- **Cache-Aside:** The canonical example for this project. The service checks Redis first; on miss, fetches from upstream (User Service for profiles/blocklists), stores the result with a TTL, then returns it. This isolates cache-miss logic from business logic and ensures consistency across all downstream consumers.
- **Dependency Inversion (SOLID D):** Controllers and other services depend on `DiscoveryCacheService` (abstraction), not `RedisTemplate` directly (concrete class). Enables testing with in-memory stubs and prevents cache logic from leaking into business logic.
- **Single Responsibility (SOLID S):** `DiscoveryCacheService` owns all Redis interactions; no business logic, no database queries—only cache orchestration.

## Agent implementation notes

**Key files to create:**
- `discovery-service/src/main/java/com/shareconnectsave/discovery/cache/DiscoveryCacheService.java` — Spring component wrapping RedisTemplate
- `discovery-service/src/main/resources/application.yml` — Add `cache.ttls.*` configuration properties (or extend existing yml if present)

**Guidance:**
- Use Spring's `RedisTemplate<String, Object>` and Jackson for JSON serialization/deserialization
- Refer to `java-spring-boot` skill for Spring patterns and configuration details
- Treat the managed Sets (`scan:active_sessions`, `scan:eligible_users`) as membership lists—use Redis SADD/SREM/SMEMBERS; no TTL on these
- Cache miss for profiles/blocklists: if `getProfile(userId)` finds no key in Redis, call upstream User Service via WebClient, store the result with the configured TTL, return it. Wrap the WebClient call in try/catch; on upstream failure, return empty/null (don't cache failures)
- **Important:** If T022, T023, or T025 have already been implemented with inline `RedisTemplate` calls in their controllers or services, refactor those callsites to inject and use `DiscoveryCacheService` instead. This is a consolidation ticket—do not leave duplicate Redis logic in place.
- Do NOT expose RedisTemplate directly to controllers—all external callers must go through DiscoveryCacheService methods only.
