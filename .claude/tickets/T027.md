# T027 — Resilience4j Circuit Breaker (User Service calls)

## Why this ticket exists
Discovery queries need to call User Service to get up-to-date profile info for the people showing up in someone's radar. Right now, if User Service becomes slow or goes down, every discovery request that touches it would sit there waiting on a timeout — one at a time, for every user scanning nearby. That drags down the whole discovery experience for everyone, not just the person whose data is unavailable, and it directly breaks the platform's promise of a fast, responsive radar screen (discovery results must come back in under 500ms for 95% of requests, even under load). This ticket makes the Discovery Service stop hammering a failing User Service and instead immediately fall back to something useful — a cached profile, or a clearly-marked placeholder — so the radar screen keeps working even when a dependency is having a bad day.

## What to build
- A named Resilience4j circuit breaker instance called `userService`, wrapping every `WebClient` call from Discovery Service to User Service.
- Circuit breaker configuration block in `application.yml` under the `userService` instance:
  - `slidingWindowSize: 10`
  - `failureRateThreshold: 50`
  - `waitDurationInOpenState: 30s`
- A fallback method invoked whenever the circuit is open or a call fails:
  - First, attempt to serve the cached profile from Redis (the cache populated by T026's Redis caching layer) if one exists for that user id.
  - If no cached profile exists, return a minimal placeholder object: `{ "id": "<id>", "name": "Unknown", "unavailable": true }`.
- Actuator health integration so the current state of the `userService` circuit breaker (CLOSED / OPEN / HALF_OPEN) is visible on `/actuator/health`.

## Technical specification
Wrap all `WebClient` calls to User Service with a Resilience4j circuit breaker named `userService`.

Config in `application.yml`:
- `slidingWindowSize: 10`
- `failureRateThreshold: 50`
- `waitDurationInOpenState: 30s`
- Fallback: return cached profile from Redis if available, else return a minimal placeholder `{ "id": "<id>", "name": "Unknown", "unavailable": true }`

## Acceptance criteria
- [ ] 5 consecutive failures → circuit opens, subsequent calls hit fallback immediately
- [ ] After 30 s → circuit half-opens, next call attempts real request
- [ ] Circuit state visible on `/actuator/health`

## Patterns demonstrated
- **Circuit Breaker** — Plain English: think of the circuit breaker in your home's electrical panel. When something downstream draws too much current (a fault), the breaker trips and cuts power immediately, rather than letting the fault keep drawing current and risking a fire. It only lets power flow again after someone checks that it's safe. Real-world analogy: it's the same idea as a business that stops sending orders to a supplier who has failed to deliver the last several times in a row — instead of placing (and losing) another order, they switch to a backup supplier until the original one proves it's reliable again. Why it's needed here: without it, every discovery request that calls a struggling User Service would wait out a full timeout before failing, one request at a time, which multiplies under load and blows through the 500ms P95 budget for the entire discovery query — not just the part touching User Service. The breaker in this ticket "trips" after 5 of the last 10 calls fail (50% failure rate over a sliding window of 10), immediately routes all further calls to the fallback (cached profile or placeholder) for 30 seconds, then cautiously lets one real call through (`HALF_OPEN`) to check if User Service has recovered.
- **Decorator** — Plain English: a decorator wraps an existing object and adds new behavior around it, without the object itself knowing it's been wrapped and without changing the shape callers use to interact with it. Real-world analogy: putting a protective case on a phone — the phone still works exactly the same way (same buttons, same screen), but the case adds shock absorption you didn't have to build into the phone itself. Why it's needed here: the code that calls User Service still looks like a normal `WebClient` call from the caller's point of view — it doesn't need to know retry logic, fallback logic, or open/closed state exist. Resilience4j's `@CircuitBreaker` annotation (or programmatic decorator) transparently wraps the real call with this resilience logic, the same shape as the Decorator example CLAUDE.md's pattern table already names for Resilience4j around `IUserServiceClient`-shaped calls.

## Agent implementation notes
- Key files to create (paths relative to project root, under `discovery-service`):
  - `src/main/resources/application.yml` — add the `resilience4j.circuitbreaker.instances.userService` config block (`slidingWindowSize`, `failureRateThreshold`, `waitDurationInOpenState`), plus enabling `management.endpoint.health.show-details` and the circuit breaker health indicator so state surfaces on `/actuator/health`.
  - The client class that wraps `WebClient` calls to User Service (created in an earlier task in this phase) — add the `@CircuitBreaker(name = "userService", fallbackMethod = "...")` annotation (or equivalent programmatic decoration) to every method that calls out to User Service.
  - A fallback method (same class, or a small dedicated fallback handler) implementing the two-step fallback: check Redis cache first (reuse T026's cache lookup), then fall back to the minimal placeholder object.
- Specific patterns to use: follow the `java-spring-boot` skill file's guidance on Resilience4j annotation usage and actuator configuration.
- What NOT to do:
  - Do not name the circuit breaker instance anything other than exactly `userService` — the `application.yml` config block, the `@CircuitBreaker(name = ...)` annotation, and any health indicator lookup must all reference this exact same name or they will silently fail to connect.
  - Do not skip the Redis cache-lookup step in the fallback and jump straight to the placeholder — the spec's fallback order is cache first, placeholder only if no cached profile exists.
  - Do not swallow or silently discard the exception that triggered the fallback — log it, so a real User Service outage is visible in logs and not just inferred from placeholder responses.
  - Do not forget to expose circuit breaker health details on `/actuator/health` — this is a named acceptance criterion, not just a nice-to-have, and requires explicit `management.health.circuitbreakers.enabled` (or equivalent) configuration, not just adding the dependency.
  - Do not implement retry logic as a substitute for the circuit breaker — this ticket is specifically about stopping calls once a threshold is hit, not about retrying individual calls.
