# T028 — Discovery Service Docker Image

## Why this ticket exists

The Discovery Service (written in Java) needs to run alongside the rest of the platform in the local dev/CI Docker Compose stack. Without a Dockerfile, the service cannot be containerized, which blocks full-stack integration testing and prevents other services from discovering and connecting to it over the compose network. This ticket makes Discovery Service runnable as a peer to the API Gateway, User Service, and future services in the same development environment.

## What to build

- A Dockerfile at `discovery-service/Dockerfile` with two stages:
  - Build stage using `eclipse-temurin:21-jdk` to compile the Maven project
  - Runtime stage using `eclipse-temurin:21-jre-alpine` to keep the image lean
- A service block in `docker-compose.yml` named `discovery-service` (port 8082) with a healthcheck that calls `GET /actuator/health`
- The built image should be under 300 MB

## Technical specification

Multi-stage Dockerfile:
1. `build` stage: `eclipse-temurin:21-jdk` + Maven wrapper
2. `runtime` stage: `eclipse-temurin:21-jre-alpine`

Wire into `docker-compose.yml`. Healthcheck: `GET /actuator/health`.

## Acceptance criteria

- [ ] `docker compose up discovery-service` starts and health passes
- [ ] Image size under 300 MB

## Patterns demonstrated

- **Multi-stage build** — separates the heavy JDK build toolchain from the minimal JRE-alpine runtime, so the shipped image doesn't carry compiler, build tools, or development dependencies — only what is needed to run the compiled JAR. Teaches the principle of "build once, ship lean."
- **Container healthcheck** — Spring Boot Actuator's `/actuator/health` endpoint lets Docker Compose continuously verify the service is alive, not just started, so orchestration doesn't route traffic to a broken container.

## Agent implementation notes

- Key files to create/edit:
  - `discovery-service/Dockerfile` (new)
  - `docker-compose.yml` (edit to add `discovery-service` service block)

- The Dockerfile must use Maven wrapper (`mvnw` or `mvnw.cmd` on Windows) in the build stage, not assume Maven is installed globally — this ensures consistency across environments.

- Healthcheck in the compose file should use `curl` to hit the Spring Boot Actuator endpoint `GET http://localhost:8082/actuator/health`. Allow sufficient time for Spring Boot startup using `interval`, `timeout`, and `start_period` compose healthcheck fields.

- The runtime stage must `COPY --from=build` the compiled JAR from the build stage — do not rely on a pre-built JAR in the working directory.

- Alpine images are minimal; if the healthcheck fails because `curl` is unavailable, use `wget` or implement a custom healthcheck script.

- Do NOT hardcode port numbers inside the Dockerfile — the `docker-compose.yml` entry controls the external port mapping (8082).

- Do NOT create a `.dockerignore` file yet — use default Maven build behavior for now.

- Verify the final image size with `docker images` after build. If it exceeds 300 MB, review the runtime stage for unnecessary layers or cached dependencies.
