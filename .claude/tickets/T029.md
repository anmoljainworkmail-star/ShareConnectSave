# T029 — Spring Boot Setup + DB Schema

## Why this ticket exists
Right now there is no runnable Connection Service — no way for a traveler's "send request" tap to ever be recorded anywhere. This ticket stands the service up so it can boot, talk to its own database, and run its Flyway migration on startup. Without it, nothing else in Phase 5 has anywhere to live: no PENDING → ACCEPTED → EXPIRED state machine, no TTL expiry scheduler, no outbox relay firing `connection.accepted` to Kafka — all of Phase 5's promised behavior depends on this service existing first. Connection Service is also where the ConnectionLifecycleSaga's steps begin (saga ID = connection_id), so getting the entity and table shape right here sets the foundation every later saga step in Chat, Rating, and Discovery builds on.

## What to build
- Maven project `connection-service` (Java 21, Spring Boot 3) — same setup pattern as T021 (`discovery-service`)
- Dependencies: Spring Web, Spring Data JPA, Spring Kafka, Validation, Actuator, Lombok, MapStruct, Flyway, plus `shared-java-lib` (T003) for `ErrorResponse` / `GlobalExceptionHandler`
- `src/main/resources/application.yml` with `dev` and `prod` Spring profiles, `spring.threads.virtual.enabled: true` in the shared/base section
- `DataSource` config reading `CONNECTION_DB_HOST`, `CONNECTION_DB_PORT`, `CONNECTION_DB_NAME`, `CONNECTION_DB_USERNAME`, `CONNECTION_DB_PASSWORD` environment variables
- Flyway migration for the `connection_requests` table (see T006 schema) — a migration already exists at `src/services/connection-service/src/main/resources/db/migration/V001__connection_service_initial_schema.sql`; verify it matches this ticket's needs rather than creating a duplicate `V002` that re-declares the same table
- JPA entity `ConnectionRequest` mapped to `connection_requests`, with `status` as a Java `enum` (`PENDING`, `ACCEPTED`, `DECLINED`, `EXPIRED`) stored as a string, matching columns: `id`, `requester_id`, `recipient_id`, `status`, `created_at`, `expires_at`, `updated_at`
- `GET /actuator/health` returning `{ "status": "UP" }` once SQL Server is reachable and Flyway has run

## Patterns demonstrated
**Database per Service** — `connection_requests` lives only in Connection Service's own schema; Chat, Rating, and Discovery learn about connection state only through Kafka events, never a cross-service query or join.

**Single Responsibility (SOLID-S)** — this ticket wires infrastructure only (DB connectivity, Flyway, health check, the bare entity/table shape). No controllers, no state-transition logic, no scheduler — those are deliberately left to later Phase 5 tickets.

**Open/Closed (SOLID-O)** — `status` is stored as a plain string column, not a SQL `CHECK` constraint enumerating values. What counts as a valid status is business logic living in the Java `enum`, so adding a future status is a code change, not a migration.

**Repository (GoF)** — later tickets will access `ConnectionRequest` rows through an `IConnectionRequestRepository`-style interface built on Spring Data JPA, never raw `EntityManager` queries scattered through the codebase; this ticket only lays the entity groundwork that repository will sit on.

## Agent implementation notes
- Key files to create/verify:
  - `/services/connection-service/pom.xml` — Maven parent `spring-boot-starter-parent`, Java 21, dependency on `com.shareconnectsave:shared-java-lib`
  - `/services/connection-service/src/main/java/com/shareconnectsave/connection/ConnectionServiceApplication.java` — `@SpringBootApplication` entry point
  - `/services/connection-service/src/main/resources/application.yml` — base config + `dev`/`prod` profile blocks, all secrets/hosts via `${ENV_VAR}` placeholders per the `java-spring-boot` skill
  - `src/services/connection-service/src/main/resources/db/migration/V001__connection_service_initial_schema.sql` already exists — read it before writing any entity code; do not add a second migration that re-creates `connection_requests`
  - `/services/connection-service/src/main/java/com/shareconnectsave/connection/domain/ConnectionRequest.java` — `@Entity`, `@Getter @Builder @NoArgsConstructor @AllArgsConstructor` (per skill; avoid Lombok `@Data`), `status` field typed as a `ConnectionStatus` enum with `@Enumerated(EnumType.STRING)`
  - `/services/connection-service/src/main/java/com/shareconnectsave/connection/domain/ConnectionStatus.java` — enum: `PENDING`, `ACCEPTED`, `DECLINED`, `EXPIRED`
  - `/services/connection-service/src/main/java/com/shareconnectsave/connection/exception/` — thin re-export of `shared-java-lib`'s `GlobalExceptionHandler`, same pattern as T021 — do not copy its code
- Follow the `java-spring-boot` skill's package-by-feature layout (`com.shareconnectsave.connection.*`) so later tickets (state machine, TTL scheduler, outbox relay) slot in without restructuring
- `application.yml` must read `CONNECTION_DB_HOST`, `CONNECTION_DB_PORT`, `CONNECTION_DB_NAME`, `CONNECTION_DB_USERNAME`, `CONNECTION_DB_PASSWORD`, and `KAFKA_BROKERS` — no hardcoded connection strings, matching the user's `process.env.*`-for-config preference
- `spring.threads.virtual.enabled: true` goes in the base (shared) section of `application.yml`, not inside a single profile
- Actuator: only expose `health` (and `info` if trivial) in `management.endpoints.web.exposure.include`
- What NOT to do:
  - Do not write any controller, saga step, or TTL scheduler logic — that starts in later Phase 5 tickets. This ticket is setup + schema only.
  - Do not create a new Flyway migration if `V001__connection_service_initial_schema.sql` already covers the table — check it first
  - Do not use `RestTemplate` anywhere, even in placeholder code — use `WebClient` per the skill
  - Do not hardcode `localhost` or container IPs in `application.yml` — everything comes from environment variables

## Known follow-ups
From T024's review: `MissingRequestHeaderException` on a missing `X-User-Id` currently falls through `shared-java-lib`'s `GlobalExceptionHandler` catch-all and returns a raw 500 instead of a clean 400. This ticket adds no controllers yet, so it isn't triggered here — but any future Connection Service controller in this codebase that reads `X-User-Id` via `@RequestHeader` inherits this gap. Note it for whichever later Connection Service ticket adds the first controller; the actual fix belongs in `shared-java-lib` (tracked against T091), not here.
