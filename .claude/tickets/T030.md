# T030 — Request Lifecycle Endpoints

## Why this ticket exists
Right now Connection Service can boot and reach its database (T029), but there is still no way for a traveler to actually send, accept, or decline a request — the "send request" tap has nowhere to land. This ticket builds the five endpoints that turn `connection_requests` from an empty table into the real state machine promised by the requirements: `pending → accepted / declined`. It is also the first place the ConnectionLifecycleSaga actually runs — accepting a request is Step 1 of that saga, and this ticket is what writes the `connection.accepted` event to the outbox and records the saga's first step in `saga_state`. Without this ticket, Chat Service has nothing to react to (no `connection.accepted` ever fires), so no chat can ever open, and the entire Phase 5 goal — "the state machine for connection requests" — stays unmet.

## What to build
- `ConnectionController` — `POST /connections`, `POST /connections/{id}/accept`, `POST /connections/{id}/decline`, `GET /connections/pending`, `GET /connections/active`
- `ConnectionService` interface + `ConnectionServiceImpl` — holds all state-transition logic; controller stays thin (per user preference: every controller delegates to a service layer)
- `IConnectionRequestRepository extends JpaRepository<ConnectionRequest, UUID>` — query methods for "pending inbound for recipient", "active (ACCEPTED) connection involving user as either requester or recipient"
- State-transition guard: a `Map<ConnectionStatus, Set<ConnectionStatus>>` (or equivalent) encoding only `PENDING → ACCEPTED` and `PENDING → DECLINED` as valid; anything else throws `InvalidStateTransitionException`
- `ActiveConnectionExistsException` — thrown when the requester or recipient already has an `ACCEPTED` connection
- `ForbiddenConnectionActionException` — thrown when the caller (`X-User-Id`) is not the connection's `recipient_id` on accept/decline
- Domain-specific `@RestControllerAdvice` (connection-service local, alongside the shared `GlobalExceptionHandler` from `shared-java-lib`) mapping: `InvalidStateTransitionException` → 409 `INVALID_STATE_TRANSITION`, `ActiveConnectionExistsException` → 409 `ACTIVE_CONNECTION_EXISTS`, `ForbiddenConnectionActionException` → 403
- `IRequestLimitCache` interface (`int getLimit(UUID userId)`) + a `ConcurrentHashMap`-backed default implementation returning a `DEFAULT_REQUEST_LIMIT` fallback for any user not yet present — this is the same bean T033 (Kafka consumer for `trust.score.updated`) will later populate; T030 only reads it and ships the empty/default-returning shape
- On `POST /connections`: reject with 409 (reuse `ACTIVE_CONNECTION_EXISTS`-style limit check, but this is a distinct rule) if the requester already has `request_limit` pending outbound requests — read the limit from `IRequestLimitCache`
- On `POST /connections/{id}/accept`, inside one `@Transactional` method: update status to `ACCEPTED`, write the `connection.accepted` event via `IOutboxService.publish(...)` (from T003/`shared-java-lib` or wherever the outbox skill wires it in for this service), and upsert a `saga_state` row (`saga_id = connection_id`, `saga_type = "ConnectionLifecycle"`, `current_step = "ACCEPTED"`, `status = "in_progress"`) — all three in the same transaction, per the Outbox Pattern
- `CreateConnectionDto` `{ recipientId }`, `ConnectionCreatedResponse` `{ connectionId }`, `ConnectionResponse` (for the `pending`/`active` list endpoints) via a MapStruct `ConnectionMapper`

## Technical specification
**Service:** `connection-service`
**Language:** Java
**Depends on:** T029
**Skills/Commands:** none

**Spec:**
- `POST /connections` — send a request. Body: `{ "recipient_id" }`. Reads sender from `X-User-Id`. Creates record with status `PENDING`, `expires_at = now + 10 min`. Returns `{ "connection_id" }`.
- `POST /connections/:id/accept` — caller must be the recipient. Transitions to `ACCEPTED`.
- `POST /connections/:id/decline` — caller must be the recipient. Transitions to `DECLINED`.
- `GET /connections/pending` — returns caller's pending inbound requests.
- `GET /connections/active` — returns caller's accepted (open) connection.

State machine rules:
- Only `PENDING` → `ACCEPTED` or `DECLINED` transitions are valid.
- A user can only have one active connection at a time.
- Requester cannot have more than `request_limit` pending outbound requests (limit from Trust Service via Kafka, cached locally).

**Acceptance criteria:**
- [ ] Invalid state transition returns 409 with `INVALID_STATE_TRANSITION`
- [ ] Duplicate active connection returns 409 with `ACTIVE_CONNECTION_EXISTS`
- [ ] Non-recipient trying to accept/decline returns 403

## Acceptance criteria
- [ ] Invalid state transition returns 409 with `INVALID_STATE_TRANSITION`
- [ ] Duplicate active connection returns 409 with `ACTIVE_CONNECTION_EXISTS`
- [ ] Non-recipient trying to accept/decline returns 403

## Patterns demonstrated
**Saga (Choreography)** — the `accept` endpoint is Step 1 of `ConnectionLifecycleSaga`: Connection Service does its own local transaction (status → `ACCEPTED`) and publishes `connection.accepted`; it has no idea Chat Service or Notification Service exist, or what they'll do next.

**Outbox Pattern** — the status update, the outbox row for `connection.accepted`, and the `saga_state` write all happen inside one `@Transactional` method, so a crash between "update DB" and "publish to Kafka" can never leave a half-finished saga step.

**Single Responsibility (SOLID-S)** — `ConnectionController` only translates HTTP ↔ DTOs; every transition rule, limit check, and exception decision lives in `ConnectionServiceImpl`.

**Open/Closed (SOLID-O)** — valid transitions are data (a map from status to its allowed next statuses), not a chain of `if/else`. Loosening or tightening the state machine later is a data change, not new conditional branches.

**Dependency Inversion (SOLID-D)** — `ConnectionServiceImpl` depends on `IConnectionRequestRepository`, `IOutboxService`, and `IRequestLimitCache` — all interfaces. None of them care whether the limit cache is in-memory today or Redis-backed later, and tests can substitute any of the three without touching the service.

**Event-Driven Architecture** — `request_limit` is never fetched with a synchronous call to Trust Service. It arrives (eventually, via T033) as a Kafka-driven update to a local cache; this ticket's read path is written against that contract from day one even though nothing populates it yet.

**API Gateway (trust boundary)** — `X-User-Id` is read directly off the request header with no re-validation; the JWT was already checked at the YARP gateway before this request ever reached Connection Service.

## Agent implementation notes
- Key files to create (paths from project root, under `src/services/connection-service/src/main/java/com/shareconnectsave/connection/`):
  - `connection/ConnectionController.java`
  - `connection/ConnectionService.java` (interface) and `connection/ConnectionServiceImpl.java`
  - `connection/IConnectionRequestRepository.java` — extends `JpaRepository<ConnectionRequest, UUID>`; add derived-query or `@Query` methods for "pending inbound by recipient" and "active connection by either party" rather than filtering in Java
  - `connection/domain/CreateConnectionDto.java`, `ConnectionCreatedResponse.java`, `ConnectionResponse.java`
  - `connection/mapper/ConnectionMapper.java` — MapStruct, per the `java-spring-boot` skill's "DTO mapping" section
  - `connection/exception/InvalidStateTransitionException.java`, `ActiveConnectionExistsException.java`, `ForbiddenConnectionActionException.java`
  - `connection/exception/ConnectionExceptionHandler.java` — `@RestControllerAdvice`, sits alongside (does not replace) `shared-java-lib`'s `GlobalExceptionHandler`
  - `connection/cache/IRequestLimitCache.java` + `connection/cache/InMemoryRequestLimitCache.java` — `@Component`, `ConcurrentHashMap<UUID, Integer>`, a `DEFAULT_REQUEST_LIMIT` constant, a `getLimit(UUID)` read method and an `update(UUID, int)` write method that T033 will call later
  - `saga/SagaState.java` entity + `saga/ISagaStateRepository.java` if not already created by T029 — check first; if T029 already added a shared saga table entity, reuse it rather than duplicating
- Follow the skill's Dependency Inversion section exactly: `ConnectionController` depends on `ConnectionService` (interface), never `ConnectionServiceImpl` directly
- Use guard clauses, not nested `if/else`, for the transition/ownership/limit checks in `ConnectionServiceImpl` — check ownership first, then state validity, then the active-connection/limit rules, returning or throwing early at each step (per user preference)
- The `@Transactional` accept method must call the repository update, `IOutboxService.publish("connection.accepted", ...)`, and the saga-state upsert in that order, inside the same method — do not split them across separate `@Transactional` boundaries or the atomicity guarantee the Outbox Pattern exists to provide is lost
- `GET /connections/active` returns the single accepted connection (if any) for the caller — caller can be either `requester_id` or `recipient_id` on that row; write the repository query to check both columns
- What NOT to do:
  - Do not call Trust Service synchronously (WebClient/`RestTemplate`) to get `request_limit` — that defeats the whole point of caching it locally via Kafka; always read `IRequestLimitCache`
  - Do not implement the `trust.score.updated` Kafka consumer itself here — that is T033's job; this ticket only creates the cache interface/bean it will write into
  - Do not implement a TTL expiry scheduler in this ticket — `expires_at` is only set on creation here; the `@Scheduled` expiry job referenced in the Phase 5 goal is separate ticket scope
  - Do not let the shared `GlobalExceptionHandler` swallow the three domain-specific exceptions into a generic 500 — they need their own local `@RestControllerAdvice` mapping to the exact codes in the acceptance criteria
  - Do not use `@Data` on the `SagaState` or DTO classes — follow the skill's `@Getter @Builder @NoArgsConstructor @AllArgsConstructor` convention
