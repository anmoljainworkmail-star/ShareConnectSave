# T031 — Request TTL Expiry Job

## Why this ticket exists
A connection request that nobody responds to is supposed to give up after 10 minutes (T030 sets `expires_at` on creation), but nothing currently reads that column back. Without this ticket, a `PENDING` request just sits there forever — the requester's outbound-request-limit slot stays consumed indefinitely, the recipient's inbox never clears out, and no `connection.expired` event ever fires, so Notification Service has nothing to tell either user. This ticket is what actually enforces the TTL promised in the requirements, and it is the first place in the project a `@Scheduled` job runs — the piece the Phase 5 goal calls out by name ("TTL expiry runs on schedule").

## What to build
- `ConnectionExpiryScheduler` — `@Scheduled(fixedRate = 60000)` (every 1 minute), calls into `ConnectionService`/`ConnectionServiceImpl`, does not contain business logic itself
- `ConnectionServiceImpl.expireOverdueRequests()` (or equivalent method on `ConnectionService`) — finds all `PENDING` requests where `expires_at < now`, and for each one, inside one `@Transactional` boundary per request: transitions status to `EXPIRED` and writes a `connection.expired` outbox row via `IOutboxService.publish(...)`
- `IConnectionRequestRepository` — add a derived/`@Query` method such as `findByStatusAndExpiresAtBefore(ConnectionStatus.PENDING, Instant.now())`
- `connection.expired` event payload: `{ connection_id, requester_id }`, matching the Kafka topic contract consumed by Notification Service
- Reuses the existing `OutboxRelay` (from T029/shared outbox wiring) to actually publish to Kafka — this ticket only writes outbox rows, it does not talk to Kafka directly
- Logging + resilience: if the outbox write itself succeeds but the relay's later Kafka publish fails, the scheduler run must not fail or throw — that failure belongs to `OutboxRelay`'s own retry loop, not this scheduler

## Technical specification
### T031 — Request TTL Expiry Job

**Service:** `connection-service`
**Language:** Java
**Depends on:** T030
**Skills/Commands:** none

**Spec:**
Scheduled task (`@Scheduled`, runs every 1 minute): find all `PENDING` requests where `expires_at < now`, transition them to `EXPIRED`.

For each expired request, publish `connection.expired` Kafka event.

**Acceptance criteria:**
- [ ] Pending request past `expires_at` → transitioned to `EXPIRED` within 1 minute
- [ ] `connection.expired` event published per expired request
- [ ] Scheduler does not fail if Kafka is temporarily unavailable (log + retry)

## Acceptance criteria

## Patterns demonstrated
**Outbox Pattern** — the `EXPIRED` status update and the `connection.expired` outbox row are written in the same local DB transaction; the `OutboxRelay`'s later, separate publish step is the only part that can fail on Kafka being down, which is exactly why the DB-side transition is never at risk.

**Saga (Choreography) — compensating step** — expiry is a terminal, no-response branch of `ConnectionLifecycleSaga`: Connection Service does its own local transition and fires a past-tense fact (`connection.expired`); it has no idea Notification Service exists or what it will do with that fact.

**Single Responsibility (SOLID-S)** — `ConnectionExpiryScheduler` only decides *when* to run; it delegates *what* to do (querying, transitioning, writing the outbox row) entirely to `ConnectionServiceImpl`, matching the same split already used for `OutboxRelay` (publishes only, no business logic).

**Idempotency** — because the query filters strictly on `status = PENDING`, a request already moved to `EXPIRED` by a previous run (or concurrently accepted/declined) is never picked up again on the next tick; re-running the scheduler on the same data is safe.

**Event-Driven Architecture** — `connection.expired` is a statement of fact about something that already happened in this service's own database, published for any interested subscriber (today: Notification Service) without Connection Service knowing or caring who's listening.

## Agent implementation notes
- Key files to create (paths from project root, under `src/services/connection-service/src/main/java/com/shareconnectsave/connection/`):
  - `connection/scheduler/ConnectionExpiryScheduler.java` — `@Component`, `@Scheduled(fixedRate = 60000)` method, injects `ConnectionService` only
  - Add `expireOverdueRequests()` to the existing `ConnectionService` interface and `ConnectionServiceImpl` (created in T030) rather than creating a new service class
  - Add the derived query method to the existing `IConnectionRequestRepository` (created in T030)
  - `connection/kafka/event/ConnectionExpiredEvent.java` (or wherever T030's `connection.accepted` event POJO lives — put this alongside it) — fields `connection_id`, `requester_id`
- Enable scheduling once at the application level: `@EnableScheduling` on the main `@SpringBootApplication` class (check first — T029 may already have added it for another reason; do not duplicate the annotation)
- Process each overdue request in its own `@Transactional` method call (loop in the scheduler/service, transactional boundary per request) so one bad row can't roll back every other expiry in the same tick
- Follow the same outbox call shape T030 already used for `connection.accepted` — `IOutboxService.publish("connection.expired", payload)` inside the same transaction as the status update, per the Outbox Pattern
- Use a guard clause at the top of the per-request expiry method (e.g., re-check status is still `PENDING` before transitioning) rather than nested `if/else`, per user preference
- What NOT to do:
  - Do not call the Kafka producer or `KafkaTemplate` directly from the scheduler or service — always go through `IOutboxService`; publishing is `OutboxRelay`'s job, not this ticket's
  - Do not wrap the whole scheduler tick in a single try/catch that swallows everything — if one request's transition fails, log it and continue to the next; don't let one bad row silently skip the rest of the batch
  - Do not add retry/backoff logic for Kafka inside this ticket's code — that resilience already belongs to `OutboxRelay` (built in T029/T030's outbox wiring); this ticket's job is only to write the outbox row correctly and let the relay do its job
  - Do not query with `LocalDateTime.now()` if the rest of the codebase uses `Instant` for `expires_at` — check T030's `ConnectionRequest` entity field type first and match it exactly
