# T032 — Kafka Producer: connection.accepted + connection.expired

## Why this ticket exists
T030 and T031 already decide *when* Connection Service should tell the rest of the platform something happened — a request was accepted, or a request expired unanswered — and both write their call as `outboxService.publish(...)` inside the same transaction as the status update. But neither ticket builds the thing that call points at: there is no `outbox` table, no `IOutboxService`, and nothing that ever actually talks to Kafka. Until this ticket ships, those calls have nowhere real to land, Chat Service never learns a connection was accepted (so it never opens a chat room), and Notification Service never learns a request expired (so neither user is told). This is also the first time Connection Service touches Kafka at all, and it is the one place `KafkaTemplate` is allowed to be injected in this service — everywhere else depends only on the `IOutboxService` abstraction, so the moment the shared `shared-java-lib` outbox module lands in Phase 14 (T091/T093), this local implementation can be swapped out without touching T030's or T031's code.

## What to build
- `outbox` table via a new Flyway migration in `connection-service` (mirrors the shape used across every producing service, per the `kafka-outbox` skill)
- `OutboxEvent` JPA entity — `id` (UUID, doubles as `event_id` for consumer dedup), `topic`, `partitionKey`, `payload` (JSON string), `status` (`PENDING` / `PROCESSED`), `createdAt`, `processedAt`
- `IOutboxRepository extends JpaRepository<OutboxEvent, UUID>` — a query method for "pending rows oldest first"
- `IOutboxService` interface — `publish(String topic, String partitionKey, Object payload)` — and `OutboxServiceImpl`, which serializes `payload` to JSON and inserts a `PENDING` `OutboxEvent` row using the *caller's* existing transaction (no new transaction boundary of its own)
- `OutboxRelay` — `@Component`, `@Scheduled(fixedDelay = 500)`, `@Transactional` per batch — polls pending rows, publishes each to Kafka via `KafkaTemplate<String, String>` using `partitionKey` as the Kafka message key, marks the row `PROCESSED` on success, leaves it `PENDING` (to retry next tick) on failure
- Wires T030's and T031's already-specified `outboxService.publish(...)` call sites to this real implementation:
  - `ConnectionServiceImpl`'s `accept(...)` transition → `outboxService.publish("connection.accepted", connectionId.toString(), connectionAcceptedEvent)`
  - `ConnectionServiceImpl`'s `expireOverdueRequests(...)` per-row transition → `outboxService.publish("connection.expired", connectionId.toString(), connectionExpiredEvent)`
- Reuses (does not duplicate) the `ConnectionAcceptedEvent` and `ConnectionExpiredEvent` payload POJOs from T030/T031

## Patterns demonstrated
**Outbox Pattern** — the accept/expire transitions never call Kafka directly; they write a row to the local `outbox` table in the same transaction as their status update, and `OutboxRelay` is the only component that ever calls `KafkaTemplate`. A crash between "DB commit" and "Kafka publish" can never lose the event — it just gets published on the next 500 ms tick.

**Single Responsibility (SOLID-S)** — `OutboxRelay` only publishes; it contains no business logic about connections, no state-transition rules, and no knowledge of what `connection.accepted` or `connection.expired` mean. `OutboxServiceImpl` only knows how to write a row; it doesn't know what a connection is either.

**Dependency Inversion (SOLID-D)** — `ConnectionServiceImpl` (from T030/T031) depends on `IOutboxService`, never on `KafkaTemplate` or `Confluent`/Spring Kafka types directly. It has no idea whether events end up on Kafka, a log file, or nowhere yet.

**Liskov Substitution (SOLID-L)** — this ticket's `OutboxServiceImpl` is a local, connection-service-only implementation of `IOutboxService`. When Phase 14 (T091/T093) replaces it with the shared `shared-java-lib` version, every caller in `ConnectionServiceImpl` keeps working unchanged — the substitute behaves identically from the caller's point of view.

**Observer (GoF, via events)** — `connection.accepted` and `connection.expired` are each published exactly once, with no idea who (if anyone) is listening. Chat Service and Notification Service both react to `connection.accepted` independently; Connection Service never calls either of them directly.

**Saga (Choreography), continued** — publishing `connection.accepted` is what lets `ConnectionLifecycleSaga` move to its next step (Chat Service opening a room); publishing `connection.expired` is the saga's no-response terminal branch notifying Notification Service. Connection Service's job ends at "publish the fact" — it never orchestrates what happens next.

**Idempotency (groundwork)** — the outbox row's own `id` is reused as the event's `event_id` in the published envelope, which is what lets every consumer (T033 and beyond) later deduplicate a redelivered message. This ticket lays that groundwork; it does not itself need to deduplicate anything.

## Agent implementation notes
- Key files to create (paths from project root, under `src/services/connection-service/src/main/java/com/shareconnectsave/connection/`):
  - `outbox/OutboxEvent.java` — `@Entity @Table(name = "outbox")`, `@Getter @Builder @NoArgsConstructor @AllArgsConstructor` (no Lombok `@Data`, per skill convention)
  - `outbox/OutboxStatus.java` — enum `PENDING`, `PROCESSED`
  - `outbox/IOutboxRepository.java` — extends `JpaRepository<OutboxEvent, UUID>`, add `findByStatusOrderByCreatedAtAsc(OutboxStatus status, Pageable pageable)`
  - `outbox/IOutboxService.java` — interface, single method `publish(String topic, String partitionKey, Object payload)`
  - `outbox/OutboxServiceImpl.java` — `@Service`, injects `IOutboxRepository` + `ObjectMapper`, serializes `payload` to JSON, saves a `PENDING` row; must run inside whatever transaction the caller already opened — do not annotate this method `@Transactional` itself if that would start a new, separate transaction from `ConnectionServiceImpl`'s
  - `outbox/OutboxRelay.java` — `@Component`, injects `IOutboxRepository` + `KafkaTemplate<String, String>`, `@Scheduled(fixedDelay = 500)` method wrapped `@Transactional`, fetches `PageRequest.of(0, 50)` pending rows ordered oldest-first, sends each via `kafkaTemplate.send(topic, partitionKey, payload)`, marks `PROCESSED` + `processedAt` only after a successful send
  - `src/main/resources/db/migration/V002__connection_service_outbox_table.sql` — `outbox` table: `id`, `topic`, `partition_key`, `payload`, `status`, `created_at`, `processed_at` — check the migration folder first; if T030 or T031 already added a `V002`, number this one accordingly rather than colliding
- Follow the `kafka-outbox` skill's Java code sample for the exact shape of `OutboxEvent`, `IOutboxService`, and the `@Scheduled(fixedDelay = 500)` relay loop — this ticket is that sample, implemented for `connection-service`
- Partition key for both topics is `connection_id` (as a string) — pass it explicitly to `outboxService.publish(...)`, never derive it inside `OutboxRelay`
- Wire the `IOutboxService` bean into `ConnectionServiceImpl` (T030) and its `expireOverdueRequests()` method (T031) via constructor injection; if those methods were written against a not-yet-existing interface, this ticket is what makes that interface real — do not change the shape of the `.publish(...)` calls those tickets already specified
- Reuse `ConnectionAcceptedEvent` and `ConnectionExpiredEvent` (created in T030/T031) as the `payload` argument — do not create second copies of these DTOs
- What NOT to do:
  - Do not call `KafkaTemplate` from `ConnectionServiceImpl`, the accept endpoint, or the expiry scheduler — `OutboxRelay` is the only class in this service allowed to inject `KafkaTemplate`
  - Do not wrap `OutboxServiceImpl.publish(...)` in its own `@Transactional` boundary — it must participate in the caller's existing transaction, or the whole point of the Outbox Pattern (DB write + outbox write are atomic) is lost
  - Do not build the full generic `shared-java-lib` outbox module here — that is explicitly Phase 14 (T091/T093) scope; this ticket is a connection-service-local implementation only, matching the interface shape so the later swap is a Liskov-safe substitution, not a rewrite
  - Do not add retry-count/DLQ logic to `OutboxRelay` in this ticket — on a failed send, simply leave the row `PENDING` so the next 500 ms tick retries it naturally; DLQ handling is scoped to Report Service (T054) per the `kafka-outbox` skill, not here
  - Do not skip the `event_id` — the outbox row's `id` must be included in the published Kafka message envelope so downstream consumers can deduplicate
