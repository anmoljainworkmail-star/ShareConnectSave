# T033 — Kafka Consumer: trust.score.updated (request limit cache)

## Why this ticket exists
Rating Service recalculates a user's trust score whenever ratings come in, and publishes the result — including a `request_limit` — on `trust.score.updated`. Connection Service is the place that actually enforces how many connection requests a user can send (T030), but it has no idea what a user's current limit is unless it listens for this event. Without this ticket, a user whose trust score just dropped (or recovered) keeps sending requests under their old, stale limit — the throttling rule described in REQUIREMENTS.md never actually takes effect, and T030 has nothing to enforce against.

## What to build
- Kafka listener class (e.g. `TrustScoreUpdatedConsumer`) subscribed to topic `trust.score.updated`
- Idempotency check against the shared `processed_events` table (`event_id`, `processed_at`) before acting — skip if already processed, insert if not, prune after 7 days (same rule as every other consumer in this project)
- In-memory cache keyed by `user_id` storing `request_limit` (ConcurrentHashMap or Caffeine cache, TTL-managed)
- A read accessor on that cache for T030 to call when enforcing send limits (e.g. `RequestLimitCache.getLimit(userId)`)
- On message receipt: parse payload (`user_id`, `new_score`, `badge_level`, `request_limit`), update the cache entry for that `user_id`, mark event processed

## Technical specification
Listen to `trust.score.updated`. Cache `request_limit` per `user_id` in a local in-memory map (ConcurrentHashMap, TTL managed manually or via Caffeine cache). Used by T030 to enforce send limits.

## Acceptance criteria
- [ ] Updated limit takes effect on next request send attempt (within 1 Kafka poll cycle)

## Patterns demonstrated
- **Observer (via events)** — Connection Service reacts to `trust.score.updated` independently of Rating Service (the publisher) and Discovery Service (the other subscriber); neither side needs to know who else is listening.
- **Idempotency** — Kafka's at-least-once delivery means this event can arrive more than once; the `processed_events` check guarantees re-processing the same event doesn't corrupt the cache state.
- **Cache-Aside (adjacent)** — this is the write side of a cache kept warm by events rather than populated lazily on read miss; call this out as the event-driven cousin of the Cache-Aside pattern used elsewhere (e.g. Discovery Service's Redis profile cache), not the same mechanism.
- **Single Responsibility** — the consumer only updates the cache; it does not enforce limits itself (that stays in T030) and does not talk to Kafka's outbox (it's a consumer, not a producer).

## Agent implementation notes
- Key files to create (paths from project root):
  - `connection-service/src/main/java/.../kafka/consumer/TrustScoreUpdatedConsumer.java`
  - `connection-service/src/main/java/.../cache/RequestLimitCache.java`
  - `connection-service/src/main/java/.../dto/TrustScoreUpdatedEvent.java`
  - Reuse the existing `processed_events` repository/entity from earlier consumers in this service (e.g. T025's pattern in discovery-service) — do not create a second, differently-shaped idempotency table
- Patterns to use: follow the `kafka-outbox` skill's consumer-side conventions for idempotency check placement and event deserialization; follow `java-spring-boot` skill conventions for `@KafkaListener` wiring and bean scoping (the cache should be a singleton bean, not re-created per message)
- What NOT to do:
  - Do not skip the `processed_events` idempotency check just because this consumer only mutates an in-memory cache instead of a DB row — at-least-once delivery still applies, and a duplicate delivery re-applying the same `request_limit` is harmless today but the check itself is the concept being taught here and must not be treated as optional
  - Do not let the cache silently grow unbounded — if using Caffeine, set an explicit `maximumSize` and TTL; if using a plain `ConcurrentHashMap`, document (and ideally implement) an eviction/expiry strategy rather than leaving it as a permanent map
  - Do not have T030 read this event directly or duplicate consumption — T030 must only read through `RequestLimitCache`'s accessor, keeping the consumer as the single writer
