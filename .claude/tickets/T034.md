# T034 — Connection Service Docker Image

## Why this ticket exists

Connection Service is written in Java and, right now, cannot run in the local Docker Compose stack — it has no Dockerfile. Until it's containerized, it can't be started alongside SQL Server, MongoDB, Kafka, and Redis via `/docker-up`, which blocks any full-stack integration testing of the connection request lifecycle (the state machine T029–T033 just built) against the rest of the platform. This ticket makes Connection Service runnable as a peer to Discovery Service and the API Gateway in the same dev environment, following the exact packaging pattern already proven for Discovery Service in T028.

## What to build

- A Dockerfile at `connection-service/Dockerfile` with two stages:
  - Build stage using `eclipse-temurin:21-jdk` to compile the Maven project (via the Maven wrapper)
  - Runtime stage using `eclipse-temurin:21-jre-alpine` to keep the image lean
- The service block for `connection-service` already exists in `src/infra/docker-compose.yml` (port `8083:8080`, builds from `context: ../../src/services/connection-service`, `dockerfile: Dockerfile`) — this ticket supplies the Dockerfile that block expects
- Fix the latent Spring profile / datasource credential gap in `src/infra/docker-compose.override.yml`'s `connection-service` block (see Known follow-ups) before first run

## Patterns demonstrated

- **Multi-stage build** — separates the heavy JDK build toolchain from the minimal JRE-alpine runtime, so the shipped image doesn't carry compiler, build tools, or dev dependencies, only what's needed to run the compiled JAR. Teaches "build once, ship lean."
- **Container healthcheck** — Spring Boot Actuator's `/actuator/health` endpoint lets Docker Compose continuously verify the service is alive, not just started, so orchestration doesn't route traffic to a broken container.

## Agent implementation notes

- Key files to create/edit:
  - `src/services/connection-service/Dockerfile` (new)
  - `src/infra/docker-compose.override.yml` (edit — fix the `connection-service` env block per the known follow-up below; do this proactively, not after hitting error 18456)
- The service block in `src/infra/docker-compose.yml` (lines ~337–357) already exists — do not duplicate or re-add it. Confirm the Dockerfile it references (`dockerfile: Dockerfile`, build context `src/services/connection-service`) matches where you actually create the file.
- The Dockerfile must use the Maven wrapper (`mvnw`/`mvnw.cmd`) in the build stage, not assume Maven is installed globally — same reasoning as T028: consistency across dev machines and CI.
- The runtime stage must `COPY --from=build` the compiled JAR from the build stage — do not rely on a pre-built JAR already sitting in the working directory.
- Healthcheck already wired in `docker-compose.yml` hits `http://localhost:8080/actuator/health` via `curl`; if Alpine's minimal base doesn't have `curl` available, either install it in the runtime stage or fall back to `wget`.
- Do NOT hardcode port numbers inside the Dockerfile — `docker-compose.yml` already controls the external port mapping (`8083:8080`).
- Do NOT create a `.dockerignore` file yet — same deferral T028 made, stay consistent.

## Known follow-ups

- Verify the final image size with `docker inspect --format {{.Size}}` or `docker save`, not `docker images` — T028 found `docker images` reports a size (~450MB) that doesn't match the true image size (~152MB) corroborated by `docker inspect`/`docker save`; the root cause is an unconfirmed containerd-snapshotter display quirk, not BuildKit attestation/SBOM metadata as previously assumed. Also note `docker history`'s summed layer size (~298MB uncompressed) sits only ~2MB under the 300MB budget, so an uncompressed-size-based check could flip pass/fail depending on which metric is used — use the inspect/save number as authoritative.
- Before assuming `SPRING_PROFILES_ACTIVE=docker` works for connection-service, confirm `connection-service`'s `application.yml` actually defines a `docker` profile document. `src/infra/docker-compose.override.yml`'s `connection-service` block (lines 102–106) currently sets `SPRING_PROFILES_ACTIVE=docker` and `SPRING_DATASOURCE_URL`, but no `SPRING_DATASOURCE_USERNAME`/`PASSWORD` — this is the exact same latent bug T028 found and fixed for discovery-service (activating a nonexistent profile silently no-ops, so the datasource username/password placeholders never bind, and the app connects to SQL Server with an empty username — error 18456). Fix proactively by adding explicit `SPRING_DATASOURCE_USERNAME=sa` / `SPRING_DATASOURCE_PASSWORD=${SA_PASSWORD:?...}` env vars directly in the override file, the same way discovery-service was fixed (lines 75–76 of that file), rather than waiting to hit the error at runtime.
