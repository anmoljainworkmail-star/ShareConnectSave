# T035 — Chat Service Setup + MongoDB

## Why this ticket exists

Chat is the only part of ShareConnectSave where real conversation content lives, and that content is supposed to disappear — the platform's entire privacy promise is "no chat history after the conversation ends." Right now there is no `chat-service` project at all, so there is nowhere for messages to be stored, and nothing enforcing that deletion promise in code. This ticket stands up the Chat Service project and its MongoDB connection, and — critically — makes the service itself create the TTL (time-to-live) index that auto-deletes old messages, rather than relying only on a one-time database init script. Without this, every later chat ticket (SignalR hub, message send/receive, saga compensation on chat failure) has nothing to build on, and the "messages are ephemeral by design" guarantee from REQUIREMENTS.md would depend entirely on a script a developer might forget to run against a fresh database.

## What to build

- New `chat-service` .NET 9 project (MVC Controllers, matching the rest of the platform's routing style).
- `MongoDB.Driver` NuGet package added to the project.
- Mongo connection configured from `process.env.MONGO_CONNECTION_STRING` — never a hardcoded connection string.
- `IChatRoomRepository` and `IMessageRepository` interfaces (Repository pattern, Interface Segregation — Chat Service depends only on the collection operations it actually needs, kept as two narrow interfaces rather than one).
- Entities matching the T007 schema:
  - `chat_rooms` collection: `_id`, `connection_id`, `user_a_id`, `user_b_id`, `status`, `created_at`, `closed_at`.
  - `messages` collection: matches T007 schema, including `sent_at`.
- Startup logic that programmatically creates (or confirms) a TTL index on `messages.sent_at`, using an idempotent `CreateIndex` call — safe to run every time the service starts, including against an already-indexed collection.
- Service should start and successfully connect to MongoDB before serving any requests.

## Technical specification

Add `MongoDB.Driver` NuGet. Configure via `process.env.MONGO_CONNECTION_STRING`. Repositories: `IChatRoomRepository`, `IMessageRepository`.

Entities match T007 schema. TTL index on `messages.sent_at` is created programmatically on startup (idempotent `CreateIndex` call).

## Acceptance criteria

- [ ] Service starts connected to MongoDB
- [ ] TTL index exists on `messages.sent_at` on first run

## Patterns demonstrated

- **Repository** — `IChatRoomRepository` and `IMessageRepository` hide "where the data actually lives" (MongoDB collections) behind a simple collection-like interface; callers never write a raw Mongo query themselves.
- **Interface Segregation (SOLID)** — chat rooms and messages are split into two separate repository interfaces instead of one combined `IChatRepository`, so a class that only needs messages isn't forced to depend on chat-room operations it never calls.
- **Dependency Inversion (SOLID)** — controllers and any future services inject `IChatRoomRepository` / `IMessageRepository`, not a concrete `MongoChatRoomRepository`, so the implementation can be swapped (e.g. for an in-memory fake in tests) without touching callers.
- **Idempotency** — `CreateIndex` is called every time the service starts, but creating an index that already exists is a safe no-op; this is the same "do it twice, get the same result as once" guarantee the project applies to Kafka consumers, applied here to startup migrations instead of message processing.
- **Defense-in-depth (system design)** — the TTL index is created both by the T007 Mongo init script and, independently, by this service's own startup code, so the ephemeral-chat privacy guarantee holds even if a developer points the service at a fresh Mongo instance that never ran the init script.

## Agent implementation notes

- Key files to create:
  - `src/services/chat-service/ChatService.csproj` — new .NET 9 MVC project, add `MongoDB.Driver` package reference here.
  - `src/services/chat-service/Program.cs` — composition root (Builder pattern, same as every other service's `Program.cs`); registers the Mongo client/database, repository implementations, and calls the TTL index setup on startup before the app starts accepting requests.
  - `src/services/chat-service/Entities/ChatRoomEntity.cs` and `src/services/chat-service/Entities/MessageEntity.cs` — match the T007 field names exactly (`_id`, `connection_id`, `user_a_id`, `user_b_id`, `status`, `created_at`, `closed_at` for chat rooms; T007's message fields including `sent_at`).
  - `src/services/chat-service/Repositories/IChatRoomRepository.cs` + `ChatRoomRepository.cs`.
  - `src/services/chat-service/Repositories/IMessageRepository.cs` + `MessageRepository.cs`.
  - `src/services/chat-service/Infrastructure/MongoIndexInitializer.cs` (or similar) — the class whose only job is ensuring the `messages.sent_at` TTL index exists; keep this separate from the repositories themselves (Single Responsibility — repositories do CRUD, this class does schema/index setup).
- Read `MONGO_CONNECTION_STRING` via `process.env`-style configuration binding (i.e. `IConfiguration` reading from environment variables, consistent with the user's "never hardcode config" rule) — do not hardcode `mongodb://localhost:27017` anywhere, including in `appsettings.json` defaults used for local dev without an env var.
- Use `IMongoCollection<MessageEntity>.Indexes.CreateOneAsync` with `CreateIndexOptions { ExpireAfter = TimeSpan.Zero }` (or the TTL duration the T007 schema specifies, if a nonzero expiry was defined there — check `sent_at`'s intended TTL duration against T007 rather than assuming `TimeSpan.Zero`) — the MongoDB driver's `CreateOneAsync` for an index that already exists with identical options is already idempotent, so no manual "does this index exist" check is needed before calling it.
- Do NOT create a message-history or export endpoint — REQUIREMENTS.md is explicit that no such endpoint exists by design, not as a missing feature. Do NOT add a generic `IChatRepository` combining rooms and messages — keep the two interfaces separate (Interface Segregation, see Patterns above).
- Do NOT wire up the SignalR hub, message send/receive endpoints, or the saga compensation step (`connection.chat-failed`) in this ticket — those belong to later Phase 6 tickets. This ticket is connection + schema + TTL enforcement only.
- Follow the project's JPA naming convention is Java-only; for .NET entities here, no `Entity` suffix convention has been mandated for C# classes in CLAUDE.md, but naming them `ChatRoomEntity` / `MessageEntity` here keeps them visually distinct from any future DTOs in this service, consistent with the spirit of the Java rule.
