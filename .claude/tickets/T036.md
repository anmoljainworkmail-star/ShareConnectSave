# T036 — SignalR Hub + Real-time Messaging

## Why this ticket exists

T035 gave Chat Service a place to store messages and a TTL index that guarantees they disappear — but nothing yet delivers a message to the other traveler, and nothing yet lets either user retrieve the short message history that should exist while a chat is still open. Without this ticket, two mutually-accepted travelers have an open connection but no way to actually talk, and there is no way to close out a successful meetup. This ticket adds the real-time delivery layer (SignalR hub) and the two REST endpoints a chat screen needs: recent message history, and the "Met Successfully" action that ends the platform's involvement in that connection, per the responsibility boundary in REQUIREMENTS.md.

## What to build

- `ChatHub : Hub` (SignalR hub) in `chat-service` with three methods:
  - `JoinRoom(chatId)` — adds the caller's connection to SignalR group `chat:{chatId}`.
  - `SendMessage(chatId, content)` — persists the message to MongoDB (via `IMessageRepository` from T035), then broadcasts it to group `chat:{chatId}`.
  - `LeaveRoom(chatId)` — removes the caller's connection from group `chat:{chatId}`.
- MVC controller (not the hub) exposing:
  - `GET /chats/:id/messages` — returns the last N messages for the chat, sorted ascending by `sent_at`. N is configurable, max 50.
  - `POST /chats/:id/met` — marks "Met Successfully" for the calling user, and triggers the chat-close flow once both users have confirmed.
- SignalR configured to use the Redis backplane, **Redis DB 1** specifically (DB 0 is already reserved for Discovery Service's cache from T008 — do not collide with it), via `Microsoft.AspNetCore.SignalR.StackExchangeRedis`.

## Technical specification

`ChatHub : Hub` with methods:
- `JoinRoom(chatId)` — add connection to SignalR group `chat:{chatId}`
- `SendMessage(chatId, content)` — persist to MongoDB, broadcast to group
- `LeaveRoom(chatId)` — remove from group

REST endpoints:
- `GET /chats/:id/messages` — returns last N messages (N configurable, max 50)
- `POST /chats/:id/met` — marks met successfully, triggers chat close flow

SignalR backplane: Redis DB 1 (`Microsoft.AspNetCore.SignalR.StackExchangeRedis`).

## Acceptance criteria

- [ ] Two clients in same group receive messages in real-time
- [ ] Messages persisted to MongoDB before broadcast
- [ ] `GET /chats/:id/messages` returns messages sorted ascending by `sent_at`

## Patterns demonstrated

- **Single Responsibility (SOLID)** — `ChatHub` only handles real-time connection/group management and delegates persistence to `IMessageRepository`; it does not contain REST/history logic, and the controller does not contain real-time logic.
- **Dependency Inversion (SOLID)** — `ChatHub` and the new `ChatController` inject `IMessageRepository` / `IChatRoomRepository` (from T035) and a new `IChatService`, never a concrete Mongo class directly.
- **Thin Controller / Service Layer** — the MVC controller only validates input and calls `IChatService`; all "mark met, check if both users met, trigger close flow" logic lives in the service, not the controller.
- **Observer (via SignalR groups)** — clients subscribed to a `chat:{chatId}` group react independently to a broadcast `SendMessage` call; the hub does not need to know who, or how many clients, are listening.
- **Database per Service / Cache-Aside boundary (system design)** — Redis DB 1 is dedicated to the SignalR backplane so Chat Service's realtime state never collides with Discovery Service's cache in Redis DB 0, even though both share the same Redis instance.
- **Saga step (system design)** — `POST /chats/:id/met` is the trigger point for the next step of the `ConnectionLifecycleSaga` (eventually publishing `chat.closed` once both users confirm); this ticket only needs to call into that step, not implement the whole saga.

## Agent implementation notes

- Key files to create:
  - `src/services/chat-service/Hubs/ChatHub.cs` — the SignalR hub. `JoinRoom`, `SendMessage`, `LeaveRoom` only. Inject `IMessageRepository` and `IChatRoomRepository` (or a thin `IChatService` wrapping them — prefer this so the hub itself stays free of business logic).
  - `src/services/chat-service/Controllers/ChatController.cs` — MVC controller (per CLAUDE.md's ".NET services use MVC Controllers, not Minimal API" rule) with `GET /chats/{id}/messages` and `POST /chats/{id}/met`. This controller must be thin and delegate to `IChatService` — do not query MongoDB or touch SignalR groups directly from the controller.
  - `src/services/chat-service/Services/IChatService.cs` + `ChatService.cs` — owns the business logic: fetching last-N messages, marking a user as "met successfully", and deciding when both sides have confirmed (triggering the close flow / saga step).
  - `src/services/chat-service/Program.cs` — register `AddSignalR().AddStackExchangeRedis(...)` pointed at Redis **DB 1** (read the Redis connection string from `process.env`-style configuration, same as T035's Mongo connection string — never hardcode `localhost`), map the hub endpoint (e.g. `app.MapHub<ChatHub>("/hubs/chat")`), and register `IChatService`.
- **Do NOT put REST endpoint logic inside `ChatHub`.** The hub is for real-time group messaging only (`JoinRoom`/`SendMessage`/`LeaveRoom`). `GET /chats/:id/messages` and `POST /chats/:id/met` belong on the MVC controller, which itself must stay thin and delegate to `IChatService` — this follows both the project's "MVC Controllers, not Minimal API" rule and its "thin controllers require a service layer" rule. A common mistake on this kind of ticket is writing the history/met-flow logic as extra hub methods or as inline controller code instead of a separate service class — avoid both.
- Cap N at 50 server-side in `IChatService`, regardless of what a caller requests — do not trust a client-supplied limit above the max.
- Sort messages ascending by `sent_at` at the query level (e.g. in `IMessageRepository`'s query, or in `IChatService` after fetching) — do not rely on insertion order.
- `SendMessage` must persist before broadcasting (acceptance criterion requires persistence-before-broadcast, not fire-and-forget in parallel) — await the repository call, then broadcast to the group.
- Do not implement the full `ConnectionLifecycleSaga` compensating-transaction logic in this ticket; `POST /chats/:id/met` only needs to record the "met" confirmation and call into the next step (publishing whatever event marks the chat as closed) — the broader saga/outbox wiring is out of scope here unless a later ticket says otherwise.
- Reuse the `IChatRoomRepository` / `IMessageRepository` interfaces and `ChatRoomEntity` / `MessageEntity` entities created in T035 — do not redefine them.
