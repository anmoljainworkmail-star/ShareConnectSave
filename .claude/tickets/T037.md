# T037 — Chat Lifecycle (Open / Auto-close)

## Why this ticket exists
A chat that opens but never reliably closes is a trust and privacy problem, not just a bug. The platform's whole promise in REQUIREMENTS.md is temporary, disposable chat — "No message history persists after chat closes" is listed as a hard requirement, and CLAUDE.md says the platform's involvement ends the moment both users mark Met Successfully. Without this ticket, there is no code path that actually enforces either of those closing rules: rooms would stay OPEN forever, messages would rely solely on MongoDB's TTL index to eventually clean up (a window, not a guarantee), and downstream services (Rating Service in particular) would never learn a chat ended, so the mandatory post-chat rating flow could never trigger. This ticket is what turns "chat is temporary" from a policy statement into an enforced state machine.

## What to build
- `ChatRoom` state machine with three states: `OPEN` → `CLOSING` → `CLOSED`.
- `POST /chats/{id}/met` endpoint (MVC controller action) — either user calls this to mark Met Successfully.
  - Transitions room to `CLOSING`.
  - Starts a 5-minute grace timer (`Task.Delay`) before finalizing the close.
  - After the grace period, transitions to `CLOSED`.
- `ChatAutoCloseHostedService` — an `IHostedService` background worker that polls every 5 minutes for rooms that have been `OPEN` longer than 2 hours, and auto-closes them.
- Shared close routine (`ICloseChatRoomService` or similar) used by both the `met` endpoint's grace-timer completion and the auto-close poller, so there is exactly one place that implements "what happens when a room closes":
  - Explicitly delete all messages for that room from MongoDB (do not rely on the TTL index alone).
  - Publish a `chat.closed` Kafka event (via the Outbox pattern, consistent with other producers in this codebase).
  - Transition room status to `CLOSED`.
- Room open/close timestamps needed to support the 2-hour auto-close check (e.g. `OpenedAtUtc` on the chat room document/record).

## Technical specification
### T037 — Chat Lifecycle (Open / Auto-close)

**Service:** `chat-service`
**Language:** .NET 9
**Depends on:** T036
**Skills/Commands:** none

**Spec:**
Chat room states: `OPEN` → `CLOSING` → `CLOSED`.

- Open: created when `connection.accepted` Kafka event received (T038).
- `POST /chats/:id/met`: transitions to `CLOSING`, starts 5-min grace timer (background `Task.Delay`), then `CLOSED`.
- Auto-close: `IHostedService` polls every 5 minutes, closes rooms open longer than 2 hours.

On close (any path): delete all messages from MongoDB (not just TTL expiry — explicit delete), publish `chat.closed` Kafka event.

## Acceptance criteria
- [ ] Met Successfully → room closes after 5-min grace, messages deleted
- [ ] Room open > 2 hours → auto-closed
- [ ] `chat.closed` event published on all close paths
- [ ] Messages are explicitly deleted, not just left to TTL (belt-and-suspenders)

## Patterns demonstrated
- **Single Responsibility (SOLID S)** — the shared close routine only knows how to close a room (delete messages, publish event, flip status); it has no opinion on *why* a room is closing (grace timer vs. 2-hour poll), keeping that decision in the two callers.
- **Template/shared-routine reuse over duplication** — both close triggers (met-grace-timer and auto-close poll) funnel into one close implementation, so "what closing means" can only be defined in one place; this is the same motivation behind `IOutboxService` being the single abstraction every Kafka producer in this project depends on (Dependency Inversion, SOLID D).
- **Observer (via events)** — `chat.closed` is published once, without the Chat Service knowing or caring who reacts to it; Rating Service picks it up to trigger ratings. Same shape as `connection.accepted` elsewhere in this project.
- **Outbox Pattern** — the `chat.closed` publish must go through the same outbox-table-then-relay mechanism as every other Kafka producer in this codebase, so a crash between closing the room and publishing the event can't cause a silent split-brain (room marked CLOSED in SQL but no event ever sent).
- **IHostedService (background worker)** — the auto-close poller is a long-running background task managed by the .NET host lifecycle, not a request-triggered action; this is the standard .NET idiom for "do this periodically regardless of traffic."

## Agent implementation notes
- Key files to create (paths are illustrative — follow this service's existing folder conventions from T035/T036):
  - `chat-service/Controllers/ChatController.cs` — add the `POST /chats/{id}/met` action (thin controller, delegates to a service — see `feedback-thin-controllers-require-service-layer` convention already established in this codebase since T018).
  - `chat-service/Services/IChatLifecycleService.cs` / `ChatLifecycleService.cs` — owns the `met` transition, the grace timer, and calls the shared close routine.
  - `chat-service/Services/ICloseChatRoomService.cs` / `CloseChatRoomService.cs` (or fold into `ChatLifecycleService` if the skill file's conventions prefer fewer abstractions — check `dotnet-mvc-controllers` skill) — the single shared "close a room" implementation: delete messages, publish `chat.closed` via outbox, set status `CLOSED`.
  - `chat-service/HostedServices/ChatAutoCloseHostedService.cs` — polls every 5 minutes for rooms `OPEN` longer than 2 hours and invokes the shared close routine.
  - Register the hosted service in `Program.cs` via `builder.Services.AddHostedService<ChatAutoCloseHostedService>()` (Builder pattern already established in this codebase's composition roots).
- Follow this service's existing `dotnet-mvc-controllers` skill conventions for controller/service separation — do not put Mongo or Kafka calls directly in the controller.
- What NOT to do:
  - Do not implement the close logic twice (once inline in the `met` grace-timer continuation, once inline in the hosted service poll loop) — both must call the same shared service method. Duplicating it is the most common mistake for this kind of two-trigger lifecycle ticket and defeats the point of "on close (any path)" in the spec.
  - Do not skip the explicit MongoDB delete because "the TTL index will get it eventually" — the spec and REQUIREMENTS.md both call this out as a hard, non-negotiable requirement, independent of TTL.
  - Do not publish `chat.closed` directly via a Kafka producer client — it must go through the outbox table like every other producer in this project, or it will be inconsistent with the rest of the codebase's Saga/Outbox approach.
  - `Task.Delay` for the 5-minute grace timer is an in-process timer — note (but do not fix in this ticket) that it will not survive a service restart mid-grace-period; that's an acceptable known limitation for this ticket's scope, not something to silently work around with added complexity.

## Known follow-ups
A prior design discussion (surfaced from T030's follow-up notes, not a `/review-task` finding) found that `ConnectionStatus` has no `CANCELLED` or equivalent early-exit state — today a user can only end an ACCEPTED connection via mutual "Met Successfully" or the 2-hour chat timeout, with no way to bail out early if unhappy with the match. That note flagged T037 as a candidate place to address it. This ticket does **not** do so: T037 is scoped strictly to the two documented close paths (Met Successfully grace-close, and 2-hour auto-close timeout) and must not add a connection-side status transition or early-exit path. This is intentionally out of scope here — flag it as such rather than silently ignoring it, so a future ticket (or a SPECS.md update introducing a "cancel connection" requirement) can pick it up deliberately.
