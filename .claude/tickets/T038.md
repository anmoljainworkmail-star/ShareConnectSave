# T038 — Kafka Consumer: connection.accepted

## Why this ticket exists
Right now, two users can mutually accept a connection request and nothing happens on the chat side — there is no code that reacts to that acceptance at all. REQUIREMENTS.md is explicit that chat "opens only after mutual acceptance of a connection request," and the whole point of Connection Service publishing `connection.accepted` (T032) is that other services react to it independently, without Connection Service needing to know who's listening. Without this ticket, that event has no listener on the Chat Service side: no chat room ever gets created, neither user is notified, and the entire temporary-chat feature described in REQUIREMENTS.md section 6 simply cannot start. This is the one piece of code that turns "two people agreed to meet" into "a chat room actually exists and both phones know about it."

## What to build
- A Kafka consumer in `chat-service` subscribed to the `connection.accepted` topic.
- On receipt of a valid, not-yet-processed event: create a new `chat_room` MongoDB document with status `OPEN`.
- Idempotency check against a `processed_events` collection/table before acting, so a redelivered `connection.accepted` for a connection that already has an OPEN room does not create a second room.
- SignalR notification: send a `ChatOpened` event to both users via their personal SignalR groups (`user:{id}`), one group per participant on the connection.

## Technical specification
### T038 — Kafka Consumer: connection.accepted

**Service:** `chat-service`
**Language:** .NET 9
**Depends on:** T037, T009
**Skills/Commands:** none

**Spec:**
Consume `connection.accepted`. On receipt: create a new `chat_room` document with status `OPEN`, notify both users via SignalR (send `ChatOpened` event to each user's personal SignalR group `user:{id}`).

## Acceptance criteria
- [ ] Kafka event → chat room created within 1 poll cycle
- [ ] Both users receive `ChatOpened` SignalR notification

## Patterns demonstrated
- **Observer (via events)** — `connection.accepted` is published once by Connection Service; Chat Service (this ticket) and Notification Service each react independently without Connection Service knowing or caring who is listening.
- **Idempotency** — Kafka delivery is at-least-once, so this consumer must check `processed_events` before creating a room; processing the same `connection.accepted` message twice must not produce two chat rooms.
- **Database per Service** — Chat Service creates and owns the `chat_room` document in its own MongoDB store; it does not reach into Connection Service's database to read or confirm the connection's state.
- **Single Responsibility (SOLID S)** — the consumer's only job is "turn this event into a room + a notification"; it does not implement chat lifecycle/closing logic (that's T037's `ICloseChatRoomService`) and does not publish any outbound event itself.

## Agent implementation notes
- Key files to create (follow this service's existing folder conventions from T035/T036/T037):
  - `chat-service/Messaging/Consumers/ConnectionAcceptedConsumer.cs` — the Kafka consumer/background service that subscribes to `connection.accepted`.
  - `chat-service/Services/IChatRoomService.cs` / `ChatRoomService.cs` (or extend the lifecycle service from T037 if the skill conventions prefer fewer abstractions) — owns creating the `chat_room` document; the consumer calls into this rather than talking to MongoDB directly.
  - Reuse or extend whatever `processed_events` idempotency helper already exists from earlier Kafka consumer tickets (see T033's `trust.score.updated` consumer for the established pattern) — do not invent a second idempotency mechanism.
  - SignalR notification goes through the Chat Service's hub (from T036) — send `ChatOpened` to each user's `user:{id}` group; look up both participant ids from the `connection.accepted` event payload, not from a second call back to Connection Service.
- Follow the `kafka-outbox` skill's idempotent-consumer section for the `processed_events` check-then-act shape (check first, create room, record processed, in that order — matching the established pattern from T033).
- Follow the `dotnet-mvc-controllers` skill's service-layer convention: the consumer class should be thin and delegate persistence + notification to injected services (`IChatRoomService`, the SignalR hub context), not do Mongo/SignalR calls inline.
- What NOT to do:
  - Do not publish a `connection.chat-opened` (or similarly named) Kafka event from this consumer. A future Phase 14 ticket (T096, not yet created) adds that topic to the contracts and Chat Service's own outbox relay — it does not exist yet, and inventing the publish call here would create a producer for a topic no other service's schema or consumer contract knows about.
  - Do not skip the `processed_events` idempotency check "because Connection Service's outbox relay already guarantees at-least-once delivery, not exactly-once" — that guarantee is exactly why this check is required here, not a reason to omit it.
  - Do not create the chat room directly from the controller or from Connection Service's call — this must be driven only by the consumed Kafka event, per the Event-Driven Architecture principle in CLAUDE.md (services react to things that happened, they are not commanded).
  - Do not query Connection Service's database or API to re-confirm the connection is accepted — trust the event payload; cross-service DB reads violate Database-per-Service.
