# T039 — Kafka Producer: chat.closed

## Why this ticket exists
T037 already decides *when* a chat room closes (Met Successfully + 5-min grace, or the 2-hour auto-close timeout) and already calls a shared close routine to delete the room's messages and flip its status to `CLOSED`. But nothing in Chat Service has ever talked to Kafka before this ticket — T035/T036/T037 only needed Mongo and SignalR — so there is no `outbox` table, no `IOutboxService`, and no relay process in this service yet. Until this ticket ships, `chat.closed` never leaves Chat Service: Rating Service never learns a chat ended, so the mandatory post-"Met Successfully" rating prompt (REQUIREMENTS.md section 7) never fires, and Notification Service never gets to tell either user the conversation is over. This is also the saga step where a silent gap would be worst: the room is already gone (messages deleted, status `CLOSED`) by the time this event would publish, so if the publish is lost, there is no second chance to tell anyone it happened — which is exactly why it must be written to the local outbox in the same transaction as the close, not fired off directly.

## What to build
- First `outbox` table + `IOutboxService` + `OutboxRelay` for `chat-service` (this service has never published to Kafka before).
- `OutboxEvent` entity/table — same shape as every other producing service in this codebase (per the `kafka-outbox` skill): id (doubles as `event_id`), topic, partition key, payload, status (`PENDING`/`PROCESSED`), created/processed timestamps.
- `IOutboxService.Publish(topic, partitionKey, payload)` — writes a `PENDING` outbox row inside the caller's existing transaction/unit of work. No new transaction boundary of its own.
- `OutboxRelay` — a background worker (`IHostedService`, matching the `ChatAutoCloseHostedService` idiom already in this service from T037) that polls pending outbox rows and publishes each to Kafka via `Confluent.Kafka`, using `partition_key` as the Kafka message key, marking rows `PROCESSED` on success and leaving them `PENDING` to retry on failure.
- Wires T037's shared close routine (`ICloseChatRoomService` / `ChatLifecycleService`, whichever name T037 landed on) to call `IOutboxService.Publish("chat.closed", chatId, chatClosedEvent)` in the same local transaction as the messages-deleted + status-`CLOSED` write — on **both** close paths (grace-timer completion and the 2-hour auto-close poll), since both funnel through that one shared routine.
- `ChatClosedEvent` payload matching `chat.closed.schema.json` (T002): `chat_id`, `connection_id`, `user_a_id`, `user_b_id`, `closed_reason`.

## Patterns demonstrated
- **Outbox Pattern** — the close routine never calls `Confluent.Kafka` directly; it writes a row to the local `outbox` table in the same transaction as the messages-deleted + status-`CLOSED` write, and `OutboxRelay` is the only component that ever talks to Kafka. A crash between "room closed in the DB" and "event published" can't cause a silent split-brain, matching the same guarantee Connection Service's T032 already demonstrated.
- **Single Responsibility (SOLID S)** — `OutboxRelay` only publishes pending rows; it has no idea what a chat room, a connection, or a rating is. `IOutboxService`'s implementation only knows how to write a row; it doesn't decide when a room closes (that's still entirely T037's job).
- **Dependency Inversion (SOLID D)** — T037's close routine depends on `IOutboxService`, never on `IProducer<string, string>`/`Confluent.Kafka` types directly, so it has no idea whether the event ends up on Kafka, a log, or nowhere yet.
- **Liskov Substitution (SOLID L)** — this ticket's outbox implementation is local to chat-service, same as Connection Service's T032 implementation is local to connection-service; callers depend only on `IOutboxService`'s contract, so a future shared implementation can substitute in without touching T037's code.
- **Observer (GoF, via events)** — `chat.closed` is published exactly once, with Chat Service having no idea who's listening. Rating Service and Notification Service each react independently, matching the same shape as `connection.accepted` and `chat.closed`'s sibling events elsewhere in this project.
- **Idempotency (groundwork)** — the outbox row's own id is reused as the event's `event_id` in the published envelope, which is what lets Rating Service and Notification Service's consumers dedupe a redelivered message. This ticket lays that groundwork; it doesn't need to dedupe anything itself.

  - `chat-service/Outbox/OutboxEvent.cs` — entity matching the `outbox` table shape from the `kafka-outbox` skill.
  - `chat-service/Outbox/OutboxStatus.cs` — `PENDING` / `PROCESSED`.
  - `chat-service/Outbox/IOutboxService.cs` / `OutboxService.cs` — `Publish(string topic, string partitionKey, object payload)`, serializes payload to JSON, inserts a `PENDING` row using the caller's already-open transaction/`DbContext` — do not start a new transaction here.
  - `chat-service/Outbox/OutboxRelay.cs` — `IHostedService` (same idiom as `ChatAutoCloseHostedService` from T037), polls pending rows on a short interval, publishes each via `Confluent.Kafka`'s `IProducer<string, string>` using `partition_key` as the message key, marks `PROCESSED` only after a successful send, leaves `PENDING` on failure for the next tick.
  - A new EF Core migration adding the `outbox` table — check the service's existing migrations first and number accordingly.
  - `chat-service/Events/ChatClosedEvent.cs` — the payload DTO: `chat_id`, `connection_id`, `user_a_id`, `user_b_id`, `closed_reason`.
  - Modify T037's shared close routine to call `IOutboxService.Publish("chat.closed", chatId, chatClosedEvent)` instead of whatever placeholder/TODO it currently has — this is the one call site; both close paths (grace-timer and auto-close poll) already route through it, so do not add a second call site.
- Follow the `kafka-outbox` skill's relay section for the exact polling/transactional shape; follow the `dotnet-mvc-controllers` skill's DI conventions for registering `IOutboxService` and the hosted relay in `Program.cs` (Builder pattern, same composition-root style as every other service).
- `closed_reason` should distinguish the two close paths T037 already defines (Met Successfully vs. 2-hour auto-close timeout) — check `chat.closed.schema.json` (T002) for the exact enum/string values the contract expects rather than inventing new ones here.
- What NOT to do:
  - Do not publish to Kafka directly from the code path that closes the room (T037's grace-timer continuation or the auto-close poller) — write the outbox row in the same transaction as the close, and let `OutboxRelay` be the only thing that ever calls `Confluent.Kafka`. This is the single most common mistake for this ticket shape.
  - Do not wrap `IOutboxService.Publish(...)` in its own transaction — it must participate in the caller's existing transaction (the same one that deletes messages and sets status `CLOSED`), or the whole point of the Outbox Pattern (atomicity between business-data change and event write) is lost.
  - Do not build a second, parallel notion of "what closing means" — this ticket only adds the publish call inside T037's existing shared close routine; it must not duplicate the messages-delete or status-transition logic.
  - Do not add retry-count/DLQ handling to `OutboxRelay` in this ticket — on a failed send, leave the row `PENDING` so the next poll retries it naturally, consistent with Connection Service's T032 relay.
  - Do not skip including `event_id` in the published envelope — downstream consumers (Rating Service, Notification Service) need it to dedupe.
