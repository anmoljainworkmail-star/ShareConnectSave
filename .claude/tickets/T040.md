# T040 — Chat Service Docker Image

## Why this ticket exists
Chat Service is written in .NET and, right now, cannot run in the local Docker Compose stack — it has no Dockerfile. The `chat-service` block already exists in `src/infra/docker-compose.yml` (port `8084:8080`, depends on `mongodb`/`redis`/`kafka`, healthcheck hitting `/health`) and in `docker-compose.override.yml` (Mongo connection string, Redis connection for the SignalR backplane, Kafka bootstrap) — but `docker compose up chat-service` fails today because there's nothing to build. Without this ticket, Chat Service can't be started alongside the other 8 microservices for full-stack integration testing of Phase 6's chat flow: chat opening on `connection.accepted`, TTL-based message deletion, and the `chat.closed` event T039 just wired up. This ticket only supplies the missing Dockerfile — it does not touch the compose wiring, which is already correct.

## What to build
- `src/services/chat-service/Dockerfile` — multi-stage build, same proven pattern as `api-gateway` (T014):
  - `build` stage: `mcr.microsoft.com/dotnet/sdk:9.0`, restores `chat-service.csproj`, publishes Release output.
  - `runtime` stage: `mcr.microsoft.com/dotnet/aspnet:9.0`, installs `curl` (needed for the existing compose healthcheck), copies only the published output, entrypoint `dotnet chat-service.dll`.
- No changes to `src/infra/docker-compose.yml` or `docker-compose.override.yml` — both already have correct `chat-service` blocks wired to MongoDB, Redis, and Kafka. Verify them, don't duplicate them.

## Patterns demonstrated
- **Multi-stage build** — separates the heavy SDK build toolchain from the minimal ASP.NET runtime image, so the shipped image carries no compiler, NuGet cache, or source tree — only the published binaries needed to run.
- **Separation of Build-Time and Run-Time Concerns** — the runtime stage never runs `dotnet build`/`dotnet restore`; it only executes what the build stage already produced.

## Agent implementation notes
- Key files to create:
  - `src/services/chat-service/Dockerfile` (new) — this is the only file this ticket should create.
- Pattern to follow: copy the exact two-stage shape already shipped in `src/services/api-gateway/Dockerfile` (T014), adapted to this project name:
  - `COPY chat-service.csproj ./` then `RUN dotnet restore` before `COPY . .` and `dotnet publish`, for Docker layer caching (restore layer is only invalidated when the `.csproj` itself changes).
  - Runtime stage installs `curl` via `apt-get` (same as gateway) because `docker-compose.yml`'s existing healthcheck runs `curl -f http://localhost:8080/health` from inside the container, and `mcr.microsoft.com/dotnet/aspnet:9.0` doesn't ship `curl` by default.
  - `COPY --from=build /app/publish .` — never `COPY . .` in the runtime stage.
  - `ENTRYPOINT ["dotnet", "chat-service.dll"]`.
  - Do NOT set `ASPNETCORE_URLS`/`ASPNETCORE_ENVIRONMENT` via `ENV` in the Dockerfile — `docker-compose.yml` and `docker-compose.override.yml` already set both; duplicating them creates two sources of truth that can drift.
- What NOT to do (common mistakes for this task type):
  - Do not re-add or edit the `chat-service` service block in `src/infra/docker-compose.yml` or `docker-compose.override.yml` — both already exist and are correctly wired (ports, healthcheck, `depends_on: mongodb, redis, kafka`, Mongo/Redis/Kafka env vars). This ticket is Dockerfile-only.
  - Unlike `api-gateway` (T014), which only needed to reach other HTTP services, chat-service's existing `depends_on` already requires `mongodb` and `redis` to be `service_healthy`, not just `kafka` — do not assume a plain HTTP-service dependency chain is enough when verifying this ticket; confirm the container can actually resolve and reach `mongodb:27017` and `redis:6379` on the compose network, since a missing/misconfigured Mongo or Redis connection string would fail silently at runtime rather than at build time.
  - Do not hardcode port numbers inside the Dockerfile — `docker-compose.yml` already controls the external port mapping (`8084:8080`).
  - Do not create a `.dockerignore` file — same deferral made consistently since T028/T034.
  - Do not assume the SQL-Server-specific `SPRING_PROFILES_ACTIVE` gap documented for Java services (T028/T034 follow-ups) applies here — chat-service is ASP.NET Core (`ASPNETCORE_ENVIRONMENT`), not Spring Boot, and already has no such gap in its override block.
