# T041 — Spring Boot Setup + DB Schema

## Why this ticket exists
Right now there is no runnable Rating Service — no way for the system to store ratings after a chat closes or to calculate the trust score that drives visibility and request throttling in Discovery and Connection services. This ticket stands the service up so it can boot, talk to its own database, and run its Flyway migrations on startup. Without it, Phase 7's promised behavior has nowhere to live: no rating persistence, no trust score recalculation, no `rating.submitted` or `trust.score.updated` event consumers — all depend on this service existing first. Rating Service also establishes the `TrustScoreCalculator` (the pure function that other services will eventually call), so getting the entity and schema shapes right here sets the foundation that later phase tickets (notification push, discovery limiting, connection throttling) build on.

## What to build
- Maven project `rating-service` (Java 21, Spring Boot 3) — same setup pattern as T021 (`discovery-service`)
- Dependencies: Spring Web, Spring Data JPA, Spring Kafka, Validation, Actuator, Lombok, MapStruct, Flyway, plus `shared-java-lib` (T003) for `ErrorResponse` / `GlobalExceptionHandler`
- `src/main/resources/application.yml` with `dev` and `prod` Spring profiles, `spring.threads.virtual.enabled: true` in the shared/base section
- `DataSource` config reading `RATING_DB_HOST`, `RATING_DB_PORT`, `RATING_DB_NAME`, `RATING_DB_USERNAME`, `RATING_DB_PASSWORD` environment variables
- Flyway migration for the `ratings` and `trust_scores` tables (see T006 schema) — create `/services/rating-service/src/main/resources/db/migration/V001__rating_service_initial_schema.sql`
- JPA entities:
  - `Rating` mapped to `ratings` table, with columns: `id`, `rater_id`, `rated_id`, `connection_id`, `tags` (persisted as JSON array), `created_at`
  - `TrustScore` mapped to `trust_scores` table, with columns: `id`, `user_id`, `score`, `badge_level`, `request_limit`, `updated_at`
- Enum: `BadgeLevel` with values `NONE`, `TRUSTED` (used in `TrustScore.badge_level`)
- Enum: `RequestLimit` with values `UNLIMITED`, `THROTTLED`, `SUSPENDED` (used in `TrustScore.request_limit`)
- `GET /actuator/health` returning `{ "status": "UP" }` once SQL Server is reachable and Flyway has run

## Patterns demonstrated
**Database per Service** — `ratings` and `trust_scores` live only in Rating Service's own schema; Discovery, Connection, and Chat services learn about trust state only through Kafka events (`trust.score.updated`), never a cross-service query or join.

**Single Responsibility (SOLID-S)** — this ticket wires infrastructure only (DB connectivity, Flyway, health check, the bare entity/table shapes). No endpoints, no calculator logic, no Kafka consumers — those are deliberately left to later Phase 7 tickets.

**Open/Closed (SOLID-O)** — `badge_level` and `request_limit` are stored as plain string columns, not SQL `CHECK` constraints enumerating values. What counts as valid badge levels or request limits is business logic living in Java enums, so adding a future badge or limit category is a code change, not a migration. Similarly, `tags` is a JSON array — new tag types can be added to the system without altering the schema.

**Repository (GoF)** — later tickets will access `Rating` and `TrustScore` rows through `ISpringDataRatingRepository` and `ITrustScoreRepository`-style interfaces built on Spring Data JPA, never raw `EntityManager` queries scattered through the codebase; this ticket only lays the entity groundwork that repositories will sit on.

- Key files to create/verify:
  - `/services/rating-service/pom.xml` — Maven parent `spring-boot-starter-parent`, Java 21, dependency on `com.shareconnectsave:shared-java-lib`
  - `/services/rating-service/src/main/java/com/shareconnectsave/rating/RatingServiceApplication.java` — `@SpringBootApplication` entry point
  - `/services/rating-service/src/main/resources/application.yml` — base config + `dev`/`prod` profile blocks, all secrets/hosts via `${ENV_VAR}` placeholders per the `java-spring-boot` skill
  - `/services/rating-service/src/main/resources/db/migration/V001__rating_service_initial_schema.sql` — Flyway migration creating `ratings` and `trust_scores` tables exactly as defined in T006
  - `/services/rating-service/src/main/java/com/shareconnectsave/rating/domain/Rating.java` — `@Entity`, `@Getter @Builder @NoArgsConstructor @AllArgsConstructor` (per skill; avoid Lombok `@Data`), `tags` field typed as `String` with `@Column(columnDefinition = "NVARCHAR(MAX)")` to store JSON array
  - `/services/rating-service/src/main/java/com/shareconnectsave/rating/domain/TrustScore.java` — `@Entity`, same Lombok pattern, `badge_level` typed as `BadgeLevel` enum with `@Enumerated(EnumType.STRING)`, `request_limit` typed as `RequestLimit` enum with `@Enumerated(EnumType.STRING)`
  - `/services/rating-service/src/main/java/com/shareconnectsave/rating/domain/BadgeLevel.java` — enum: `NONE`, `TRUSTED`
  - `/services/rating-service/src/main/java/com/shareconnectsave/rating/domain/RequestLimit.java` — enum: `UNLIMITED`, `THROTTLED`, `SUSPENDED`
  - `/services/rating-service/src/main/java/com/shareconnectsave/rating/exception/` — thin re-export of `shared-java-lib`'s `GlobalExceptionHandler`, same pattern as T021 — do not copy its code
- Follow the `java-spring-boot` skill's package-by-feature layout (`com.shareconnectsave.rating.*`) so later tickets (rating submission, trust score calculation, Kafka consumers) slot in without restructuring
- `application.yml` must read `RATING_DB_HOST`, `RATING_DB_PORT`, `RATING_DB_NAME`, `RATING_DB_USERNAME`, `RATING_DB_PASSWORD`, and `KAFKA_BROKERS` — no hardcoded connection strings, matching the user's `process.env.*`-for-config preference
- `spring.threads.virtual.enabled: true` goes in the base (shared) section of `application.yml`, not inside a single profile
- Actuator: only expose `health` (and `info` if trivial) in `management.endpoints.web.exposure.include`
- When creating the Flyway migration SQL file (`V001__rating_service_initial_schema.sql`), ensure:
  - `ratings` table includes a non-nullable foreign key constraint to `users` table via `rater_id` and `rated_id` (even though User Service owns the `users` table, Rating Service should document this dependency in the migration as a comment or in the constraint name)
  - `tags` column uses SQL Server's `NVARCHAR(MAX)` for JSON flexibility
  - `trust_scores` table includes an index on `user_id` for fast lookups by later queries
  - Both tables have indexes on `created_at` / `updated_at` for time-range queries (not required for this ticket but good practice per T006's acceptance criteria)
- What NOT to do:
  - Do not write any controller, calculator logic, or Kafka consumer code — those start in later Phase 7 tickets. This ticket is setup + schema only.
  - Do not create a Flyway migration if one already exists at the expected path — check it first
  - Do not use `RestTemplate` anywhere, even in placeholder code — use `WebClient` per the skill
  - Do not hardcode `localhost` or container IPs in `application.yml` — everything comes from environment variables
  - Do not add validation constraints at the entity level (e.g., `@NotNull`, `@Size`) — keep entities as simple data containers; validation belongs in service/controller layers
