# T042 — Rating Submission Endpoint

## Why this ticket exists
Right now Rating Service can boot and reach its database (T041), but there is still no way for a traveler to submit a rating after a chat closes — the endpoint that triggers trust score recalculation does not exist. This ticket builds the single POST endpoint that turns `ratings` from an empty table into a real, auditable record of traveler behavior. Ratings are the only input to the Trust Score Calculator (T043); without this endpoint, there is nothing to rate, nothing to recalculate, and the entire Phase 7 goal — "trust score calculation drives discovery visibility" — stays unmet. Additionally, this endpoint is the entry point for the rating.submitted Kafka event, which Chat Service and Notification Service depend on to know when to prompt users and when to close rating windows.

## What to build
- **Outbox infrastructure (rating-service has none yet — build it here, mirroring connection-service's T032 exactly, scaled to this service):**
  - `outbox` table via a new Flyway migration (`V002__rating_service_outbox_table.sql`)
  - `OutboxEvent` JPA entity — `id` (UUID, app-assigned, doubles as the event's `event_id` for consumer dedup), `topic`, `partitionKey`, `payload` (JSON string), `status` (`PENDING`/`PROCESSED`), `createdAt`, `processedAt`
  - `OutboxStatus` enum — `PENDING`, `PROCESSED`
  - `OutboxRepository extends JpaRepository<OutboxEvent, UUID>` — plain name, no `I` prefix (this project's repository naming convention; connection-service's own `OutboxRepository` was already renamed away from `IOutboxRepository` to match)
  - `IOutboxService` interface — `publish(String topic, String partitionKey, String eventId, Object payload)` (note: `eventId` is a caller-supplied parameter, not auto-generated — the caller already minted a UUID for the event payload's own `event_id` field and passes the same value here so one id does double duty as both the Kafka envelope's dedup key and this outbox row's primary key) — and `OutboxServiceImpl`, which serializes `payload` to JSON and inserts a `PENDING` row using the caller's existing transaction (no `@Transactional` of its own)
  - `OutboxRelay` — `@Component`, `@Scheduled(fixedDelay = 500)`, `@Transactional` per batch — polls pending rows oldest-first, publishes each to Kafka via `KafkaTemplate<String, String>` using `partitionKey` as the message key, marks `PROCESSED` on a successful synchronous send (`.get()`), leaves `PENDING` on failure (next tick retries — no DLQ/retry-count logic, same as T032)
  - This is the only outbox code rating-service needs for this ticket; later Phase 7 tickets (T044's `trust.score.updated` producer) reuse this same `IOutboxService`/`OutboxRelay`, they don't rebuild it
- `RatingController` — `POST /ratings`
- `RatingService` interface + `RatingServiceImpl` — holds all validation logic, outbox publishing, and persistence; controller stays thin (per user preference: every controller delegates to a service layer)
- `IRatingRepository extends JpaRepository<Rating, Long>` — query methods for "has this user rated this connection already" (via count or existence check). `Rating`'s id is `Long` (BIGINT IDENTITY, see T041's `V001__rating_service_initial_schema.sql`), not `UUID` — same convention every other service on this platform uses (BIGINT ids, never UUID).
- `RatingTag` enum — all positive and negative tags from REQUIREMENTS.md §7 as values. Note: `contracts/openapi/rating-service.yaml`'s `RatingTag` schema uses human-readable wire strings with spaces/punctuation (`"On time"`, `"Didn't show up"`, `"Asked for money"`, etc.), which are not valid Java enum identifiers — map each enum constant's JSON representation explicitly (e.g. Jackson `@JsonValue`/`@JsonCreator`, or a dedicated `fromWireValue()`/`toWireValue()` pair) rather than relying on Jackson's default enum (de)serialization, which would otherwise read/write the Java identifier name (`ON_TIME`) instead of the contract's actual string (`"On time"`)
- Domain-specific `@RestControllerAdvice` (rating-service local, alongside the shared `GlobalExceptionHandler` from `shared-java-lib`) mapping: `DuplicateRatingException` → 409 `RATING_ALREADY_SUBMITTED`, `InvalidRatingTagException` → 400 `INVALID_RATING_TAG`, `ChatNotClosedException` → 400 `CHAT_NOT_CLOSED`
- `DuplicateRatingException`, `InvalidRatingTagException`, `ChatNotClosedException` — domain-specific exceptions
- `RatingSubmissionDto` `{ connection_id, rated_id, tags, comment }` (field names and optional `comment` match `contracts/openapi/rating-service.yaml`'s `RatingSubmitRequest` exactly — not `rated_user_id`, which doesn't match the contract or `Rating.ratedId`), `RatingResponse` (for echo-back after submission, optional for client display) via MapStruct `RatingMapper`
- On `POST /ratings`, inside one `@Transactional` method: validate the submitter (rater) is not rating themselves, check if rating already exists on this connection/rater pair, validate all tags are in the `RatingTag` enum, validate the connection's chat is closed (Kafka-sourced via a `ClosedChat` or similar cache, or HTTP call to Connection Service if available in your T041 design), persist the rating, write the `rating.submitted` event via `IOutboxService.publish("rating.submitted", connectionId.toString(), eventId, ratingSubmittedEvent)` (the `IOutboxService` built as part of this ticket, above — partition key is `connection_id`, matching connection-service's own convention of partitioning by the aggregate the event is about), all in the same transaction per the Outbox Pattern
- `RatingSubmittedEvent` payload record matching `contracts/kafka/rating.submitted.schema.json`: `event_id` (UUID, newly minted here — the same value passed to `IOutboxService.publish`), `rating_id`, `rater_id`, `rated_id`, `tags`. Per this platform's established convention (see `TrustScoreUpdatedEvent`'s own comment in discovery-service/connection-service), every id on the wire is a **stringified `Long`**, not a `java.util.UUID` — `Rating.id`/`raterId`/`ratedId` are all `Long` (BIGINT), so serialize each as `.toString()`, even though the JSON schema's `format: uuid` annotation (a project-wide placeholder, not enforced) suggests otherwise

## Technical specification
**Service:** `rating-service`
**Language:** Java
**Depends on:** T041

**Spec:**
`POST /ratings`
Body: `{ "connection_id", "rated_id", "tags": ["Friendly", "On time"], "comment" }` (field names and the `RatingTag` enum's exact casing match `contracts/openapi/rating-service.yaml`)
Reads rater from `X-User-Id`.

Validation:
- Tags must be from the allowed set (REQUIREMENTS.md §7).
- Cannot rate the same connection twice.
- `connection_id` must match a closed chat (validate via Kafka-sourced data or HTTP to Connection Service).

Persist to `ratings` table. Publish `rating.submitted` Kafka event.

**Acceptance criteria:**
- [ ] Valid rating → persisted, event published
- [ ] Duplicate rating → 409 with `RATING_ALREADY_SUBMITTED`
- [ ] Invalid tag → 400 with `INVALID_RATING_TAG`
- [ ] `OutboxRelay` publishes a `PENDING` outbox row to Kafka within 500 ms and marks it `PROCESSED`
- [ ] `rating.submitted` event schema matches `contracts/kafka/rating.submitted.schema.json` exactly (Title Case tag strings, stringified-`Long` ids)

## Patterns demonstrated
**Outbox Pattern** — the rating insert, the outbox row for `rating.submitted`, and the correlation to the closed chat all happen inside one `@Transactional` method, so a crash between "update DB" and "publish to Kafka" can never leave a rating without its event published.

**Single Responsibility (SOLID-S)** — `RatingController` only translates HTTP ↔ DTOs; every validation rule, duplicate check, and exception decision lives in `RatingServiceImpl`. The pure trust score math (what trust score results from these tags) is NOT in this ticket — that belongs to T043's `TrustScoreCalculator`.

**Open/Closed (SOLID-O)** — valid rating tags are data (the `RatingTag` enum), not a chain of `if/else` statements checking strings. Adding a new tag is a data change (add to the enum), not new conditional branches in the validator.

**Dependency Inversion (SOLID-D)** — `RatingServiceImpl` depends on `IRatingRepository` and `IOutboxService` — all interfaces. Tests can substitute either without touching the service.

**Event-Driven Architecture** — this endpoint does not synchronously call Trust Service to recalculate scores. It publishes `rating.submitted`; T043 and beyond listen to that event and react.

**Idempotency (via Kafka contract)** — the `rating.submitted` event includes a unique `event_id`. Any consumer hearing it twice will detect the duplicate and skip re-processing (via a `processed_events` table or similar pattern, already established in T038).

**API Gateway (trust boundary)** — `X-User-Id` is read directly off the request header with no re-validation; the JWT was already checked at the YARP gateway before this request ever reached Rating Service.

- What NOT to do:
  - Do not call `KafkaTemplate` from `RatingController` or `RatingServiceImpl` — `OutboxRelay` is the only class in this service allowed to inject `KafkaTemplate`
  - Do not wrap `OutboxServiceImpl.publish(...)` in its own `@Transactional` boundary — it must participate in the caller's existing transaction
  - Do not add retry-count/DLQ logic to `OutboxRelay` — leaving a failed row `PENDING` is the entire retry mechanism for this ticket, same as T032
  - Do not implement the trust score recalculation logic itself here — that is T043's job; this ticket only publishes the event that triggers it
  - Do not call Trust Service synchronously to recalculate scores — publish the Kafka event and let the event-driven system handle it
  - Do not hardcode the allowed tags as string literals in a validator — use the `RatingTag` enum and iterate over it or check `RatingTag.values()`
  - Do not let the shared `GlobalExceptionHandler` swallow the three domain-specific exceptions into a generic 500 — they need their own local `@RestControllerAdvice` mapping to the exact codes in the acceptance criteria
  - Do not use `@Data` on the `Rating` entity, `OutboxEvent` entity, or DTO classes — follow the skill's `@Getter @Builder @NoArgsConstructor @AllArgsConstructor` convention
  - Do not persist the rating before validating it is not a duplicate — check the repository first (guard clause), throw if duplicate, then persist
