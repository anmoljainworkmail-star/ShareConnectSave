# T042 — Rating Submission Endpoint

## Why this ticket exists
Right now Rating Service can boot and reach its database (T041), but there is still no way for a traveler to submit a rating after a chat closes — the endpoint that triggers trust score recalculation does not exist. This ticket builds the single POST endpoint that turns `ratings` from an empty table into a real, auditable record of traveler behavior. Ratings are the only input to the Trust Score Calculator (T043); without this endpoint, there is nothing to rate, nothing to recalculate, and the entire Phase 7 goal — "trust score calculation drives discovery visibility" — stays unmet. Additionally, this endpoint is the entry point for the rating.submitted Kafka event, which Chat Service and Notification Service depend on to know when to prompt users and when to close rating windows.

## What to build
- `RatingController` — `POST /ratings`
- `RatingService` interface + `RatingServiceImpl` — holds all validation logic, outbox publishing, and persistence; controller stays thin (per user preference: every controller delegates to a service layer)
- `IRatingRepository extends JpaRepository<Rating, UUID>` — query methods for "has this user rated this connection already" (via count or existence check)
- `RatingTag` enum — all positive and negative tags from REQUIREMENTS.md §7 as values, stored as `@Enumerated(EnumType.STRING)` on the Rating entity
- Domain-specific `@RestControllerAdvice` (rating-service local, alongside the shared `GlobalExceptionHandler` from `shared-java-lib`) mapping: `DuplicateRatingException` → 409 `RATING_ALREADY_SUBMITTED`, `InvalidRatingTagException` → 400 `INVALID_RATING_TAG`, `ChatNotClosedException` → 400 `CHAT_NOT_CLOSED`
- `DuplicateRatingException`, `InvalidRatingTagException`, `ChatNotClosedException` — domain-specific exceptions
- `RatingSubmissionDto` `{ connection_id, rated_user_id, tags }`, `RatingResponse` (for echo-back after submission, optional for client display) via MapStruct `RatingMapper`
- On `POST /ratings`, inside one `@Transactional` method: validate the submitter (rater) is not rating themselves, check if rating already exists on this connection/rater pair, validate all tags are in the `RatingTag` enum, validate the connection's chat is closed (Kafka-sourced via a `ClosedChat` or similar cache, or HTTP call to Connection Service if available in your T041 design), persist the rating, write the `rating.submitted` event via `IOutboxService.publish(...)` (from T003/`shared-java-lib` or wherever the outbox skill wires it in for this service), all in the same transaction per the Outbox Pattern

## Technical specification
**Service:** `rating-service`
**Language:** Java
**Depends on:** T041

**Spec:**
`POST /ratings`
Body: `{ "connection_id", "rated_user_id", "tags": ["friendly", "on_time"] }`
Reads rater from `X-User-Id`.

Validation:
- Tags must be from the allowed set (REQUIREMENTS.md §7).
- Cannot rate the same connection twice.
- `connection_id` must match a closed chat (validate via Kafka-sourced data or HTTP to Connection Service).

Persist to `ratings` table. Publish `rating.submitted` Kafka event.

**Acceptance criteria:**
- [ ] Valid rating → persisted, event published
- [ ] Duplicate rating → 409 with `RATING_ALREADY_SUBMITTED`
- [ ] Invalid tag → 400 with `INVALID_RATING_TAG`

## Patterns demonstrated
**Outbox Pattern** — the rating insert, the outbox row for `rating.submitted`, and the correlation to the closed chat all happen inside one `@Transactional` method, so a crash between "update DB" and "publish to Kafka" can never leave a rating without its event published.

**Single Responsibility (SOLID-S)** — `RatingController` only translates HTTP ↔ DTOs; every validation rule, duplicate check, and exception decision lives in `RatingServiceImpl`. The pure trust score math (what trust score results from these tags) is NOT in this ticket — that belongs to T043's `TrustScoreCalculator`.

**Open/Closed (SOLID-O)** — valid rating tags are data (the `RatingTag` enum), not a chain of `if/else` statements checking strings. Adding a new tag is a data change (add to the enum), not new conditional branches in the validator.

**Dependency Inversion (SOLID-D)** — `RatingServiceImpl` depends on `IRatingRepository` and `IOutboxService` — all interfaces. Tests can substitute either without touching the service.

**Event-Driven Architecture** — this endpoint does not synchronously call Trust Service to recalculate scores. It publishes `rating.submitted`; T043 and beyond listen to that event and react.

**Idempotency (via Kafka contract)** — the `rating.submitted` event includes a unique `event_id`. Any consumer hearing it twice will detect the duplicate and skip re-processing (via a `processed_events` table or similar pattern, already established in T038).

**API Gateway (trust boundary)** — `X-User-Id` is read directly off the request header with no re-validation; the JWT was already checked at the YARP gateway before this request ever reached Rating Service.

## Agent implementation notes
- Key files to create (paths from project root, under `src/services/rating-service/src/main/java/com/shareconnectsave/rating/`):
  - `rating/RatingController.java`
  - `rating/RatingService.java` (interface) and `rating/RatingServiceImpl.java`
  - `rating/IRatingRepository.java` — extends `JpaRepository<Rating, UUID>`; add a derived-query or `@Query` method for "count where connection_id AND rater_id" (or "exists") rather than filtering in Java
  - `rating/domain/RatingTag.java` — enum with at least `FRIENDLY, RESPECTFUL, ON_TIME, GOOD_COMMUNICATION, WOULD_TRAVEL_AGAIN, DIDNT_SHOW_UP, FAKE_DESTINATION, ABUSIVE, SPAM, ASKED_FOR_MONEY`
  - `rating/domain/RatingSubmissionDto.java`, `RatingResponse.java`
  - `rating/mapper/RatingMapper.java` — MapStruct, per the `java-spring-boot` skill's "DTO mapping" section
  - `rating/exception/DuplicateRatingException.java`, `InvalidRatingTagException.java`, `ChatNotClosedException.java`
  - `rating/exception/RatingExceptionHandler.java` — `@RestControllerAdvice`, sits alongside (does not replace) `shared-java-lib`'s `GlobalExceptionHandler`
  - Check T041 to see if `Rating` entity was already defined (likely yes, since T041 handles the schema). If T041 did not create it, create `rating/domain/Rating.java` as the JPA entity with `@Id UUID id`, `UUID connection_id`, `UUID rater_id`, `UUID rated_user_id`, `Set<RatingTag> tags` (stored as a delimited string or JSON in a TEXT column), `LocalDateTime created_at`, `LocalDateTime updated_at`. If T041 already defined it, verify it has all these fields and skip creating it here.
- Follow the skill's Dependency Inversion section exactly: `RatingController` depends on `RatingService` (interface), never `RatingServiceImpl` directly
- Use guard clauses, not nested `if/else`, for the validation checks in `RatingServiceImpl` — check self-rating first (rater == rated_user_id), then duplicate, then tag validity, then closed-chat status, returning or throwing early at each step (per user preference)
- The `@Transactional` POST method must call the repository save, `IOutboxService.publish("rating.submitted", ...)`, in that order, inside the same method — do not split them across separate `@Transactional` boundaries or the atomicity guarantee the Outbox Pattern exists to provide is lost
- To validate that the chat is closed: T041 specifies the schema for `ratings` — check if it references a foreign key to `connection_requests` or if it includes a denormalized `connection_status` column. If T041 leaves this ambiguous, resolve it with your skill's guidance on "Kafka-sourced data caching" (similar to how Connection Service's T033 consumer populates `IRequestLimitCache` from `trust.score.updated` events). For now, assume you can query closed chats from a cache or a query to the Connection Service via HTTP (do NOT synchronously call Trust Service — that would violate event-driven architecture).
- The `event_id` on the `rating.submitted` outbox row must be a UUID; `IOutboxService.publish(...)` should auto-generate it or accept it as a parameter. Check the `java-spring-boot` skill or T003's implementation for the exact shape.
- What NOT to do:
  - Do not implement the trust score recalculation logic itself here — that is T043's job; this ticket only publishes the event that triggers it
  - Do not call Trust Service synchronously to recalculate scores — publish the Kafka event and let the event-driven system handle it
  - Do not hardcode the allowed tags as string literals in a validator — use the `RatingTag` enum and iterate over it or check `RatingTag.values()`
  - Do not let the shared `GlobalExceptionHandler` swallow the three domain-specific exceptions into a generic 500 — they need their own local `@RestControllerAdvice` mapping to the exact codes in the acceptance criteria
  - Do not use `@Data` on the `Rating` entity or DTO classes — follow the skill's `@Getter @Builder @NoArgsConstructor @AllArgsConstructor` convention
  - Do not persist the rating before validating it is not a duplicate — check the repository first (guard clause), throw if duplicate, then persist
