# T043 — Trust Score Algorithm

## Why this ticket exists

Without a trust score algorithm, the platform has no way to distinguish between reliable travelers and bad actors. Every user looks the same to the discovery algorithm — safe users get throttled alongside abusive ones, and there's no way to automatically suspend accounts that ignore warnings. The trust score is the single number that gates discovery visibility, request-send frequency, and triggers manual review escalation. It's the backbone of a safe platform.

## What to build

- **TrustScoreCalculator** — pure domain service class that computes trust scores from rating history
- **TrustScoreResult** — immutable record (or final class) holding the output: `score` (double), `badgeLevel` (enum), `requestLimit` (enum)
- **BadgeLevel** — enum: `NONE`, `TRUSTED` (with eligibility rules: score ≥ 4.5 AND ≥ 10 ratings) — already exists from T041, do not recreate
- **RequestLimit** — enum: `UNLIMITED`, `THROTTLED`, `SUSPENDED` — already exists from T041 (`domain/RequestLimit.java`), do not recreate and do not rename its values (e.g. not `THROTTLED_3_PER_DAY` — the "3/day" policy number is NOT part of the category name; see below for where that number actually lives)
- **Boundary mapping (Tech Lead decision):** `RequestLimit` is an internal category — it never leaves Rating Service as a string. T044's Kafka producer and T045's HTTP endpoint both need to convert it to a plain integer matching the existing `trust.score.updated` Kafka contract and `GET /trust/:userId` OpenAPI contract (both already declare `request_limit` as `integer`, and discovery-service/connection-service already consume it as one). Add a single conversion method this ticket owns so T044/T045 don't each invent their own mapping — e.g. `RequestLimit.wireValue()` returning: `UNLIMITED -> Integer.MAX_VALUE`, `THROTTLED -> 3`, `SUSPENDED -> 0`.
- Unit test suite covering all algorithm edge cases (new user, high/low scores, suspension threshold), including a test asserting `wireValue()`'s mapping for all three categories

The calculator takes only data: a list of ratings and report counts. It returns a fully computed trust profile. No repository calls, no Kafka templates, no HTTP clients.

## Technical specification

`TrustScoreCalculator` — pure domain service, no I/O. Inputs: full rating history for a user. Output: `TrustScoreResult { score, badgeLevel, requestLimit }`.

Algorithm:
- Base score: weighted average of last 50 ratings (recent ratings weighted higher).
- Negative tag multipliers: `abusive` and `asked_for_money` count double.
- Badge levels: `none` (< 4.0), `trusted` (≥ 4.5, ≥ 10 ratings).
- Request limits: `unlimited` (score ≥ 3.5), `throttled: 3/day` (2.5–3.5), `suspended: 0` (< 2.5 or ≥ 3 `report.filed` events).

## Acceptance criteria

- [ ] Unit tests cover: new user (no ratings), high score, low score, suspension threshold
- [ ] Algorithm is a pure function — no DB calls, fully unit testable

## Patterns demonstrated

**Single Responsibility Principle** — `TrustScoreCalculator` does exactly one job: compute trust scores from rating history. It doesn't read from a database, publish to Kafka, or call any external service. Why it matters here: trust scoring is pure math. By isolating it from I/O concerns, we make it trivially unit-testable (no mocks, no containers), easy to reason about (inputs → outputs, nothing else), and safe to refactor later (no hidden dependencies to break). This is the canonical example of SRP in this project — a class that does one thing so well it needs nothing but data.

**Strategy pattern (via enum)** — `BadgeLevel` and `RequestLimit` are enums that encapsulate the rules for what happens at each score range. Future scoring rules (e.g., a new "Super Trusted" badge level at score 4.9) can be added to the enum without changing the calculator's logic.

**Dependency Inversion** — `TrustScoreCalculator` should not depend on concrete rating storage. The caller (e.g., a service layer) retrieves ratings from a repository and passes them to the calculator. This keeps the calculator testable and reusable.

## Agent implementation notes

**Files to create:**
- `src/main/java/com/shareconnectsave/rating/domain/TrustScoreCalculator.java` — pure function, no Spring annotations needed, no @Service
- `src/main/java/com/shareconnectsave/rating/domain/TrustScoreResult.java` — use a record (Java 16+) or immutable final class
- `src/test/java/com/shareconnectsave/rating/domain/TrustScoreCalculatorTest.java` — comprehensive unit tests

**Files that already exist (from T041) — modify, do not recreate:**
- `src/main/java/com/shareconnectsave/rating/domain/BadgeLevel.java` — enum with eligibility checks already defined; no changes needed unless eligibility logic requires a helper method here
- `src/main/java/com/shareconnectsave/rating/domain/RequestLimit.java` — add the `wireValue()` boundary-mapping method described above (`UNLIMITED -> Integer.MAX_VALUE`, `THROTTLED -> 3`, `SUSPENDED -> 0`); do not change the enum's existing three values or their names

**Implementation guidance:**
- Consult `java-spring-boot` skill file for domain service patterns and unit testing strategy
- Keep the calculator stateless and deterministic — same input always produces same output
- Use clear variable names for weighting factors; add a comment explaining the weighted-average formula
- Test edge cases: empty rating list (new user), exactly 10 ratings (badge eligibility threshold), exactly 3 reports (suspension threshold), exactly 2.5 score (throttle boundary)
- Do not inject any repository, Kafka template, or HTTP client into this class
- Do not perform any I/O (database queries, Kafka publishes) inside this class
- The calling service (RatingService, later in T044) will fetch the rating history and pass it to this calculator

**What NOT to do:**
- Do not make TrustScoreCalculator a Spring @Service — it's a plain domain class
- Do not add a constructor that takes Repository or KafkaTemplate
- Do not call Database or Kafka inside the calculator
- Do not use magic numbers without explanation — extract scoring weights and thresholds to named constants with inline comments
