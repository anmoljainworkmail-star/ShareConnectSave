# T044 — Kafka Consumer + Producer

## Why this ticket exists
Trust scores are the foundation of discovery visibility and safety — but right now there is no code in Rating Service that actually calculates or publishes them. REQUIREMENTS.md section 7 states that high scores earn a Trusted badge, low scores throttle request-sending, and very low scores suspend accounts entirely. Without this ticket, those scores never get computed when ratings arrive, reports are filed, or chat rooms close. The three Kafka consumers here (chat.closed, rating.submitted, report.filed) are what trigger all trust recalculation in the system. Without them, the entire trust-based discovery filter and safety enforcement described in REQUIREMENTS.md section 7 remains unimplemented.

## What to build
- Three Kafka consumers in `rating-service`:
  - `ChatClosedConsumer` — subscribed to `chat.closed` topic; on receipt, store `{ connection_id, user_a_id, user_b_id }` to a local `closed_chats` table to validate that rating submissions are for real connections only.
  - `RatingSubmittedConsumer` — subscribed to `rating.submitted` topic; on receipt, invoke `TrustScoreCalculator` to recalculate the `rated_user_id`'s score, write the new score + badge level + request limit to the `users` table, then publish `trust.score.updated` to Kafka via the outbox.
  - `ReportFiledConsumer` — subscribed to `report.filed` topic; check if `report_count_for_target` (from the event payload) meets or exceeds the configured threshold (default 3); if yes, force recalculate the reported user's trust score immediately.
- A single pure-math function `TrustScoreCalculator` — no side effects, no DB calls, only receives a list of `RatingSubmission` records and returns a `TrustScoreResult` (`score`, `badge_level`, `request_limit`). This keeps the scoring logic testable and reusable.
- Idempotency check against a `processed_events` table (shared pattern from T033/T038) before acting on any Kafka event, so a redelivered message does not recalculate the score twice.
- Outbox write (same transaction as trust score update) for the `trust.score.updated` event, published by a background relay (already created in T043).

## Patterns demonstrated
- **Single Responsibility (SOLID S)** — `TrustScoreCalculator` does pure math only: receives ratings, returns a score. It never talks to the database, publishes events, or makes network calls. The consumer classes handle orchestration (fetch ratings, call the calculator, persist the result, enqueue the outbox event), but the scoring logic itself is isolated and testable. This separation makes trust-score recalculation logic reusable and bug-resistant.
- **Idempotency** — All three consumers check a `processed_events` table before acting. Kafka at-least-once delivery means a message may be redelivered; processing it twice must produce the same result as once. If `chat.closed` is redelivered, the connection is already stored, so the insert or upsert is safe. If `rating.submitted` is redelivered, the score recalculation produces the same output (same input ratings → same output), and the outbox entry is idempotent via `event_id`.
- **Self-Consuming Kafka Pattern** — Rating Service publishes `rating.submitted` (T043, Rating Submission endpoint) and Rating Service also consumes it here. This is safe and intentional: the submitter does not calculate the score immediately (that might block the HTTP response). Instead, Rating Service publishes the submission event to Kafka, then this consumer reacts to it asynchronously. Because both producer and consumer follow the Outbox Pattern and Idempotency rules, consuming your own event is no different from consuming anyone else's — same guarantees apply. This decouples the HTTP endpoint (which must return quickly) from the score calculation (which may involve database reads and Kafka publishing).
- **Observer (via events)** — `chat.closed` is published once by Chat Service; Rating Service (this ticket) listens independently, stores the connection context for validation. Discovery Service (T059) and Connection Service (T062) also consume the same event. Each subscriber reacts independently without Chat Service knowing or caring who is listening.
- **Database per Service** — Rating Service stores connections, ratings, trust scores, and the processed_events log in its own schema. It does not query Connection Service or Chat Service databases — it trusts the event payload.
- **Outbox Pattern** — When `rating.submitted` or `report.filed` triggers a score recalculation, Rating Service writes the new score and an outbox entry (containing `trust.score.updated` event) in the same database transaction. A background relay (from T043) polls the outbox every 500 ms and publishes to Kafka. This ensures that if Rating Service crashes after the score write but before publishing, the event is not lost — it remains in the outbox and publishes when the relay restarts.

## Agent implementation notes
- Key files to create (follow rating-service's existing structure from T043):
  - `rating-service/src/main/java/com/shareconnectsave/rating/messaging/consumers/ChatClosedConsumer.java` — Kafka consumer subscribing to `chat.closed`; on receipt, upsert into `closed_chats` table (or reuse schema if Rating Service already has this from T043).
  - `rating-service/src/main/java/com/shareconnectsave/rating/messaging/consumers/RatingSubmittedConsumer.java` — Kafka consumer subscribing to `rating.submitted`; calls `TrustScoreCalculator` and publishes `trust.score.updated` via outbox.
  - `rating-service/src/main/java/com/shareconnectsave/rating/messaging/consumers/ReportFiledConsumer.java` — Kafka consumer subscribing to `report.filed`; checks threshold and triggers recalculation if needed.
  - `rating-service/src/main/java/com/shareconnectsave/rating/service/TrustScoreCalculator.java` — Pure function (or a static utility, or a stateless service) that takes `List<RatingSubmission>` and returns `TrustScoreResult`. No dependencies on repositories, Kafka, or Spring context. Testable in isolation — unit tests pass in mock ratings and verify output scores, badge levels, and request limits.
  - `rating-service/src/main/java/com/shareconnectsave/rating/repository/ProcessedEventRepository.java` (or extend T043's equivalent if it exists) — stores and queries the `processed_events` table for idempotency checks.
  - Database migrations: tables for `closed_chats`, `processed_events` (if not already present from T043), and ensure `users` table has `trust_score`, `badge_level`, `request_limit_per_hour` columns.
- Follow the `kafka-outbox` skill's idempotent-consumer section: check `processed_events` first (skip if found), then process the event, then record the event_id + timestamp in `processed_events`. Match the established pattern from T033 and T038.
- The `TrustScoreCalculator` must be pure: no `@Autowired` dependencies, no database calls. Pass all inputs as parameters. Tests should construct it with `new TrustScoreCalculator()` and call methods directly. Inject it into the consumers via constructor, but keep the calculator itself free of Spring concerns. This demonstrates Single Responsibility and makes the scoring logic portable to other services if needed in the future (e.g., a separate scoring microservice).
- Rating submission events and report events both trigger score recalculation. Ensure that if both arrive for the same user within a short window, they are processed in order (Kafka guarantees order per partition; ensure user_id is the partition key). The final score reflects all inputs.
- The threshold for report-based recalculation should be read from configuration (e.g. `rating.report.suspension.threshold=3`). Make it injectable into the `ReportFiledConsumer` so it can be changed without code changes.
- Outbox event payload for `trust.score.updated` must include: `user_id`, `new_score`, `badge_level`, `request_limit`. See REQUIREMENTS.md Kafka Message Schemas table for the contract.
- What NOT to do:
  - Do not call the trust score calculator synchronously from the HTTP endpoint (T043's Rating Submission controller). Let the consumer do it. The endpoint publishes the event to Kafka and returns immediately.
  - Do not implement the score calculation logic inside the consumer class itself. Extract it to `TrustScoreCalculator` so it is testable and reusable.
  - Do not skip the `processed_events` idempotency check for any of the three consumers. Kafka at-least-once is not a substitute for idempotent handling.
  - Do not query Connection Service's or Chat Service's databases to validate that a connection is real — trust the event payload.
  - Do not publish `trust.score.updated` directly to Kafka. Write it to the outbox table in the same transaction as the score update, and let the background relay (T043) publish it. This is the Outbox Pattern and prevents lost events on service crash.
  - Do not hard-code the report threshold (3); make it configurable.
  - Do not call Rating Service's own HTTP endpoint from the `RatingSubmittedConsumer` to get ratings. Fetch them directly from the database (same service owns the data).
