# T045 — Trust Score Badges + Throttle Enforcement

## Why this ticket exists
Rating Service has calculated and stored trust scores in the database, but right now there's no way for other services to read that data. Connection Service has an in-memory cache of request limits, but that cache is write-only — it only gets populated when Rating Service publishes a `trust.score.updated` event. This creates two dangerous failure modes: when Connection Service restarts, the in-memory cache wipes clean and every low-trust user silently gets reset to the permissive default limit (5 requests) until Rating Service happens to republish an event for them; and when Connection Service runs on multiple replicas sharing a Kafka consumer group, any replica that didn't consume a particular user's partition never learns their real limit at all. This ticket closes the gap by giving Rating Service a read endpoint so Connection Service can implement a proper Cache-Aside pattern: on a cache miss (whether from restart or scale-out), synchronously fetch the real limit from Rating Service, cache it, and use it — instead of silently defaulting and hoping for a Kafka event to arrive.

## What to build

**In rating-service:**
- New HTTP GET endpoint `GET /trust/:userId` that returns the current trust score record, badge level (calculated from score and minimum rating count), and request limit for that user.
- Response includes: `userId`, `trustScore` (decimal), `requestLimit` (integer), `isTrusted` (boolean), `ratingCount` (integer).
- Endpoint queries the `trust_scores` table (updated by T044's recalculation logic) and returns the latest record for that user.

**In connection-service:**
- Update the existing `InMemoryRequestLimitCache` to implement Cache-Aside pattern: when `getLimit(userId)` is called and the user is not in cache, make a synchronous call to Rating Service's new endpoint, cache the result, and return it (do not silently default to 5).
- New client layer (mirroring Discovery Service's `UserServiceClient` pattern exactly):
  - `src/main/java/com/example/connectionservice/client/RatingServiceClient.java` (interface)
  - `src/main/java/com/example/connectionservice/client/impl/RatingServiceClientImpl.java` (implementation using `WebClient` + Resilience4j `@CircuitBreaker`)
  - `src/main/java/com/example/connectionservice/client/config/RatingServiceClientConfig.java` (WebClient bean)
  - `src/main/java/com/example/connectionservice/config/RatingServiceProperties.java` (configuration holder for base URL)
- New Resilience4j circuit breaker configuration block in `application.yml` under `resilience4j.circuitbreaker.instances.ratingService`.
- When the circuit is open (Rating Service unreachable), `getLimit()` falls back to `DEFAULT_REQUEST_LIMIT` (5) — same fail-open posture as today, now an explicit, reviewed decision.
- Update `InMemoryRequestLimitCache` to use the new client and implement the two-step fallback: first call Rating Service, on circuit-open or failure, fall back to default.

## Technical specification
`GET /trust/:userId` — returns current trust score, badge level, and request limit for a user. Used by Admin Service and Connection Service.

Update `trust_scores` table on every recalculation.

**Cross-service requirement — closes a gap left open by T033:**
T033 built `connection-service`'s `InMemoryRequestLimitCache` as write-only: it is populated solely by the `trust.score.updated` consumer, and a cache miss silently falls back to `DEFAULT_REQUEST_LIMIT` (5) — a *permissive* default. Until this ticket, that was unavoidable because no endpoint existed to read the real value. Two real failure modes stem from this: (1) a pod restart wipes the in-memory cache and silently re-permissions every low-trust user to the default until Rating Service happens to republish an event for them; (2) with multiple connection-service replicas sharing one Kafka consumer group, a replica that never consumed a given user's partition never learns their real limit at all.

This ticket must also update `connection-service` to make `getLimit()` a genuine Cache-Aside read: on a cache miss, synchronously call this new `GET /trust/:userId` endpoint, cache the returned `request_limit`, and return it — instead of silently defaulting. Build the client mirroring Discovery Service's existing `UserServiceClient` pattern exactly: WebClient + Resilience4j `@CircuitBreaker` (`client/RatingServiceClient.java` + `RatingServiceClientImpl.java` + `RatingServiceClientConfig.java` + `RatingServiceProperties`, `resilience4j.circuitbreaker.instances.ratingService` block in `application.yml`, `rating-service.base-url` config). When the circuit is open (Rating Service unreachable), fall back to `DEFAULT_REQUEST_LIMIT` via a `fallbackMethod` — same fail-open posture as today, now an explicit, reviewed decision rather than an accidental one.

## Acceptance criteria
- [ ] Response matches current `trust_scores` table record
- [ ] `trusted` badge only returned when conditions met (≥ 4.5, ≥ 10 ratings)
- [ ] `connection-service`'s `getLimit()` calls `GET /trust/:userId` on a cache miss and caches the result (no more silent default-on-miss for a user Rating Service actually has data for)
- [ ] Simulated Rating Service outage (circuit open) → `getLimit()` falls back to `DEFAULT_REQUEST_LIMIT`, `createConnection` still succeeds
- [ ] Restarting connection-service no longer resets a known low-trust user's limit back to default — a fresh `getLimit()` call re-fetches their real limit from Rating Service

## Patterns demonstrated
- **Cache-Aside** — Plain English: instead of pre-loading everything you might need, load data on first use and keep it nearby for next time. Real-world analogy: a librarian who doesn't memorize every book in the library but remembers books they've recently grabbed for patrons — when someone asks for a book they've retrieved before, it's faster to grab it from the recently-used shelf than to search the whole library again. Why it's needed here: Connection Service doesn't need to know every user's limit ahead of time, and Kafka events might not arrive reliably for every user (especially after restarts or when a replica misses a partition). Cache-Aside means: ask only when you need it, store the answer for next time, and if you don't have a cached answer, get it now synchronously instead of guessing. This ticket builds the synchronous read half (Rating Service's endpoint) so Connection Service can actually fetch the real answer on a cache miss, instead of silently defaulting.
- **Circuit Breaker** — Plain English: think of the circuit breaker in your home's electrical panel. When something downstream draws too much current (a fault), the breaker trips and cuts power immediately, rather than letting the fault keep drawing current and risking a fire. It only lets power flow again after someone checks that it's safe. Real-world analogy: it's the same idea as a business that stops sending orders to a supplier who has failed to deliver the last several times in a row — instead of placing (and losing) another order, they switch to a backup supplier until the original one proves it's reliable again. Why it's needed here: if Rating Service becomes slow or unavailable, Connection Service should not wait out a full timeout on every `getLimit()` call; instead, after a few failures, the circuit opens and immediately returns the fallback default (same safe behavior as today), allowing Connection Service to keep processing connection requests without cascading failure.
- **Decorator** — Plain English: a decorator wraps an existing object and adds new behavior around it, without the object itself knowing it's been wrapped and without changing the shape callers use to interact with it. Real-world analogy: putting a protective case on a phone — the phone still works exactly the same way (same buttons, same screen), but the case adds shock absorption you didn't have to build into the phone itself. Why it's needed here: the code in `InMemoryRequestLimitCache` that calls Rating Service will look like a normal `WebClient` call from its point of view — it doesn't need to know retry logic, fallback logic, or open/closed state exist. Resilience4j's `@CircuitBreaker` annotation transparently wraps the real call with this resilience logic.

- **Connection Service (closes the gap from T033):**
  - Key files to create/modify (paths relative to project root, under `connection-service`):
    - `src/main/java/com/example/connectionservice/client/RatingServiceClient.java` (interface) — define a single method: `TrustData getTrustData(String userId)`.
    - `src/main/java/com/example/connectionservice/client/impl/RatingServiceClientImpl.java` (implementation) — use `WebClient` to call Rating Service; wrap with `@CircuitBreaker(name = "ratingService", fallbackMethod = "fallbackGetTrustData")`.
    - `src/main/java/com/example/connectionservice/client/config/RatingServiceClientConfig.java` — configure and expose a `WebClient` bean (follow Discovery Service's `UserServiceClientConfig` pattern exactly).
    - `src/main/java/com/example/connectionservice/config/RatingServiceProperties.java` — holder for `rating-service.base-url` configuration (follow Discovery Service's `UserServiceProperties` pattern).
    - `src/main/resources/application.yml` — add:
      - `rating-service.base-url` property (example: `http://rating-service:8080`)
      - `resilience4j.circuitbreaker.instances.ratingService` block with:
        - `slidingWindowSize: 10`
        - `failureRateThreshold: 50` (same as userService)
        - `waitDurationInOpenState: 30s`
      - Enable circuit breaker health indicator (e.g., `management.health.circuitbreakers.enabled: true`)
    - Modify `src/main/java/com/example/connectionservice/cache/InMemoryRequestLimitCache.java`:
      - Inject the new `RatingServiceClient`.
      - Update `getLimit(userId)` to implement Cache-Aside: check in-memory cache first; on miss, call `ratingServiceClient.getTrustData(userId)`, extract `requestLimit`, cache it, return it.
      - The fallback method (invoked when the circuit is open) returns `DEFAULT_REQUEST_LIMIT` (5) — same safe posture as today.
      - Add logging when a miss is resolved via Rating Service call (helps debugging cache behavior).

- **Specific patterns to use:** Follow the `java-spring-boot` skill file's guidance on Resilience4j annotation usage, WebClient configuration, and circuit breaker health indicators.

- **What NOT to do:**
  - Do not change the fail-open posture on circuit-open — falling back to `DEFAULT_REQUEST_LIMIT` is an explicit, accepted design decision, not something to "fix" or make stricter. The whole point is that Connection Service continues working even when Rating Service is down.
  - Do not name the circuit breaker instance anything other than exactly `ratingService` — the `application.yml` config block, the `@CircuitBreaker(name = ...)` annotation, and any health indicator lookup must all reference this exact same name or they will silently fail to connect.
  - Do not skip the cache-first step in `getLimit()` and jump straight to calling Rating Service every time — the Cache-Aside pattern's whole value is avoiding redundant calls.
  - Do not swallow the exception that triggered the fallback — log it so a real Rating Service outage is visible in logs and not just inferred from seeing the default limit used.
  - Do not implement retry logic as a substitute for the circuit breaker — this ticket is specifically about stopping calls once a threshold is hit, not about retrying individual calls.
  - Do not hard-code the Rating Service URL — it must come from `application.yml` (via `RatingServiceProperties`).
