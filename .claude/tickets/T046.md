# T046 — Rating Service Docker Image

## Why this ticket exists

Rating Service is written in Java and, right now, cannot run in the local Docker Compose stack — it has no Dockerfile. Until it's containerized, it can't be started alongside the other services via `/docker-up`, which blocks full-stack testing of the trust score calculation (the TrustScoreCalculator T045 just built) and the self-consuming Kafka pattern it drives (rating.submitted → recalculate → trust.score.updated). This ticket makes Rating Service runnable as a peer to Discovery Service, Connection Service, and the API Gateway in the same dev environment, following the exact packaging pattern already proven for Connection Service in T034 and Discovery Service in T028.

## What to build

- A Dockerfile at `src/services/rating-service/Dockerfile` with two stages:
  - Build stage using `eclipse-temurin:21-jdk` to compile the Maven project (via the Maven wrapper)
  - Runtime stage using `eclipse-temurin:21-jre-alpine` to keep the image lean
- The service block for `rating-service` already exists in `src/infra/docker-compose.yml` (port `8085:8080`, builds from `context: ../../src/services/rating-service`, `dockerfile: Dockerfile`) — this ticket supplies the Dockerfile that block expects
- Fix the latent Spring profile / datasource credential gap in `src/infra/docker-compose.override.yml`'s `rating-service` block (see Known follow-ups) before first run — add explicit `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD` env vars following the same pattern Connection Service used in T034
- Add an explanatory comment to `src/services/rating-service/application.yml` near the existing `dev` / `prod` profile documents explaining why the override env-var workaround is necessary (see Known follow-ups)

## Patterns demonstrated

- **Multi-stage build** — separates the heavy JDK build toolchain from the minimal JRE-alpine runtime, so the shipped image doesn't carry compiler, build tools, or dev dependencies, only what's needed to run the compiled JAR. Teaches "build once, ship lean."
- **Container healthcheck** — Spring Boot Actuator's `/actuator/health` endpoint lets Docker Compose continuously verify the service is alive, not just started, so orchestration doesn't route traffic to a broken container.
- **Size budgeting via docker inspect** — `docker images` reports a misleading size due to containerd-snapshotter display quirks; the authoritative metric is `docker inspect --format {{.Size}}` or `docker save`, which must stay under 300MB uncompressed. Teaches observability: measure the real thing, not the convenient output.

- The Dockerfile must use the Maven wrapper (`mvnw`/`mvnw.cmd`) in the build stage, not assume Maven is installed globally — same reasoning as T034: consistency across dev machines and CI.
- The runtime stage must `COPY --from=build` the compiled JAR from the build stage — do not rely on a pre-built JAR already sitting in the working directory.
- Healthcheck already wired in `docker-compose.yml` hits `http://localhost:8080/actuator/health` via `curl`; if Alpine's minimal base doesn't have `curl` available, either install it in the runtime stage or fall back to `wget`.
- Do NOT hardcode port numbers inside the Dockerfile — `docker-compose.yml` already controls the external port mapping (`8085:8080`).
- Do NOT create a `.dockerignore` file yet — same deferral T028 and T034 made, stay consistent.
- When fixing the docker-compose.override.yml env block for rating-service, copy the exact pattern Connection Service used in T034 (explicit `SPRING_DATASOURCE_USERNAME=sa` / `SPRING_DATASOURCE_PASSWORD=${SA_PASSWORD:?...}` entries, with clear precedent lines cited). Do not rely on a `docker` profile document that doesn't exist.

## Known follow-ups

- **Docker image size display quirk (T028 finding, applies to all Java service images):** `docker images` reports a size (~450MB) that does not match the true image size (~152MB) corroborated by `docker inspect --format {{.Size}}` and `docker save`. The root cause is an unconfirmed containerd-snapshotter display quirk, not BuildKit attestation/SBOM metadata as previously assumed. Verified with `--provenance=false --sbom=false` (unchanged ~450MB in docker images, still ~152MB in inspect/save). For this ticket's size-budget check, use `docker inspect .Size` or `docker save` as the authoritative metric, not `docker images`. Note: `docker history`'s summed layer size comes to ~298MB uncompressed, only ~2MB under the 300MB budget, so an uncompressed-size-based check could flip pass/fail depending on the metric chosen — use inspect/save.

- **Missing `docker` Spring profile for credential binding (T034 fix, applies to rating-service now):** `src/infra/docker-compose.override.yml` currently sets `SPRING_PROFILES_ACTIVE=docker` for rating-service, but `src/services/rating-service/application.yml` does not define a `docker` profile document. Activating a nonexistent Spring profile silently no-ops, so datasource username/password placeholders never bind, and the app connects to SQL Server with an empty username — error 18456. This is the exact bug T028 and T034 found and fixed. Fix proactively by adding explicit `SPRING_DATASOURCE_USERNAME=sa` and `SPRING_DATASOURCE_PASSWORD=${SA_PASSWORD:?...}` env vars directly in the `src/infra/docker-compose.override.yml` rating-service block, bypassing the profile system entirely via Spring's relaxed env-var binding. See T034's lines 102–106 and discovery-service's lines 75–76 for the exact shape.

- **Latent future regressions due to missing profile explanation (T034 follow-up note):** No comment currently documents *why* a `docker` Spring profile is activated when it matches zero profile documents in any Java service. A future engineer could reasonably "clean up" the override env vars thinking a real `docker` profile handles datasource credentials, reintroducing error 18456. Add a one-line comment in `src/services/rating-service/application.yml` near the existing `dev` and `prod` profile sections explaining that env-var overrides in docker-compose.override.yml bypass the profile system intentionally (e.g., `# docker profile intentionally omitted; datasource creds injected via env vars in docker-compose.override.yml`). This teaches the next engineer the design decision so it isn't mistaken for dead config.
