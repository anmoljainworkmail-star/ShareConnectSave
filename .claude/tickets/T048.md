# T048 — SignalR Notification Hub

## Why this ticket exists
A user with the PWA open right now has no way to see a new connection request, an acceptance, a decline, or an expiry the instant it happens — today they would need to refresh or poll to find out. T047 gave Notification Service a way to push to a closed app (FCM), but closed-app delivery is the wrong channel for someone actively looking at the screen: it's slower, noisier, and not how a "live" product should feel. Without this ticket, Phase 8's fan-out layer has a background channel but no foreground one, and every later ticket that reacts to `connection.requested`, `connection.accepted`, `connection.declined`, or `connection.expired` has nowhere to send a real-time event. This hub is that missing foreground channel — the Notification Service's half of the real-time layer, mirroring the hub Chat Service already runs for in-chat messages.

## What to build
- `NotificationHub : Hub` in `notification-service`
- On connect, join the caller to their personal group `user:{X-User-Id}` — same group-naming convention as Chat Service's personal group
- No client-invokable methods — this hub only pushes server-to-client; clients never call into it
- Events published to a user's group (by later tickets, not this one — this ticket only builds the hub and the publish-capable infrastructure):
  - `ConnectionRequest` — new inbound request
  - `RequestAccepted` — your request was accepted
  - `RequestDeclined` — your request was declined
  - `RequestExpired` — your request expired
  - `ChatOpened` — also sent by Chat Service; Notification Service must deduplicate on its side
- Redis backplane on the same Redis instance Chat Service uses, DB 1 (`SIGNALR_REDIS_CONNECTION` env var, `AddStackExchangeRedis`)
- Hub endpoint mapped in `Program.cs` (e.g. `/hubs/notifications`)

## Technical specification
`NotificationHub : Hub`. On connect, users join their personal group `user:{X-User-Id}`.

The service publishes SignalR events to user groups (does not receive from clients). Events:
- `ConnectionRequest` — new inbound request
- `RequestAccepted` — your request was accepted
- `RequestDeclined` — your request was declined
- `RequestExpired` — your request expired
- `ChatOpened` — (also sent by Chat Service, Notification Service deduplicates)

Redis backplane (DB 1) shared with Chat Service.

## Acceptance criteria
- [ ] User connected to hub receives their targeted events
- [ ] Redis backplane means events work across multiple Notification Service replicas

## Patterns demonstrated
- **Observer (GoF), via SignalR groups** — `Clients.Group("user:{id}")` broadcasts to every connection that previously joined that personal group; the hub has no idea who or how many clients are listening, and each subscriber reacts independently. Same shape as this project's Kafka topics and as Chat Service's `ChatHub`, just transported over a live WebSocket instead of a message broker.
- **Single Responsibility** — `NotificationHub`'s only job is connection/group lifecycle management (who is in which personal group). It does not decide *when* to notify, does not touch Kafka, and does not contain FCM logic — that judgment lives in the Kafka consumers of later tickets, which call into this hub's group-send surface.
- **Dependency Inversion** — later tickets' Kafka consumers depend on `IHubContext<NotificationHub>` (the abstraction ASP.NET Core SignalR provides for pushing from outside a hub instance), not on constructing or holding a `NotificationHub` directly.

## Agent implementation notes
- Key files to create (paths from project root):
  - `src/services/notification-service/Hubs/NotificationHub.cs`
  - `src/services/notification-service/Extensions/HttpContextExtensions.cs` — if not already present in this service, port the identity-extraction helper from `src/services/chat-service/Extensions/HttpContextExtensions.cs` (same `TryGetUserId` shape) rather than inventing a new one
  - `src/services/notification-service/Program.cs` — extend with `AddSignalR().AddStackExchangeRedis(...)`, the hub endpoint mapping, and (if not already present from T047) the composition-root wiring
- Reference `src/services/chat-service/Hubs/ChatHub.cs` directly for the exact shape to mirror:
  - `OnConnectedAsync` override that calls `TryGetCallerUserId` and, on success, `Groups.AddToGroupAsync(Context.ConnectionId, SignalRGroupNames.User(userId))` — do not throw if the header is missing/invalid, just log a warning and skip joining (matches Chat Service's personal-group behavior exactly, since a connection with no resolvable identity may still be useful for other purposes)
  - Read `X-User-Id` via `Context.GetHttpContext()` + the shared `HttpContextExtensions.TryGetUserId` helper — never decode a JWT inside the hub; the gateway has already validated it and injected the header
  - A `SignalRGroupNames` helper (or equivalent) with a `User(userId)` method producing `"user:{id}"` — keep the group-naming convention identical to Chat Service's so both hubs are legible as the same pattern applied twice
- Reference `src/services/chat-service/Program.cs` for the Redis backplane wiring verbatim: read `SIGNALR_REDIS_CONNECTION` from configuration, call `AddStackExchangeRedis` with `DefaultDatabase` explicitly set to **1** (not the default 0 — Discovery Service already owns DB 0 for its profile cache on the same Redis container; an unset index would silently collide). Use the exact same env var name, `SIGNALR_REDIS_CONNECTION`, so both services read the same config entry in docker-compose.
- Since this hub has no client-invokable methods (unlike `ChatHub`'s `JoinRoom`/`SendMessage`), do not add any — a user is only ever added to their own personal group server-side on connect. Do not add a method that lets a client join an arbitrary group; that would let one user eavesdrop on another's notifications.
- What NOT to do:
  - Do not implement the Kafka consumers or the actual `ConnectionRequest`/`RequestAccepted`/`RequestDeclined`/`RequestExpired`/`ChatOpened` publish calls in this ticket — this ticket builds the hub and its group-join/backplane plumbing only; the events are wired up by the later Phase 8 tickets that consume `connection.requested`, `connection.accepted`, etc.
  - Do not build the `ChatOpened` deduplication logic here — that belongs with whichever later ticket consumes the event that triggers it; this ticket's job is only to make sure the hub and backplane exist for that logic to call into.
  - Do not invent a different group-naming convention or a different Redis DB index — reuse Chat Service's exactly, since both hubs share one backplane and a mismatch would silently break cross-replica delivery.
  - Do not write unit tests for this ticket (per the no-piecemeal-test-retrofits convention — all testing is deferred to the dedicated testing tickets).
