# T049 — Kafka Consumers — Connection Lifecycle Fan-Out to SignalR + FCM

## Why this ticket exists
Connection Service has been publishing `connection.requested`, `connection.accepted`, and `connection.expired` to Kafka since earlier phases, but nothing has ever subscribed to them. Right now the only way a recipient learns about a new connection request is by the app polling `GET /connections/pending` on its own schedule — so a user can sit for a while before finding out someone wants to connect. This ticket adds the first real subscriber to those three topics: it wires Notification Service to react the moment each event arrives and push the right alert (SignalR for an app that's open, FCM for one that isn't). Without this ticket, Phase 8 is not complete — the phase's own exit condition is specifically that `connection.requested` and `connection.accepted` each trigger both an FCM push and a SignalR event.

## What to build
- Kafka consumer(s) in `notification-service` subscribed to three topics:
  - `connection.requested` → send `RequestReceived` notification to the **recipient**
  - `connection.accepted` → send `RequestAccepted` notification to the **requester**
  - `connection.expired` → send `RequestExpired` notification to the **requester**
- Each notification is delivered two ways:
  - SignalR event pushed to the user's hub connection (if currently connected)
  - FCM push notification (if the user is not connected to the hub)
- Idempotent-consumer dedup (`processed_events`-style), backed by **Redis**, not SQL/Mongo — decided up front since `notification-service` has no database at all (T047/T048 only gave it FCM, SignalR, and a Redis connection). Store each processed event as a Redis key `processed_events:{eventId}` with a TTL matching Kafka's 7-day retention, reusing the same Redis connection string already wired up for the SignalR backplane. Use **logical DB index 2**, the next free index after T008's existing convention (DB 0 = Discovery Service cache, DB 1 = SignalR backplane) — never DB 1, or idempotency keys would share a keyspace with SignalR group-routing state. Update `/infra/README.md`'s DB-index table (from T008) to add this new row. The TTL replaces the cron-based pruning job the SQL/Mongo versions of this pattern need (see `kafka-outbox` skill's "Pruning processed_events" section) — Redis expires the key itself, nothing has to remember to delete it later. Known accepted trade-off: `redis.conf`'s `maxmemory-policy allkeys-lru` (T008) could in theory evict an unexpired idempotency key under memory pressure before Kafka would ever redeliver it — acceptable for a 256MB dev Redis holding a handful of small keys, not something this ticket needs to solve.
- Consumers read all needed data (connection id, requester id, recipient id, any display info) directly from the event payload. No outbound HTTP call to Connection Service to check current status before acting.
- **Connection-tracking store for the "SignalR if connected, else FCM" decision** — decided up front since this can't be a plain in-memory flag: `notification-service` can run multiple replicas (that's the entire reason T048 added the Redis backplane), so "is this user connected to the hub" must mean "connected to *any* replica," not just this process. Track it as a Redis **Set** per user: `NotificationHub.OnConnectedAsync` (T048) does `SADD notif:online:{userId} {connectionId}`; a new `OnDisconnectedAsync` override does `SREM notif:online:{userId} {connectionId}`. A user counts as connected if `SCARD notif:online:{userId} > 0` — a Set of connection ids, not a boolean or counter, so a user with two open tabs stays correctly "online" after closing just one of them (closing the second tab removes the last member, `SCARD` returns 0, same self-correcting shape as SignalR's own group membership). Same Redis connection as the backplane, same DB index as `processed_events` (index 2) — different key prefix (`notif:online:` vs `processed_events:`) so the two concerns don't collide in the same keyspace.
- **Cross-service addition — User Service** (required for the FCM half of this ticket to do anything real; logged as a gap during T047's review since no prior ticket ever added this field):
  - EF Core migration: add a nullable `FcmToken` column to the `User` entity.
  - `PublicUserProfileDto` serializes it as `fcm_token` — this is the exact property name `notification-service`'s `UserServiceClient` (T047) already reads; no change needed on the notification-service side once this ships.
  - New endpoint `PATCH /users/me/fcm-token` — body `{ "fcm_token": "..." }`, persists against the **caller's own** user id only, resolved from the gateway-injected `X-User-Id` header (same identity convention as every other `/users/me` action). Never accepts a target user id in the route or body — a device only ever registers its own token.

## Technical specification
Kafka consumers:
- `connection.requested` → notify recipient via SignalR + FCM (`RequestReceived`) — added post-T030 so the recipient learns of a new inbound request in real time, instead of only discovering it via `GET /connections/pending` polling
- `connection.accepted` → notify requester via SignalR + FCM (`RequestAccepted`)
- `connection.expired` → notify requester via SignalR + FCM (`RequestExpired`)

Connection Service sends `connection.requested` when a request is created and `connection.accepted` when recipient accepts — this service fans out both.

Event staleness (accepted, by design — see the `kafka-outbox` skill's "Event staleness after
an outage" section): if the Kafka outage/backlog window outlives a request's 10-minute TTL,
this consumer may process `connection.requested` for a connection that has already moved to
`EXPIRED` by the time the message arrives. Do not add a synchronous call back to Connection
Service to check "is this still current" before notifying — that reintroduces the tight
coupling Kafka exists to remove. Send the notification regardless; the recipient's own next
action (opening the request) hits Connection Service directly and sees the real, current
status. Partition key is `connection_id` for all three topics (set by Connection Service in
T032), so a same-connection `connection.requested`/`connection.expired` pair always arrives
in the order they actually happened, even after a large replay.

## Acceptance criteria
- [ ] Event consumed → SignalR notification delivered to connected client within 1 s
- [ ] FCM push sent if user not connected to hub
- [ ] Consumer does not call back to Connection Service to re-validate state before notifying — notifies from the event payload alone, even for a since-expired connection
- [ ] User Service: `PATCH /users/me/fcm-token` persists a token against the caller's own id (from `X-User-Id`), rejecting any attempt to set another user's token
- [ ] User Service: `GET /users/{id}` now serializes a real `fcm_token` value once one has been registered — `notification-service`'s existing `UserServiceClient` (T047) picks it up with no code change on its side

## Patterns demonstrated
- **Observer (via events)** — Connection Service publishes `connection.requested` / `connection.accepted` / `connection.expired` once, with no knowledge of who's listening; Notification Service (and potentially future subscribers) react independently. This ticket is the first consumer to actually prove that decoupling out.
- **Idempotency** — each consumer must check the shared `processed_events`-style store (from T009) before acting, so Kafka's at-least-once delivery guarantee can never cause a duplicate push to a user.
- **Event-Driven Architecture** — the consumer reacts to a past-tense fact (`connection.requested` = "this happened"), not a command, and is explicitly forbidden from treating the payload as "still current" — it notifies from what the event says, not from a fresh lookup.
- **Single Responsibility** — the consumer's only job is "turn this event into a SignalR push + an FCM push." It does not own connection-state logic, and it does not decide whether the connection is still valid; that stays Connection Service's and the recipient's own app's job.

Follow `dotnet-mvc-controllers` skill conventions for how services are registered/injected in this codebase (constructor injection, interfaces not concrete classes).
- User Service side — confirm the actual current shape of these files before editing, don't assume:
  - `src/services/user-service/Models/User.cs` — add the `FcmToken` property (nullable string).
  - `src/services/user-service/Migrations/` — add a new migration following the same one-column-add shape as `20260904172514_AddIdentityBadgeToUsers.cs`; never edit an already-applied migration file.
  - `src/services/user-service/Dtos/PublicUserProfileDto.cs` — add the `fcm_token` property.
  - `src/services/user-service/Controllers/UserProfileController.cs` + `src/services/user-service/Services/UserProfileService.cs` (via `IUserProfileService`) — add the `PATCH /users/me/fcm-token` action; resolve the caller's id the same way the rest of this controller's `/users/me` actions already do (gateway-injected `X-User-Id` header), not a route parameter.
- What NOT to do:
  - Do not call Connection Service's HTTP API from any of these consumers to re-check connection status before notifying — this is explicitly called out as the wrong move in both SPECS.md and the acceptance criteria. The notification fires from the event payload alone, every time, even for an event describing a connection that has since expired.
  - Do not add a synchronous "is user online" check that blocks the consumer — checking hub connection state and falling back to FCM should be fast and local (e.g. a connection-tracking store), not a network round trip that can stall the consumer loop.
  - Do not write ad hoc per-topic dedup logic — use the shared T009 infrastructure so all consumers across all services behave identically (Liskov Substitution: any consumer plugging into the shared idempotency abstraction must behave the same way).
  - Do not let `PATCH /users/me/fcm-token` accept a target user id from the caller (route, query, or body) — it must always act on the id resolved from `X-User-Id`, exactly like every other `/users/me` action already does. Accepting a caller-supplied id would let one user overwrite another user's registered device token.

## Known follow-ups
From the T031 design discussion on event staleness after a Kafka outage: if Kafka is down long enough for a connection's 10-minute TTL to elapse, Connection Service's outbox will end up queuing both `connection.requested` and `connection.expired` for the same connection, and the relay publishes them back-to-back once Kafka recovers. This is expected/safe, not a bug — but only if this consumer treats `connection.requested` purely as "this happened" and never as "this is still true," and never calls back to Connection Service to check current state before notifying. That requirement is already captured above in both the Technical Specification and the third acceptance criterion; no additional action needed beyond implementing the consumer exactly as specified (notify from the event payload alone).
