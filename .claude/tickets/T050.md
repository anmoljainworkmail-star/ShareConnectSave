# T050 — Notification Service Docker Image

## Why this ticket exists
Notification Service is the fan-out layer that turns Kafka events into FCM push notifications and SignalR real-time events — but right now it only runs if a developer has the .NET 9 SDK installed locally and starts it by hand. The `notification-service` block already exists in `src/infra/docker-compose.yml` (lines 432–458: port `8086:8080`, `depends_on: sqlserver, sqlserver-init, redis, kafka` all gated on health/completion, healthcheck hitting `curl -f http://localhost:8080/health`) — but `docker compose up notification-service` fails today because there's no Dockerfile to build. Without this ticket, the connection-request-to-push-notification flow this phase exists to prove (T049's Kafka consumers firing FCM + SignalR on `connection.requested` / `connection.accepted`) can't be exercised end-to-end in the local stack alongside the other 8 services. This is the fourth and final .NET service Dockerfile in the project (after api-gateway/T014, user-service, chat-service/T040) — so its only job is supplying the missing Dockerfile, not touching the compose wiring, which is already correct.

## What to build
- `src/services/notification-service/Dockerfile` — multi-stage build, same proven pattern as `api-gateway` (T014):
  - `build` stage: `mcr.microsoft.com/dotnet/sdk:9.0`, restores `notification-service.csproj`, publishes Release output.
  - `runtime` stage: `mcr.microsoft.com/dotnet/aspnet:9.0`, installs `curl` (needed for the existing compose healthcheck), copies only the published output, entrypoint `dotnet notification-service.dll`.
- `src/services/notification-service/.dockerignore` — excludes `bin/`, `obj/`, `.vs/`, copied exactly from `src/services/api-gateway/.dockerignore` (see Known follow-ups — this is not optional for this ticket).
- No changes to `src/infra/docker-compose.yml` or `docker-compose.override.yml` — the `notification-service` block already exists and is correctly wired (ports, healthcheck, `depends_on: sqlserver, sqlserver-init, redis, kafka`, `ASPNETCORE_ENVIRONMENT`/`ASPNETCORE_URLS`). Verify it, don't duplicate it.

## Acceptance criteria
- [ ] `src/services/notification-service/.dockerignore` exists (`bin/`, `obj/`, `.vs/`), copied from `api-gateway`'s/`user-service`'s `.dockerignore`, created before the first build
- [ ] `docker compose build notification-service` succeeds (actual Linux-container build, not just static review — AC specifically targets the MSB4018 failure mode seen on T040)
- [ ] `docker compose up notification-service` starts without error and the container reaches `(healthy)` status, not `(unhealthy)` or stuck `(starting)`
- [ ] `curl http://localhost:8086/health` from the host returns `200`
- [ ] Image size verified via `docker inspect shareconnectsave/notification-service:dev --format='{{.Size}}'` (or `docker save` + measure) — NOT `docker images`, which reports compressed/shared-layer sizes that understate the real footprint — confirmed under `200000000` bytes (~200MB)

## Patterns demonstrated
- **Multi-stage build** — separates the heavy SDK build toolchain from the minimal ASP.NET runtime image, so the shipped image carries no compiler, NuGet cache, or source tree — only the published binaries needed to run.
- **Separation of Build-Time and Run-Time Concerns** — the runtime stage never runs `dotnet build`/`dotnet restore`; it only executes what the build stage already produced.
- **Healthcheck as a Dependency Gate** — matches the pattern already used by `sqlserver`, `redis`, and `kafka` in `docker-compose.yml`: the container isn't considered "up" just because the process started — Compose waits until `/health` actually answers `200` before anything depending on `notification-service` treats it as available.

## Agent implementation notes
- Key files to create:
  - `src/services/notification-service/.dockerignore` (new) — create this FIRST, before any build attempt. Copy `src/services/api-gateway/.dockerignore` (or `user-service`'s) exactly: `bin/`, `obj/`, `.vs/`. Do NOT cite T028/T034 (Java/Maven services) as precedent for skipping this — see Known follow-ups below for why that reasoning is wrong for a .NET service.
  - `src/services/notification-service/Dockerfile` (new) — copy the exact two-stage shape already shipped in `src/services/api-gateway/Dockerfile` (T014), adapted to this project name:
    - `COPY notification-service.csproj ./` then `RUN dotnet restore` before `COPY . .` and `dotnet publish`, for Docker layer caching (the restore layer is only invalidated when the `.csproj` itself changes).
    - Runtime stage installs `curl` via `apt-get` (same as gateway/chat-service) because `docker-compose.yml`'s existing healthcheck runs `curl -f http://localhost:8080/health` from inside the container, and `mcr.microsoft.com/dotnet/aspnet:9.0` doesn't ship `curl` by default. Follow with `rm -rf /var/lib/apt/lists/*` to stay inside the 200MB budget.
    - `COPY --from=build /app/publish .` — never `COPY . .` in the runtime stage.
    - `ENTRYPOINT ["dotnet", "notification-service.dll"]`.
    - Do NOT set `ASPNETCORE_URLS`/`ASPNETCORE_ENVIRONMENT` via `ENV` in the Dockerfile — `docker-compose.yml` already sets both (lines 451–452); duplicating them creates two sources of truth that can drift.
- What NOT to do (common mistakes for this task type):
  - Do not re-add or edit the `notification-service` service block in `src/infra/docker-compose.yml` or `docker-compose.override.yml` — both already exist and are correctly wired (ports `8086:8080`, healthcheck, `depends_on: sqlserver, sqlserver-init, redis, kafka`). This ticket is Dockerfile + `.dockerignore` only.
  - Do not hardcode port numbers inside the Dockerfile — `docker-compose.yml` already controls the external port mapping.
  - Do not skip the `.dockerignore` and do not justify skipping it by pointing at T028/T034 (Java services) — those are a different language toolchain and a different (and since-corrected) deferral; see Known follow-ups.
  - Do not verify image size with `docker images` — its output can reflect shared/cached layers and compressed sizes, not the real on-disk footprint; use `docker inspect ... --format='{{.Size}}'` or `docker save` instead.

## Known follow-ups
A prior Docker image ticket (T040, Chat Service) discovered that skipping `.dockerignore` on a .NET service causes a real build failure, not just a theoretical one. T040's own ticket text incorrectly cited T028/T034 (Java/Maven services) as precedent for skipping `.dockerignore`, when the actual .NET precedent it was meant to copy — `api-gateway` (T014) — always ships one specifically to prevent this exact failure. Without it, `COPY . .` in the Dockerfile copied the host's own locally-built `obj/` folder (present because the project had been opened/restored in Visual Studio) into the Linux build stage, overwriting the clean restore the container's own `RUN dotnet restore` had just produced. Visual Studio's restore bakes a Windows-only NuGet fallback path (`C:\Program Files (x86)\Microsoft Visual Studio\Shared\NuGetPackages`) into `obj/chat-service.csproj.nuget.g.props`; `dotnet publish --no-restore` then failed immediately inside the Linux container with `MSB4018: Unable to find fallback package folder`. This was only caught running a real `docker compose build`, not by `/review-task`'s static analysis (no Docker engine was available in that review environment). `notification-service/` already has local `bin/`/`obj/` on disk today and no `.dockerignore` yet, so it will hit this identical failure on its first real `docker compose build` unless this ticket adds the `.dockerignore` upfront — which it does, per the acceptance criteria and implementation notes above.
