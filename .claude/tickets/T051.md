# T051 — Spring Boot + Spring Data MongoDB Setup

## Why this ticket exists

Right now `report-service` is an empty Spring Initializr skeleton (just a `spring.application.name` line and no dependencies beyond what Initializr ships by default) — there is nowhere to store a report, and no way for a later ticket to query "all reports filed against this user" to drive escalation. Reports are the input to the whole escalation flow described in REQUIREMENTS.md (`report.filed` → count checked → threshold hit → trust recalculated → discovery updated), so until this service can actually persist a report and look it up by the reported user's id, none of that flow can exist. This ticket is infrastructure-only: it wires `report-service` to MongoDB and proves the connection works, exactly the same scope T035 was for `chat-service` (Mongo plumbing, no business logic yet). It also matters as a teaching ticket: every other Java service in this platform (`discovery-service`, `connection-service`, `rating-service`, `admin-service`) uses SQL Server + JPA — this is the only Java service on MongoDB, so it's the one place that demonstrates Spring Data MongoDB's repository-derived-query style side by side with the JPA style used everywhere else.

## What to build

- Add dependencies to `report-service`'s `pom.xml`: Spring Web, Spring Data MongoDB, Spring Kafka, Validation, Actuator, Lombok, MapStruct.
- `Report` document class (`@Document(collection = "reports")`) with at minimum: `id` (String, `@Id`), `reporterId`, `reportedId`, `reason` (enum — see Patterns), `createdAt`.
- `ReportRepository extends MongoRepository<Report, String>` with a derived query method `List<Report> findByReportedId(String reportedId)`.
- `application.yml` (replacing the current bare `application.properties`) configuring `spring.data.mongodb.uri` from an environment variable — see Technical specification below for the exact variable name, which is already fixed by the existing `docker-compose.override.yml` entry for this service.
- Virtual threads enabled (`spring.threads.virtual.enabled: true`), matching every other Java service's Spring Boot Setup ticket (T021/T029/T041/T056).
- Actuator health endpoint reachable at `/actuator/health` (already wired into this service's Docker healthcheck in `docker-compose.yml`), exposing only `health,info`, not `*`.
- Service must start and successfully connect to MongoDB before serving requests.

## Technical specification

Dependencies: Spring Web, Spring Data MongoDB, Spring Kafka, Validation, Actuator, Lombok, MapStruct.

**MongoDB connection — corrected convention (see Known follow-ups #2 below):** do NOT configure this via a raw `process.env.MONGO_CONNECTION_STRING` read, and do not invent a new variable name. `src/infra/docker-compose.override.yml` already has a `report-service` block (added ahead of this ticket, alongside the other Phase 9 service stubs) that sets:

```
SPRING_DATA_MONGODB_URI=${REPORT_MONGODB_URI:-mongodb://mongodb:27017/ReportServiceDb}
```

Spring Boot's relaxed env-var binding maps `SPRING_DATA_MONGODB_URI` directly to the `spring.data.mongodb.uri` property — the same mechanism `rating-service`/`discovery-service` already rely on for `SPRING_DATASOURCE_URL` → `spring.datasource.url`. So `application.yml` must declare `spring.data.mongodb.uri` (not a custom property name), bound as `${SPRING_DATA_MONGODB_URI:...}` in the `dev` profile so a developer can `mvn spring-boot:run` this service standalone against `docker-up`'s infra. Use the Mongo container's **host-mapped** port for the dev-profile default — `mongodb:27017` is only reachable from inside the Compose network; a developer running outside Docker needs `mongodb://localhost:27018/ReportServiceDb` (27018 is the host port `docker-compose.yml`'s `mongodb` service maps, same pattern `rating-service`'s `application.yml` uses for its own dev-profile SQL Server port). The `prod` profile must have no default — a missing value should fail startup loudly, same as every other service's prod profile block.

`ReportRepository extends MongoRepository<Report, String>`.

This service is the only Java service using MongoDB — demonstrates Spring Data MongoDB alongside the JPA services.

## Acceptance criteria

- [ ] Service starts connected to MongoDB
- [ ] `ReportRepository.findByReportedId()` query works

## Patterns demonstrated

- **Repository (via Spring Data)** — `ReportRepository` is a plain interface (`extends MongoRepository<Report, String>`); Spring Data generates the implementation and even the query body for `findByReportedId` from the method name alone. Same "hide where the data lives behind a collection-like interface" idea as every other `IXxxRepository` in this project, but here the framework writes the concrete class for you instead of a developer hand-rolling it.
- **Database per Service** — `report-service` owns the `ReportServiceDb` Mongo database exclusively; `chat-service`'s `ChatServiceDb` lives on the same physical Mongo container but is a completely separate logical database, and no other service is allowed to query either one directly.
- **No Hardcoded Config** — the Mongo URI is read from `spring.data.mongodb.uri`, itself bound to an environment variable, never a literal `mongodb://...` string in committed code; only the `dev` profile gets a convenience default, and only because it points at the developer's own local infra, not a shared or production instance.
- **Open/Closed (SOLID O)** — report reason categories (Harassment, Fake profile, Inappropriate content, Asked for money, Other) are defined as an enum, not a string validated by scattered `if/else` checks — adding a new reason later means adding an enum constant, not touching validation logic.

## Agent implementation notes

- Key files to create/change (all under `src/services/report-service/`):
  - `pom.xml` — add `spring-boot-starter-web`, `spring-boot-starter-data-mongodb`, `spring-boot-starter-validation`, `spring-boot-starter-actuator`, `spring-kafka`, `lombok`, and MapStruct (`mapstruct` + `mapstruct-processor` as an annotation processor), matching the dependency set already used by `rating-service`/`discovery-service`'s `pom.xml` for the non-Mongo pieces.
  - `src/main/resources/application.yml` — replace `application.properties`. Mirror `rating-service`'s `application.yml` structure: a shared top-level section (`spring.application.name: report-service`, `spring.threads.virtual.enabled: true`, `management.endpoints.web.exposure.include: health,info`), then `---`-separated `dev` and `prod` profile documents each setting `spring.data.mongodb.uri` per the Technical specification above. Delete `application.properties` once `application.yml` covers everything it had (just the application name).
  - `src/main/java/com/shareconnectsave/report_service/model/Report.java` (or `domain/`, matching whatever package layout `rating-service` uses for its JPA entities) — `@Document(collection = "reports")`, fields `id`, `reporterId`, `reportedId`, `reason` (enum, see below), `createdAt`.
  - `src/main/java/com/shareconnectsave/report_service/model/ReportReason.java` — enum: `HARASSMENT`, `FAKE_PROFILE`, `INAPPROPRIATE_CONTENT`, `ASKED_FOR_MONEY`, `OTHER`.
  - `src/main/java/com/shareconnectsave/report_service/repository/ReportRepository.java` — `public interface ReportRepository extends MongoRepository<Report, String> { List<Report> findByReportedId(String reportedId); }`.
- Follow the `java-spring-boot` skill's Spring Data MongoDB section for `@Document`/`@Id` usage and for how derived-query method names (`findByReportedId`) map to the generated query — this is the first place in the codebase doing this, so don't copy JPA `@Query`/`@Entity` patterns from `rating-service` by habit.
- Naming note: CLAUDE.md's "JPA `@Entity` classes take an `Entity` suffix" rule is scoped specifically to JPA. `Report` here is a Spring Data MongoDB `@Document`, not a JPA `@Entity` — use the plain name `Report` (matching the spec's own `MongoRepository<Report, String>` signature) rather than `ReportEntity`; don't extend a JPA-specific naming rule to a different persistence technology it was never written for.
- Repository naming: per the existing project convention (see Known follow-ups), this is `ReportRepository`, never `IReportRepository` — Java repositories in this codebase are plain interfaces with no `I`-prefix, unlike the C# services.
- What NOT to do: do not add any `@RestController` endpoints, Kafka producers/consumers, or the threshold/escalation logic in this ticket — that's later Phase 9 tickets (T052+). This ticket is connection + repository + startup health only, same scope boundary T035 held for `chat-service`.
- Do not use `process.env.MONGO_CONNECTION_STRING` or any variable name not already present in `docker-compose.override.yml`'s `report-service` block — the correct variable is `SPRING_DATA_MONGODB_URI` (optionally sourced from `REPORT_MONGODB_URI` in `.env`, per that file's existing default).
