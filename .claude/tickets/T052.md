# T052 — Report Submission

## Why this ticket exists

Right now `report-service` can connect to MongoDB and look up reports by target (T051), but there is no way for a traveler to actually file one — the single most important safety mechanism in REQUIREMENTS.md section 8 does not exist yet. This ticket builds the one endpoint that turns a user's "this person made me uncomfortable / this profile looks fake / this person asked for money" into a durable, counted record. It also publishes `report.filed`, which is the trigger for the entire `ReportEscalationSaga` (report filed → count checked → threshold hit → trust recalculated → discovery updated) — without this ticket, Admin Service never learns a report exists, repeat offenders never get escalated, and Rating Service's trust score never reflects a pattern of bad behavior. Business value: this is the platform's abuse-reporting entry point — the thing that lets "women-only mode" and "trust score" actually mean something, instead of being safety features with no way to ever trigger.

## What to build

- Extend T051's `Report` document (do not recreate it) with the fields this endpoint needs: `connectionId` (nullable — set when the report originates from inside a chat, per REQUIREMENTS.md §8), `details` (nullable, max 1000 chars), `status` (new `ReportStatus` enum: `OPEN`, `ESCALATED`, `REVIEWED`, `DISMISSED` — defaults to `OPEN` at creation; only T053 ever transitions it away from `OPEN`), plus two outbox-style bookkeeping fields: `eventPayload` (String, the pre-serialized `report.filed` JSON) and `outboxPublishedAt` (`Instant`, nullable — `null` means "not yet relayed to Kafka").
- `POST /reports` endpoint (`ReportController`, thin — delegates everything to `ReportService`/`ReportServiceImpl`). Reads the reporter from `X-User-Id`. Request/response field names and the `reason` wire format follow `contracts/openapi/report-service.yaml` exactly (see Technical specification — this differs from SPECS.md's generic field names).
- `ReportOutboxRelay` — a `@Scheduled(fixedDelay = 500)` poller that is the only class in this service allowed to inject `KafkaTemplate`. Polls `reports` for `outboxPublishedAt == null`, publishes each document's `eventPayload` to the `report.filed` topic keyed by `reportedId`, then marks it published. This is report-service's equivalent of `connection-service`'s `OutboxRelay` (T032) and `rating-service`'s (T042) — same guarantee, adapted to Mongo (see below for exactly how).
- `ReportFiledEvent` payload matching `contracts/kafka/report.filed.schema.json`: `event_id`, `report_id`, `reporter_id`, `reported_id`, `reason`, `report_count_for_target`.

## Technical specification

**Original spec (SPECS.md, verbatim):**
`POST /reports`
Body: `{ "reported_user_id", "reason", "context" }`
Reads reporter from `X-User-Id`.
Persist to MongoDB `reports` collection. Count how many reports the target has received (all time). Publish `report.filed` Kafka event including `report_count_for_target`.

**Refined — real field names (contract wins over SPECS.md's generic prose, same precedent T042 set for `RatingSubmissionDto`):**
`contracts/openapi/report-service.yaml`'s `ReportCreateRequest` schema is the actual wire contract: `{ "reported_id", "reason", "connection_id"? , "details"? }` — **not** `reported_user_id`/`context`. Use `reported_id` and `details`. Also include the already-contracted `connection_id` (nullable) even though SPECS.md's one-line spec omits it — REQUIREMENTS.md §8 explicitly allows reporting from within a chat, and the contract already models it; dropping it would silently break that flow.

`reason` on the wire is the Title Case string set from the contract's `ReportReason` schema (`"Harassment"`, `"Fake profile"`, `"Inappropriate content"`, `"Asked for money"`, `"Other"`) — the same five values as T051's already-built `ReportReason` Java enum (`HARASSMENT`, `FAKE_PROFILE`, `INAPPROPRIATE_CONTENT`, `ASKED_FOR_MONEY`, `OTHER`). T051 built the enum but never gave it a wire mapping (no endpoint existed yet). Add Jackson `@JsonValue`/`@JsonCreator` (or `fromWireValue()`/`toWireValue()`) to `ReportReason` now, exactly the technique `RatingTag` already uses in `rating-service` (T042) — do not rely on Jackson's default enum (de)serialization, which would emit `HARASSMENT` instead of `"Harassment"`.

**Known contract drift — do not try to reconcile it yourself:** `contracts/kafka/report.filed.schema.json`'s own `reason` enum (`harassment`, `fake_profile`, `inappropriate_content`, `scam`, `abusive_behaviour`, `spam`, `other`) does **not** match either REQUIREMENTS.md §8, the OpenAPI `ReportReason` schema, or T051's Java enum — it's missing `asked_for_money` and has three categories (`scam`, `abusive_behaviour`, `spam`) that exist nowhere else in this project. Treat the OpenAPI contract + T051's enum as authoritative (five categories, Title Case on HTTP, and reuse the exact same `ReportReason` enum/mapping for the Kafka payload's `reason` field too — one enum, one source of truth, serialized two ways). Do not add `SCAM`/`ABUSIVE_BEHAVIOUR`/`SPAM` constants to satisfy the Kafka schema file — that file is the one that's wrong. This is a `/validate-contracts` finding for the Tech Lead to fix in the schema file itself, not something to paper over in code.

**Response contract:** `contracts/openapi/report-service.yaml`'s `Report` schema requires `status` in the response body — this is why `ReportStatus` (defaulting to `OPEN`) is added to the document in this ticket, even though nothing transitions it yet (that's T053).

**The real Mongo-only outbox approach (report-service has no SQL database — figure this out before copying T032/T042's SQL-table shape verbatim):**

Every other Java producer in this project (`connection-service` T032, `rating-service` T042) builds a *separate* `outbox` table + JPA entity + repository, because SQL Server supports proper multi-statement transactions — the business row and the outbox row commit together. `report-service` has no SQL database at all (MongoDB-only, per T051), and this project's own dev Mongo instance is a **single standalone node, not a replica set**, so it cannot do multi-document transactions either — a separate `outbox` collection would need one to get the same atomicity a SQL transaction gives for free, and wouldn't have it.

`chat-service` (the only other Mongo-only producer in this codebase, T039) already solved exactly this problem: instead of a second collection, it folds the "pending outbox event" fields directly onto the business document itself (`ChatRoomEntity.OutboxEventType`/`OutboxPayload`/`OutboxCreatedAt`/`OutboxPublishedAt`), so the business write and the "event is now pending" write are the *same* single-document write — and MongoDB already guarantees a single-document write is atomic, even on a standalone node, no transaction needed. See `src/services/chat-service/HostedServices/OutboxRelayHostedService.cs`'s own header comment for the full reasoning; it explicitly documents this as a deliberate Tech-Lead deviation from the generic SQL-shaped outbox skill text.

This ticket follows that same precedent: `eventPayload` + `outboxPublishedAt` live directly on `Report`, not on a separate `outbox` collection. The `POST /reports` handler mints the report's own `id` (a `UUID.randomUUID().toString()`, app-assigned — same "mint the id before the row exists so it can be embedded in its own payload" technique `OutboxEvent.id` uses on the SQL side), builds the complete `ReportFiledEvent` (using that same id for both `report_id` and `event_id` — one report is filed exactly once and published exactly once, so there's no second event that would need a distinct `event_id`), serializes it to `eventPayload`, and saves the whole `Report` document — business data and "event pending" flag — in one `ReportRepository.save(...)` call. `ReportOutboxRelay` is the only thing that ever reads `eventPayload` back out and talks to Kafka.

**Counting `report_count_for_target`:** query `reportRepository.findByReportedId(reportedId)` (T051's existing derived query) *before* inserting the new report, and use `existing.size() + 1` as `report_count_for_target` (the count must include the report just filed, per the contract's own description: "including this one"). This is a read-then-write, not a single atomic counter increment — acceptable here for the same reason the folded-outbox design is acceptable: a standalone Mongo node already can't give you a transactional atomic counter across concurrent requests either, and an off-by-one under a genuine race (two reports against the same target landing in the same instant) only means a threshold-escalation check fires one event later than ideal — it does not lose a report or corrupt data. Do not attempt to build a distributed lock or `findAndModify`-based atomic counter for this ticket; that is disproportionate to the actual risk here.

## Acceptance criteria

- [ ] Report persisted to MongoDB
- [ ] `report.filed` event published
- [ ] `report_count_for_target` in event is accurate

## Patterns demonstrated

- **Outbox Pattern, Mongo-adapted** — the business write (the report) and the "this needs to be published" flag live in the exact same document and the exact same `save()` call, so there is no window where a report exists but nothing records that its event still needs publishing. Same guarantee as every SQL-backed outbox in this project, achieved without a transaction, because MongoDB's single-document write atomicity is the thing doing the work instead.
- **Single Responsibility (SOLID-S)** — `ReportOutboxRelay` only moves pending rows to Kafka; it has no idea what a report, a reason, or a threshold is. `ReportServiceImpl` decides what a report is and builds the event; it never touches `KafkaTemplate` directly.
- **Dependency Inversion (SOLID-D)** — `ReportServiceImpl` depends on `ReportRepository` (an abstraction), never on `MongoTemplate`/`KafkaTemplate` concrete wiring beyond what the relay itself needs.
- **Open/Closed (SOLID-O)** — `ReportReason` stays a closed enum with a wire-value mapping; adding a sixth reason later is a one-line enum addition plus one mapping entry, not a change to any `if/else` validation chain.
- **Observer (GoF, via events)** — `report.filed` is published once; Admin Service (and, per the Kafka topic table, eventually Rating Service's threshold-driven trust recalculation path) reacts independently. Report Service has no idea who's listening.
- **Database per Service** — `report-service` owns `reports` exclusively; it never queries Admin Service's or Rating Service's data to decide what to persist or publish.

## Agent implementation notes

- Key files to create/change (all under `src/services/report-service/src/main/java/com/shareconnectsave/report_service/`, matching T051's existing package layout):
  - `model/Report.java` — **extend**, don't recreate: add `connectionId` (String, nullable), `details` (String, nullable), `status` (`ReportStatus`, default `ReportStatus.OPEN`), `eventPayload` (String, nullable), `outboxPublishedAt` (`Instant`, nullable). `id` changes from Mongo-auto-generated to **app-assigned** (`UUID.randomUUID().toString()` set before the first `save()`) — needed so the id can be embedded in its own `eventPayload` before the document is persisted.
  - `model/ReportStatus.java` — new enum: `OPEN`, `ESCALATED`, `REVIEWED`, `DISMISSED`.
  - `model/ReportReason.java` — **extend** T051's existing enum with Jackson `@JsonValue`/`@JsonCreator` (or `fromWireValue()`/`toWireValue()`) mapping to the Title Case wire strings, per Technical specification above. Do not create a second reason enum.
  - `repository/ReportRepository.java` — **extend** T051's interface with a derived query for the relay: `List<Report> findByOutboxPublishedAtIsNullOrderByCreatedAtAsc(Pageable pageable)`.
  - `dto/ReportCreateDto.java` — record: `@JsonProperty("reported_id") String reportedId`, `@JsonProperty("reason") ReportReason reason`, `@JsonProperty("connection_id") String connectionId`, `@JsonProperty("details") String details` — per-field `@JsonProperty` on a record, same convention `connection-service`'s `CreateConnectionDto`/`ConnectionResponse` already use (see that service's `domain/` package for the exact idiom) — not a project-wide Jackson naming strategy.
  - `dto/ReportResponse.java` — record matching the contract's `Report` schema: `id`, `reporter_id`, `reported_id`, `reason`, `connection_id`, `details`, `status`, `created_at` (each `@JsonProperty`-annotated to snake_case).
  - `mapper/ReportMapper.java` — MapStruct, `Report` ↔ `ReportCreateDto`/`ReportResponse`, per the `java-spring-boot` skill's DTO-mapping section.
  - `controller/ReportController.java` — `POST /reports`, `@RequestHeader("X-User-Id") String reporterId`, delegates to `ReportService`, returns `201` + `ReportResponse`.
  - `service/ReportService.java` (interface) + `service/ReportServiceImpl.java` — holds all the logic: guard-clause validation (reporter cannot report themselves — compare `reporterId` to `reportedId` and reject early), count lookup, id minting, event-payload building, single `save()` call. Controller stays thin per standing project convention.
  - `kafka/event/ReportFiledEvent.java` — record matching `contracts/kafka/report.filed.schema.json`: `event_id`, `report_id`, `reporter_id`, `reported_id`, `reason`, `report_count_for_target` (plain integer), each `@JsonProperty`-annotated, same idiom as `connection-service`'s `kafka/event/ConnectionAcceptedEvent.java`.
  - `kafka/ReportOutboxRelay.java` — `@Component`, `@Scheduled(fixedDelay = 500)`, injects `ReportRepository` + `KafkaTemplate<String, String>` + (for the partial-update step) `MongoTemplate`. Each tick: fetch a page of `findByOutboxPublishedAtIsNullOrderByCreatedAtAsc(PageRequest.of(0, 50))`; for each, `kafkaTemplate.send("report.filed", report.getReportedId(), report.getEventPayload()).get()` (synchronous, same reasoning as the SQL relays — don't mark published before Kafka has acknowledged); on success, use `MongoTemplate.updateFirst(Query.where("id").is(report.getId()), Update.set("outboxPublishedAt", Instant.now()), Report.class)` — a **targeted single-field update**, not a full-document re-save, so a concurrent read of the same document is never clobbered. This is the one new Spring Data MongoDB technique this ticket introduces beyond T051's plain `MongoRepository` usage — explain it with a short comment where it's used (what `MongoTemplate` is for, and why a partial update beats re-saving the whole entity here). Leave `outboxPublishedAt` untouched (still `null`) on failure — the next tick retries, no DLQ/retry-count bookkeeping (that's T054, explicitly out of scope here, same boundary the `kafka-outbox` skill draws for Report Service).
- What NOT to do:
  - Do not build a separate `outbox` MongoDB collection, or anything resembling the SQL-backed `OutboxEvent`/`OutboxRepository`/`IOutboxService` shape from `connection-service`/`rating-service` — Mongo-only services fold the outbox fields onto the business document instead (see Technical specification above).
  - Do not call `KafkaTemplate` from `ReportController` or `ReportServiceImpl` — `ReportOutboxRelay` is the only class allowed to touch it.
  - Do not add retry-count tracking, a DLQ topic publish, or any `report.filed.dlq` logic in this ticket — that is T054's entire scope, and skill-map.md deliberately does not load the `kafka-outbox` skill for this ticket for that reason.
  - Do not implement `GET /reports` or `GET /reports/{id}` — they're in the OpenAPI contract but not in this ticket's spec or acceptance criteria; leave them for whichever ticket wires up Admin Service's review queue.
  - Do not implement any threshold/escalation decision logic (comparing `report_count_for_target` to a limit, flipping `status` to `ESCALATED`) — that is T053. This ticket only computes and publishes the count; it does not act on it.
  - Do not add the Kafka schema file's `SCAM`/`ABUSIVE_BEHAVIOUR`/`SPAM` reason values anywhere in code — see the "Known contract drift" note above.
  - Do not re-validate the JWT or second-guess `X-User-Id` — it was already validated at the YARP gateway, same trust boundary every other service in this platform relies on.
  - Be aware (do not attempt to fix here): `shared-java-lib`'s `GlobalExceptionHandler` has no handler for `MissingRequestHeaderException` yet (flagged in T051), so a request missing `X-User-Id` will currently surface as a raw 500 instead of a clean 400 until T091 lands the shared fix.
