# T053 — Escalation Threshold Logic

## Why this ticket exists

Right now `report-service` can file a report, count how many reports a target has received, and publish that count on `report.filed` (T052) — but nothing ever acts on the count. A repeat offender with ten reports against them looks exactly like a first-time offender with one, both sitting as plain `OPEN` documents, and Admin Service has no durable, queryable signal that says "this account needs a human to look at it now." This ticket is what turns raw report volume into an actual priority signal: once a target crosses the escalation threshold, their reports are flagged so the admin review queue can surface them ahead of everything else, and the fact of escalation is published on the event itself so any downstream consumer (today: nothing yet; eventually: Admin Service's own queue aggregation in Phase 10) doesn't have to re-derive it. Business value: this is the difference between "reports exist" and "reports against a repeat offender actually surface to a human reviewer" — the second half of REQUIREMENTS.md §8's safety promise, and the Report-Service-owned leg of `ReportEscalationSaga` (`report filed → count checked → threshold hit → trust recalculated → discovery updated`; the last two steps belong to Rating/Discovery and are out of scope here).

## What to build

- `ReportEscalationService` (or logic inside `ReportServiceImpl` — see Technical specification for why a separate collaborator is warranted) that, on every new report, checks `report_count_for_target` against a configurable threshold (`report.escalation.threshold`, env-backed, default `3`).
- When the threshold is met or exceeded: **bulk-update every historical `Report` document for that `reportedId`** (not just the triggering one) to `status: ESCALATED`, stamping a `reportCountAtEscalation` snapshot field used for queue sorting.
- Extend `ReportFiledEvent` (and its Kafka schema) with a new required `escalated` boolean field, computed before the event is serialized into `eventPayload` — same single-document outbox write T052 already established, no new write path.
- `GET /reports/queue` — new admin-only endpoint, not yet in the OpenAPI contract (see Technical specification): returns every `Report` with `status: ESCALATED`, sorted by `reportCountAtEscalation` descending.
- Admin-role guard: reads `X-User-Role` directly (no Spring Security — see below), rejects non-admin callers with `403`.

## Technical specification

**Original spec (SPECS.md, verbatim):**
On each new report, if `report_count_for_target` ≥ escalation threshold (configurable, default 3): mark the user's reports as `escalated` in MongoDB, include `escalated: true` in the Kafka event.
`GET /reports/queue` — admin endpoint (requires `X-User-Role: admin`), returns all `escalated` reports sorted by target's report count descending.

**"Mark the user's reports as escalated" = all historical reports for that target, not just the new one.** T052 already reserved `ReportStatus.ESCALATED` as a value "only T053 ever transitions it away from OPEN" and `GET /reports/queue` is explicitly a review *queue* — if only the triggering report flipped status, the queue would show one `ESCALATED` row sitting next to N `OPEN` rows for the same repeat offender, which defeats the purpose (an admin reviewing this user needs to see their whole history surfaced together, not reconstruct it by also querying `GET /reports/{id}` N more times). Use a single `MongoTemplate.updateMulti(Query.where("reportedId").is(reportedId), Update.update("status", ReportStatus.ESCALATED).set("reportCountAtEscalation", count), Report.class)` call, run **after** the triggering report's own `save()` (T052's existing outbox-protected write) — this naturally picks up the just-saved report too, since it matches on `reportedId`, so there's no need to special-case the new document's initial status. This bulk update is a plain mutable-state write, not part of the outbox invariant (it never touches `eventPayload`/`outboxPublishedAt`), so it's safe as a second, separate write — same reasoning T052 already used to justify its own read-then-write count as "acceptable, not exactly-once-critical."

**Config property — exact name and style, matching the one existing precedent in this codebase (`rating-service`'s `ReportFiledConsumer`, which already reads its own independent `report.filed` threshold):**
```yaml
report:
  escalation:
    threshold: ${REPORT_ESCALATION_THRESHOLD:3}
```
Inject with `@Value("${report.escalation.threshold}")` as a non-final field (same mixed constructor-injection-plus-`@Value`-field style `ReportFiledConsumer` already uses, for the same reason: `@RequiredArgsConstructor` only generates params for `final` fields). This is a *different* threshold than `rating.report.suspension.threshold` — Rating Service's consumer independently decides when to recalculate trust score off the same `report_count_for_target` number; Report Service's own threshold here decides when to escalate its own queue. Two services, two independently configurable policies, same raw signal — do not try to unify them into one shared property.

**Admin-role check — no Spring Security exists yet, don't invent it here.** Grepped the codebase for an existing `X-User-Role` convention before writing this: the only *planned* Spring Security setup (`OncePerRequestFilter` reading `X-User-Role`, populating `SecurityContext`) is **T056**, and it is scoped specifically to `admin-service` in Phase 10 — Phase 9 (this phase) ships before it, and no other Java service has a security filter chain. The actual established convention for header-based checks in this codebase (`rating-service`, `discovery-service`, `connection-service`) is a plain `@RequestHeader` read plus a guard clause that throws a domain-specific `RuntimeException`, caught by a local `@RestControllerAdvice` living next to the feature code (`RatingExceptionHandler` + `SelfRatingException` is the clearest example). Follow that same shape here: `@RequestHeader("X-User-Role") String role` in `ReportController`, guard clause `if (!"admin".equals(role)) throw new NotAdminException(userId);`, mapped to `403` by a new `ReportExceptionHandler` (first one in this service — T052 didn't need one since its only guard clause was self-report, which SPECS.md/T052 left as the shared handler's generic 500; not this ticket's job to retrofit that). Do not reference or wait for T056 — it doesn't exist yet and isn't this service's dependency anyway.

**Contract gaps this ticket must close (not drift — these simply haven't been built yet, unlike T052's genuine three-way reason-enum disagreement):**
1. `contracts/openapi/report-service.yaml` currently has `GET /reports` and `GET /reports/{id}` but no `GET /reports/queue` path at all. Add it: admin-only (`X-User-Id` + `X-User-Role` params, same as the other two admin paths in this file), `200` → array of the existing `Report` schema, `401`/`403`/`500` inline exactly like the other two admin paths already do in this same file (this file does not use a shared reusable `Forbidden` response component the way `admin-service.yaml` does — match this file's own existing inline style, not the other service's).
2. `contracts/kafka/report.filed.schema.json` has `additionalProperties: false` and no `escalated` property — add it as a new required boolean field. Also correct the file's own stale `description` and `report_count_for_target` field description, both of which currently say "Admin Service... escalates" / "Admin Service uses this to auto-escalate" — per this ticket's spec, **Report Service** computes and publishes the escalation decision synchronously, before the event is even built; Admin Service (Phase 10) only ever reads the already-decided `escalated` flag (or `report_count_for_target`, independently, the way Rating Service already does for its own unrelated threshold). Update the comments to reflect that, don't leave the stale claim in place once this ticket makes it provably wrong.
3. Do not touch `admin-service.yaml`'s separate `/admin/queue` endpoint or its `ReviewQueueItem` schema — that's a distinct, cross-service aggregation view (it includes `trust_score`, which `report-service` has no access to) built in Phase 10 (T057), not the same thing as this ticket's `GET /reports/queue`.

## Acceptance criteria

- [ ] 3rd report against same user → `escalated: true` in Kafka event
- [ ] `GET /reports/queue` returns only escalated reports
- [ ] Non-admin calling queue endpoint → 403

## Patterns demonstrated

- **Open/Closed (SOLID-O)** — the threshold is a config value (`report.escalation.threshold`), not a literal `3` buried in an `if`; raising or lowering it is a config/env change, never a code change.
- **Single Responsibility (SOLID-S)** — the escalation decision (count vs. threshold, bulk status flip) stays in its own method/collaborator, separate from `ReportOutboxRelay` (which still only ever talks to Kafka) and separate from the admin-role authorization guard (which lives at the controller boundary, not mixed into escalation logic).
- **Outbox Pattern (Mongo-adapted), reused not reinvented** — `escalated` is computed and folded into `eventPayload` *before* the same single-document `save()` T052 already performs; this ticket adds a decision, not a new write path.
- **Repository (via Spring Data)** — the queue query is a derived method (`findByStatusOrderByReportCountAtEscalationDesc`), same "framework writes the query" idea T051 already established for `findByReportedId`.

  - Do not add a separate Mongo `outbox` collection or a second `eventPayload`-style write for the bulk status update — it is plain mutable business state, not part of the outbox invariant, and is safe as a second write.
