# T054 — Kafka Producer: report.filed — Retry + Dead Letter Handling

## Why this ticket exists

**The Problem, in plain English:** right now, `ReportOutboxRelay` (built in T052) picks up a filed report, tries once to hand it to Kafka (`kafkaTemplate.send(...).get()`), and if that one attempt throws — a one-second network blip, a broker doing a leader election, anything transient — the relay just moves on to the next document in the page. The report itself is safe (it's already durably saved in MongoDB by T052's single-document write), but nobody downstream ever hears about it on that tick, and there's zero trace in any log that a publish was even attempted and failed. Because `outboxPublishedAt` stays `null`, the *next* tick (500ms later) will pick the same document back up and try again — so a truly transient failure quietly self-heals. But today there is no distinction between "will self-heal in half a second" and "Kafka has been unreachable for 20 minutes and every tick is failing the exact same way" — both look identical: silence. For report-service specifically, that silence is worse than for any other producer in this project, because `report.filed` is the trigger for the *entire* abuse-escalation flow (REQUIREMENTS.md §8) — a repeat-offender report that never reaches Admin Service doesn't just arrive late, it arrives **never**, with nothing in any log to tell an operator it ever existed.

**What a Dead Letter Queue (DLQ) is, plain English:** think of a DLQ like a "we couldn't deliver this, here's a copy, come look" shelf at a post office. When a delivery van (the Kafka publish) fails to drop off a package (the event) after a few honest attempts, instead of just losing it silently, someone sets the package aside on a labeled shelf — can't deliver this right now, but here it is, go deal with it by hand. In most systems that "shelf" is literally a separate Kafka topic. In this ticket it's simpler: the "shelf" is a clearly-tagged ERROR log line carrying the entire undelivered event, because (as the Technical specification below explains) report-service's outbox has no spare field to mark a document "permanently failed," and a second real Kafka topic would be the wrong tool for a failure whose root cause is usually "Kafka itself is the thing that's unreachable."

**Why it matters:** retrying a few times with a short pause between attempts turns the single-blip case from "silently drops this tick, self-heals next tick with zero visibility" into "retries immediately, and only makes noise if it's genuinely still failing after three tries" — cutting log spam for the harmless case while guaranteeing the stuck-for-minutes case is impossible to miss.

**How this solves it:** wrap the existing `KafkaTemplate.send()` call inside `ReportOutboxRelay` with a small manual retry loop (3 attempts, exponential backoff between them). If all 3 attempts in a tick fail, log the complete event — not just "publish failed," the actual `report_id`, `reported_id`, and full `eventPayload` JSON — at `ERROR` level under a dedicated, greppable marker. No new Mongo field, no new Kafka topic, no change to `POST /reports`'s behavior: `outboxPublishedAt` stays `null` either way, so the very next 500ms tick naturally retries again on its own — the dead-letter log is a breadcrumb for a human, not a state transition.

## What to build

- Wrap the single publish call inside `ReportOutboxRelay.relayPendingEvents()` (`src/services/report-service/src/main/java/com/shareconnectsave/report_service/kafka/ReportOutboxRelay.java`, built in T052) in a manual retry loop — **not** Spring Retry's `@Retryable`. No Java service in this codebase has introduced `spring-retry` yet (verified: no `@Retryable`/`RetryTemplate` anywhere in the repo), and T053 just set the precedent of preferring a plain, explicit mechanism over adopting a new framework the codebase hasn't needed yet (same call T053 made for the admin-role check over introducing Spring Security early). A small `for` loop with `Thread.sleep()` backoff is cheap here specifically because `spring.threads.virtual.enabled: true` is already on for this service (T051) — blocking a virtual thread for a few hundred milliseconds costs nothing like blocking a platform thread would.
- Retry shape: up to 3 total attempts per document per tick. Attempt 1 immediate; if it throws, sleep 200ms then attempt 2; if that throws, sleep 400ms then attempt 3 (exponential backoff, base 200ms, ×2 per attempt). No sleep after the final attempt.
- If all 3 attempts throw: do **not** mark `outboxPublishedAt` — leave it `null` exactly as today, so the document is picked up again on the relay's next tick (this is what makes a real Kafka outage self-heal once Kafka recovers, with no extra bookkeeping). Instead, log one `ERROR`-level line tagged with a fixed marker (`DEAD_LETTER_REPORT_FILED`) containing: `report.getId()`, `report.getReportedId()`, the full `report.getEventPayload()` JSON string, the attempt count, and the final exception — this is the entire "dead letter," there is no second Kafka topic and no new Mongo collection/field.
- If any attempt (1, 2, or 3) succeeds: proceed exactly as T052 already does — the targeted `MongoTemplate.updateFirst(...)` partial update stamping `outboxPublishedAt`. No behavior change on the success path at all.
- None of this touches `POST /reports`, `ReportController`, or `ReportServiceImpl` — the retry/dead-letter logic lives entirely inside the relay's own background tick, which already runs fully decoupled from the HTTP request (see Agent implementation notes — "What NOT to do" for why this matters for the acceptance criteria).

## Technical specification

**Original spec (SPECS.md, verbatim):**
Wrap `KafkaTemplate.send()` with a retry policy (3 attempts, exponential backoff). Failed events after retries → logged with full payload for manual replay.

**Refined — which call site, and what "DLQ" concretely means here:**

The call being wrapped is the exact line T052 built in `ReportOutboxRelay`:
```java
kafkaTemplate.send("report.filed", report.getReportedId(), report.getEventPayload()).get();
```

The `kafka-outbox` skill file's generic DLQ section shows a different shape — publishing the failed payload to a literal second topic (`report.filed.dlq`) and flipping an `OutboxStatus.DLQ` enum value. **Do not follow that shape.** It was written for the generic SQL-backed outbox design (a separate `OutboxEvent` entity with an `OutboxStatus` enum), which is not what report-service has. T052 deliberately gave `Report` no `OutboxStatus` field at all — only `eventPayload` + nullable `outboxPublishedAt` folded onto the business document itself, because a standalone (non-replica-set) Mongo node can't give a second collection the same atomicity a SQL transaction gives for free (see T052's Technical specification). There is no status field to flip to `DLQ`, and publishing to a second live Kafka topic is the wrong tool for a failure whose most likely cause is "Kafka itself is unreachable right now" — a second topic on the same broker would fail for the identical reason. This is the same kind of situation T052 flagged with the Kafka schema's mismatched `reason` enum: generic/prior text that doesn't match this service's actual, already-built design. Follow the task spec's own literal acceptance criteria instead — "logged with full payload for manual replay" — which this ticket implements as a structured `ERROR` log line, nothing more. Flag the skill file's `report.filed.dlq`-topic example as stale for the Tech Lead to correct later (a `/validate-contracts`-style finding), not something to silently reconcile by inventing a topic nobody asked this service to own.

**Backoff numbers:** 200ms, 400ms (i.e., `200 * 2^(attempt-1)` ms between attempts, attempts numbered 1-3, no sleep after attempt 3). These are small on purpose — they only need to survive a sub-second network blip; anything longer-lived is exactly the case meant to fall through to the dead-letter log and wait for the relay's normal 500ms-tick self-healing once Kafka recovers.

## Acceptance criteria

- [ ] Transient Kafka failure → retried up to 3 times
- [ ] Permanent failure → logged with payload, HTTP response still 201 (report saved)

## Patterns demonstrated

- **Dead Letter Queue (DLQ), log-based variant** — the "shelf for undeliverable packages" concept, implemented here as a tagged `ERROR` log carrying the full event rather than a second Kafka topic, because this service's folded-field outbox design has no state field to flip and a second topic would share Kafka's own failure mode. Same intent as a classic DLQ topic (nothing gets silently lost, a human can act on it), different mechanism chosen to fit this service's actual constraints.
- **Decorator (GoF)** — the retry loop wraps the existing `kafkaTemplate.send(...).get()` call transparently: same call, same return shape, callers of `relayPendingEvents()` (there are none outside the scheduler) see no interface change, just more resilient behavior underneath. Same shape as the Resilience4j circuit breaker around Discovery Service's calls to User Service (see CLAUDE.md's Classic Design Patterns table) — wrap, don't rewrite.
- **Single Responsibility (SOLID-S), preserved** — `ReportOutboxRelay` still only moves pending documents to Kafka; it gains a retry/backoff/log concern around that one job, not a new one. It still has no idea what a report, a reason, or an escalation threshold is.
- **Idempotency, reused not reinvented** — because a dead-lettered document's `outboxPublishedAt` is left `null`, the relay's normal next-tick query naturally retries it again once Kafka recovers; this relies on the same at-least-once-delivery assumption the project's Kafka consumers already handle via `processed_events` deduplication (see `kafka-outbox` skill) — a report might, in the worst case, get published more than once across ticks if a "failure" was actually a false negative (Kafka accepted it but the ack was lost), and that's fine because consumers are already built to tolerate duplicates.

## Agent implementation notes

- Key file to modify: `src/services/report-service/src/main/java/com/shareconnectsave/report_service/kafka/ReportOutboxRelay.java` (the only class in T052 allowed to touch `KafkaTemplate` — this ticket does not change that boundary).
  - Add two `private static final` constants: `MAX_PUBLISH_ATTEMPTS = 3` and `INITIAL_BACKOFF_MS = 200`.
  - Extract the per-document publish into a small private method, e.g. `private boolean publishWithRetry(Report report)`, returning whether it ultimately succeeded. Loop `attempt` from 1 to `MAX_PUBLISH_ATTEMPTS`; on success return `true` immediately; on exception, if `attempt < MAX_PUBLISH_ATTEMPTS`, `Thread.sleep(INITIAL_BACKOFF_MS * (1L << (attempt - 1)))` and continue; if it was the last attempt, log the dead-letter line and return `false`.
  - In `relayPendingEvents()`'s per-document loop: call `publishWithRetry(report)`; only run the existing `MongoTemplate.updateFirst(...)` partial update (stamping `outboxPublishedAt`) when it returns `true`. When it returns `false`, do nothing further for that document this tick — move on to the next one in the page; it stays eligible for the next tick's query exactly as it is today.
  - Dead-letter log line: use the class's existing SLF4J `Logger`, `log.error(...)`, message prefixed with the literal marker `DEAD_LETTER_REPORT_FILED` so it's trivially greppable in aggregated logs, including `reportId`, `reportedId`, `eventPayload` (the full JSON string, not a truncated/summarized version — "manual replay" requires the complete payload), attempt count, and the caught exception (pass it as the log call's final argument so the stack trace is captured, don't just call `.getMessage()`).
  - Add a short comment above `publishWithRetry` naming the Decorator and log-based-DLQ concepts per this project's "name the pattern, explain why, plain English first" convention (see CLAUDE.md) — this is the first DLQ-flavored code in the project, so don't assume the reader has seen the term before.
- Patterns to use: `java-spring-boot` skill for general Spring Boot/logging conventions; `kafka-outbox` skill's Dead Letter Queue section for the concept — but see Technical specification above for why this ticket deliberately deviates from that section's literal `report.filed.dlq`-topic/`OutboxStatus.DLQ` example.
- What NOT to do:
  - Do not add `spring-retry` to `pom.xml` or use `@Retryable`/`@EnableRetry` — no precedent in this codebase yet (see What to build above); a manual loop is simpler, explicit, and consistent with T053's "don't introduce new framework magic early" precedent.
  - Do not create a `report.filed.dlq` Kafka topic, an `OutboxStatus` enum, or any new field on `Report` — see Technical specification's explanation of why the skill file's generic example doesn't fit this service's folded-field outbox design.
  - Do not make retry **synchronous with the HTTP request**. `POST /reports` (T052) already returns `201` the instant `ReportServiceImpl` completes its single `save()` call — it has never called Kafka directly and does not change in this ticket. All retry/backoff/dead-letter logic lives entirely inside `ReportOutboxRelay`'s own `@Scheduled(fixedDelay = 500)` background tick, which already runs on a separate thread, fully decoupled from any HTTP request thread. This is exactly why "Permanent failure → logged with payload, HTTP response still 201" holds together: the HTTP response was already sent, possibly hundreds of milliseconds (or ticks) before the relay even attempts to publish that report, so there is nothing for the retry loop to block.
  - Do not touch `ReportController`, `ReportServiceImpl`, or `ReportCreateDto`/`ReportResponse` — this ticket is 100% inside `ReportOutboxRelay`.
  - Do not add retry/backoff around the existing `MongoTemplate.updateFirst(...)` partial-update call — that call is a local Mongo write, not the flaky external dependency this ticket is protecting against; only the `KafkaTemplate.send(...)` call gets wrapped.
  - Be aware (do not attempt to fix here): same `MissingRequestHeaderException` gap flagged in T051/T052/T053 — irrelevant to this ticket since it adds no new endpoint, noted here only for completeness.
