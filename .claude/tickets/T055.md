# T055 — Report Service Docker Image

## Why this ticket exists

Report Service is the 9th and final `/docker-up` peer to containerize — without a Dockerfile it can't join the local Docker Compose stack, which blocks end-to-end testing of the report → escalate → Kafka DLQ flow (T051–T054) alongside the other eight services. This is also the first service in the stack backed by MongoDB instead of SQL Server, so this ticket is the proof that the same packaging pattern (multi-stage Maven build, health-checked container) generalizes across datastores, not just across JPA services.

## What to build

- `src/services/report-service/Dockerfile` — multi-stage build (`eclipse-temurin:21-jdk` build stage, `eclipse-temurin:21-jre-alpine` runtime stage), following the exact shape of `src/services/rating-service/Dockerfile` (T046)
- `src/services/report-service/.dockerignore` — Java-appropriate (`target/`, `.mvn/wrapper/*.jar` cache noise, IDE files) — unlike T028/T034/T046, which deferred this, this ticket adds it now
- Verify/fix `src/infra/docker-compose.yml`'s `report-service` build block (context/dockerfile path) against whatever `report-service/pom.xml` actually depends on by the time this ticket starts
- Confirm `src/infra/docker-compose.override.yml`'s `report-service` env block (already present — see Technical specification) is correct and sufficient; do not duplicate it
- Add the "docker profile intentionally omitted" explanatory comment to `report-service`'s `application.yml` once it exists (see Technical specification — it does not exist yet)

## Technical specification

**Verified current state as of this ticket being written (re-check at implementation time, since T051–T054 land first):**

1. **`docker-compose.yml` already has the `report-service` service block** (lines 460–482): image `shareconnectsave/report-service:dev`, port `8087:8080`, `depends_on: mongodb, kafka` (both `service_healthy`), healthcheck `curl -f http://localhost:8080/actuator/health`. **Build context is currently `../../src/services/report-service` with `dockerfile: Dockerfile`** — i.e., scoped to report-service's own folder only, the same narrow shape T046 found stale for rating-service. **Do not trust this blindly.** Check `report-service/pom.xml` for a `shared-java-lib` dependency once T051–T053 have landed (every other Java service — discovery, connection, rating — ends up depending on `shared-java-lib` for `ErrorResponse`/`GlobalExceptionHandler`, even though neither T051's nor T052's spec mentions it explicitly). If report-service depends on `shared-java-lib`, this build context **must** be widened to `context: ../../src/services` / `dockerfile: report-service/Dockerfile`, and the Dockerfile must install `shared-java-lib` from source first (copy the exact pre-build layer from `rating-service/Dockerfile`). If it genuinely does not depend on `shared-java-lib`, the existing narrow context is fine and should be left alone — verify, don't assume either way.

2. **`docker-compose.override.yml` already has the `report-service` env block** (lines 244–248) and it is already correct for this service's actual needs:
   ```
   SPRING_PROFILES_ACTIVE=docker
   SPRING_DATA_MONGODB_URI=${REPORT_MONGODB_URI:-mongodb://mongodb:27017/ReportServiceDb}
   SPRING_KAFKA_BOOTSTRAP_SERVERS=${KAFKA_BOOTSTRAP:-kafka:9092}
   ```
   This is the T028/T034/T046 env-var-override workaround, already applied correctly — report-service needs no further fix here. Do not re-add or duplicate this block.

3. **No `application.yml` exists yet** — `report-service/src/main/resources/` currently only has the default `application.properties` (single line: `spring.application.name=report-service`), because T051 (which will presumably convert this to `application.yml` with `dev`/`prod` profile documents, per the pattern every other Java service used) has not shipped yet. When this ticket starts, check whether T051 created `application.yml` with `dev`/`prod` profile documents. If so, add the same one-line explanatory comment rating-service has (`application.yml` lines 156–160): `docker` profile intentionally omitted; datasource/Mongo creds injected via env vars in `docker-compose.override.yml` — because `SPRING_PROFILES_ACTIVE=docker` (set in `docker-compose.yml`) matches zero profile documents and silently no-ops. If `application.yml` still doesn't exist by the time this ticket runs, flag it back rather than inventing the file structure — that's T051's job, not T055's.

4. **Size budget:** use `docker inspect --format {{.Size}}` or `docker save | wc -c` as the authoritative image size metric, target under 300MB uncompressed. Do **not** trust `docker images`' reported size — it has shown a ~3x discrepancy (reports ~450MB when the real size is ~152MB) on this machine, attributed to a containerd-snapshotter display quirk, not BuildKit attestation/SBOM metadata (that theory was tested and ruled out). Also be aware `docker history`'s summed layer size (~298MB uncompressed for the rating-service image) is close enough to the 300MB budget that which metric you pick can flip pass/fail — use inspect/save, not history, as the gate.

## Acceptance criteria

- [ ] `docker compose up report-service` starts cleanly and its healthcheck passes (depends on `mongodb` and `kafka` both being `service_healthy` first)
- [ ] Image size verified via `docker inspect --format {{.Size}}` or `docker save`, not `docker images` — under 300MB uncompressed
- [ ] Build context in `docker-compose.yml` matches what `report-service/pom.xml` actually requires (widened to `../../src/services` only if a `shared-java-lib` dependency is confirmed present)
- [ ] `.dockerignore` added at `src/services/report-service/.dockerignore`
- [ ] If `application.yml` exists by this point, it carries the "docker profile intentionally omitted" explanatory comment; if it doesn't exist yet, this is called out explicitly rather than silently skipped

## Patterns demonstrated

Minimal pattern content here — this is Docker packaging, not business logic. The one notable teaching point is **Multi-stage build** (same as T028/T034/T046: separates the JDK+Maven build toolchain from the lean JRE-alpine runtime image) applied for the first time to a MongoDB-backed rather than SQL-backed service, showing the same container shape is datastore-agnostic. No SOLID or GoF pattern is being forced onto this ticket.

- **What NOT to do:** don't trust this ticket's (or T055's SPECS.md one-liner's) "same pattern as T028" claim at face value for build context — T046's own follow-up explicitly warns that a templated "context already scoped to the service's own folder" claim was stale for rating-service once `shared-java-lib` entered the picture. Verify `report-service/pom.xml` for real before deciding the context is fine as-is.
- Don't add a `docker` Spring profile document that doesn't actually exist — keep using the override-env-var workaround (already correctly in place for report-service in `docker-compose.override.yml`) and document why with a one-line comment, same as T046 did for rating-service.

## Known follow-ups

- **Image size display quirk (T028, affects T034/T046/T055/T061):** `docker images` over-reports size (~450MB) vs. the real size (~152MB) confirmed by `docker inspect`/`docker save`; root cause is a containerd-snapshotter display quirk, not BuildKit attestation. Use inspect/save as the authoritative metric for this ticket's size-budget check.
- **Missing `docker` Spring profile (T028/T034, affects T046/T055/T061):** `SPRING_PROFILES_ACTIVE=docker` matches zero profile documents in any Java service's `application.yml` so far; for report-service this is already correctly worked around via explicit env vars in `docker-compose.override.yml` (Mongo URI + Kafka bootstrap, not SQL credentials, since this service uses MongoDB). Confirm this is still true once T051 lands, and add the explanatory comment to `application.yml` once that file exists.
- **Undocumented reason for the no-op `docker` profile (T034 follow-up, affects T046/T055/T061):** add the one-line comment explaining the env-var-override workaround near wherever `application.yml`'s `dev`/`prod` profile documents end up, so a future engineer doesn't "clean up" the override env vars thinking a real `docker` profile exists.
- **Stale "narrow build context" claims in templated tickets (T046 finding #2, affects T055/T061):** don't trust a ticket's prose claim that the build context is already correctly scoped — verify the actual `docker-compose.yml` block and whether `report-service/pom.xml` depends on `shared-java-lib` before building, to avoid a `docker build` dependency-resolution failure on first run.
