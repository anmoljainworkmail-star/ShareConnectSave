# T056 — Spring Boot + Spring Security Setup

## Why this ticket exists
Admin Service is where a human finally acts on everything the rest of the platform has
been quietly escalating since Phase 9 — a low trust score or a pile of reports queues
someone for manual review, but nobody can actually review, override a score, or suspend
an account until this service exists and only lets real admins through. Every other Java
service in this project reads `X-User-Role` as a plain header check inline in the
controller — fine for "is this a user acting on their own data," but not fine for "can
this request suspend someone's account." Without a real security layer, admin-service
would either be wide open (anyone who finds the URL can suspend accounts) or would need
the same inline-guard-clause copy-pasted onto every endpoint with no central place to fix
it once. This ticket builds that central gate, and — because it's the first one — also
decides how this project's error responses stay consistent even when Spring Security
itself (not our own code) is the thing producing the rejection.

## What to build
- New Spring Boot project skeleton for `admin-service` (doesn't exist beyond its Phase 0
  folder stub yet) — `pom.xml`, `AdminServiceApplication` main class, `application.yml`
  (dev/docker profiles, following the same convention as every other Java service).
- `AdminRoleAuthenticationFilter` (a `OncePerRequestFilter`) — reads `X-User-Role` from
  the incoming request and, if it equals `"admin"`, populates
  `SecurityContextHolder` with an authenticated `UsernamePasswordAuthenticationToken`
  carrying a `ROLE_ADMIN` granted authority. No JWT re-validation — the gateway already
  did that.
- `SecurityConfig` class with a `SecurityFilterChain` bean:
  - `/actuator/health` → `permitAll()`
  - everything else → `.authorizeHttpRequests().anyRequest().hasRole("ADMIN")`
  - registers `AdminRoleAuthenticationFilter` in the chain
  - disables session creation (`STATELESS`) and CSRF (no cookies/browser forms involved,
    gateway-to-service call)
- `AdminAuthenticationEntryPoint` (handles "not authenticated at all" — missing/blank
  header) and `AdminAccessDeniedHandler` (handles "authenticated but wrong role" — should
  not occur given the filter's binary logic, but Spring Security's contract still expects
  both beans) — both write this project's standard `{code, message, traceId}` error
  envelope as the 403 body, not Spring Security's default body.
- `pom.xml` dependencies: `spring-boot-starter-web`, `spring-boot-starter-security`,
  `spring-boot-starter-actuator`, `lombok`. **Do not add
  `spring-boot-starter-data-jpa` or a SQL Server JDBC driver** — see the spec conflict
  flagged below; this ticket should ship HTTP-client-ready, not JPA-ready, pending Tech
  Lead's decision.

## Technical specification
**From SPECS.md (verbatim):**

Dependencies: Spring Web, Spring Security, JPA (read-only access to `users_db`,
`ratings_db`), Actuator, Lombok.

Spring Security config: all endpoints require `X-User-Role: admin` header. Implement as
a `OncePerRequestFilter` that reads the header (set by gateway) and populates
`SecurityContext`. No JWT re-validation.

**Refined technical specification (this ticket's own addition):**

1. **`AdminRoleAuthenticationFilter extends OncePerRequestFilter`**
   - Reads `request.getHeader("X-User-Role")`.
   - If equal to `"admin"` (case-sensitive, matching the gateway's documented contract),
     builds `new UsernamePasswordAuthenticationToken(principal, null, List.of(new
     SimpleGrantedAuthority("ROLE_ADMIN")))` and sets it on
     `SecurityContextHolder.getContext()`.
   - If the header is missing, blank, or any value other than `"admin"` — **does not
     throw**. It simply leaves the `SecurityContext` unauthenticated and calls
     `filterChain.doFilter(request, response)` to let the rest of the chain run.
     Authentication populates; it never itself rejects. Authorization (the
     `SecurityFilterChain`'s `hasRole("ADMIN")` rule) is what rejects, downstream.

2. **`SecurityConfig` (`@Configuration` + `@EnableWebSecurity`)**
   - One `SecurityFilterChain` bean:
     - `.csrf(csrf -> csrf.disable())`
     - `.sessionManagement(sm -> sm.sessionCreationPolicy(STATELESS))`
     - `.authorizeHttpRequests(auth -> auth
         .requestMatchers("/actuator/health").permitAll()
         .anyRequest().hasRole("ADMIN"))`
     - `.addFilterBefore(adminRoleAuthenticationFilter,
         UsernamePasswordAuthenticationFilter.class)`
     - `.exceptionHandling(ex -> ex
         .authenticationEntryPoint(adminAuthenticationEntryPoint)
         .accessDeniedHandler(adminAccessDeniedHandler))`

3. **`AdminAuthenticationEntryPoint implements AuthenticationEntryPoint`**
   - Fires when an unauthenticated request hits a protected endpoint (the common case:
     header missing or wrong value).
   - Writes HTTP 403 (not 401 — there is no login flow to redirect to; this project
     treats "no valid role" as a flat access denial, same as every other service) with
     this project's standard envelope: `{ "code": "FORBIDDEN", "message": "Admin role
     required", "traceId": <from MDC/request> }`.

4. **`AdminAccessDeniedHandler implements AccessDeniedHandler`**
   - Fires if an authenticated-but-insufficient-authority case is ever reached (not
     reachable today given the filter only ever grants `ROLE_ADMIN` or nothing, but
     required by Spring Security's API and kept for correctness/future-proofing if a
     second role is ever introduced).
   - Same envelope shape as the entry point.

5. **No `@RequestHeader("X-User-Role")` guard-clause code anywhere in admin-service's own
   controllers** — that's the whole point of building the filter chain instead. Any
   controller-level role check here would be redundant with, and could drift from, the
   filter chain.

## Acceptance criteria
- [ ] Request without `X-User-Role: admin` → 403
- [ ] `/actuator/health` is public (excluded from security filter)
- [ ] 403 response body matches this project's standard error envelope
  (`{code, message, traceId}`), not Spring Security's default body
- [ ] A request with `X-User-Role: admin` reaches a protected endpoint successfully
  (add a trivial `GET /admin/ping` or similar if no other endpoint exists yet to prove
  the chain works end-to-end)

## Patterns demonstrated
- **Filter chain (Spring Security)** — this is the project's first real Spring Security
  usage. Plain English: instead of every endpoint individually checking "is this person
  allowed in," one gatekeeper checks ID at the door before anyone reaches any endpoint.
  Every other Java service (Discovery, Connection, Rating, Report) does the inline
  `@RequestHeader` + guard-clause version instead — deliberately, because a full security
  filter chain was overkill for "does this request belong to this user." Admin Service is
  where the stakes (suspend an account, override a trust score) justify the extra
  machinery.
- **Single Responsibility Principle** — `AdminRoleAuthenticationFilter` only ever
  authenticates (decides "who is this"); it never decides "are they allowed" (that's the
  `SecurityFilterChain`'s authorization rule) and never touches business logic. Splitting
  authentication from authorization is what lets the same filter be reused if a second
  role is added later without touching the authorization rule, and vice versa.
- **Strategy (via Spring Security's pluggable handlers)** — `AuthenticationEntryPoint` and
  `AccessDeniedHandler` are both interfaces Spring Security calls into; swapping in this
  project's own implementations changes *how* a rejection is reported without touching
  *how* a rejection is detected.
- **Decorator-ish contrast, named explicitly** — think of the filter chain as a layer
  wrapped around every controller in this service, versus the other services' shape of
  baking the same check inline inside each controller method. Same goal (reject
  non-admins), different place the check lives — centralized vs. repeated per-endpoint.

## Agent implementation notes
- Key files to create (all paths relative to project root):
  - `admin-service/pom.xml`
  - `admin-service/src/main/java/.../AdminServiceApplication.java`
  - `admin-service/src/main/resources/application.yml` (dev + docker profiles; no
    migrations/Flyway needed here since this ticket is not adding its own schema —
    see the HTTP-only recommendation below)
  - `admin-service/src/main/java/.../security/AdminRoleAuthenticationFilter.java`
  - `admin-service/src/main/java/.../security/SecurityConfig.java`
  - `admin-service/src/main/java/.../security/AdminAuthenticationEntryPoint.java`
  - `admin-service/src/main/java/.../security/AdminAccessDeniedHandler.java`
- Patterns/conventions to follow from the `java-spring-boot` skill file: import
  shared-java-lib's `ExceptionHandlingConfig` for the standard error envelope shape so
  the two new handlers above produce byte-for-byte the same JSON shape as every other
  service's `GlobalExceptionHandler` output; enable virtual threads from day one
  (`spring.threads.virtual.enabled: true`) as every other service does.
- **Genuine spec conflict — Tech Lead must resolve before approving this ticket:**
  SPECS.md's own task text for T056 says "JPA (read-only access to `users_db`,
  `ratings_db`)." But CLAUDE.md's System Design Principles table says: "Database per
  Service — Admin Service reads others via HTTP, not direct DB joins." And T057's own
  spec (`GET /admin/users/:id`) describes data being "pulled via HTTP to User Service,"
  "from Rating Service," "from Report Service" — i.e. T057 already assumes HTTP-only
  access, not JPA, and every other Phase 10 ticket (T057–T060) only ever calls other
  services over HTTP via `WebClient`. Recommendation: do **not** add
  `spring-boot-starter-data-jpa` or any JDBC driver for `users_db`/`ratings_db` in this
  ticket — set admin-service up as an HTTP-client-only service (WebClient beans can be
  added in T057 when they're actually needed). This is flagged, not silently resolved —
  approve this ticket only once you've picked a side.
- What NOT to do:
  - Don't re-validate the JWT — the entire point of reading `X-User-Role` directly is
    skipping that; the gateway already validated it.
  - Don't let Spring Security's default 403 body leak through unmatched — without the
    custom `AuthenticationEntryPoint`/`AccessDeniedHandler` pair, a 403 here would use
    Spring's default body shape and violate this project's error-envelope rule that every
    other service already satisfies.
  - Don't forget `/actuator/health` must stay public even with
    `.anyRequest().hasRole("ADMIN")` as the catch-all rule — order matters in
    `authorizeHttpRequests()`, the permitAll rule for health must be registered before
    the catch-all.
  - Don't add any inline `@RequestHeader("X-User-Role")` guard-clause checks inside
    admin-service's own controllers — the filter chain is the single place this is
    decided.

## Known follow-ups
- A separate, already-known gap exists project-wide: `MissingRequestHeaderException` on
  a missing `X-User-Id` currently falls through to shared-java-lib's catch-all exception
  handler and returns a raw 500 instead of a clean 400. That fix belongs to T091 (a
  one-time addition to the shared `GlobalExceptionHandler`) and is explicitly out of
  scope here, same as it was for T051/T052/T053/T054.
- **This ticket's own, different version of that problem, which T091 will NOT fix for
  this service:** because admin-service now runs a real Spring Security filter chain,
  a missing/malformed `X-User-Role` header is rejected by Spring Security itself,
  *before* the request ever reaches Spring MVC's dispatcher — so Spring MVC's exception
  handling (and therefore T091's eventual `MissingRequestHeaderException` handler) never
  even gets a chance to run for this failure path. This ticket's
  `AdminAuthenticationEntryPoint` is the only place that failure is handled for
  admin-service, independent of whatever T091 later does for every other service. Do not
  assume T091 will retroactively cover this service's 403 path — it can't.
