# T057 — Review Queue Endpoints

## Why this ticket exists
Report Service and Rating Service have been quietly escalating repeat offenders and suspending
accounts from discovery since Phase 7 and Phase 9 shipped — but until now, no human has ever
seen any of it. A user can be suspended and nobody at ShareConnectSave knows, can review why,
or can bring them back. This ticket is the payoff of the whole ReportEscalationSaga: it gives an
admin a queue of suspended accounts, a single page that pulls together a user's profile, trust
score, and report history from three different services, and a button to reinstate someone who
was wrongly or no-longer-deservedly suspended. Without it, suspension is a one-way, invisible
door — accounts go in and nobody, including the platform's own operators, can get them back out.

## What to build
- `ReviewQueueController` in admin-service exposing:
  - `GET /admin/queue` — lists suspended accounts
  - `GET /admin/users/{id}` — aggregated user detail view
  - `POST /admin/users/{id}/reinstate` — reinstates a suspended account
- `UserServiceClient` (WebClient + Resilience4j `@CircuitBreaker`) — fetches profile + status from
  User Service, and flips status to `active` on reinstate
- `RatingServiceClient` (WebClient + Resilience4j `@CircuitBreaker`) — fetches trust score from
  Rating Service
- `ReportServiceClient` (WebClient + Resilience4j `@CircuitBreaker`) — fetches report history from
  Report Service (reads only — never touches `GET /reports/queue`)
- `ReviewQueueItem` response DTO — includes `trust_score`, distinct from Report Service's own
  narrower `GET /reports/queue` response shape
- `AdminOutboxEntity` / `admin_outbox` table (or Mongo-folded equivalent per T056's chosen
  persistence) + `AdminOutboxRelay` — admin-service's first Kafka producer, publishing
  `trust.score.updated` on reinstate
- `ReviewQueueService` — orchestrates the three WebClient calls and the outbox write; the only
  class that knows how to assemble a `ReviewQueueItem` from three upstream responses

## Technical specification

### Spec (verbatim from SPECS.md)
- `GET /admin/queue` — lists accounts in manual review (status = `suspended` in User Service, pulled via HTTP to User Service)
- `GET /admin/users/:id` — full user view: profile, trust score (from Rating Service), report history (from Report Service)
- `POST /admin/users/:id/reinstate` — sets user status back to `active`, publishes `trust.score.updated` with reinstated limits

All inter-service calls use WebClient with Resilience4j.

**Acceptance criteria:**
- [ ] Suspended user appears in queue
- [ ] Reinstate → user active within 1 poll cycle
- [ ] User detail page aggregates data from 3 services correctly

### Refined technical specification

**`ReviewQueueItem` response shape** (per CLAUDE.md's `admin-service.yaml` reference — this is a
distinct, cross-service aggregation view, NOT Report Service's own `GET /reports/queue` response):
```json
{
  "userId": "uuid",
  "displayName": "string",
  "status": "suspended",
  "trustScore": 0.0,
  "reportCount": 0,
  "suspendedAt": "iso-8601 timestamp"
}
```
`trustScore` comes from Rating Service and is the field Report Service's own queue has no access
to — this is the whole reason this ticket's queue is a separate concept from T053's.

**`GET /admin/users/{id}` — exactly 3 services, aggregated:**
1. **User Service** (HTTP, via `UserServiceClient`) — profile fields + current `status`
2. **Rating Service** (HTTP, via `RatingServiceClient`) — current trust score
3. **Report Service** (HTTP, via `ReportServiceClient`) — report history for this user (read-only;
   do not call or modify `GET /reports/queue`)

**Partial-failure degradation** (this is the point of wrapping all three in Resilience4j, not
just a checkbox): if any one of the three upstream calls fails or trips its circuit breaker, the
endpoint must NOT 500 the whole response. Each client's fallback returns a typed "unavailable"
placeholder for its slice only (e.g. `trustScore: null` + a `trustScoreUnavailable: true` flag,
or an empty report list + `reportHistoryUnavailable: true`), and the controller still returns
`200 OK` with whatever data it successfully gathered, plus a flag per section so the admin UI can
show "trust score unavailable" instead of silently rendering `0` or an empty list as if it were
real data. A single downstream outage must never hide an otherwise-reviewable account from an
admin.

**`POST /admin/users/{id}/reinstate` mechanics:**
This endpoint does two things, and both must happen, in this order:
1. Call `UserServiceClient.setStatus(id, "active")` — synchronous HTTP call, User Service is the
   system of record for status.
2. Write a `trust.score.updated` event (with reinstated limits/visibility) to admin-service's own
   outbox table/document in the same local transaction as any local state change this endpoint
   makes, then let `AdminOutboxRelay` publish it to Kafka. This is admin-service's first time
   acting as a Kafka producer — reuse the existing Outbox Pattern (SQL-based `outbox` table with
   a polling relay, or the Mongo-folded single-document variant from T052, whichever matches
   what T056 set up admin-service's own datastore as) exactly as every other producer in this
   project does it. Business code must never call `KafkaTemplate.send()` directly — always
   through the outbox, same invariant as every other Kafka-producing service.

If step 1 succeeds but step 2's local write fails, the whole reinstate request should fail
(rollback), since an inconsistent "active in User Service but Discovery never re-enabled" state
is worse than retrying the whole reinstate action.

## Patterns demonstrated
- **Facade-like aggregation** — `ReviewQueueService` is the first place in the project that
  combines read data from three separate services into one caller-facing shape, so the
  controller and the admin UI never need to know there are three upstream calls happening.
- **Outbox Pattern (reused, not reinvented)** — admin-service becomes a Kafka producer for the
  first time on the reinstate path, and must follow the exact same "write to outbox table in the
  same transaction, relay publishes later" discipline every other producer in this project uses.
  Prevents split-brain between admin-service's own write and the `trust.score.updated` event
  reaching Kafka.
- **Decorator (Resilience4j Circuit Breaker)** — each of `UserServiceClient`,
  `RatingServiceClient`, and `ReportServiceClient` wraps a plain WebClient call transparently with
  retry/fallback behavior, same shape as Discovery Service's existing `UserServiceClientImpl`.
- **Interface Segregation** — three separate client interfaces (one per upstream service) rather
  than one god-client, so each only exposes the handful of calls admin-service actually needs.
- **Dependency Inversion** — `ReviewQueueService` depends on `UserServiceClient` /
  `RatingServiceClient` / `ReportServiceClient` interfaces, not concrete WebClient usage, so each
  can be swapped for an in-memory fake in tests.

## Agent implementation notes
- Key files to create (paths from project root, under
  `src/admin-service/src/main/java/com/shareconnectsave/adminservice/`, matching T056's package
  layout):
  - `controller/ReviewQueueController.java`
  - `service/ReviewQueueService.java`
  - `client/UserServiceClient.java`, `client/RatingServiceClient.java`,
    `client/ReportServiceClient.java` (interfaces) + their WebClient-based implementations
  - `dto/ReviewQueueItem.java`, `dto/UserDetailResponse.java`
  - `outbox/AdminOutboxEntity.java` (or Mongo-folded equivalent), `outbox/AdminOutboxRelay.java`
- Patterns to use: follow the java-spring-boot skill's WebClient + Resilience4j
  `@CircuitBreaker` conventions already established in discovery-service's
  `UserServiceClientImpl` — same annotation style, same fallback-method shape. For the outbox
  side, follow the same outbox/relay pattern already shipped in prior Kafka-producing tickets
  (T052's Mongo-folded variant, or the SQL `outbox` table variant used elsewhere) — match
  whichever persistence T056 already set up for admin-service, don't introduce a second one.
- What NOT to do:
  - Don't touch Report Service's own `GET /reports/queue` endpoint or its `ReviewQueueItem`
    schema — per CLAUDE.md, that is a deliberately distinct, narrower concept (escalated reports,
    sorted by `reportCountAtEscalation`) from this ticket's `GET /admin/queue` (suspended user
    accounts, including `trust_score` which Report Service has no access to). Do not merge them,
    do not rename one to match the other.
  - Don't implement direct DB joins against `users_db` or `ratings_db`. Every cross-service read
    in this ticket is HTTP, per CLAUDE.md's Database per Service principle. This resolves T056's
    own spec-conflict flag: T057's spec text says "pulled via HTTP" — that is the correct
    instruction, and any JPA/direct-DB-access mention in T056's SPECS.md text should be
    disregarded for this ticket.
  - Don't call `KafkaTemplate.send()` directly anywhere in `ReviewQueueService` or the
    controller — always through `AdminOutboxRelay`.

## Known follow-ups
- Report counts and ordering surfaced from Report Service can slightly undercount a repeat
  offender under concurrent report submissions (T053's own pre-accepted TOCTOU race on
  `reportCountAtEscalation`). Do not present report counts/history from `GET /admin/users/{id}`
  as an exact, real-time guarantee anywhere in admin-facing copy or documentation — they reflect
  whatever ordering/count Report Service handed over at read time.
- Report Service stamps `reportCountAtEscalation` for its own internal sort but never exposes it
  in `ReportResponse`/the OpenAPI `Report` schema, so an admin reading raw report history via this
  ticket has no direct visibility into why Report Service ordered a user's reports the way it
  did. Consider surfacing a `reportCount` directly on this ticket's own `ReviewQueueItem` /
  user-detail response (as already specified above) rather than requiring an admin to count
  report history entries by hand.
