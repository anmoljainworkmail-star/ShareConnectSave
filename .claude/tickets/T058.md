# T058 — Trust Score Override

## Why this ticket exists
Trust scores today are computed entirely by machine: every rating and every report pushes a
recalculation that can throttle a user's requests or suspend them from discovery altogether.
That machine has no judgment — it can't tell the difference between someone who genuinely
behaved badly and someone who got mass-reported unfairly by a group of bad actors, or someone
who deserves a second chance after a rough patch. Without this ticket, there is no human valve
on that automation: a wrongly-suspended user stays suspended forever, with no admin able to
correct it, because nothing in the system lets a person override what the algorithm decided.

## What to build
- `AdminTrustScoreController` — `PATCH /admin/users/{id}/trust-score` in `admin-service`.
- `AdminTrustScoreService` (interface `IAdminTrustScoreService` is NOT the convention here —
  follow existing admin-service naming) — orchestrates the call to Rating Service and the
  audit log write. Does not compute or validate trust score math itself.
- A Rating Service HTTP client call (reuse whatever typed client admin-service already uses for
  other cross-service calls from T052-T057, e.g. `RatingServiceClient`) to forward the override.
- `TrustScoreOverrideAuditLog` (in-memory, e.g. a `List` behind a small component/bean, or a
  simple repository-shaped wrapper around an in-memory store) — captures admin's `X-User-Id`,
  target user id, new score, reason, and timestamp.

## Technical specification
**Spec (verbatim from SPECS.md):**
> `PATCH /admin/users/:id/trust-score`
> Body: `{ "score", "reason" }`
>
> Calls Rating Service `PATCH /trust/:userId` with override. Logs the override action with
> admin's `X-User-Id` and reason.

**Refined technical specification:**

1. **Endpoint:** `PATCH /admin/users/{id}/trust-score` in `admin-service`.
   - Request body: `{ "score": number, "reason": string }`.
   - Caller identity comes from the `X-User-Id` header (the admin), injected by the gateway —
     same convention as every other service in this project. Admin role is enforced the same
     way every other admin-service endpoint does it in this phase (custom filter reading
     `X-User-Role`, per the Phase 10 goal) — do not re-validate JWT here.
   - On success, returns the updated trust score payload as echoed back by Rating Service (or
     a thin wrapper around it) plus a `201`/`200` with the audit entry's id, admin's choice.

2. **Cross-service contract gap — DO NOT SKIP:**
   `contracts/openapi/rating-service.yaml` was read in full as part of preparing this ticket.
   It currently defines exactly three operations on Rating Service: `POST /ratings`,
   `GET /ratings/trust-score`, and `GET /ratings/trust-score/{userId}`. **There is no
   `PATCH /trust/:userId` (or any PATCH) operation defined anywhere in this contract.**
   SPECS.md's task text for T058 assumes this endpoint already exists on Rating Service — it
   does not. This is a genuine unmet cross-service dependency, not a detail this ticket's own
   implementation can close, because the endpoint belongs to `rating-service` (Phase 7), not
   `admin-service` (Phase 10).
   **Recommendation to the Tech Lead: do not approve T058 until one of the following happens:**
   - (a) a small follow-on ticket is created against `rating-service` to add
     `PATCH /trust/{userId}` (accepting an override score + reason, writing it to the
     `trust_scores` table, publishing `trust.score.updated` same as the automatic path so
     downstream consumers like Discovery Service stay consistent), and its OpenAPI contract is
     updated first — then T058 implements the admin-service side against that real contract; or
   - (b) T058's scope is explicitly narrowed for now (e.g. admin-service builds its own
     controller + audit log and stubs/mocks the Rating Service call behind a feature flag or a
     clearly marked `// TODO: Rating Service has no PATCH /trust/:userId yet` call site) with an
     explicit understanding that it cannot be exercised end-to-end until the Rating Service
     endpoint ships.

3. **Design tension — override vs. automatic recalculation (investigated, flagged, not
   resolved by this ticket):**
   Rating Service's recalculation flow (`TrustScoreRecalculationServiceImpl.recalculate`,
   triggered by `RatingSubmittedConsumer` on `rating.submitted` and `ReportFiledConsumer` on
   `report.filed`) **unconditionally overwrites** the stored `TrustScore` row's `score`,
   `badgeLevel`, `requestLimit`, and `reportCount` every time it runs — it always fully
   recomputes from the user's raw rating history plus current report count via
   `TrustScoreCalculator.calculate(...)` and calls `trustScore.applyRecalculation(...)`. There
   is no `isOverridden` / `overriddenAt` field or any other resistance mechanism on the
   `TrustScore` entity today.
   **Consequence:** the instant the next `rating.submitted` or `report.filed` event fires for
   that user after an admin override, the override is silently erased and replaced by whatever
   the automatic formula computes — the admin would have no way to know this happened unless
   they re-check the score later.
   **This is a real open design question, not a bug this ticket should silently patch:** is an
   admin override meant to be a *permanent correction* that the system must respect going
   forward (requiring a schema change to `TrustScore` in Rating Service — e.g. an
   `overriddenAt` / `overrideExpiresAt` field that `TrustScoreRecalculationServiceImpl` checks
   and skips or respects before overwriting), or is it meant to be a *point-in-time fix* that
   the system is allowed to legitimately recompute past on the next event (acceptable if the
   admin's intent was "fix this one bad data point right now," not "lock this score forever")?
   **Recommendation:** Tech Lead should decide this explicitly before or alongside approving
   the Rating Service follow-on ticket in point 2 above — it changes what that follow-on ticket
   needs to build (a plain overwrite vs. a sticky-override field). This ticket (T058) does not
   implement either answer; it only surfaces the question.

## Acceptance criteria
- [ ] Override applied to Rating Service
- [ ] Override audit log entry created (in-memory log for now, file-backed in prod)

## Patterns demonstrated
- **Single Responsibility** — `AdminTrustScoreController`/`AdminTrustScoreService` only forward
  the override request and record the audit entry; they never compute or validate the trust
  score formula themselves (that stays Rating Service's `TrustScoreCalculator`'s job).
- **Audit logging as its own concern** — the audit write is a separate, explicit step from the
  business action (forwarding the override), not folded into the same method silently.
- **Thin controller, service-layer delegation** — per this project's established convention
  (see T018 feedback), the controller only parses the request/headers and calls the service;
  all orchestration (Rating Service call + audit write) lives in
  `AdminTrustScoreService`.

    project's existing `...Dto` / `...Response` suffix convention, not bare class names.
- Patterns to use: thin controller → service layer (per `feedback-thin-controllers-require-
  service-layer`); Single Responsibility between "forward the override" and "log the override."
- What NOT to do:
  - Do not have admin-service recompute, validate, or second-guess the trust score formula
    itself — that is Rating Service's `TrustScoreCalculator`'s sole job (Single Responsibility,
    already named in that class's own comments).
  - Do not skip the audit log because it's "in-memory for now" — the acceptance criteria and
    the business requirement are explicit that it must still capture the admin's `X-User-Id`
    and `reason`, even though the storage mechanism is a placeholder.
  - **Do not implement this ticket's Rating Service call against a real `PATCH /trust/:userId`
    endpoint without first confirming it exists** — it does not exist in
    `contracts/openapi/rating-service.yaml` as of this writing (verified above). Flag this to
    whoever runs `/start-task T058` and prefer NOT approving/starting this ticket until the
    Tech Lead has resolved the contract gap in point 2 of the Technical Specification above.
  - Do not add an `isOverridden`/sticky-override field to Rating Service's `TrustScore` entity
    as part of this ticket — that decision and that schema change belong to Rating Service
    (out of `admin-service`'s scope) and depend on the Tech Lead's answer to the design
    question in point 3 above.
