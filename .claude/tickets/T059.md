# T059 — Account Suspend

## Why this ticket exists
Right now a bad actor can only be flagged — T053's escalation logic queues them for review
and T057 gives an admin a queue to look at, but nobody can actually pull the trigger. This
ticket is that trigger: the admin-facing action that takes a reviewed account out of
circulation. Without it, every report, every escalation, every row in T057's review queue is
just a list with no consequence attached — the user stays fully visible in Discovery, can
still send and receive connection requests, and the whole ReportEscalationSaga this platform
has been building since Phase 9 has no enforcement step at the end of it.

## What to build
- `AccountSuspendController` (or an additional method on T057's `ReviewQueueController`,
  whichever `ReviewQueueController` ends up looking like once T057 ships) exposing
  `POST /admin/users/{id}/suspend`
- `SuspendUserRequest` DTO — `{ reason: string }`
- `AdminSuspendService` (or a new method on T057's `ReviewQueueService` — orchestration shape
  is identical, just the opposite direction of T057's reinstate) that, in order:
  1. Calls `UserServiceClient` to set the target user's status to `suspended`
  2. Calls `ConnectionServiceClient` to expire the user's active (pending/accepted)
     connection requests
  3. Writes a `trust.score.updated` event with `request_limit: 0` to admin-service's own
     outbox (reusing T057's `AdminOutboxRelay` — do not stand up a second producer)
- `ConnectionServiceClient` (WebClient + Resilience4j `@CircuitBreaker`) — new client,
  admin-service's first call into Connection Service
- **Cross-service companion work this ticket surfaces (see Technical Specification below)**:
  a new admin-only status-mutation path on User Service, and a new admin-only bulk-expire
  endpoint on Connection Service. Neither exists today. This ticket cannot be fully
  implemented until at least one of them lands — flag this to the Tech Lead before approving.

## Technical specification

### Spec (verbatim from SPECS.md)
`POST /admin/users/:id/suspend`
Body: `{ "reason" }`

Calls User Service to set status = `suspended`. Publishes `trust.score.updated` with
`request_limit: 0` to remove from discovery.

**Acceptance criteria:**
- [ ] Suspended user removed from Discovery's `scan:eligible_users` within 1 Kafka poll
- [ ] User's active connection requests expired immediately (via Connection Service HTTP call)

### Refined technical specification — cross-service gaps found, verified against the actual contracts

**1. User Service — no admin-suspend endpoint exists today. This is a real contract gap, not
an oversight to work around in admin-service.**

I read `contracts/openapi/user-service.yaml` directly:
- `PUT /profile` is the only status-mutation endpoint, and it is strictly self-service: its
  only identity parameter is `X-User-Id`, which the service treats as "the caller," not a
  path-addressable target. There is no `PUT /users/{id}` or any path-parameterized mutation
  an admin could call to change *someone else's* status. There is also no `X-User-Role`
  bypass modeled anywhere in this file.
- Worse than a missing route: `Profile.status` and `ProfileUpdateRequest.status` are both
  defined as `enum: [looking_for_companion, not_available]`. There is no `suspended` (or
  `active`) value in the schema at all. `status` here models discovery *availability*, not
  account *standing* — these are different axes, and "suspended" doesn't fit into either
  existing value without redefining what the field means.
- T057's own ticket already assumes `UserServiceClient.setStatus(id, "active")` exists for
  its reinstate path and has the identical gap, unaddressed. This ticket's suspend path and
  T057's reinstate path are two ends of the same missing capability — fixing it once (as a
  companion change to User Service) unblocks both.
- **Contract decision made — tracked as T102.** Rather than a gateway-routed
  `PATCH /admin/users/{id}/status`, T102 adds internal-only, Docker-network-reachable endpoints
  (`GET /users/internal?accountStatus=suspended`, `GET /users/internal/{id}`,
  `PUT /users/internal/{id}/account-status`) matching the exact wire shape admin-service's
  `UserServiceClientImpl` already shipped against in T057 — no gateway route, no `X-User-Role`
  bypass needed, since every real caller is admin-service calling directly inside the Docker
  network (same trust boundary T057's own `RatingServiceClientImpl`/`ReportServiceClientImpl`
  calls already use). The new field is `account_status` (`active`/`suspended`), kept fully
  separate from the existing availability `status` field — same two-different-axes reasoning
  this ticket already laid out above. **Do not start building this ticket's own suspend call
  until T102 has shipped** — `T059` now formally depends on it (see frontmatter).

**2. Connection Service — no bulk-expire-by-user endpoint exists today. Also a real gap.**

I read `contracts/openapi/connection-service.yaml` directly:
- The only mutation endpoints are `PUT /connections/{id}/accept` and
  `PUT /connections/{id}/decline`, both scoped to a single connection id and authorized by
  checking that the caller (`X-User-Id`) is the recipient of that specific request. There is
  no bulk operation, no "all connections for user X" endpoint, and — same gap as User
  Service — `X-User-Role` isn't modeled as a parameter anywhere in this contract, so there's
  no admin bypass path to reuse even if a bulk endpoint existed.
- **Required companion change, out of scope for admin-service itself:** Connection Service
  needs a new admin-only endpoint — e.g.
  `PUT /admin/connections/users/{userId}/expire-active` — that transitions every `pending`
  or `accepted` connection where the user is either `requester_id` or `recipient_id` to
  `expired`, callable only with `X-User-Role: admin`. **Do not start building
  `ConnectionServiceClient`'s expire call in this ticket until that endpoint exists.**

**3. `trust.score.updated` payload — no gap, reuse the existing schema exactly.**

The event is already defined and already shipped by Rating Service (T043) and consumed by
Discovery and Connection Service. Fields (per
`TrustScoreUpdatedEvent` / `REQUIREMENTS.md` §Kafka topics):
`event_id`, `user_id` (stringified id, not a UUID type — match the existing wire convention),
`new_score`, `badge_level`, `request_limit`. For a suspend, publish `request_limit: 0` and
`badge_level: "restricted"` (the lowest tier already defined by T043's three-way mapping — do
not invent a fourth badge level). `new_score` should be left as whatever the user's current
persisted score is — a suspend is an availability action, not a re-scoring action, so this
ticket must NOT recompute or alter the trust score itself, only `request_limit`.

**4. Outbox — zero new producer infrastructure.** T057 already builds `AdminOutboxEntity`
(or its Mongo-folded equivalent, matching whatever T056 set admin-service's datastore up as)
and `AdminOutboxRelay` for its own reinstate path's `trust.score.updated` publish. This
ticket's publish is the same event type, same relay, different payload values — add a second
call into the same outbox write path, do not create a parallel one.

## Acceptance criteria
- [ ] Suspended user removed from Discovery's `scan:eligible_users` within 1 Kafka poll
- [ ] User's active connection requests expired immediately (via Connection Service HTTP call)

## Patterns demonstrated
- **Simple synchronous orchestration (not a Saga)** — this endpoint makes two ordered,
  synchronous HTTP calls (User Service, then Connection Service) and one Kafka publish, all
  triggered by one admin action. It is not choreographed via events the way
  `ConnectionLifecycleSaga` is — there's no compensating-transaction step if one leg fails
  partway (see the ordering/rollback note below), so don't call this a Saga. It is the same
  "aggregate three upstream effects behind one caller-facing action" shape T057's reinstate
  already establishes, just the opposite direction.
- **Outbox Pattern (reused, not reinvented)** — the `trust.score.updated` publish goes
  through T057's `AdminOutboxRelay`, the same discipline every other Kafka producer in this
  project follows: write to the outbox in the same local transaction, let the relay publish
  later, never call `KafkaTemplate.send()` directly from business code.
- **Interface Segregation** — `ConnectionServiceClient` is a new, narrow interface (this
  ticket needs exactly one call: expire-active-by-user), not an addition bolted onto an
  unrelated existing client.
- **Dependency Inversion** — `AdminSuspendService` (or the extended `ReviewQueueService`)
  depends on `UserServiceClient` / `ConnectionServiceClient` interfaces, not concrete
  WebClient usage, matching T057's own client shape.

## Agent implementation notes
- Key files to create (paths from project root, under
  `src/services/admin-service/src/main/java/com/shareconnectsave/admin_service/`, matching
  T057's package layout):
  - `dto/SuspendUserRequest.java`
  - `client/ConnectionServiceClient.java` (interface) + WebClient-based implementation —
    new; reuse the `UserServiceClient` / `RatingServiceClient` Resilience4j `@CircuitBreaker`
    conventions T057 already establishes
  - Either a new `AccountSuspendController` + `AdminSuspendService`, or new methods added
    onto T057's `ReviewQueueController` / `ReviewQueueService` — whichever the Tech Lead
    prefers once T057 has actually shipped; do not duplicate the WebClient/outbox wiring
    either way
- Patterns to use: same WebClient + Resilience4j `@CircuitBreaker` conventions as T057's
  `UserServiceClient`/`RatingServiceClient`; same outbox write path as T057's reinstate.
- Ordering and failure handling: call User Service (set `suspended`) first, then Connection
  Service (expire active requests), then write the outbox event, matching the order the
  acceptance criteria are checked in. If the User Service call fails, stop — don't expire
  connections or publish anything for a user who was never actually suspended. If Connection
  Service's call fails after User Service already succeeded, the endpoint should still fail
  the whole request (don't publish `trust.score.updated` for a half-finished suspend) — same
  "don't leave an inconsistent state as if it succeeded" rule T057's reinstate spec already
  establishes for its own two-step sequence.
- What NOT to do:
  - Don't implement `UserServiceClient`'s suspend call or `ConnectionServiceClient`'s expire
    call against endpoints that don't exist — both require a companion contract/implementation
    change to User Service and Connection Service respectively (see Technical Specification
    above). Surface this to the Tech Lead; don't invent a workaround like calling `PUT
    /profile` with a smuggled status value, since the schema's enum would reject it anyway.
  - Don't build a second outbox/relay for admin-service — T057 already built
    `AdminOutboxRelay`; this ticket only adds a new payload going through it.
  - Don't call `KafkaTemplate.send()` directly from `AdminSuspendService`.
  - Don't recompute or alter the user's `new_score` — this action only ever sets
    `request_limit: 0` and `badge_level: "restricted"`; trust score recalculation is Rating
    Service's exclusive responsibility (Single Responsibility), not admin-service's.
