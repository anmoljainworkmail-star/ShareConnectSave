# T060 — Dashboard Queries

## Why this ticket exists
Right now an admin can only act on one flagged account at a time (the queue from T057,
suspend/reinstate from T058/T059) — there is no single place to see how the platform is
doing as a whole: how many people are actively using it, how much activity is happening
today, and who's racking up reports before they even hit the escalation threshold. Without
this ticket, an admin has no landing-page view at all — they'd have to already know a
user's ID before they could look anything up. This also introduces the project's first
in-process cache (Caffeine), which matters because this endpoint's whole job is to be
looked at repeatedly (a dashboard that's refreshed every 60 seconds per the Phase 10 goal)
— without a cache, every refresh would re-trigger calls to four other services just to
redraw the same numbers that haven't changed yet.

## What to build
- `GET /admin/stats` on `admin-service`, returning a single `DashboardStatsResponse` with:
  - `totalActiveUsers`
  - `totalScansToday`
  - `totalConnectionsAcceptedToday`
  - `totalReportsToday`
  - `topReportedUsers` (top 5, by report count, last 7 days)
- `DashboardStatsService` — orchestrates the 4 downstream HTTP calls (via `WebClient`,
  Resilience4j-wrapped, same convention as T057/T059) and assembles the response.
- Caffeine `Cache<String, DashboardStatsResponse>` with a single fixed key (e.g.
  `"dashboard-stats"`) and a 60s `expireAfterWrite`, so a cache hit skips all 4 downstream
  calls entirely.
- **Companion endpoints this ticket depends on existing in 4 OTHER services before
  admin-service can call them for real data** — see Technical Specification below. This
  is the schedule risk the Tech Lead needs to resolve before approving.

## Technical specification

**From SPECS.md (verbatim):**

`GET /admin/stats` — returns:
- Total active users
- Total scans today
- Total connections today (accepted)
- Total reports today
- Top 5 most-reported users (last 7 days)

Data sourced via HTTP calls to respective services. Cache response 60 s in Caffeine.

**Refined technical specification — actual contract audit (this ticket's own addition):**

I checked every downstream service's OpenAPI contract in `contracts/openapi/` against each
of the 5 metrics. **None of the 4 downstream services currently expose an endpoint shaped
for what this ticket needs.** This is not a clean "4 HTTP calls, done" ticket — it is
blocked on new work in User, Discovery, and Connection Service, and partially blocked on
Report Service.

| Metric | Source service | Endpoint needed | Status |
|---|---|---|---|
| Total active users | User Service | `GET /users/stats` or similar count endpoint | **Does not exist.** `user-service.yaml` only exposes `GET /profile` (caller's own profile, self-scoped) and `/blocks`. There is no admin-facing listing or count endpoint of any kind — User Service has zero bulk-read surface today. |
| Total scans today | Discovery Service | `GET /scan/stats` or similar | **Does not exist.** `discovery-service.yaml` only exposes `/scan/start`, `/scan/stop`, `/scan/nearby`, `/ble/resolve`, `/settings/women-only` — all caller-scoped to the user's own active scan. No admin/aggregate surface at all. |
| Total connections accepted today | Connection Service | `GET /connections/stats` or similar | **Does not exist.** `connection-service.yaml` only exposes `/connections` (create), `/connections/pending` (caller-scoped: the caller's own sent+received pending requests), and per-id get/accept/decline. There is no admin-wide listing endpoint of any kind — same gap as User Service. |
| Total reports today | Report Service | reuse existing `GET /reports` (admin-only, lists ALL reports) | **Partially usable today.** `report-service.yaml` already has `GET /reports` as admin-only and returns every `Report` with `created_at` and `status`. Admin Service *could* call this and filter/count client-side for "today" without a new Report Service endpoint — inefficient at scale (pulls the whole report table every cache-miss) but functionally unblocked right now. |
| Top 5 most-reported users (last 7 days) | Report Service | new aggregate endpoint, e.g. `GET /reports/top-reported?days=7&limit=5` | **Does not exist, and `GET /reports/queue` (T053) is NOT a substitute.** `/reports/queue` only returns reports whose `status == escalated`, sorted by the `reportCountAtEscalation` snapshot taken at the moment escalation happened — it silently excludes any user who has multiple reports in the last 7 days but hasn't crossed the escalation threshold yet, and the snapshot count can be stale relative to "right now." This ticket needs a live group-by-`reported_id` count over a rolling 7-day window regardless of escalation status — a fundamentally different query. Could be computed client-side in Admin Service from `GET /reports` (same inefficiency caveat as above), but the *correct* long-term home for this aggregation is Report Service, which owns the data (Database per Service). |

**Biggest open question for the Tech Lead — pick one before approving:**
1. **Companion tickets first (recommended):** create small follow-up tickets for User,
   Discovery, and Connection Service, each adding one narrow admin-only stats/count
   endpoint (e.g. `GET /users/stats`, `GET /scan/stats`, `GET /connections/stats`), plus
   one for Report Service adding `GET /reports/top-reported`. This keeps every service
   answering its own aggregate queries over its own data — consistent with "Database per
   Service: nobody else touches it directly" and with how Admin Service already proxies
   through HTTP everywhere else (T057's `/admin/users/:id/reports`). T060 is then
   correctly re-sequenced to depend on those tickets, not just T056.
2. **Admin Service reads the raw data directly (via JPA/direct DB count queries)** for
   whichever services don't get a stats endpoint — this directly contradicts the System
   Design Principles table in CLAUDE.md ("Admin Service reads others via HTTP, not direct
   DB joins") and the T056 ticket's own explicit recommendation to ship admin-service as
   HTTP-client-only with no JPA dependency. Not recommended, but flagged as the only other
   real option.
3. **Partial compromise:** ship only the Report Service metrics now (using the existing
   `GET /reports` endpoint client-side, accepting the inefficiency), stub the other 3
   metrics as `null`/`0` with a clear "not yet available" signal, and let this ticket's
   scope grow once companion tickets land. Riskiest for `/admin/stats`'s own acceptance
   criteria ("all 5 metrics returned") since 3 of them would be fake until then.

This ticket as written assumes **option 1** is picked — the implementation notes below
describe calling real stats endpoints on the 4 services. If the Tech Lead instead picks
option 2 or 3, this ticket needs to be rewritten before `/start-task T060` runs.

## Acceptance criteria
- [ ] All 5 metrics returned
- [ ] Response cached, subsequent calls within 60 s don't hit downstream services

## Patterns demonstrated
- **Cache-Aside** — Caffeine in-memory cache on the aggregate response, same concept as
  Discovery Service's Redis cache-aside (`/scan/nearby`) but in-process instead of
  distributed, since this is a single-instance dashboard query, not cross-replica shared
  state: on a miss, populate from the 4 downstream calls; on a hit, skip them entirely.
- **Circuit Breaker (Resilience4j)** — each of the 4 downstream calls is wrapped
  individually, same convention as T057/T059's `WebClient` calls to User/Rating/Report
  Service, so one slow/down service degrades its own metric, not the whole dashboard.
- **Single Responsibility** — `DashboardStatsService` only assembles the aggregate view;
  it does not calculate trust scores, does not decide escalation, and does not own any of
  the 4 underlying counts — each source service remains the one place that count is
  actually computed, consistent with Database per Service.

## Agent implementation notes
- Key files to create (paths from project root):
  - `src/services/admin-service/src/main/java/.../dashboard/DashboardStatsController.java`
    — the `GET /admin/stats` endpoint, thin, delegates to the service layer (per this
    project's "thin controllers require a service layer" convention).
  - `src/services/admin-service/src/main/java/.../dashboard/DashboardStatsService.java`
    — orchestrates the 4 WebClient calls + Caffeine cache lookup/populate.
  - `src/services/admin-service/src/main/java/.../dashboard/DashboardStatsResponse.java`
    — the response DTO.
  - `src/services/admin-service/src/main/java/.../config/CacheConfig.java` — defines the
    Caffeine `Cache<String, DashboardStatsResponse>` bean.
  - `src/services/admin-service/src/main/resources/application.yml` — add a
    `admin.dashboard.cache-ttl-seconds: 60` property (Options Pattern /
    `@ConfigurationProperties`, same convention this project already uses elsewhere for
    configurable values) — **do not hardcode `60` in Java code**, bind it from config so
    it matches `process.env`-style externalized config used across the rest of the
    project.
- Patterns to use: a manual `Cache<K,V>` (Caffeine's `Caffeine.newBuilder()`) bean rather
  than Spring's `@Cacheable` annotation — a manual cache makes the single fixed key and
  the "don't cache a partial/degraded result" rule (below) explicit and inspectable,
  rather than hidden behind annotation magic.
- What NOT to do:
  - Don't call the 4 downstream services synchronously with no per-call timeout/circuit
    breaker — a single slow service must not make the whole `/admin/stats` request hang.
    Use the same Resilience4j `TimeLimiter` + `CircuitBreaker` convention T057/T059 use
    around their `WebClient` calls.
  - Don't silently cache a partial/degraded response as if it were a complete 5-metric
    one. If one downstream call fails or times out, either (a) don't populate the cache
    for this cycle at all and return the degraded response with an explicit per-metric
    flag (e.g. a `stale`/`unavailable` marker on that one field), or (b) serve the last
    good cached value for just that metric with an "as of" timestamp — but never return a
    `0` or `null` for a failed metric indistinguishable from a genuine zero count.
  - Don't build this against placeholder/fake downstream endpoints without flagging it —
    if the Tech Lead picks option 2 or 3 above instead of real companion endpoints, this
    ticket's implementation notes no longer apply as written and must be revisited first.
