# T061 — Admin Service Docker Image

## Why this ticket exists

Admin Service is the 9th and final microservice in the platform's architecture diagram to
need a Docker image — without it, admin-service can't join the local `/docker-up` stack
alongside the other eight services, which blocks end-to-end testing of the review-queue flow
(T056/T057: suspend → review → reinstate → `trust.score.updated`) the same way a missing
Dockerfile would have blocked any earlier service. It closes out Phase 10 the exact way T055
closed out Phase 9 for Report Service, and T028/T034/T040/T046/T050 closed out their own
phases before that. It is also, potentially, the most structurally different Docker ticket
of the nine: if T056/T057's open JPA-vs-HTTP-only question resolves toward HTTP-only, this
would be the first Java service in the platform with no direct SQL Server or MongoDB
connection at all — worth getting right rather than copy-pasting blind.

- `src/services/admin-service/.dockerignore` — new

  494–516) — build context, and whether the `sqlserver` / `sqlserver-init` `depends_on`

## Technical specification

**Verified current state as of this ticket being written (re-check at implementation time,
since T056/T057 land first):**

1. **`docker-compose.yml` already has the `admin-service` block** (lines 494–516): image
   `shareconnectsave/admin-service:dev`, port `8088:8080`, build context currently
   `../../src/services/admin-service` with `dockerfile: Dockerfile` — the same narrow,
   single-folder shape T046 found stale for rating-service and T055 had to re-verify for
   report-service. **Do not trust this blindly.** Once T056/T057 have landed, check
   `admin-service/pom.xml` for a `shared-java-lib` dependency — every Java service past T051
   has ended up depending on it for `ErrorResponse`/`GlobalExceptionHandler`, even when its
   own ticket didn't mention it explicitly. If admin-service depends on `shared-java-lib`,
   widen the build context to `context: ../../src/services` / `dockerfile:
   admin-service/Dockerfile`, and have the Dockerfile install `shared-java-lib` from source
   first — copy that pre-build layer exactly from `report-service/Dockerfile` (T055), the
   most recent precedent. If it genuinely doesn't depend on it, leave the narrow context
   alone.

2. **`depends_on` currently lists `sqlserver` (`service_healthy`), `sqlserver-init`
   (`service_completed_successfully`), and `kafka` (`service_healthy`)** — this was set up
   as a template default before T056 resolved its own open question (T056's ticket
   explicitly says "Do not add `spring-boot-starter-data-jpa` or a SQL Server JDBC driver...
   pending Tech Lead's decision"). By the time this ticket starts, check what T056/T057
   actually shipped:
   - If admin-service ended up with a real JPA/SQL Server datasource (read-only access to
     `users_db`/`ratings_db` per SPECS.md's original wording) — the `sqlserver` /
     `sqlserver-init` `depends_on` entries are correct, leave them.
   - If T056/T057 resolved toward HTTP-only (WebClient calls to User Service and Rating
     Service instead of direct JPA reads) — admin-service needs **no** SQL Server dependency
     at all, and these `depends_on` entries should be removed. This would make admin-service
     the first Java service in the platform with no DB driver, no Flyway, nothing but Kafka +
     WebClient + Caffeine in its `pom.xml` — a genuinely different packaging shape, not just a
     cosmetic difference. Verify before touching the compose file either way.

3. **No `application.yml` exists yet** — admin-service itself doesn't exist beyond its
   Phase 0 folder stub as of this ticket being written. When this ticket starts, check
   whether T056 created `application.yml` with `dev`/`docker` (or `dev`/`prod`) profile
   documents. If so, and if a datasource is present, add the same one-line explanatory
   comment every prior Java service has (e.g. `rating-service/application.yml`): `docker`
   profile intentionally omitted; datasource creds injected via env vars in
   `docker-compose.override.yml` — because `SPRING_PROFILES_ACTIVE=docker` (already set in
   `docker-compose.yml` line 510) matches zero profile documents and silently no-ops. If
   admin-service turns out to have no datasource at all, note explicitly in your
   implementation notes that no such comment was needed and why, rather than silently
   skipping it.

4. **Dockerfile shape** — follow `src/services/report-service/Dockerfile` (T055) exactly,
   the most recent and most relevant precedent (also a late-phase Java service Docker
   ticket with the same shared-java-lib build-context verification need):
   - Build stage: `eclipse-temurin:21-jdk`, Maven-wrapper build (`./mvnw` + offline/package),
     same `shared-java-lib` pre-install layer if confirmed needed (see point 1).
   - Runtime stage: `eclipse-temurin:21-jre-alpine`, `curl` installed for the healthcheck,
     `COPY --from=build .../target/*.jar app.jar` wildcard copy.
   - Do not hardcode `EXPOSE`/port or set `SPRING_PROFILES_ACTIVE`/`server.port` via `ENV` —
     both are already controlled by `docker-compose.yml` (port `8088:8080`,
     `SPRING_PROFILES_ACTIVE=docker` at line 510).

5. **Size budget:** use `docker inspect --format {{.Size}}` or `docker save | wc -c` as the
   authoritative image size metric, target under 300MB uncompressed. Do **not** trust
   `docker images`' reported size — confirmed on this machine to over-report by roughly 3x
   (~450MB shown vs. ~152MB real), a containerd-snapshotter display quirk, not a BuildKit
   attestation artifact. If admin-service ships with no DB driver at all (see point 2), its
   real image should land smaller than every prior Java service's — worth noting in the PR
   if so, as evidence the HTTP-only packaging shape is genuinely lighter.

## Patterns demonstrated

Minimal pattern content here — this is Docker packaging, not business logic, same as
T028/T034/T046/T055. The one notable point, if it holds true once T056/T057 ship: should
admin-service resolve toward HTTP-only (no direct JPA access to `users_db`/`ratings_db`), it
would be the **first** Java service in this platform with no SQL Server or MongoDB connection
at all — worth calling out as a genuinely different packaging shape, not a trivial variant
(no DB driver dependency, no Flyway, nothing but Kafka + WebClient + Caffeine). Otherwise,
same **Multi-stage build** teaching point as every prior Docker ticket (separates the
JDK+Maven build toolchain from the lean JRE-alpine runtime image) applies unchanged. No
SOLID or GoF pattern should be forced onto this ticket.
