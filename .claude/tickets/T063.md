# T063 — Auth Flow (Google Sign-In + OTP)

## Why this ticket exists

Right now the Angular PWA has no way for a traveler to actually get in. The backend already knows how to issue and verify identity — `user-service` validates a Google sign-in and mints a JWT (T016), and verifies a phone number via OTP (T017) — but none of that is reachable from the app a real traveler holds in their hand. Until this ticket ships, every other frontend screen (discovery radar, connection requests, chat) has no logged-in user to work with, and no way to attach proof-of-identity to a single API call. This ticket is the front door: it turns "I tapped Sign in with Google and typed the code I got by text" into a stored JWT that every subsequent screen and every subsequent HTTP request can rely on, and it is also the gatekeeper — unauthenticated users must never reach a protected screen, and a JWT that has quietly expired must not be allowed to silently fail every request afterward.

## What to build

- `LoginComponent` — renders the Google Sign-In button and handles the sign-in callback
- `OtpVerifyComponent` — phone number input + 6-digit OTP input, two-step verification screen
- `AuthService` — wraps `POST /auth/google`, `POST /auth/otp/send`, `POST /auth/otp/verify`; stores/retrieves the JWT; exposes a token-access method
- `AuthGuard` — route guard that redirects unauthenticated users to `LoginComponent`
- `AuthInterceptor` — HTTP interceptor that adds `Authorization: Bearer <jwt>` to every outgoing API request

## Technical specification

Two screens: `LoginComponent`, `OtpVerifyComponent`.

- `LoginComponent`: renders Google Sign-In button (`@angular/google-signin-ewf-fortlet` or direct GSI script). On success → call `POST /auth/google`, store JWT in `localStorage`.
- `OtpVerifyComponent`: phone input + 6-digit OTP input. Calls `POST /auth/otp/send` and `POST /auth/otp/verify`.
- `AuthGuard` — redirects unauthenticated users to login.
- `AuthInterceptor` — adds `Authorization: Bearer <jwt>` to all API requests.

## Acceptance criteria

- [ ] Full Google → OTP flow completes and JWT is stored
- [ ] Protected routes redirect to login when unauthenticated
- [ ] Expired JWT → refresh attempted, then logout

## Patterns demonstrated

- **Single Responsibility (S)** — `AuthService` only handles authentication calls and token storage; it does not know about routing or UI state, which stay in the components and guard.
- **Dependency Inversion (D)** — `LoginComponent` and `OtpVerifyComponent` depend on `AuthService`'s public methods, not on `HttpClient` or `localStorage` directly, so the token-storage mechanism can change without touching the components.
- **Guard (Angular routing)** — `AuthGuard` centralizes the "is this user allowed here" check in one place instead of every protected component re-checking auth state itself.
- **Interceptor (cross-cutting concern)** — `AuthInterceptor` attaches the JWT to every outgoing request in one place, the same "handle it once, centrally" idea the API Gateway applies server-side, just on the client.

## Agent implementation notes

**Key files to create:**
- `src/frontend/src/app/auth/auth.module.ts` — `AuthModule`, declares both components, imports routing
- `src/frontend/src/app/auth/login/login.component.ts` (+ `.html`) — Google Sign-In button, success handler
- `src/frontend/src/app/auth/otp-verify/otp-verify.component.ts` (+ `.html`) — phone + OTP input, calls send/verify
- `src/frontend/src/app/auth/auth.service.ts` — `AuthService`: `signInWithGoogle()`, `sendOtp()`, `verifyOtp()`, `getToken()`, `storeToken()`, `clearToken()`, `isAuthenticated()`
- `src/frontend/src/app/auth/auth.guard.ts` — `AuthGuard implements CanActivate`
- `src/frontend/src/app/auth/auth.interceptor.ts` — `AuthInterceptor implements HttpInterceptor`
- Update the root routing module to register `AuthGuard` on protected feature routes and register `AuthInterceptor` in the app's providers (`HTTP_INTERCEPTORS`)

**Patterns to use:**
- Reference the `angular-pwa` skill for module structure, routing, and interceptor registration conventions for this project.
- Module-based only — `LoginComponent` and `OtpVerifyComponent` must be declared in an `NgModule` (`AuthModule`), lazy-loaded via `loadChildren`. No standalone components, per project-wide Angular rules.
- Early-return guard clauses in `AuthGuard` and in validation logic (e.g. reject malformed OTP input before calling the API), per this project's stated preference.
- JWT storage in `localStorage`, read/written only through `AuthService` — no component or guard should touch `localStorage` directly.

**What NOT to do:**
- Do not call `localStorage` from `LoginComponent`, `OtpVerifyComponent`, `AuthGuard`, or `AuthInterceptor` directly — route everything through `AuthService` so the storage mechanism stays swappable.
- Do not build `LoginComponent` or `OtpVerifyComponent` as standalone components — this project is module-based only, with no exceptions.
- Do not implement profile setup (name/photo/language/gender) or identity verification (selfie/liveness) in this ticket — those are later tickets; this ticket stops at "JWT stored, user authenticated."
- Do not silently drop requests on an expired JWT — attempt a refresh first, and only log the user out (clear token, redirect to login) if the refresh itself fails.
- Do not hardcode the API base URL or any config value — use environment configuration per this project's `process.env.*`-equivalent convention for Angular (environment files), never a literal string in the service.

## Known follow-ups

`AuthService`'s token-access method must be structured so it can be passed directly into SignalR's `accessTokenFactory` in `HubConnectionBuilder` (T067/T068 will need this). Do not soften or drop this.
