# T064 — Radar UI Component

## Why this ticket exists

This is the screen the entire product is named for — the moment a traveler opens the app, taps Start Scan, and sees whether anyone nearby is heading the same way. Every other feature (connection requests, chat, ratings) only exists because this screen found a match first. Without it, Discovery Service's geospatial queries (T049-era work) have no face — there is no way for a real traveler to see a nearby companion, read their card, or act on it. This ticket also closes a gap the backend spec quietly depends on: a user's "looking" / "unavailable" status is not just a Settings checkbox, it has to track the radar screen's own lifecycle too, or Discovery Service will keep matching someone who closed the app and walked away.

## What to build

- `RadarComponent` — animated SVG radar with current user at center, continuous rotating sweep, discovered users rendered as positioned animated dots
- `UserCardComponent` — bottom-sheet/card showing a discovered user's details, reused as-is by `InboundRequestComponent` (T067) for the sender's card
- An authenticated-photo-fetch helper (service or shared method) — fetches a user's photo via an authenticated HTTP call and exposes a blob URL, used by `UserCardComponent` wherever a photo is rendered
- Start Scan / exit lifecycle wiring in `RadarComponent` — `PATCH /user/users/me` with `{"status": "looking"}` on Start Scan, `{"status": "unavailable"}` on exit/close, using the same status-write path `SettingsComponent` (T070) uses

## Technical specification

`RadarComponent` — animated SVG radar:
- Current user at center
- Rotating sweep animation (CSS `@keyframes`)
- Discovered users appear as animated dots, positioned by approximate bearing and distance
- Tap a dot → opens `UserCardComponent`

`UserCardComponent` — shows: name, photo, rating stars, destination, "leaving in X min", route match %, preferred language, Send Request button. Photo requires a valid JWT to fetch (REQUIREMENTS.md §2, decided during Phase 3 integration testing) — cannot be a plain `<img src="{{photo_url}}">`; fetch it via an authenticated call and bind the resulting blob URL instead. `T067`'s `InboundRequestComponent` reuses this component for the sender's card, so this applies there too, not just the Radar screen.

Mode indicator badge: "GPS" (green) or "BLE" (orange, with range note).

**Start Scan / exit status lifecycle** (REQUIREMENTS.md §3, decided during Phase 3 integration testing — status is not left to only the Settings toggle): tapping Start Scan calls `PATCH /user/users/me` with `{"status": "looking"}` before/alongside starting the scan itself; exiting or closing the scan calls `PATCH /user/users/me` with `{"status": "unavailable"}`. This is the SAME endpoint/field `SettingsComponent`'s status toggle (T070) writes — no separate API, just two different UI triggers for one field. The Settings toggle must remain fully usable independently (e.g. to go "unavailable" mid-scan without leaving the radar screen, or "looking" without ever starting a scan).

## Acceptance criteria

- [ ] Radar sweep animation runs continuously while scan is active
- [ ] User card renders all required fields
- [ ] User card's photo is fetched with an authenticated request (not a bare `<img src>`) and still renders correctly
- [ ] Mode badge switches correctly
- [ ] Tapping Start Scan sets `status: looking` via `PATCH /users/me`
- [ ] Exiting/closing the scan sets `status: unavailable` via `PATCH /users/me`
- [ ] Settings toggle (T070) still correctly reflects/overrides status when used independently of scanning

## Patterns demonstrated

- **Single Responsibility (S)** — `RadarComponent` owns scan lifecycle and sweep/dot rendering; `UserCardComponent` owns displaying one user's details; the photo-fetch helper owns only turning a protected photo URL into a renderable blob URL. None of the three does another's job.
- **Interface Segregation (I), applied to UI reuse** — `UserCardComponent` is shaped around "show one discovered user's data," not "be the Radar screen," which is exactly why `InboundRequestComponent` (T067) can reuse it for an unrelated screen without inheriting anything Radar-specific.
- **Don't Repeat Yourself, via a shared authenticated-fetch helper** — every photo in the app goes through one authenticated-fetch-to-blob-URL path instead of each component reinventing the JWT-attached request, so the §2 photo-auth rule only has to be gotten right once.
- **Single source of truth for state** — `status: looking/unavailable` lives in exactly one place (`user-service`, written via `PATCH /users/me`); Radar and Settings are two independent UI triggers writing the same field, not two competing copies of availability state.

## Agent implementation notes

This is a visually-risky screen. An approved reference mockup already exists for this exact screen and the Tech Lead has signed off on it — matching it precisely is part of the acceptance bar, not a nice-to-have.

- The `angular-pwa` skill file has a "Visual reference" section pointing to `FIGMA_SPEC.md` and an approved reference mockup for **Screen 07 — Radar Active (GPS Mode)** at https://claude.ai/artifact/CAu6pBZqysAqa8yKct6jrw. Match that mockup's radar ring/sweep/glow mechanics, dot pulse timing, and bottom-sheet layout pixel-for-pixel — do not reimplement from the written spec text alone; the mockup is the source of truth for visual details the spec text doesn't fully capture.

**Key files to create:**
- `src/frontend/src/app/radar/radar.module.ts` — `RadarModule`, declares both components, lazy-loaded
- `src/frontend/src/app/radar/radar/radar.component.ts` (+ `.html`, `.css`) — SVG radar, sweep `@keyframes`, dot positioning by bearing/distance, Start Scan / exit lifecycle calls
- `src/frontend/src/app/radar/user-card/user-card.component.ts` (+ `.html`, `.css`) — fields listed above, Send Request button; built so `InboundRequestComponent` (T067, different module) can import and reuse it rather than duplicate it
- `src/frontend/src/app/shared/authenticated-photo.service.ts` (or equivalent shared location) — authenticated photo fetch → blob URL helper, consumed by `UserCardComponent`
- Extend the existing status-write path used by `SettingsComponent`/`AuthService`-adjacent user service rather than creating a second `PATCH /users/me` implementation

**What NOT to do:**
- Do not use a bare `<img src="{{photo_url}}">` anywhere a user photo is shown — every gateway route including static photo files requires a JWT (REQUIREMENTS.md §2), so a plain `<img>` tag will fail to attach the Authorization header and the photo will not load. Fetch via `HttpClient`/`fetch()` with the auth header, convert the response to a blob URL, and bind that.
- Do not build a second, Radar-specific status-write method — reuse the exact same `PATCH /user/users/me` call path that `SettingsComponent` (T070) will use for its toggle.
- Do not let the Radar lifecycle disable or bypass the Settings toggle — a user must be able to flip status independently of whether a scan is active.
- Do not build `RadarComponent` or `UserCardComponent` as standalone components — this project is module-based only, no exceptions.
- Do not reimplement the radar visuals from the written spec text alone without checking the approved mockup — sweep timing, dot pulse, ring/glow styling, and bottom-sheet layout must match the mockup, not just satisfy the prose description.
- Do not skip revoking/cleaning up blob URLs created by the photo-fetch helper when a card is destroyed — leaking blob URLs on a screen that renders many discovered users is an easy memory leak to introduce here.
