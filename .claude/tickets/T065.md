# T065 — BLE Mode (Web Bluetooth API)

## Why this ticket exists
GPS discovery only ever answers "who is near me right now" — it has no memory. If two
travelers spend a connectivity-dead stretch (subway tunnel, elevator, parking garage) sitting
next to each other, GPS discovery never runs during that window, and by the time signal
returns, one or both may have moved on. Without a fallback, every encounter during a
connectivity gap is invisible and unrecoverable, permanently — a traveler could pass within
arm's reach of their ideal travel companion and the platform would simply never know. This
ticket builds the client half of the fix: while the device is offline, it scans for and
remembers nearby BLE broadcasts, so that the moment connectivity returns, those fleeting
encounters become resolvable candidates through the same connection-request flow as any GPS
match. It does not enable chatting or matching while offline — its entire value is "recover
the identity of who I passed."

## What to build
- `BleDiscoveryService` (Angular, injectable, belongs to the feature module that owns
  discovery — not a standalone service per this project's module-based Angular rule)
- `fromEvent(window, 'offline')` / `fromEvent(window, 'online')` listeners driving a mode
  switch between GPS discovery and BLE discovery
- A "Nearby offline users (BLE scan)" UI panel that activates on the offline transition and
  initiates a Web Bluetooth scan for devices advertising the app's known Service UUID
- Empty-result messaging: "No BLE companions found nearby. Enable data to use GPS discovery."
- iOS / unsupported-browser fallback: if `navigator.bluetooth === undefined`, show "Bluetooth
  discovery not supported on iOS. Enable data to continue." instead of attempting a scan
- On reconnect (`online` event): stop BLE scanning, resume GPS discovery mode, and call
  `POST /scan/ble/resolve` with whatever tokens were collected during the offline window
- **Seed registration is proactive, not reactive to the offline event** — see Technical
  specification addendum below. `BleDiscoveryService` must register/refresh the BLE seed via
  `POST /scan/ble/seed` while the device is still online (e.g. at scan start, alongside T064's
  GPS scan-start flow, or on seed-nearing-expiry), never inside the `offline` handler itself.

## Technical specification

### Spec (verbatim from SPECS.md)
`BleDiscoveryService`:
1. Detect when device goes offline (`fromEvent(window, 'offline')`).
2. On offline: call `POST /scan/ble/token` (while still resolving from cache), then start BLE advertising (not supported via Web Bluetooth — note: Web Bluetooth supports scanning only, not advertising). Re-architect: use BLE scanning to detect nearby devices that are advertising a known service UUID via a native companion (or flag as future mobile app feature).

**Revised scope for PWA:**
Web Bluetooth API supports scanning but not advertising from a browser. Update: BLE offline mode in the PWA shows a "Nearby offline users (BLE scan)" UI that initiates a Bluetooth scan for devices advertising the app's service UUID. This requires the companion device to be running a native app or a specific BLE peripheral. For MVP, show the UI and scan, but if no devices found show "No BLE companions found nearby. Enable data to use GPS discovery."

On reconnect: call `POST /scan/ble/resolve` with any detected tokens.

iOS: detect via `navigator.bluetooth === undefined`, show "Bluetooth discovery not supported on iOS. Enable data to continue."

**Acceptance criteria:**
- [ ] Goes offline → BLE mode UI activates
- [ ] `navigator.bluetooth` unavailable → iOS message shown
- [ ] Returns online → GPS mode resumes, resolve called with detected tokens

### Addendum — reconciled against T024 v2 (shipped, status: done), the actual backend contract

The spec text above predates T024's rework and is stale in two ways the developer agent must
not implement literally:

1. **`POST /scan/ble/token` no longer exists.** T024 was reworked (v1 → v2) specifically
   because a server-minted, 5-minute-lived token requires a server round-trip to keep rotating
   — which is impossible during the exact outage BLE mode exists to cover, and a device that
   starts scanning already offline would never have had a token to broadcast in the first
   place. T024 v2 replaces it with `POST /scan/ble/seed`: the client registers one long-lived
   secret seed (while it has signal) and derives rotating broadcast values from it locally,
   offline, using `broadcastValue = HMAC-SHA256(seed, floor(unixEpochSeconds /
   ble.window.seconds))`, truncated to 16 bytes, window default 300s. `POST /scan/ble/resolve`
   is unchanged in shape (`{ "tokens": [...] }` in, array of user cards out).
2. **Calling seed registration from inside the `offline` handler is backwards and will not
   work.** By definition, the device has no connectivity at the moment the `offline` event
   fires, so an HTTP call made at that moment cannot reach `/scan/ble/seed`. Seed
   registration/refresh must happen proactively while online — at scan start (coordinate with
   T064's Radar UI scan-start flow) and again whenever the current seed is nearing its TTL —
   so a valid seed is already cached client-side *before* any offline transition occurs. The
   `offline` handler's only job is to switch the UI into BLE scan mode and start deriving
   broadcast values from the already-registered seed; it must not call the network.

Routing note: both endpoints are served by discovery-service behind the API gateway's
`/discovery` prefix (`PathRemovePrefix: /discovery`), i.e. the frontend calls
`POST /discovery/ble/seed` and `POST /discovery/ble/resolve`, not the bare `/scan/ble/...`
paths the original spec text used — confirmed against `contracts/openapi/discovery-service.yaml`
(`/ble/resolve` is documented there; `/ble/seed` is implemented per T024 v2 but is currently
**not yet documented** in that OpenAPI file — flag this to `/validate-contracts` as a known gap,
do not treat its absence from the contract file as evidence the route doesn't exist).

## Patterns demonstrated
- **Observer (via RxJS)** — `fromEvent(window, 'offline'/'online')` lets `BleDiscoveryService`
  react to connectivity changes without the browser needing to know anything about what's
  listening, same shape as the Kafka Observer pattern named elsewhere in this project, just at
  the browser-event layer instead of the message-bus layer.
- **Graceful degradation / progressive fallback** — three distinct client capability tiers
  (GPS online, BLE offline on supported browsers, no-Bluetooth-at-all on iOS) each get their
  own UI state rather than one path failing silently.
- **Rolling identifiers derived from a locally-held secret** — the client-side half of T024
  v2's concept (same mechanism Apple/Google's Exposure Notification system uses): broadcast
  values rotate every 5 minutes without any server round-trip, because they're derived from a
  seed the client already holds.
- **Database per Service / API Gateway** — `BleDiscoveryService` only ever talks to
  discovery-service's routes through the gateway's `/discovery` prefix; it has no knowledge of
  discovery-service's internals (Redis candidate scoping, `ble_seeds` table, etc.).

## Agent implementation notes
- Key files to create (paths from project root, Angular module-based convention — no
  standalone components):
  - `src/frontend/src/app/discovery/services/ble-discovery.service.ts`
  - Whatever BLE scan UI component T064's discovery feature module already defines a slot for
    (e.g. `src/frontend/src/app/discovery/components/ble-scan-panel/`) — register it on
    the existing discovery `NgModule`, do not create a new feature module for this ticket
- Patterns to use: RxJS `fromEvent` + `takeUntil`/`switchMap` for the online/offline mode
  switch; inject `HttpClient` against the gateway-relative `/discovery/ble/seed` and
  `/discovery/ble/resolve` paths (match whatever base-URL/environment convention T063's Auth
  Flow ticket already established for calling the gateway).
- What NOT to do:
  - Do not implement `POST /scan/ble/token` or attempt BLE *advertising* from the browser —
    Web Bluetooth only supports scanning, never advertising; this was already corrected by the
    spec's own "Revised scope for PWA" section and further superseded by T024 v2's seed model.
  - Do not call `/scan/ble/seed` (or `/discovery/ble/seed`) from inside the `offline` event
    handler — see the Addendum above. Seed registration is a proactive, while-online
    operation.
  - Do not attempt to resolve profile details while offline — BLE mode only ever shows
    "Nearby user (offline)" with signal-strength-as-distance; resolution happens exclusively
    after reconnect via `/scan/ble/resolve`.
  - Do not build a native-companion-app integration — out of scope for this ticket (the spec
    explicitly flags true BLE advertising as a future mobile-app feature, not PWA scope).

## Known follow-ups
Backend review of `BleTokenServiceImpl.resolveTokens` (Connection/Discovery) found no
self-exclusion guard — unlike GPS discovery, nothing currently stops a user's own BLE
broadcast from resolving back to their own profile card if a client somehow detected its own
signal. This is an unpatched backend gap (cosmetic, not a security defect), not something to
route around here. If a resolved BLE card ever comes back representing the current user
themselves, handle it gracefully in the UI (e.g. silently omit it from the "Nearby offline
users" list) rather than assuming the backend will always filter it out.
