# T066 — Discovery Filters Panel

## Why this ticket exists
Travelers don't all want the same search — someone walking to a nearby station wants a tight 0.5 km radius and a tight departure window, while someone planning ahead wants a wider net. Without a filters panel, every user is stuck with the server's hardcoded defaults, which either floods them with irrelevant matches or hides nearby companions who fall just outside the fixed radius. This panel also carries the women-only safety toggle — but only for the users it legally and ethically applies to, since gender must never surface as a visible concept to anyone it doesn't belong to.

## What to build
- A slide-up filter panel component (bottom-sheet style) presented from the radar/discovery screen
- Radius slider, 0.5 km to 5 km
- Departure time window selector: ±15 / ±30 / ±60 min
- Women-only toggle, rendered only when the current user's gender is female — absent entirely (not just visually hidden) for all other users
- Wire the panel's selected values into `ScanSessionService` as the single source of truth for current filter state
- On next scan start, `ScanSessionService` includes the stored filter values in the `POST /scan/start` request body
- Apply REQUIREMENTS.md defaults when no filter has been explicitly changed yet: 1 km radius, ±30 min window

## Acceptance criteria
- [ ] Women-only toggle hidden for non-female users
- [ ] Filter changes apply on next scan start
- [ ] Default values match REQUIREMENTS.md (1 km, ±30 min)

## Patterns demonstrated
- Module-based Angular architecture: the filter panel is a declared component within its feature's NgModule, never a standalone component, per this project's Angular Rules.
- Single Responsibility: the filter panel component only renders controls and emits selection changes; `ScanSessionService` is the one place that owns and persists filter state.
- Single source of truth: `ScanSessionService` is the only place filter values live, so the panel UI and the scan-start request can never drift out of sync.

## Agent implementation notes
- Key files to create (paths indicative — confirm exact feature module location from T064's output):
  - `src/app/features/discovery/components/discovery-filters-panel/discovery-filters-panel.component.ts` (+ `.html`, `.css`)
  - Update to `src/app/features/discovery/services/scan-session.service.ts` (or wherever T064 created it) to add filter state fields and include them in the `POST /scan/start` payload
  - Registration of the new component in the relevant feature `NgModule` (not standalone)
- Patterns to use:
  - Reactive form controls (or two-way bound simple fields) for the slider, time-window selector, and toggle
  - Guard clause / early-return style for the gender check that decides whether to render the women-only toggle, consistent with this project's preference for early returns over nested conditionals
- What NOT to do:
  - Do not render the women-only toggle in the DOM (even with `display: none` or `hidden` CSS) for non-female users — use a structural directive (e.g. `*ngIf`) so the control and its backing logic never exist in the DOM for a user it doesn't apply to. A visually-hidden-only approach still leaks that the feature exists and how it's wired, which runs counter to REQUIREMENTS.md §10's rule that gender is only ever used as a server-side filter predicate, never exposed.
  - Do not fetch or store the user's gender value anywhere the panel's own code can read it beyond the single boolean/condition needed to decide visibility — don't introduce a new client-side gender field if one isn't already exposed by an existing profile service from an earlier ticket.
  - Do not create the component as a standalone Angular component — this project is module-based only.
  - Do not send filter values directly from the component to the backend — always go through `ScanSessionService` so scan-start stays the single integration point.
  - Do not invent additional filter controls, routes, or persistence (e.g. localStorage) beyond what the spec and acceptance criteria describe.
