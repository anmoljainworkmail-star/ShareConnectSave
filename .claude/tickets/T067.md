# T067 — Connection Request Flow

## Why this ticket exists
This is the moment a traveler actually reaches out to another traveler — the core transaction the entire platform exists to broker. Everything upstream (profiles, discovery radius, trust scores) only matters if a user can tap "send," have the other person see it in real time, accept it, and land in a chat. If this flow is slow, silent, or loses events on a flaky connection, requests go unanswered, users assume the app is broken, and the platform's core promise — "find a travel companion nearby, right now" — fails at the last step.

## What to build
- Send button on `UserCardComponent` that calls `POST /connections` and transitions the card into a "Request sent" state.
- `NotificationService` (Angular) that subscribes to the SignalR notifications hub and listens for the `ConnectionRequest`, `RequestAccepted`, `RequestDeclined`, and `RequestExpired` events.
- On `ConnectionRequest` → show an in-app banner + play a sound.
- `InboundRequestComponent` with Accept / Decline buttons, displaying the sender's card.
- On `RequestAccepted` → navigate to chat.
- On `RequestDeclined` / `RequestExpired` → show a toast with the correct message.

## Technical specification
- Send button on `UserCardComponent` → calls `POST /connections`, shows "Request sent" state.
- `NotificationService` (Angular) subscribes to SignalR hub. On `ConnectionRequest` event → shows in-app banner + sound.
- `InboundRequestComponent` — Accept / Decline buttons, shows sender's card.
- On `RequestAccepted` event → navigate to chat.
- On `RequestDeclined` / `RequestExpired` → show toast.

## Acceptance criteria
- [ ] Full send → accept → chat navigation works
- [ ] Decline and expiry show correct feedback
- [ ] SignalR reconnects automatically on connection drop

## Patterns demonstrated
- **Observer (via SignalR events)** — `NotificationService` reacts to `ConnectionRequest` / `RequestAccepted` / `RequestDeclined` / `RequestExpired` events pushed from the server; it doesn't poll, and the server doesn't need to know who's listening.
- **Single Responsibility** — `NotificationService` only owns the hub connection and event dispatch; it doesn't contain navigation or UI rendering logic itself, it delegates those to components/routing.
- **Module-based Angular architecture** — `InboundRequestComponent` and the connection-request UI belong to a feature NgModule per the project's Angular Rules (no standalone components).

## Agent implementation notes
- Key files to create (paths from project root):
  - `src/frontend/src/app/core/services/notification.service.ts` — SignalR hub subscription + event dispatch
  - `src/frontend/src/app/features/connections/components/inbound-request/inbound-request.component.ts` (+ `.html`/`.css`) — Accept/Decline UI
  - Updates to `UserCardComponent` (from T064) to add the Send button and "Request sent" state
  - Connections feature module routing/wiring as needed to host `InboundRequestComponent`
- `InboundRequestComponent` reuses `UserCardComponent` from T064 to render the sender's card — including its authenticated photo-fetch requirement. Do not build a second card component or duplicate photo-fetching logic.
- Use `HubConnectionBuilder` with `accessTokenFactory` for the notifications hub connection — see Known follow-ups below, this is not optional.
- What NOT to do:
  - Do not create a standalone component — everything here belongs to an NgModule per project Angular Rules.
  - Do not poll for connection request status — this flow is event-driven via SignalR, not request/response polling.
  - Do not hardcode the hub URL or token source — pull the JWT from T063's `AuthService`/token storage.
  - Do not skip reconnect handling — SignalR's automatic reconnect must be configured, not left to fail silently on a dropped connection.

## Known follow-ups
`NotificationService`'s SignalR `HubConnectionBuilder` must use `accessTokenFactory` pointed at T063's `AuthService` token storage — the gateway expects the JWT as a `?access_token=` query-string parameter for hub routes (`/hubs/notifications`), not an `Authorization` header, because browsers can't set custom headers on a WebSocket upgrade request. Do not soften or drop this.
