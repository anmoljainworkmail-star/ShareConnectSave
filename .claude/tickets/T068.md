# T068 — Chat UI

## Why this ticket exists
Chat is the one moment in the whole platform where two strangers who matched on intent to travel together actually talk to each other — if messages don't arrive in real time, or if "Met Successfully" doesn't clearly hand the user off to rating, the entire discovery-to-meetup flow ends in a dead screen and users lose trust in the app right when it matters most.

## What to build
- `ChatComponent` (module-based, registered in its feature module — no standalone components)
- Message list: reverse scroll, newest message at the bottom
- Text input + send button
- "Met Successfully" button — prominent, positioned above the input
- Header showing both users' names
- Offline banner shown when the SignalR connection drops; message input disabled while offline
- SignalR subscription to `ChatHub`:
  - On `ChatOpened` event → navigate to this component
  - On `ChatClosed` event → navigate to the rating screen
- "Met Successfully" tap → confirmation dialog → on confirm, proceed to rating screen

## Technical specification
`ChatComponent`:
- Message list (reverse scroll, newest at the bottom)
- Text input + send button
- "Met Successfully" button (prominent, above input)
- Shows both users' names in header
- Offline banner when disconnected from SignalR

On `ChatOpened` SignalR event → navigate here.
On `ChatClosed` event → navigate to rating screen.

## Acceptance criteria
- [ ] Messages appear in real-time without refresh
- [ ] Met Successfully → confirmation dialog → rating screen
- [ ] Offline state shows banner, input disabled

## Patterns demonstrated
- **Observer (via events)** — the `ChatHub` SignalR connection pushes `ChatOpened`/`ChatClosed`/message events to subscribers without the hub needing to know who's listening; `ChatComponent` reacts independently, same shape as the Kafka Observer usage elsewhere in the project.
- **Single Responsibility** — `ChatComponent` only renders chat state and forwards user actions; it does not own the SignalR connection lifecycle itself (that belongs to a chat connection service), keeping the component focused on presentation.
- **Database per Service / no-history-by-design** — the UI never requests or caches a message history endpoint, because Chat Service's MongoDB TTL index is the sole source of truth for message lifetime; the frontend reflects that boundary rather than working around it.

**This is a visually-risky screen with an already-built, tech-lead-approved reference mockup — match it exactly, do not improvise from the written spec alone.**

- The `angular-pwa` skill file has a "Visual reference" section pointing to `FIGMA_SPEC.md` and an approved reference mockup for **Screen 12 — Chat** at https://claude.ai/artifact/CAu6pBZqysAqa8yKct6jrw. Match that mockup's sent/received bubble styling, the system-message treatment, and the always-visible "Met Successfully" button (including its pulse animation) pixel-for-pixel — do not reimplement from the written spec text alone.
- What NOT to do:
  - Do not persist message history client-side beyond the live session (no local cache, no IndexedDB store of past messages) — this directly violates the "no history endpoint exists by design" requirement from REQUIREMENTS.md.
  - Do not build this as a standalone component — it must belong to a feature NgModule.
  - Do not add a history/export/download affordance of any kind, even as a stub.
  - Do not let the "Met Successfully" action skip the confirmation dialog.
  - Do not silently retry or hide SignalR disconnects — the offline banner and disabled input are required, not optional polish.

## Known follow-ups
`ChatComponent`'s SignalR `HubConnectionBuilder` for `ChatHub` must use `accessTokenFactory` pointed at T063's `AuthService` token storage — the gateway expects the JWT as a `?access_token=` query-string parameter for hub routes (`/hubs/chat`), not an `Authorization` header. Do not soften or drop this.
