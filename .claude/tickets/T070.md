# T070 — Profile + Settings

## Why this ticket exists
Every traveler on the platform needs a trustworthy identity and control over when they're discoverable — this ticket builds the two screens that make that possible. Without a working `ProfileComponent`, a user can't correct their name, set a verifiable photo, or declare the language they'll coordinate meetups in. Without `SettingsComponent`, a user has no manual way to go invisible (Not available) when they step away from the app, and no way to opt into women-only mode, a safety feature that depends entirely on gender being set correctly and permanently. Get the photo-fetch treatment wrong here and profile/account photos silently 401 instead of rendering; get the shared `status` field wrong and a user can be stuck "visible" when they think they've hidden themselves, or vice versa — both are trust-breaking failures for a platform whose entire premise is safe discovery.

## What to build
- `ProfileComponent` — edit name, upload/display photo, preferred language, gender (one-time set)
- `SettingsComponent` — status toggle (Looking / Not available), women-only mode toggle (gender-conditional), account info display
- Multipart photo upload call to the User Service (POST, whole file, not chunked)
- Authenticated photo-fetch for displaying the current profile photo (reuse, don't reimplement, the helper built for `UserCardComponent` / in T064/T069)
- Read/write integration with the shared `status` field, which is also written by T064's Start Scan / exit scan lifecycle

## Technical specification
`ProfileComponent` — edit name, photo (upload), preferred language, gender (one-time set, cannot change after first scan). Displaying the CURRENT photo (before/after upload) needs the same authenticated-fetch treatment as `UserCardComponent` (REQUIREMENTS.md §2) — a bare `<img src="{{photo_url}}">` will 401.
`SettingsComponent` — status toggle (Looking / Not available), women-only mode toggle (conditional on gender), account info. This toggle is one of TWO places `status` gets written — see T064's Start Scan / exit lifecycle for the other. Toggling here must work correctly regardless of whether a scan is currently active (e.g. flipping to "unavailable" from Settings while radar is still open on another tab/screen).

## Acceptance criteria
- [ ] Gender field locked after first scan session
- [ ] Women-only toggle only visible for female users
- [ ] Profile photo upload works (multipart POST to User Service)
- [ ] Current profile photo displays correctly via an authenticated fetch, not a bare `<img src>`
- [ ] Status toggle reflects the current value correctly even when it was last changed by starting/exiting a scan (T064), not just by this component itself

## Patterns demonstrated
- **Encapsulation of a cross-cutting concern** — the authenticated photo-fetch logic lives in one shared helper/service, not duplicated per component, so every photo display point gets the same auth treatment for free.
- **Single source of truth** — `status` is backend-owned state written from two independent UI entry points (Settings toggle, T064 scan lifecycle); the frontend must treat the server value as authoritative rather than caching a stale local copy.
- **Server-side authorization predicate** — women-only mode is enforced as a filter in the Discovery Service query, never trusted or re-implemented client-side; the frontend only shows/hides the toggle based on gender, it doesn't enforce the filtering itself.
- **Immutable-after-first-use field** — gender locking after the first scan session is a one-way state transition, guarding a safety-critical value (women-only mode eligibility) against post-hoc tampering.

## Agent implementation notes
- Key files to create (paths from project root):
  - `src/frontend/src/app/features/profile/profile.component.ts` (+ `.html`)
  - `src/frontend/src/app/features/profile/settings/settings.component.ts` (+ `.html`)
  - `src/frontend/src/app/features/profile/profile.module.ts` (module-based, lazy-loaded via `loadChildren` — no standalone components)
  - Reuse/extend the existing photo-service or auth-fetch helper introduced in T064/T069 rather than writing a second implementation
- Specific patterns to use:
  - Reuse the authenticated photo-fetch helper from T064/T069 — fetch via `HttpClient`/`fetch()` with the Authorization header attached, convert the response to a blob URL, bind that blob URL in the template. Do not reimplement this per component.
  - Treat `status` as shared mutable state owned by the backend. Both this ticket's Settings toggle and T064's Start/Stop Scan flow write to the same backend field — the component must read the current value from the User Service on load/focus rather than trusting a locally cached value that could have drifted if the user started/stopped a scan elsewhere.
  - Gender field: once a first scan session has occurred, the form control must be rendered disabled/read-only — this is a one-time lock, not just a UI suggestion; don't rely solely on disabling the input client-side if the backend doesn't also enforce it (confirm against whatever the User Service already returns for lock state).
- What NOT to do:
  - Do not render the profile photo with a bare `<img src="{{photo_url}}">` — it will 401 at the gateway, since every route except `POST /auth/google` requires a valid JWT, including static photo files.
  - Do not make the gender field editable after a first scan — this is an acceptance criterion, not a nice-to-have.
  - Do not show the women-only toggle to non-female users — gender must never be exposed to other users and the toggle itself must be conditionally rendered, not just conditionally functional.
  - Do not let this component maintain its own independent copy of `status` that can go stale relative to what T064's scan lifecycle writes — always defer to the backend value.
  - Do not build this as a standalone Angular component — it must belong to a NgModule per the project's Angular Rules.
