# T072 — Offline State Handling

## Why this ticket exists
A traveler loses signal mid-trip — a tunnel, a rural stretch, a dead zone between cities — and right now the app has no coherent answer for what happens next: screens that silently fail to load, a chat box that looks usable but isn't, API errors surfacing as raw JSON. This ticket is the glue ticket: it doesn't build offline capability itself (T062 already caches static screens via the service worker, T065 already built BLE discovery fallback), it builds the single `OfflineService` that detects the offline/online transition once and tells every other part of the app — profile screens, discovery, chat — to switch into its already-built offline behavior. Without it, each feature would reinvent its own online/offline check, with inconsistent timing and inconsistent messaging, and the user would get a different, confusing signal depending on which screen they happen to be on when connectivity drops.

## What to build
- `OfflineService` (Angular injectable, app-wide singleton) that listens for browser `online`/`offline` events and exposes current connectivity state to the rest of the app
- Wiring so that, when offline:
  - Static cached screens (e.g. profile) continue to load from the service worker cache (consumes T062, does not reimplement it)
  - Discovery switches to BLE mode (consumes T065, does not reimplement it)
  - Chat shows an offline banner and disables the message input
- A generic "You appear to be offline" toast/message shown whenever an API call fails because the service worker fallback kicked in, replacing any raw HTTP error object the user would otherwise see

## Technical specification
`OfflineService` — monitors `online`/`offline` events. When offline:
- Static cached screens work
- Discovery switches to BLE (T065)
- Chat shows offline banner, disables input
- All API error responses from service worker fallback → show user-friendly message

## Acceptance criteria
- [ ] Profile screen loads from cache when offline
- [ ] Chat input disabled when SignalR disconnected
- [ ] API failure → toast "You appear to be offline" instead of raw error

## Patterns demonstrated
- **Single Responsibility** — `OfflineService` only tracks and broadcasts connectivity state; it does not itself implement caching, BLE scanning, or chat UI — those stay owned by T062, T065, and the chat module respectively.
- **Observer (via events)** — `OfflineService` reacts to the browser's native `online`/`offline` events and, in turn, other modules (discovery, chat) subscribe to its state without it needing to know who's listening.
- **Centralized cross-cutting concern** — connectivity detection is handled in one place and consumed everywhere, the same shape as the API Gateway handling JWT validation once instead of per-service, preventing drift between screens.

## Agent implementation notes
- Key files to create (paths from project root):
  - `src/frontend/src/app/core/services/offline.service.ts` — the `OfflineService` itself (core/singleton, provided in root)
  - Update/inject into the chat feature module's component to disable input and show the offline banner when `OfflineService` reports offline or SignalR is disconnected
  - Update/inject into the discovery feature module to trigger the existing T065 BLE fallback when `OfflineService` reports offline
  - A shared toast/snackbar utility call (use whatever shared notification mechanism already exists in `SharedModule`) for the "You appear to be offline" message, wired into the HTTP error interceptor/service worker fallback path
- This is the integration point for T062 (service worker caching), T065 (BLE discovery), T068 (chat offline banner) — `OfflineService` is the single source of truth for connectivity state; do not add separate `navigator.onLine` checks or separate `online`/`offline` listeners inside the discovery or chat modules. They must consume `OfflineService`, not duplicate it.
- All components/services here must belong to an NgModule per project-wide Angular rules — no standalone components.
- What NOT to do:
  - Do not show raw `HttpErrorResponse` objects or stack traces to the user — always route through the friendly "You appear to be offline" message when the failure is connectivity-related
  - Do not re-implement service worker caching logic or BLE scanning logic in this ticket — only consume what T062 and T065 already expose
  - Do not add new acceptance criteria beyond the three listed above
  - Do not scatter `navigator.onLine` checks across multiple components — centralize detection in `OfflineService`
