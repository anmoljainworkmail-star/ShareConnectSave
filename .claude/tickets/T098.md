# T098 — Kestrel Limits Tuning

## Why this ticket exists
The gateway is the one true front door every request in this platform passes through, and it's
also the only service proxying long-lived SignalR WebSocket connections (Chat Service's and
Notification Service's hubs) through YARP — so Kestrel's own connection and upgrade limits matter
more here than anywhere else in the platform, and nothing has ever configured them past ASP.NET
Core's defaults. A plain HTTP request and a SignalR connection are fundamentally different shapes
of resource consumption (seconds vs. indefinitely-open), and today both are governed by whatever
Kestrel does out of the box, with no deliberate decision behind either.

## What to build
- `Program.cs`: configure `KestrelServerOptions` via `builder.WebHost.ConfigureKestrel(...)`,
  setting `Limits.MaxConcurrentConnections`, `Limits.MaxConcurrentUpgradedConnections` (the
  WebSocket-upgrade-specific ceiling — counted and enforced completely separately from the plain
  connection limit, and the setting this ticket exists to teach, since nothing else in this
  project ever distinguishes the two), `Limits.KeepAliveTimeout`, and
  `Limits.RequestHeadersTimeout` — every value read from an environment variable, none hardcoded,
  per this project's own no-hardcoded-config rule.
- A short explanation (code comment above the `ConfigureKestrel` call, or an addition to the
  `dotnet-mvc-controllers` skill file) of why `MaxConcurrentUpgradedConnections` exists as its own
  separate setting: once a SignalR connection upgrades, it stays open indefinitely, so it behaves
  nothing like a normal few-hundred-millisecond HTTP request for capacity-planning purposes, and
  one shared counter for both would let a burst of chat connections starve ordinary API traffic
  (or vice versa).

## Technical specification
```csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.Limits.MaxConcurrentConnections = int.Parse(
        Environment.GetEnvironmentVariable("KESTREL_MAX_CONCURRENT_CONNECTIONS") ?? "20");
    options.Limits.MaxConcurrentUpgradedConnections = int.Parse(
        Environment.GetEnvironmentVariable("KESTREL_MAX_CONCURRENT_UPGRADED_CONNECTIONS") ?? "10");
    options.Limits.KeepAliveTimeout = TimeSpan.FromSeconds(int.Parse(
        Environment.GetEnvironmentVariable("KESTREL_KEEPALIVE_TIMEOUT_SECONDS") ?? "30"));
    options.Limits.RequestHeadersTimeout = TimeSpan.FromSeconds(int.Parse(
        Environment.GetEnvironmentVariable("KESTREL_REQUEST_HEADERS_TIMEOUT_SECONDS") ?? "10"));
});
```
Defaults are deliberately small (learning-sized, same spirit as T097's Tomcat values) so the
limit is reachable and observable in local testing, not a production sizing recommendation.
Applied only to the gateway — this ticket is deliberately scoped to one representative .NET
service, not all four.

## Acceptance criteria
- [ ] All four Kestrel limits configured from environment variables, no hardcoded numbers
- [ ] A plain HTTP connection and a SignalR WebSocket upgrade are demonstrably counted against
      two different limits — verified manually by filling `MaxConcurrentConnections` with plain
      HTTP requests and confirming a new SignalR connection still succeeds up to its own separate
      `MaxConcurrentUpgradedConnections` ceiling
- [ ] Plain-English explanation of the upgraded-vs-plain distinction exists in a code comment or
      the skill file

## Patterns demonstrated
- **Resource Partitioning by Connection Type** — the same "one shared counter quietly defeats the
  point of separating risk shapes" idea CLAUDE.md already documents for partitioned rate limiting
  (T013's per-IP/per-user/per-phone counters), applied here to connection accounting instead of
  request-rate accounting.

## Agent implementation notes
- Key file: `api-gateway/Program.cs`.
- What NOT to do: don't change YARP's own proxy/destination timeout settings in this ticket —
  scope is Kestrel's own connector layer underneath the proxy, not the reverse-proxy layer YARP
  adds on top of it. That's a separate, equally real concern, deliberately out of scope here.
