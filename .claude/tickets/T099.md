# T099 — Load Test: Connector Saturation

## Why this ticket exists
T097 made discovery-service's Tomcat connector settings visible and controllable; this ticket is
the only place in the whole phase that actually proves those settings do something, by
deliberately undersizing the pool on purpose, watching requests queue and fail, then watching the
exact same failure disappear once the pool is sized correctly. This is the same "see it fail, see
it fixed" payoff every real gotcha in this project's README has already earned its place by
demonstrating — reading `threads.max: 10` in a YAML file and assuming you understand its
consequence is exactly the kind of "passes on paper" gap this project keeps finding everywhere
else; this ticket closes that gap for the connector layer specifically.

## What to build
- Reuse and extend T086's existing k6 script (against discovery-service's `/scan/nearby` or
  whichever endpoint T086 already targets) rather than writing a second, parallel script.
- **Run 1 — "broken":** discovery-service running with T097's deliberately small
  `threads.max: 10` / `accept-count: 5`, k6 ramping to a virtual-user concurrency well past 15.
  Capture k6's own latency/error summary, plus `tomcat.threads.busy` sampled during the run
  (a short polling script or manual `curl` loop against `/actuator/metrics/tomcat.threads.busy`
  is sufficient) showing threads pinned at `threads.max` while requests queue or time out.
- **Run 2 — "fixed":** bump `threads.max`/`accept-count` (via env var override, no file edits
  needed) to comfortably cover the same k6 concurrency, re-run the identical script, capture the
  same metrics showing no saturation.
- A short results write-up (in the ticket's own QA file) with both runs' numbers placed side by
  side — this is the recorded evidence the acceptance criteria are checked against, not a
  prose assertion that it worked.

## Technical specification
No new application code beyond what T097 already externalized — this ticket toggles the two
already-env-var-driven config values between runs and records what k6 and Actuator report. This
is deliberately a measurement-and-documentation exercise, not a code-writing one.

## Acceptance criteria
- [ ] Run 1 (undersized pool) shows measurably worse p95/p99 latency and/or a non-zero error rate
      compared to Run 2, with `tomcat.threads.busy` visibly pinned at the configured `threads.max`
      during Run 1
- [ ] Run 2 (correctly sized for the same k6 concurrency) shows no connector-induced errors
- [ ] Both runs' k6 summary output and Actuator metric samples are captured verbatim in
      `.claude/qa/T099.qa.md` as recorded evidence

## Patterns demonstrated
- **Empirical Capacity Validation** — a configuration value only means something once it has
  actually been measured under the load it exists to defend against; this ticket is this
  project's first example of validating a tunable by breaking it on purpose rather than trusting
  that a number in a config file behaves the way its name suggests.
