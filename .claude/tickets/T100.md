# T100 — Graceful Shutdown & Connection Draining

## Why this ticket exists
Every service in this platform already runs under Docker Compose, and `docker compose stop`,
`restart`, or any future redeploy all send the process a `SIGTERM` — but nothing in the first 96
tickets has ever asked what happens to a request that's already in flight at that exact moment.
Today the honest answer, for every single service, is "whatever the framework's untouched default
does," never a decision anyone actually made. This ticket turns that into a deliberate choice on
the two services T097/T098 already tuned the connector layer for.

## What to build
- **discovery-service:** enable Spring Boot's graceful shutdown
  (`server.shutdown: graceful`, `spring.lifecycle.timeout-per-shutdown-phase`). Demonstrate with a
  deliberately slow endpoint (a temporary artificial delay added to an existing one, or a new
  throwaway test endpoint in the same spirit as T056's `/admin/ping`) that a request already in
  progress completes successfully instead of being cut off mid-response when the container stops.
- **api-gateway:** hook `IHostApplicationLifetime.ApplicationStopping` to log when shutdown
  begins, and make the host's shutdown grace period explicit via
  `builder.Host.ConfigureHostOptions(opts => opts.ShutdownTimeout = ...)` rather than relying on
  .NET's implicit default.
- A documented before/after demonstration: send a slow request, run `docker compose stop
  <service>` mid-request, record the client's outcome without graceful shutdown enabled, then
  repeat with it enabled and record the difference.

## Technical specification
```yaml
# discovery-service application.yml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
```
```csharp
// api-gateway Program.cs
builder.Host.ConfigureHostOptions(opts => opts.ShutdownTimeout = TimeSpan.FromSeconds(20));

var lifetime = app.Services.GetRequiredService<IHostApplicationLifetime>();
lifetime.ApplicationStopping.Register(() =>
    Log.Information("Graceful shutdown starting — draining in-flight connections"));
```

## Acceptance criteria
- [ ] Without graceful shutdown enabled: a slow in-flight request is demonstrably cut off when
      `docker compose stop` is issued mid-request (captured as the "before" evidence)
- [ ] With graceful shutdown enabled: the identical slow request completes successfully even
      though `docker compose stop` was issued mid-request
- [ ] Both services log a clear, timestamped message the moment shutdown begins, before any
      in-flight request is actually affected

## Patterns demonstrated
- **Graceful Degradation at the Infrastructure Boundary** — the same idea behind every circuit
  breaker fallback already in this project, just pointed at "my own process is about to die"
  instead of "a dependency I depend on is struggling."

## Agent implementation notes
- Key files: `discovery-service/src/main/resources/application.yml`, `api-gateway/Program.cs`.
- What NOT to do: don't touch Kafka consumer shutdown behavior in this ticket (does a
  `@KafkaListener`/Confluent consumer finish or abandon its current record on `SIGTERM`?) — that's
  a separate, real concern this ticket deliberately doesn't cover.

## Known follow-ups
- Kafka consumer graceful shutdown (finishing vs. abandoning an in-flight record on `SIGTERM`) is
  a related gap this ticket doesn't address — candidate for a future ticket if this bonus phase is
  ever extended further.
