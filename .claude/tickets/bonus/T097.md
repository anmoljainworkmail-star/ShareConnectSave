# T097 — Tomcat Connector Tuning

## Why this ticket exists
Every request to a Java service in this platform passes through Tomcat before Spring MVC's
dispatcher — or any of this project's own code — ever sees it: Tomcat is what actually accepts
the TCP connection, decides whether a worker thread is free to handle it, and queues it if not.
Nothing in the first 96 tickets has ever looked at this layer; every service has been running on
whatever Spring Boot's untouched defaults happen to be (200 max threads, 100-deep accept queue),
invisible and unmeasured. This ticket makes that layer visible and deliberately configured on one
representative service, so T099 has something real to break and fix on purpose.

## What to build
- Explicit `server.tomcat.threads.max`, `server.tomcat.threads.min-spare`,
  `server.tomcat.accept-count`, `server.tomcat.connection-timeout`, `server.tomcat.max-connections`
  in discovery-service's `application.yml`, under the `dev` profile only — small, deliberately
  visible numbers (e.g. `threads.max: 10`, `accept-count: 5`) instead of Spring Boot's much larger
  invisible defaults, with a comment explaining these are learning-sized values for observing
  saturation, not production sizing.
- Confirm Actuator exposes Tomcat's own thread-pool metrics (`tomcat.threads.busy`,
  `tomcat.threads.config.max`, `tomcat.threads.current`) via
  `management.endpoints.web.exposure.include` already covering `metrics` (add it if not already
  present) — this is what makes the pool's live state observable from outside the JVM.
- A short plain-English explanation — in the `java-spring-boot` skill file or a new
  `docs/connector-tuning.md` — of the acceptor-thread → worker-thread-pool → OS-level
  accept-count backlog chain, and exactly what happens to the request that arrives after both the
  thread pool AND the accept-count queue are full (the OS refuses the connection outright —
  a failure mode nothing in this project has ever demonstrated).

## Technical specification
```yaml
# application.yml, dev profile
server:
  tomcat:
    threads:
      max: 10          # learning-sized — forces visible saturation under modest load (see T099)
      min-spare: 2
    accept-count: 5     # OS-level backlog once all 10 worker threads are busy
    connection-timeout: 20s
    max-connections: 50
```
Leave `prod` profile unset (or explicitly commented) with a note that real sizing requires real
measured load, which this project does not simulate at production scale.

## Acceptance criteria
- [ ] `application.yml`'s `dev` profile has explicit, commented Tomcat connector settings
      matching the values above
- [ ] `GET /actuator/metrics/tomcat.threads.busy` and
      `GET /actuator/metrics/tomcat.threads.config.max` both return real numbers reflecting the
      configured values (verified manually against a running container)
- [ ] A plain-English explanation of acceptor thread → worker thread pool → OS accept-count
      backlog exists in the skill file or a new docs file, written for someone who has never
      heard the term "connector" before

## Patterns demonstrated
- **Explicit Configuration over Invisible Defaults** — the same "no hardcoded config, make every
  tunable visible" instinct this project already applies to env vars (CLAUDE.md's own rule),
  applied one layer lower, to the embedded web server itself rather than application code.

## Agent implementation notes
- Key files: `discovery-service/src/main/resources/application.yml` (edit), plus either an
  addition to `.claude/skills/java-spring-boot.md` or a new `docs/connector-tuning.md`.
- What NOT to do: don't touch `prod` profile sizing without real load data; don't restrict or
  authenticate Actuator endpoints — this project's convention (every other service) is
  unauthenticated Actuator for local/dev visibility, not a security boundary.

## Known follow-ups
- Real production connector sizing depends on measured request duration and desired concurrency
  under genuine traffic — explicitly out of scope for a learning-sized bonus phase. T099's load
  test is what gives these specific numbers actual observable meaning.
