# T102 — User Service: Admin Internal Account-Status Endpoints

## Why this ticket exists
T057 (Admin Service's review queue) shipped already calling three User Service endpoints that
don't exist in the real codebase. Two of them were self-documented as `KNOWN GAP` in
`UserServiceClient.java`'s own javadoc by whoever implemented T057; a third (`GET /users/{id}`
for the admin user-detail view) was not flagged but has the same root problem — it hits the
real, already-shipped `GetPublicProfile` endpoint, but that endpoint returns
`PublicUserProfileDto` (`id`, `name`, `photo_url`, `identity_badge` — the privacy-minimized
shape built for peer discovery), not the `account_status`/`suspended_at`/`display_name` shape
`UserServiceClientImpl.UserProfileDto` expects. Every field on the admin's "full user view"
silently deserializes to `null` instead of throwing, which is worse than the other two calls'
honest 404/connection-refused failure. Without this ticket: `GET /admin/queue` can never list a
single suspended user, `GET /admin/users/:id` always shows a blank profile section, and T059
(Account Suspend) is explicitly blocked — its own ticket says "do not start building
`UserServiceClient`'s suspend call... until that contract decision is made."

## What to build
- A new `AccountStatus` field on the `User` entity (`src/services/user-service/Models/User.cs`)
  — a new EF Core migration, enum-like string column (`"active"` / `"suspended"`), **separate
  from the existing `Status` column** (which is the user-owned discovery-availability toggle —
  `looking`/`unavailable` — a completely different axis per that property's own existing
  comment). Default `"active"` for every existing and new row.
- Three new **internal-only** endpoints, reachable only via direct Docker-network calls (same
  trust boundary as the existing `GET /users/internal/{id}/fcm-token` precedent — no gateway
  route, no JWT) — deliberately on a `/users/internal` sub-path so they never collide with, or
  dilute the privacy guarantee of, the existing public `GET /users/{id}` discovery endpoint:
  - `GET /users/internal?accountStatus=suspended` → `SuspendedUserDto[]`
  - `GET /users/internal/{id}` → `UserProfileDto` (the admin-detail shape)
  - `PUT /users/internal/{id}/account-status` → body `{"account_status": "active"|"suspended"}`,
    returns the same `UserProfileDto` shape
- Response DTOs matching `UserServiceClientImpl`'s nested wire records **exactly** (admin-service
  already shipped these — this ticket's job is to produce JSON that satisfies them, not to design
  a new contract from scratch):
  - `{"user_id": "...", "display_name": "...", "suspended_at": "..."}` for the list
  - `{"user_id": "...", "display_name": "...", "account_status": "...", "suspended_at": "..."}`
    for the single-user and PUT responses
  - `display_name` maps from `User.Name`; `suspended_at` is a new nullable `DateTime?` column,
    set only by the PUT endpoint's transition into `"suspended"`, cleared back to `null` on a
    transition into `"active"`.

## Technical specification
Verbatim source for this gap: admin-service's `UserServiceClient.java` (`getSuspendedUsers`,
`getUser`, `setStatus` javadoc) and `UserServiceClientImpl.java` (actual WebClient calls),
already shipped in T057. SPECS.md's own T057 spec only says "status = `suspended` in User
Service, pulled via HTTP to User Service" — it never specified the endpoint shape, which is why
the gap existed silently until this audit. This ticket is the companion contract T057's own
client code already assumes.

## Acceptance criteria
- [ ] `GET /users/internal?accountStatus=suspended` returns every user whose `AccountStatus` is
      `"suspended"`, in the `SuspendedUserDto[]` shape above
- [ ] `GET /users/internal/{id}` returns 404 for a non-existent id, and the `UserProfileDto` shape
      above for a real one
- [ ] `PUT /users/internal/{id}/account-status` persists the new status, sets/clears
      `suspended_at` correctly, and returns the updated `UserProfileDto`
- [ ] A new EF Core migration adds `AccountStatus` (default `"active"`) and `SuspendedAt`
      (nullable) without touching the existing `Status` column's meaning or values
- [ ] Companion fix applied to admin-service's already-shipped `UserServiceClientImpl.java`:
      its three WebClient calls move from `/users` / `/users/{id}` / `/users/{id}/account-status`
      to `/users/internal` / `/users/internal/{id}` / `/users/internal/{id}/account-status`
- [ ] `UserServiceClient.java`'s `KNOWN GAP` javadoc comments (on `getSuspendedUsers` and
      `setStatus`) are removed/updated now that the endpoints exist

## Patterns demonstrated
- **Database per Service, enforced internally too** — even within User Service's own table, two
  conceptually different axes (discovery availability vs. account standing) get two separate
  columns instead of overloading one enum, the same lesson the `Status`/`IsOnboardingComplete`
  split (post-T018 fix) already taught for onboarding state vs. availability.
- **Internal-only endpoint boundary** — `/users/internal/...` is a trust boundary enforced by
  network topology (unreachable via the YARP gateway), not by a role check in code, matching the
  existing `GET /users/internal/{id}/fcm-token` precedent exactly.
- **Privacy by construction, preserved** — the fix deliberately does *not* add admin fields to
  the existing public `PublicUserProfileDto`/`GET /users/{id}`; a brand-new internal DTO keeps the
  public discovery contract exactly as privacy-minimized as T018/T049 originally designed it.

- Key files to create/change (paths relative to project root):
  - `src/services/user-service/Models/User.cs` — add `AccountStatus`, `SuspendedAt`
  - `src/services/user-service/Migrations/` — new migration (do not hand-edit the DB; this is a
    `dotnet ef migrations add` CLI command the Tech Lead runs, per the "CLI COMMANDS THE TECH LEAD
    RUNS, NOT YOU" rule)
  - `src/services/user-service/Dtos/` — new `AdminUserProfileDto` (or similarly named) record(s)
    matching the wire shapes above exactly; do not reuse `PublicUserProfileDto`
  - `src/services/user-service/Controllers/UserProfileController.cs` (or a new
    `AdminInternalController.cs`, developer's call — match whichever existing controller's own
    internal-endpoint convention is cleaner) — the three new `[HttpGet]`/`[HttpPut]` actions
  - `src/services/user-service/Services/UserProfileService.cs` + `IUserProfileService.cs` — new
    methods (`GetSuspendedUsersAsync`, `GetAdminProfileAsync`, `SetAccountStatusAsync`)
  - `src/services/admin-service/src/main/java/com/shareconnectsave/admin_service/client/UserServiceClientImpl.java`
    — update the three `.uri(...)` calls as described in Acceptance Criteria
  - `src/services/admin-service/.../client/UserServiceClient.java` — remove the now-stale
    `KNOWN GAP` comments
- What NOT to do:
  - Do not add `account_status`/`suspended_at` to `PublicUserProfileDto` or the existing public
    `GET /users/{id}` route — that would leak admin-only data to the peer-discovery contract.
  - Do not repurpose the existing `Status` column for account standing — it's the
    availability toggle; see its own comment for why that was already tried and reverted once.
  - Do not add a gateway route or JWT check for the three new endpoints — they are Docker-network
    internal only, same as the FCM-token precedent.
