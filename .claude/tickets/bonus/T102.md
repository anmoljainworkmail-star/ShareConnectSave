# T102 — User Service: Admin Internal Account-Status Endpoints

## Why this ticket exists

Admin Service's review queue (T057) and account suspension workflow (T059) depend on User Service endpoints that were assumed but never built. Currently, admin-service's `UserServiceClientImpl` calls public `/users` and `/users/{id}` paths expecting account management data, but those endpoints return discovery-privacy-minimized shapes that lack `account_status` and `suspended_at`. Without this ticket, the admin dashboard cannot query suspended users or manage account states end to end. This ticket closes the contract gap by adding three internal-only endpoints (reachable only within the Docker network trust boundary) that admin-service can actually call to view and modify account status.

## What to build

- **New columns on `User` entity:** `AccountStatus` (enum/string: Active/Suspended) and `SuspendedAt` (nullable DateTime), separate from the existing `Status` column (availability toggle).
- **Three new internal-only endpoints** (Docker-network reachable only, `/users/internal` prefix, no gateway route, no JWT):
  - `GET /users/internal?accountStatus=suspended` — list suspended users
  - `GET /users/internal/{id}` — fetch single user's account state
  - `PUT /users/internal/{id}/account-status` — update account status and set/clear `SuspendedAt` timestamp
- **Response DTOs** matching `UserServiceClientImpl`'s wire expectations exactly:
  - `{user_id, display_name, account_status, suspended_at}` shape for all three endpoints
  - Property names in snake_case; nullable fields handled per admin-service's deserializer
- **Update admin-service's `UserServiceClientImpl`:** Replace calls to public `/users` and `/users/{id}` paths with new `/users/internal/...` paths.

## Technical specification

Add an `AccountStatus` field to `User` (separate from the existing availability `Status` column)
plus three internal-only endpoints (Docker-network reachable only, same trust boundary as the
existing `GET /users/internal/{id}/fcm-token`): `GET /users/internal?accountStatus=suspended`,
`GET /users/internal/{id}`, and `PUT /users/internal/{id}/account-status`. Response shapes must
match admin-service's already-shipped `UserServiceClientImpl` wire DTOs exactly
(`user_id`/`display_name`/`account_status`/`suspended_at`). Companion fix: update
admin-service's `UserServiceClientImpl` to call the new `/users/internal/...` paths instead of
the public `/users`/`/users/{id}` paths it currently (incorrectly) targets.

## Acceptance criteria

- [ ] All three internal endpoints return the exact wire shapes `UserServiceClientImpl` expects
- [ ] `AccountStatus`/`SuspendedAt` are new columns, independent of the existing `Status` column
- [ ] admin-service's `UserServiceClientImpl` updated to call the new internal paths
- [ ] `UserServiceClient.java`'s `KNOWN GAP` comments removed now that the gap is closed

## Patterns demonstrated

- **Dependency Inversion:** Admin Service depends on abstractions (`IUserServiceClient`), not concrete HTTP details. User Service can change its internal endpoints without breaking admin-service's business logic.
- **Database per Service:** User Service owns its own schema, including `AccountStatus` and `SuspendedAt`. Admin Service reads via HTTP, never direct DB access, preserving service boundary.
- **Trust Boundary / Internal-Only Endpoints:** These endpoints sit behind the Docker network boundary (same as existing `GET /users/internal/{id}/fcm-token`) — never exposed to public clients. They answer internal service-to-service calls only.
- **API Contract Adherence:** Wire shape must match exactly (`user_id`, `display_name`, `account_status`, `suspended_at` — note snake_case naming). This teaches that contracts are bidirectional — clients declare what they expect, servers must deliver exactly that shape.

## Agent implementation notes

**Key files to create/modify:**
- `src/services/user-service/Models/User.cs` — add `AccountStatus` enum and `SuspendedAt` nullable DateTime column
- `src/services/user-service/Migrations/` — new migration for `AccountStatus` and `SuspendedAt` (Tech Lead runs `dotnet ef migrations add`)
- `src/services/user-service/Dtos/` (new) — `AdminUserProfileDto` record matching wire shape exactly (user_id, display_name, account_status, suspended_at)
- `src/services/user-service/Controllers/InternalUserController.cs` (new) — three endpoints: `GET /users/internal?accountStatus=suspended`, `GET /users/internal/{id}`, `PUT /users/internal/{id}/account-status`
- `src/services/user-service/Services/UserProfileService.cs` + interface — new methods for suspended users query, admin profile fetch, and account status updates
- `src/services/admin-service/src/main/java/com/shareconnectsave/admin_service/client/UserServiceClientImpl.java` — update HTTP paths from `/users` to `/users/internal/...`
- `src/services/admin-service/.../client/UserServiceClient.java` — remove `KNOWN GAP` comments

**Specific patterns to use:**
- Refer to `dotnet-mvc-controllers` skill for internal endpoint patterns and response DTO shapes
- Wire DTOs must use snake_case JSON property names (e.g. `[JsonPropertyName("user_id")]`)
- Internal endpoints should validate they're only callable within Docker network (no extra auth layer needed, trust boundary is network isolation)

**What NOT to do:**
- Do not expose `AccountStatus` or `SuspendedAt` in public `PublicUserProfileDto` or the existing public `GET /users/{id}` endpoint — that would leak admin-only data to peer-discovery clients.
- Do not repurpose or modify the existing `Status` column (availability toggle) for account standing — these are separate concerns.
- Do not add gateway routes or JWT validation for internal endpoints — they are Docker-network-internal only, same as the existing `GET /users/internal/{id}/fcm-token` precedent.
- Do not create a new migration by hand; wait for Tech Lead to run `dotnet ef migrations add` after entity model is ready.
