# T103 — Report Service: Report History by Target Endpoint

## Why this ticket exists
T057 (Admin Service's review queue) shipped already calling
`GET /reports?reportedId={userId}` on Report Service to show an admin a user's full report
history as part of `GET /admin/users/:id`. That endpoint doesn't exist — `ReportController` only
implements `POST /reports` (file a report) and `GET /reports/queue` (the escalated-only admin
queue, a different, narrower view). `ReportServiceClient.java`'s own `KNOWN GAP` javadoc already
flags this. Without this ticket, every admin user-detail lookup throws
`UpstreamUnavailableException` for its report-history section and
`ReviewQueueServiceImpl`'s degrade path (`reportHistoryUnavailable=true`) is what actually runs
in production today, not a real report history.

## What to build
- A new `GET /reports?reportedId={userId}` endpoint on the existing `ReportController`
  (`@RequestMapping("/reports")`), returning every report filed against that one user — the
  per-target counterpart to the existing escalated-only `/reports/queue`.
- Reuses `ReportRepository.findByReportedId(String)` — **this query method already exists** (it's
  how `ReportServiceImpl` counts existing reports against a target during T053's escalation
  check) and has never been exposed through a controller before. No new persistence code needed.
- Returns `List<ReportResponse>` — the exact same response type `POST /reports` and
  `GET /reports/queue` already use. Its fields (`id`, `reporter_id`, `reported_id`, `reason`,
  `connection_id`, `details`, `status`, `created_at`) are a superset of what admin-service's
  already-shipped `ReportServiceClientImpl.ReportDto` reads (`id`, `reporter_id`, `reported_id`,
  `reason`, `status`, `created_at`) — Jackson's `@JsonIgnoreProperties(ignoreUnknown = true)` on
  that client-side DTO already tolerates the two extra fields, so **no shape mismatch exists
  here** once the route is added; this is purely a missing route, not a missing or wrong contract
  (contrast with T102's `GET /users/{id}` finding).

## Technical specification
Verbatim source for this gap: admin-service's `ReportServiceClient.java` javadoc and
`ReportServiceClientImpl.java` (`GET /reports?reportedId=...`), already shipped in T057.
SPECS.md's T057 spec says only "report history (from Report Service)" with no endpoint shape —
same root cause as T102: the downstream contract was assumed, not specified, when T057 was
ticketed.

## Acceptance criteria
- [ ] `GET /reports?reportedId={userId}` returns every report (any status, not just escalated)
      filed against that one user, newest first (match `/reports/queue`'s existing sort
      direction unless a different order is more natural here — developer's call, document the
      choice)
- [ ] A user with zero reports filed against them returns an empty array, not a 404
- [ ] Response uses the existing `ReportResponse` type — no new DTO
- [ ] `ReportServiceClient.java`'s `KNOWN GAP` javadoc on `getReportHistory` is removed/updated
      now that the endpoint exists
- [ ] `contracts/openapi/report-service.yaml` gains this path (the contract file is already
      missing several shipped endpoints per T057's own review notes — this ticket does not need
      to backfill those, only add its own)

## Patterns demonstrated
- **Open/Closed, via an existing repository method** — `findByReportedId` was written for T053's
  internal escalation check and needed zero changes to serve this ticket's new external-facing
  endpoint; the repository's behavior didn't change, only a new caller was added above it.
- **Thin controller, delegating to the service layer** — matches this controller's own existing
  `getEscalatedQueue` precedent exactly: the controller does header reads and a guard clause (if
  this endpoint needs one — see implementation notes), `ReportServiceImpl` does the query.

## Agent implementation notes
- Key files to change (paths relative to project root, under
  `src/services/report-service/src/main/java/com/shareconnectsave/report_service/`):
  - `controller/ReportController.java` — new `@GetMapping` method, mapped at the class's existing
    `/reports` base path with a `reportedId` `@RequestParam`
  - `service/ReportService.java` + `ReportServiceImpl.java` — new method (e.g.
    `getHistoryForTarget(String reportedId)`) that calls the existing
    `reportRepository.findByReportedId(reportedId)` and maps via the existing `ReportMapper`
  - `contracts/openapi/report-service.yaml` — add the new path under `/reports`
- Decide and document: should this endpoint require `X-User-Role: admin` the same way
  `/reports/queue` does? It's only ever called by admin-service today (same direct Docker-network
  call pattern as `RatingServiceClientImpl`'s `/trust/{userId}` call), so the same admin-only
  guard clause `getEscalatedQueue` already uses is the consistent choice — don't leave it
  unauthenticated just because the only real caller happens to be trusted today.
- What NOT to do:
  - Don't add a new DTO — `ReportResponse` already carries every field needed.
  - Don't touch `GET /reports/queue` or its escalated-only filtering logic — this is a separate,
    additive endpoint, not a generalization of that one (same "deliberately separate, narrower
    concept" boundary `ReportServiceClient.java`'s own class comment already draws).
