# T104 — Admin Bulk-Expire Connections Endpoint

## Why this ticket exists

T059 (Account Suspend) needs to immediately clear all active connections when an admin suspends a user's account. Without this endpoint, suspended users would have orphaned pending or accepted connection requests lingering until T031's TTL expiry job runs, defeating the purpose of an immediate account action. This ticket provides the missing Connection Service endpoint so the admin suspend workflow completes end-to-end, letting T059 call a real endpoint instead of leaving a gap in the system.

## What to build

- `PUT /admin/connections/users/{userId}/expire-active` endpoint, callable only when `X-User-Role: admin` is present in the request header
- Service method that queries all `ConnectionRequest` records where the user is either `requester_id` or `recipient_id` **and** status is `PENDING` or `ACCEPTED`
- For each matched connection, transition the status to `EXPIRED` and publish a `connection.expired` event via the existing outbox-relay path (T032's producer, per-row — not a new bulk event type)
- Return HTTP 200 OK with a JSON body containing `{ "expiredCount": N }`, where N is the number of connections transitioned (zero is a valid, non-error response)
- Reject with HTTP 403 Forbidden if the `X-User-Role` header is missing or is not `admin`

## Technical specification

Add `PUT /admin/connections/users/{userId}/expire-active` to `ConnectionController` (or a new
`AdminConnectionController`, matching whichever shape fits the existing controller layout best),
callable only with `X-User-Role: admin`. Transitions every connection request where `userId` is
either `requester_id` or `recipient_id` and `status` is `PENDING` or `ACCEPTED` to `EXPIRED`, in a
single call — admin-service's suspend flow (T059) needs this to immediately clear a suspended
user's active connections rather than waiting for T031's per-request TTL expiry job. Reuses the
existing `connection.expired` Kafka producer path (T032's `OutboxRelay`) per-transitioned-row, same
as the TTL expiry job does — do not add a second Kafka producer or a bulk/summary event type.

## Acceptance criteria

- [ ] Every `PENDING`/`ACCEPTED` connection where the user is requester or recipient transitions to `EXPIRED`
- [ ] A `connection.expired` event is published per transitioned connection, via the existing outbox/relay path
- [ ] Returns `200 OK` with a count of connections expired (`0` is a valid, non-error result when the user had none active)
- [ ] Rejects with `403` when `X-User-Role` is not `admin`

## Patterns demonstrated

- **Authorization Guard Clause (early return):** The `X-User-Role: admin` check at the controller level rejects unauthorized requests immediately before any business logic runs, implementing the guard-clause pattern for cross-cutting security concerns.
- **Reuse of Existing Outbox Pattern:** Leverages T032's `connection.expired` producer and `OutboxRelay` mechanism per-row rather than creating a new bulk/summary event type, keeping event shape consistent and idempotency checks aligned — the same pattern that T031's TTL job uses.
- **Single Responsibility Principle (SOLID S):** The controller enforces the authorization boundary; the service handles the transition query and count logic; the `OutboxRelay` (separate component) publishes events. Each class has one reason to change.

## Agent implementation notes

**Key files to create/modify:**
- `src/services/connection-service/src/main/java/org/shared/connection/controller/ConnectionController.java` — add the new endpoint method (or create `AdminConnectionController.java` if the project keeps admin endpoints in a separate controller; check T029/T030 to see which style is established)
- `src/services/connection-service/src/main/java/org/shared/connection/service/ConnectionService.java` — add the service method that executes the bulk transition

**Patterns and references:**
- Follow java-spring-boot skill for service/controller layer structure and Spring `@Transactional` usage
- Reuse the existing T032 outbox-relay mechanism: for each transitioned connection, call the same Kafka producer that T031's TTL expiry job uses (do not create a new producer or event type)
- Query: select all `ConnectionRequest` rows where `(requester_id = :userId OR recipient_id = :userId) AND status IN ('PENDING', 'ACCEPTED')`, update all to status `'EXPIRED'` in a single transaction
- Per-row event publishing: after each connection is updated to EXPIRED, publish exactly one `connection.expired` event (same event type, same schema, same idempotency checks as T032)

**What NOT to do:**
- Do not add a second Kafka producer or a new bulk/summary event type like `connection.bulk-expired` — reuse the existing per-row producer
- Do not skip the `X-User-Role: admin` authorization check — guard the entire endpoint
- Do not create a new database transaction per row — wrap the entire bulk operation in one `@Transactional` method
- Do not return 200 OK with the list of expired connections themselves (verbose payload) — return only the count
- Do not assume the user exists or has any connections — zero is a valid, successful result
