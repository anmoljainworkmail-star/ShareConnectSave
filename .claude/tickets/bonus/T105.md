# T105 — Admin Stats Endpoint — Total Active Users

## Why this ticket exists

The Admin Dashboard (T060) needs real data on how many active, verified users are currently available in the system to display platform health metrics. Without this endpoint, the dashboard has no way to query User Service for that count — it remains a stubbed placeholder. This ticket fills that gap by adding a single internal-only endpoint that returns the count of users who are both verified (onboarding complete) and not suspended, giving admins immediate visibility into platform circulation.

## What to build

- `GET /users/internal/stats` endpoint in user-service
  - Guarded by the same `X-Internal-Service-Key` authorization check as T102's three internal endpoints
  - Returns JSON response with `{ "total_active_users": <integer> }`
  - Counts users where `AccountStatus` is NOT `suspended` AND `IsOnboardingComplete` is `true`
- New `getStats()` method in admin-service's `UserServiceClient`
  - Calls the new `/users/internal/stats` endpoint
  - Returns the stats response for Admin Dashboard consumption

## Technical specification

Add `GET /users/internal/stats`, internal-only (Docker-network reachable only, guarded by the
same `X-Internal-Service-Key` check as T102's three internal endpoints — reuse
`TryAuthorizeInternalCall`, do not duplicate the guard a fifth time). Returns
`{ "total_active_users": <count> }`: the count of users where `AccountStatus` is NOT `suspended`
AND `IsOnboardingComplete` is `true` — a genuinely active, verified user in circulation, not
merely a row in the table (an incomplete signup or a suspended account is not "active" for this
metric, same two-different-axes reasoning T102 already established for `AccountStatus` vs.
`Status`). Companion fix: admin-service's `UserServiceClient` gets a new `getStats()` method
calling this endpoint.

## Acceptance criteria

- [ ] `total_active_users` = count of users with `AccountStatus != suspended` AND `IsOnboardingComplete = true`
- [ ] Endpoint rejects a request missing or mismatching `X-Internal-Service-Key`, same as T102's other internal endpoints
- [ ] admin-service's `UserServiceClient` gains a `getStats()` call against this endpoint

## Patterns demonstrated

- **Trust Boundary via Internal-Only Endpoints** — Docker-network isolation + service key guard on internal statistics endpoints teaches how microservices expose aggregate data only to trusted callers, not the public API.
- **Reuse of Authorization Guard Clause (DRY / Single Responsibility)** — Calling `TryAuthorizeInternalCall` rather than duplicating the key-check logic demonstrates why a shared utility prevents drift and keeps authorization logic centralized in one place.
- **Database per Service Principle** — User Service owns the `User` table and the query logic; Admin Service never directly queries User Service's DB, only calls this endpoint via HTTP.
- **Two-Different-Axes Query Logic** — The distinction between `AccountStatus` (account standing: active/suspended) and `IsOnboardingComplete` (user verification state) being queried together teaches why a single "status" field is not enough — some dimensions are independent, and both must be evaluated for true platform health.

## Agent implementation notes

- **Key files to create/modify:**
  - `src/UserService/Controllers/UsersController.cs` — add new `[HttpGet("internal/stats")]` action method
  - `src/AdminService/Services/UserServiceClient.cs` — add `GetStatsAsync()` method that calls the endpoint
  - No new repository or service classes needed; reuse existing `IUserRepository` for the count query

- **Pattern references:**
  - See skill file `dotnet-mvc-controllers` section on **MVC Controllers** for the action method signature and response shape.
  - See `dotnet-mvc-controllers` section on **Authorization Guards** for how to call `TryAuthorizeInternalCall` — it is already in use in T102 and must be reused, not reimplemented.

- **What NOT to do:**
  - Do not add a new service layer or interface for stats — the controller can call `IUserRepository` directly for a read-only query.
  - Do not duplicate the `X-Internal-Service-Key` guard — always reuse the existing `TryAuthorizeInternalCall` method.
  - Do not include onboarding-incomplete or suspended users in the count — the WHERE clause must enforce both conditions: `AccountStatus != suspended` AND `IsOnboardingComplete = true`.
  - Do not create a new table or change the User schema — use existing columns only.

- **Ordering notes:**
  - User Service endpoint implementation (controller + repository query) must be complete before admin-service's `UserServiceClient` adds its call.
  - Ensure the repository query is efficient (filter at the database layer, not in memory).
