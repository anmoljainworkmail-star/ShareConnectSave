# T106 — Admin Stats Endpoint — Total Scans Today

## Why this ticket exists

The Admin Dashboard (T060) needs to display real-time platform engagement metrics, including how many scan sessions users have initiated today. Without this endpoint, the dashboard has no way to query Discovery Service for that aggregate — it remains a stubbed placeholder. This ticket provides the missing endpoint so admins can monitor user activity and platform health in real time, filling a critical gap left by T060's dependency on Discovery Service stats.

## What to build

- `GET /admin/scan/stats` endpoint in discovery-service
  - Guarded by Spring Security method security: `@PreAuthorize("hasRole('ADMIN')")` directly on the controller method — **not** the manual `@RequestHeader` guard clause T104/T107 use (deliberate Tech Lead choice, see Technical specification)
  - Returns JSON response with `{ "total_scans_today": <integer> }`
  - Counts rows in `scan_sessions` table where `started_at` is on or after the current UTC day's start
- New `AdminScanController` class to hold this endpoint
- New `DiscoveryAdminRoleAuthenticationFilter` (`OncePerRequestFilter`) — reads `X-User-Role` and populates `SecurityContextHolder` only when it equals `admin`, mirroring admin-service's `AdminRoleAuthenticationFilter` (T056)
- New `SecurityConfig` — `@EnableMethodSecurity`, stateless, CSRF disabled, every path `permitAll()` at the filter-chain level (method security does the actual gating on this one endpoint)
- New `AdminAccessDeniedHandler` — turns a Spring-Security-level rejection into this project's shared `{code, message, traceId}` error envelope
- `spring-boot-starter-security` added to discovery-service's `pom.xml` (not there today)
- New `getStats()` method in admin-service's `DiscoveryServiceClient`
  - Calls the new `/admin/scan/stats` endpoint
  - Returns the stats response for Admin Dashboard consumption

## Technical specification

Add `GET /admin/scan/stats` via a new `AdminScanController`. **Tech Lead decision (2026-10-25):**
unlike T104/T107's plain `@RequestHeader` guard clause, this endpoint is guarded with real Spring
Security method security — `@EnableMethodSecurity` + `@PreAuthorize("hasRole('ADMIN')")` directly
on the controller method — deliberately chosen *because* `AdminScanController` is a brand-new
class with no sibling method on an existing manual-guard controller to stay consistent with,
making it a clean place to learn the annotation-based style. This is a third real pattern for the
exact same "is this caller an admin" question, alongside T056's path-matcher
`SecurityFilterChain`/`AdminRoleAuthenticationFilter` (admin-service) and T104/T107's manual
`@RequestHeader` guard clause (connection-service) — all three enforce the identical rule from
the identical `X-User-Role` header, at three different layers (filter-chain config, a hand-written
`if`, and a method-level annotation), worth comparing side by side. Needs: the
`spring-boot-starter-security` dependency (not yet in discovery-service's `pom.xml`); a
`DiscoveryAdminRoleAuthenticationFilter` (`OncePerRequestFilter`, same shape as T056's
`AdminRoleAuthenticationFilter`) that reads `X-User-Role` and populates
`SecurityContextHolder` only when it equals `admin`, so `@PreAuthorize`'s `hasRole(...)` check has
an `Authentication` to evaluate; a `SecurityConfig` with `csrf().disable()`,
`sessionManagement(STATELESS)`, and `authorizeHttpRequests().anyRequest().permitAll()` — method
security does the actual gating here, not the filter chain's own authorization rule, so every
non-admin endpoint (`/scan/*`, `/actuator/health`) stays reachable exactly as before this ticket;
and an `AccessDeniedHandler` returning this project's shared `{code, message, traceId}`
`ErrorResponse` envelope (same reasoning as T056's own `AdminAccessDeniedHandler` — a Spring
Security rejection happens before `GlobalExceptionHandler` ever sees it). Returns
`{ "total_scans_today": <count> }`: a SQL Server count query against
`scan_sessions.started_at >= <start of current UTC day>`. This is deliberately a SQL query, not a
Redis read — `scan:active_sessions` (T023) only ever holds sessions that are *currently* active,
which answers a different question ("how many people are scanning right now") than "how many scan
sessions started today" (includes sessions already stopped).

## Acceptance criteria

- [ ] `total_scans_today` counts `scan_sessions` rows with `started_at` on or after the current UTC day's start
- [ ] Authorization is enforced via `@PreAuthorize("hasRole('ADMIN')")` on the controller method, not a manual `@RequestHeader` guard clause
- [ ] Every non-admin discovery-service endpoint (`/scan/*`, `/actuator/health`) remains reachable with no role check, unaffected by this ticket's `SecurityConfig`
- [ ] A rejection (missing/wrong `X-User-Role`) returns this project's standard `{code, message, traceId}` error envelope, not Spring Security's bare default 403
- [ ] admin-service gets a new `DiscoveryServiceClient.getStats()` call against this endpoint

## Patterns demonstrated

- **Method Security (`@PreAuthorize`)** — a Spring Security annotation that gates a single method based on the current `Authentication`'s granted authorities, evaluated at the point of call rather than at the filter-chain/path level; this is the first use of method-level security annotations anywhere in this project (T056 used path-matcher config instead), deliberately chosen here because a brand-new controller has no existing manual-guard sibling method to stay consistent with.
- **Three patterns, one question** — the exact same "is this caller an admin" check now has three different real implementations in this codebase to compare side by side: admin-service's `SecurityFilterChain` path matcher (T056), connection-service's manual `@RequestHeader` guard clause (T104/T107), and this ticket's method-level `@PreAuthorize` — same `X-User-Role` header, three layers it can be enforced at.
- **Authentication vs. Authorization (again)** — same split T056 first taught: `DiscoveryAdminRoleAuthenticationFilter` only ever records *who the caller claims to be*; `@PreAuthorize("hasRole('ADMIN')")` is the separate piece that decides *whether that's enough*.
- **Distinct Query Intent (Analytics vs. Real-Time):** The distinction between querying `scan_sessions` table for historical count ("how many scans started today") versus querying Redis for current active sessions ("who is scanning right now") teaches why the same concept requires different data sources depending on the analytical question being asked.
- **Database per Service Principle:** Discovery Service owns the `scan_sessions` table; Admin Service never directly queries Discovery Service's DB, only calls this endpoint via HTTP, maintaining the microservices boundary.

- `src/services/admin-service/.../client/DiscoveryServiceClient.java` — add `getStats()` method that calls the endpoint

**Patterns and references:**
- Follow java-spring-boot skill for controller/repository structure; read admin-service's T056 `SecurityConfig.java`/`AdminRoleAuthenticationFilter.java`/`AdminAccessDeniedHandler.java` directly as the structural template for the new filter/config/handler — same shape, just method security instead of a path-matcher authorization rule
- Query logic: Count `scan_sessions` rows where `started_at >= ZonedDateTime.now(ZoneId.of("UTC")).truncatedTo(ChronoUnit.DAYS)`
- Return a simple DTO: `{ "total_scans_today": N }` — no wrapper, no extra fields

**What NOT to do:**
- Do not fall back to a manual `@RequestHeader` guard clause — that's T104/T107's pattern; this ticket's whole point is the annotation-based alternative
- Do not lock down every discovery-service endpoint behind the new `SecurityFilterChain` — only this one method is gated, via `@PreAuthorize`, not the filter chain's own authorization rule
- Do not query Redis (`scan:active_sessions`) to answer this question — count from the SQL table only
- Do not create a new repository interface with a complex name — reuse or extend `ScanSessionRepository` with a clear method name like `countScansStartedToday()`
- Do not include ended sessions or sessions from previous days — the WHERE clause must be precise to UTC day boundaries
- Do not let a missing/wrong `X-User-Role` fall through to Spring Security's bare default 403 — the `AccessDeniedHandler` must return this project's standard error envelope

**Ordering notes:**
- Discovery Service endpoint implementation (security plumbing + controller + repository query) must be complete first
- admin-service's `DiscoveryServiceClient` can then add its call once the endpoint is verified
