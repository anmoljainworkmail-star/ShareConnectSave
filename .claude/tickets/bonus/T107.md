# T107 — Admin Stats Endpoint — Total Connections Accepted Today

## Why this ticket exists

The Admin Dashboard (T060) needs real metrics about platform activity. Right now it's stubbed with placeholder counts — this ticket builds the first of four missing stats endpoints across downstream services. Without this endpoint, the dashboard has no way to show admins how many connections were actually accepted today, leaving them blind to daily usage patterns and unable to diagnose connection-flow problems.

## What to build

- New method `getStats()` on the existing `AdminConnectionController` class (from T104)
- Single endpoint: `GET /admin/connections/stats`
- Returns JSON: `{ "total_connections_accepted_today": <integer> }`
- Query counts all `connection_requests` rows where `status = ACCEPTED` and the acceptance timestamp (the `updated_at` column written by `acceptConnection` in T030) falls on today's UTC date
- Guards the endpoint with the same `X-User-Role: admin` guard clause already used by T104's other admin methods
- In admin-service, add a new method `getStats()` to the existing `ConnectionServiceClient` class that calls this endpoint

## Technical specification

Add `GET /admin/connections/stats` as a new method on T104's existing `AdminConnectionController`
(nests naturally under `/admin/connections`, same `X-User-Role: admin` guard-clause shape as its
own `expireActiveConnections` method — reuse the class, do not create a second admin controller).
Returns `{ "total_connections_accepted_today": <count> }`: a count of `connection_requests` rows
where `status = ACCEPTED` and the timestamp of the transition *into* `ACCEPTED` falls on the
current UTC day — use whichever column `acceptConnection` (T030) already writes for that
transition (e.g. `updated_at`), not `created_at` (the request's original send time, which could
be days earlier than today's accept).

## Acceptance criteria

- [ ] `total_connections_accepted_today` counts connections whose status transitioned to `ACCEPTED` on the current UTC day
- [ ] Rejects with `403` when `X-User-Role` is not `admin`
- [ ] admin-service gets a new `ConnectionServiceClient.getStats()` call against this endpoint

## Patterns demonstrated

- **Interface Segregation (SOLID):** `AdminConnectionController` already uses a focused interface (only admin operations); this method adds to that focused set without broadening the controller's responsibility.
- **Single Responsibility (SOLID):** The query logic stays in the repository layer; the controller only handles HTTP and auth; the service layer (if used) only orchestrates.
- **Database per Service (System Design):** Connection Service owns the `connection_requests` table and speaks for its own data; Admin Service never queries it directly, only via this HTTP endpoint.
- **API Gateway pattern (explicit):** This endpoint (like T104) is not gateway-routed yet, but establishes the pattern: admin operations sit behind a service's own guard clause, not centralized.

## Agent implementation notes

- **Location:** Add the new method to the existing `AdminConnectionController` class (created in T104). Do not create a new controller.
- **Guard clause:** Copy T104's exact plain `@RequestHeader(value = "X-User-Role", required = false) String role` + `if (!ADMIN_ROLE.equals(role)) throw ...` guard clause from `expireActiveConnections()` — no Spring Security annotation here. (T106, a sibling bonus ticket, deliberately uses `@PreAuthorize` instead, but only because its controller is brand new with no existing manual-guard method to stay consistent with; this controller already has one, so the manual guard stays the correct choice for consistency within the same class.)
- **Date filtering:** Use `LocalDate.now(ZoneOffset.UTC)` to get today's date in UTC, then filter `updated_at` to rows where the date component (ignoring time) matches today. In Spring Data JPA, this is typically `@Query` with a `BETWEEN` clause spanning midnight-to-midnight UTC.
- **Repository method:** Add a new query method to `ConnectionRequestRepository` (or whatever your repository is called) with a signature like `long countAcceptedToday(LocalDate date)`. The query should be:
  ```sql
  SELECT COUNT(*) FROM connection_requests 
  WHERE status = 'ACCEPTED' 
  AND CAST(updated_at AS DATE) = ?
  ```
  (Adjust syntax for your DB — SQL Server uses `CAST(...AS DATE)`, others may vary.)
- **Response shape:** Return a DTO (e.g., `ConnectionStatsResponse`) with a single field `total_connections_accepted_today`. Do not hardcode or return a map.
- **Admin Service integration:** In `admin-service`, add a method to the existing `ConnectionServiceClient` class:
  ```java
  public ConnectionStatsResponse getStats() {
      return restTemplate.getForObject("/admin/connections/stats", ConnectionStatsResponse.class);
  }
  ```
  (Adjust based on your actual HTTP client pattern — could be `WebClient`, `Feign`, etc. Reuse whatever admin-service already uses for T104 calls.)
- **Common mistakes:**
  - Do not use `created_at` — the spec explicitly says to use the acceptance timestamp (`updated_at`).
  - Do not hardcode today's date — make it testable by accepting a `LocalDate` parameter in the repository method (optional: make the controller method pass `LocalDate.now(ZoneOffset.UTC)` automatically, but the repository should not call `now()` itself).
  - Do not add a new `AdminConnectionController` — reuse the one from T104.
  - Do not add authorization logic beyond the guard clause — T104's guard already covers this.
