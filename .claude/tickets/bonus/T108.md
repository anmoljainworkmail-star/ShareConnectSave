# T108 — Top Reported Users Endpoint

## Why this ticket exists

The Admin Dashboard (T060) needs to display the top 5 most-reported users over the last 7 days as a key metric. The existing `/reports/queue` endpoint is unsuitable because it only shows already-escalated reports with a stale point-in-time count taken at escalation time — it misses users who have accumulated multiple recent reports but haven't crossed the escalation threshold yet. Without this endpoint, administrators cannot see current reporting patterns in real time to identify which accounts are generating the most community concern. This ticket provides a fresh, live query over the full report stream to power that dashboard metric.

## What to build

- New `GET /reports/top-reported` endpoint in `ReportController` (admin-only, using the same `X-User-Role` authorization guard as existing admin endpoints)
- Query parameters: `days` (default 7), `limit` (default 5)
- Response: `List<TopReportedUserDto>` with fields `reported_id` (String) and `report_count` (long)
- MongoDB aggregation pipeline that matches reports within the rolling window, groups by `reported_id`, counts, sorts descending, and limits
- New `TopReportedUserDto` class to shape the response
- Integration hook in `admin-service`: new `ReportServiceClient.getTopReported()` method that calls this endpoint
- MongoDB query includes **all report statuses** — not a reuse of the escalation queue logic

## Technical specification

Add `GET /reports/top-reported?days=7&limit=5` to the existing `ReportController` (admin-only,
same `X-User-Role` guard as `/reports` and `/reports/queue`), defaulting `days` to 7 and `limit`
to 5 when omitted. Returns the top `limit` reported users by raw report count over a rolling
`days`-day window, across every report status — a live MongoDB aggregation
(`$match` on `createdAt >= now - days`, `$group` by `reportedId` with a count, `$sort` descending,
`$limit`), NOT a reuse of `/reports/queue`'s shape: that endpoint only returns already-`escalated`
reports sorted by a point-in-time snapshot count taken when escalation happened, which silently
excludes a user with multiple recent reports who hasn't crossed the escalation threshold yet, and
can be stale relative to "right now" — a fundamentally different query, per T060's own audit.
Response: `List<TopReportedUserDto>` — `{ reported_id, report_count }` per entry.

## Acceptance criteria

- [ ] Returns up to `limit` `reported_id`/`report_count` pairs, ordered by count descending, over the last `days` days
- [ ] Includes reports of every status, not just `escalated`
- [ ] Defaults to `days=7`, `limit=5` when query params are omitted
- [ ] Rejects with `403` when `X-User-Role` is not `admin`
- [ ] admin-service gets a new `ReportServiceClient.getTopReported()` call against this endpoint

## Patterns demonstrated

- **MongoDB Aggregation Pipeline**: demonstrates how to efficiently compute aggregates and roll up metrics on the document database, teaching the `$match → $group → $sort → $limit` pipeline pattern
- **Repository Pattern**: ReportRepository implements a specialized query method (`findTopReportedUsers`) that encapsulates the aggregation logic, so the controller and service depend on an abstraction, not raw MongoDB calls (Dependency Inversion)
- **Authorization via Headers**: admin-only guard using `X-User-Role` header inspection, teaching how the API Gateway's injected headers become the trust boundary for authorization decisions
- **Distinct Query Intent**: contrasts with T053's escalation queue to teach that different business questions require different database queries — reusing an existing query because "it kind of works" silently produces wrong results

## Agent implementation notes

**Key files to create/modify:**

- `services/report-service/src/main/java/com/shareconnectsave/report/controller/ReportController.java` — add `@GetMapping("/top-reported")` endpoint
- `services/report-service/src/main/java/com/shareconnectsave/report/dto/TopReportedUserDto.java` — new DTO with `reportedId` and `reportCount` fields
- `services/report-service/src/main/java/com/shareconnectsave/report/service/ReportService.java` — delegate to repository method
- `services/report-service/src/main/java/com/shareconnectsave/report/repository/ReportRepository.java` (or MongoDB template class) — add `findTopReportedUsers(int days, int limit)` method implementing the aggregation pipeline
- `services/admin-service/src/main/java/com/shareconnectsave/admin/client/ReportServiceClient.java` — add `getTopReported()` method

**Patterns to apply (reference java-spring-boot skill):**

- MongoDB aggregation pipeline: use Spring Data MongoDB's `Aggregation` builder with `$match`, `$group`, `$sort`, `$limit` stages
- Authorization guard: check `X-User-Role` header via a plain `@RequestHeader(required = false)` + guard clause, same manual pattern already used by `/reports` and `/reports/queue` in this same `ReportController` — do not introduce `@PreAuthorize` or any Spring Security annotation here, since that would leave this one method inconsistent with its two siblings in the same class. (T106, a sibling bonus ticket, deliberately uses `@PreAuthorize` instead, but only because its controller is brand new with nothing existing to stay consistent with.)
- Default parameter values: apply them in the controller method signature (`@RequestParam(defaultValue = "7") int days`, etc.)
- DTO mapping: use Spring Data's projection or manual mapping to shape the aggregation result as `TopReportedUserDto` entries

**What NOT to do:**

- Do NOT filter to only `status == "escalated"` — the ticket spec explicitly requires all statuses
- Do NOT reuse the `/reports/queue` endpoint's logic or query — this is a fresh aggregation that answers a different question
- Do NOT cache the result or compute it asynchronously — it must be live on each request (T060's dashboard metric needs current data)
- Do NOT expose raw `reportedId` as a UUID without checking the DTO's JsonProperty naming — ensure the JSON response matches the API contract (snake_case `reported_id` and `report_count`)
- Do NOT forget to add the endpoint to the report-service's OpenAPI spec (updatethe `contracts/openapi/report-service.yaml` file)
