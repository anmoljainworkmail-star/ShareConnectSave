# T109 — Profile Setup (Onboarding)

## Why this ticket exists

REQUIREMENTS.md §1 defines onboarding as four stages: Google sign-in, phone OTP, **mandatory** profile setup (name, photo, preferred language, gender), then an *optional* identity-verification badge. T063 (Auth Flow) built the first two and explicitly stopped at "JWT stored, user authenticated," on the assumption a later Phase 11 ticket would build the third — but no ticket in the original T062–T072 list actually does; T070 ("Profile + Settings") only covers editing an already-complete profile. This isn't just a product-requirements gap — it's confirmed against the backend's own gate: `User.IsProfileComplete()` (user-service) requires `Name`, `PhotoUrl`, `PreferredLanguage`, and `Gender != "Unspecified"` before `IsOnboardingComplete` ever flips true, and `IsOnboardingComplete` is what triggers the `user.verified` Kafka event that makes a user appear in Discovery at all (T025's consumer: *"only verified users appear in discovery"*). Without this ticket, a brand-new user who finishes Google sign-in and OTP has nowhere to go and no way to ever become discoverable — today's auth flow lands them on `/` with nothing there.

## What to build

- `ProfileSetupComponent` — the mandatory, first-time-only screen between OTP verification and the rest of the app (Figma Screen 04): name, photo, preferred language, and gender collection, gated behind `AuthGuard`.
- The first wiring of `AuthGuard` onto an actual protected route — Login and OTP are deliberately public; this is the first screen that genuinely requires a signed-in session.

## Technical specification

`ProfileSetupComponent` — the mandatory, first-time-only screen between OTP verification and the rest of the app (Figma Screen 04). Google already supplies `name` and often a `photo_url` at `POST /auth/google` time (see `AuthController.GoogleSignIn`); this screen's job is collecting whatever Google didn't provide plus the two fields it never provides at all (preferred language, gender), and persisting all of it before letting the user past this screen.

- On screen load, call `GET /users/me` (user-service, via the gateway) to pre-fill whatever is already known (`name`, `photo_url` if Google provided one, `preferred_language`'s default `"en"`).
- Name field (editable, pre-filled from Google).
- Photo: if `photo_url` is already set, show it (authenticated fetch — see REQUIREMENTS.md §2, plain `<img src>` 401s); if null, require an upload before the user can continue (same `NO_BASE_PHOTO` precondition T019's identity verification will later depend on — this is the one and only place that base photo ever gets set for a Google account with no photo).
- Preferred language selector.
- Gender selector — three options (`female | male | unspecified`), with a persistent, visible warning that this is locked after the user's first Discovery scan (T064's own acceptance criteria enforce the lock server-side; this screen only needs to warn, not enforce, since the lock cannot trigger before a scan has ever happened).
- "Continue" button: calls `PATCH /users/me` with `{name, preferred_language, gender}` (all three, even if only some changed — simpler than tracking per-field dirty state for a one-time screen) and, if a new photo was selected, `POST /users/me/photo` (multipart). Both responses can carry a fresh `access_token` (present only when `onboarding_complete` flips as a result — see `UpdateProfileResponse`/`PhotoUploadResponse`'s `[JsonIgnore(WhenWritingNull)]` contract) — when present, `AuthService.storeToken()` must be called with it, the same reissue-on-claim-change pattern T018 established server-side.
- On success, navigate to `/` (same as T063's OTP-verified landing — Radar/T064 is not built yet at the time this ticket ships, so this screen's "done" state still has nowhere protected to go; do not invent a different destination).
- `AuthGuard` must be applied to this route (`canActivate: [AuthGuard]`) — this is the first genuinely protected screen in the app; Login/OTP are deliberately public. Establishes the pattern T064 (and every later protected route) must follow — see `.claude/notes/follow-ups.md`'s "AuthGuard is never wired to any route" finding from T063's review, which this ticket resolves.
- Per the `figma-compliance` skill: this screen is one of the `--gradient-auth-bg` family (Figma: "these screens render as a centered card ... on `--gradient-auth-bg`": Login, OTP, Profile Setup) — reuse `src/frontend/src/app/auth/auth-shared.css` rather than re-declaring the gradient/bokeh/card chrome. Whether this screen's module lives under the existing `AuthModule` or a new `ProfileSetupModule` is an implementation decision for whoever picks up this ticket, not dictated here — either is consistent with the project's lazy-loaded feature-module rule, as long as it isn't declared in `AuthModule`'s existing `AuthRoutingModule` as a public route (it must sit behind `AuthGuard`, which `/auth/login` and `/auth/otp` must NOT).

## Acceptance criteria

- [ ] Screen pre-fills name/photo from `GET /users/me` where Google already supplied them
- [ ] Gender selector shows the "locked after first scan" warning
- [ ] A Google account with no photo cannot continue without uploading one (`NO_BASE_PHOTO` precondition respected client-side, not just server-side)
- [ ] "Continue" calls `PATCH /users/me` (and `POST /users/me/photo` if a new photo was chosen) and stores a refreshed `access_token` when the response includes one
- [ ] Route is guarded by `AuthGuard` — an unauthenticated visit redirects to `/auth/login`
- [ ] Reuses `auth-shared.css`'s gradient/bokeh/card chrome rather than re-declaring it
- [ ] On success, navigates to `/` (no protected home screen exists yet to send the user to instead)

## Patterns demonstrated

- **Guard (Angular routing)** — the first real use of `AuthGuard` on a protected route in this codebase; establishes the `canActivate: [AuthGuard]` pattern every later protected route (T064 onward) must follow.
- **Saga Compensation / chained condition** — `IsOnboardingComplete` only flips once BOTH phone verification (T017) and profile completion (this ticket) hold, regardless of which finishes last — this screen is the second of those two conditions, completing the same `UserOnboardingSaga` T017 started (see `.claude/skills/saga.md`).
- **Reissue-on-claim-change** — `PATCH /users/me` and `POST /users/me/photo` both conditionally return a fresh `access_token` only when a JWT-carried claim (`onboarding_complete`) actually changed — the frontend must treat "field present" as the signal to swap tokens, not assume every response carries one.

## Agent implementation notes

**Key files to create (paths relative to project root):**
- A component under the frontend's feature-module structure for this screen (module placement — whether it lives in `AuthModule`'s sibling or its own lazy-loaded `ProfileSetupModule` — is an implementation decision for whoever picks up this ticket; either is consistent with the project's lazy-loaded feature-module rule, as long as this route is NOT declared alongside `/auth/login`/`/auth/otp` inside `AuthRoutingModule`, since those two must stay public and this one must not).
- Route registration with `canActivate: [AuthGuard]` wherever this screen's route is declared.
- `AuthService` additions, if needed, for calling `GET /users/me`, `PATCH /users/me`, and `POST /users/me/photo` — check whether a profile-specific service makes more sense than extending `AuthService` (Single Responsibility: `AuthService` today only knows the four `/auth/*` endpoints and token storage; profile CRUD is arguably a different concern deserving its own service, e.g. `UserProfileService` on the frontend, mirroring the backend's own `IUserProfileService` split).

**Patterns to use:**
- Reference the `angular-pwa` skill for module structure, routing, and the authenticated-photo-fetch pattern (REQUIREMENTS.md §2: a bare `<img src="...">` 401s, every photo needs an authenticated fetch bound to a blob URL).
- Reference the `figma-compliance` skill before writing any template/CSS — read Figma Screen 04's full section, reuse `auth-shared.css`, extend `src/frontend/src/styles/tokens.css` rather than hardcoding any new value this screen needs.
- Early-return guard clauses for client-side validation (e.g. reject "Continue" before calling any endpoint if gender is still `unspecified` or no photo is set), per this project's stated preference.

**What NOT to do:**
- Do not let this screen be reachable without a valid session — it must sit behind `AuthGuard`.
- Do not invent a different post-success destination than `/` — no protected home screen exists yet.
- Do not silently drop a returned `access_token` — both `PATCH /users/me` and `POST /users/me/photo` can return one, and missing the swap means the frontend keeps using a token with a stale `onboarding_complete` claim.
- Do not implement identity verification (selfie/liveness) here — that is T110 (Phase 19), a separate, optional, later ticket. This ticket stops at "profile complete, onboarding_complete true."
- Do not build gender-lock *enforcement* here — only the warning. T064 enforces the actual lock server-side once a scan has happened.
