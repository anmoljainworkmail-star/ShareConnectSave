# T110 — Identity Verification (Selfie/Liveness Badge)

## Why this ticket exists

REQUIREMENTS.md §1 describes identity verification as the fourth onboarding-adjacent stage: *"Identity verification badge: optional step after profile setup. Flow: user submits a selfie → system does liveness + face-match against their profile photo... Verified accounts display a badge."* The backend half of this has existed since T019 (Phase 3) — `user-service` can already accept a selfie, run the Azure Face API match, and flip `identity_badge` to `true` — but nothing in the Angular app has ever called it. Unlike Profile Setup (Phase 18/T109), this step does not block a traveler from using the app at all: it is a trust signal a user can add any time after onboarding, or never. Without this ticket, that entire product feature — the "Verified" badge REQUIREMENTS.md and FIGMA_SPEC.md both describe — simply has no door for a real user to walk through, even though the platform has been able to process it since Phase 3.

## What to build

- `IdentityVerificationComponent` — Figma Screen 05: selfie capture UI, submits to `POST /users/me/verify-identity`, handles the three real outcomes (success, `NO_BASE_PHOTO`, `IDENTITY_MISMATCH`).
- An entry point into this screen from `ProfileComponent` or `SettingsComponent` (T070) — a "Verify your identity" action, visible only when the signed-in user's own `identity_badge` is currently `false`.

## Technical specification

`IdentityVerificationComponent` — reached from `ProfileComponent`/`SettingsComponent` (T070) via a "Verify your identity" entry point (not from the mandatory onboarding flow — this is a user-initiated action taken any time after onboarding, possibly never). Calls `POST /users/me/verify-identity` (multipart form, field name `selfie`) via `user-service.IdentityVerificationController`.

- Entry point: a button/row in `ProfileComponent` or `SettingsComponent`, visible only when `identity_badge` is currently `false` on the user's own profile (`GET /users/me`) — already verified users see their badge instead, not a re-verify action.
- Camera/selfie capture UI, then submit. This is synchronous, not a polling/async flow: the real `VerifyIdentityAsync` call runs the face-match inline and the HTTP response IS the final result — do not build a "pending, check back later" polling loop; none of the backend supports one (there is no separate status endpoint actually implemented — `identity_badge` on `GET /users/me`/`PATCH /users/me` responses is the only enduring signal, see Agent implementation notes below).
- Success (`200`): update local profile state's `identity_badge` to `true` from the returned profile, show the "Verified" badge, navigate back to Profile.
- `422 NO_BASE_PHOTO`: user has no `photo_url` set at all — redirect to `ProfileComponent`'s photo upload (T070) instead of showing a generic error; this should be rare in practice once Phase 18 ships, since Profile Setup already requires a photo before onboarding completes, but must still be handled (an account onboarded before this ticket shipped, or one whose photo was somehow cleared, can still hit it).
- `422 IDENTITY_MISMATCH`: show the error message from the response envelope and let the user retry with a new selfie — do not lock them out or count attempts client-side; the backend itself has no attempt-lockout for this endpoint (unlike OTP's 5-attempt lockout), so don't invent one.

## Acceptance criteria

- [ ] Entry point only appears when `identity_badge` is `false`
- [ ] Successful verification updates the badge state from the response and navigates back, with no polling/pending UI state
- [ ] `NO_BASE_PHOTO` routes the user to upload a photo instead of showing a dead-end error
- [ ] `IDENTITY_MISMATCH` allows an immediate retry with a new selfie, no client-side attempt cap
- [ ] Does not block or redirect away from Discovery/Radar at any point — this screen is reachable only from Profile/Settings, never inserted into the onboarding or Discovery flow

## Patterns demonstrated

- **Single Responsibility (S)** — `IdentityVerificationComponent` only handles the selfie-capture-and-submit flow; it does not own the entry-point visibility logic beyond reading `identity_badge`, and does not duplicate profile-photo-upload logic (that stays in T070's `ProfileComponent`).
- **Progressive Enhancement / Optional Capability** — the same system-design idea CLAUDE.md's pattern table applies to offline fallback applies here at the product level: a traveler is fully functional without this step; the badge only adds trust, it never gates a capability.
- **Build against the real contract, not the aspirational one** — this ticket is a direct, documented example of reading the shipped controller (`IdentityVerificationController.cs`) rather than the openapi spec where the two have drifted (see Agent implementation notes), the same discipline T063's `/auth/refresh` work already established for this project.

## Agent implementation notes

**Key files to create (paths relative to project root):**
- A component under the frontend's feature-module structure for this screen (module placement — whether it lives in a `ProfileModule` alongside T070's components, or its own small lazy-loaded module — is an implementation decision for whoever picks up this ticket; either is consistent with the project's lazy-loaded feature-module rule).
- An entry-point addition inside T070's `ProfileComponent`/`SettingsComponent` template + component class.

**Patterns to use:**
- Per the `figma-compliance` skill: Screen 05 is **not** part of the `--gradient-auth-bg` family (Login/OTP/Profile Setup) — it is reached post-onboarding from Profile/Settings, so follow whatever shared chrome T070's screens establish instead of importing `auth-shared.css`.
- Reference the `angular-pwa` skill for module structure, routing, and the authenticated-photo-fetch pattern (if this screen needs to display the existing base photo before capture — `REQUIREMENTS.md §2`: a bare `<img src="...">` 401s, every photo needs an authenticated fetch bound to a blob URL).

**CONTRACT DRIFT — confirmed before this ticket was written, do not rebuild the aspirational version:**
`contracts/openapi/user-service.yaml` documents a separate `GET /identity/status` returning an `IdentityStatusResponse` enum (`not_started | pending | verified | rejected`) — but `IdentityVerificationController.cs` (T019, shipped) has no such action; it only has `POST /users/me/verify-identity`, which responds synchronously with the full profile on success. Build against the controller that actually exists, not the openapi doc — do not implement a polling loop or a separate status call that has nothing to hit. If this drift needs fixing in the contract docs, that is a documentation cleanup for whoever picks up this ticket, not a reason to build a backend call that doesn't exist.

**What NOT to do:**
- Do not build a "pending/processing" state or any polling loop — the real endpoint is synchronous.
- Do not insert this screen into the mandatory onboarding flow (T109) or block Discovery/Radar access on it — it is optional, full stop.
- Do not invent a client-side attempt limit for `IDENTITY_MISMATCH` — the backend has none for this endpoint.
- Do not reuse `auth-shared.css` for this screen's chrome — it is not part of that visual family.
