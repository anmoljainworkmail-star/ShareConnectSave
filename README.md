# ShareConnectSave

## TL;DR

A travel companion discovery platform — verified travelers nearby heading the same way find each other, chat briefly, then the platform gets out of the way once they've met. Built as a learning vehicle for polyglot microservices: Java + .NET services talking only through Kafka events, each owning its own database, tied together with Saga/Outbox, SignalR, and an Angular PWA. Currently early — Phases 0-2 (foundation & contracts, infrastructure, API gateway) are done, Phase 3 (User Service) is underway, of 14 phases total.

## What this is

ShareConnectSave is a travel companion discovery platform — think of it as helping verified travelers who happen to be heading the same way find each other nearby. It only handles discovery, matching, and a temporary chat window; it deliberately stays out of ride booking, payments, and tracking. Once both people mark **Met Successfully**, the chat closes and the platform's job is done.

I'm building this primarily to *learn*, not just to ship — it's a real excuse to get hands-on with distributed microservices across two languages (Java and .NET), Kafka as an event bus, the Saga/Outbox pattern, SignalR, BLE, and an Angular PWA. Everything below is written the way I'd explain it out loud, so I can walk through it cold in an interview.

## How it's put together

The system is nine services behind a single API gateway. An Angular PWA talks to a YARP gateway, which fronts eight microservices — a mix of .NET (User, Chat, Notification) and Java/Spring Boot (Discovery, Connection, Rating, Report, Admin). Each service owns its own database; nobody reaches across into another service's tables. Services don't call each other directly for anything asynchronous — they publish events onto Kafka and react to what other services publish. Realtime stuff (chat messages, live notifications) rides over SignalR with a Redis backplane so it can scale across multiple instances.

The reason for this shape: it's a deliberately "textbook" microservices setup so that every classic distributed-systems problem — data ownership, eventual consistency, retries, duplicate delivery — shows up on purpose and gets solved on purpose, rather than avoided by keeping everything in one app.

## The story so far

### Phase 0 — Foundation & Contracts

**Jul 6, 2026 — we started with the skeleton.** Before any real code could exist, every service needed a place to live. So the first piece of work was scaffolding the whole monorepo: a folder per service (four .NET minimal API projects, five Spring Boot projects, one Angular app), stub Docker Compose entries for each, and shared tooling (`.editorconfig`, `.gitignore`) that works across both the .NET and Java worlds. Nothing in here has business logic yet — it's purely "the folders exist, the projects compile." The point of doing this first and doing it deliberately is that it makes the architecture visible from day one: separate folders per service is the physical manifestation of "database per service" and of keeping a polyglot stack (Java + .NET side by side) from turning into a tangled mess.

**Jul 10, 2026 — then we defined how services would talk to each other, before writing any of the code that actually talks.** Since Kafka is how all seven "reactive" services communicate, we wrote a JSON Schema contract for every one of the seven event types the platform produces (`user.verified`, `connection.accepted`, `chat.closed`, and so on), plus a README explaining who produces each event, who consumes it, and the partition/retention settings. This is "schema-first design" — agreeing on the exact shape of a message *before* either the producing service or the consuming service has a single line of handler code, so a .NET team and a Java team can't silently drift apart on what a field means. Every one of those schemas also carries a mandatory `event_id`, which is the seed of idempotency: because Kafka only guarantees "at least once" delivery, every consumer will eventually need to check "have I already processed this exact event_id?" before acting on a message — otherwise a redelivered message could double-charge a trust score update or reopen a closed chat.

**Aug 15, 2026 — next we agreed on how every service fails, not just how it succeeds.** Nine services behind one gateway means nine chances to invent nine different error shapes — one service returns `error`, another `message`, a third forgets to include anything traceable, and the Angular client ends up with nine special cases just to show "something went wrong." So before writing a single endpoint, we wrote one error contract: `{ code, message, traceId }`, defined once as an OpenAPI schema, with a C# record and a Java record both checked against that same schema independently rather than copying JSON shape from each other by convention. The Java side also got its first shared library, `shared-java-lib` — one `GlobalExceptionHandler` that every Java service will depend on instead of writing its own, so a decision made today about how validation errors look can't quietly drift five different ways across Discovery, Connection, Rating, Report, and Admin. The `traceId` field is the other half of the idea: it's read from the current OpenTelemetry trace context, never invented, so a user-visible error can later be pulled up in Jaeger as the exact request that failed — a fabricated ID would just be a dead end.

**Aug 16, 2026 — then we actually stood up the infrastructure the last three entries were building toward.** Docker Compose now brings up SQL Server, MongoDB, Kafka, Redis, and Kafka UI, all gated behind healthchecks so nothing tries to connect before its dependency can actually take a request — a one-shot init job creates one database per service the moment SQL Server reports healthy, so "database per service" is enforced by which connection string each service is handed, not just by convention. Getting it actually running (not just written) surfaced two real surprises no ticket predicted: ZooKeeper 3.5+ silently ignores its own `ruok` health-check command unless it's explicitly whitelisted, and — the bigger one — Kafka 4.0, which `bitnami/kafka:latest` now ships, removed ZooKeeper support entirely in favor of KRaft, a mode where Kafka manages its own cluster metadata and leader election internally instead of outsourcing that job to a second coordination system. So the original plan (a standalone Zookeeper container) was dropped in favor of Kafka running on its own as a single-node metadata quorum — which, not coincidentally, is also how Kafka is actually deployed in production today. That discovery only happened because we started running a real manual QA checklist after each review instead of trusting that code which reads correctly also runs correctly; the review step now writes one automatically, with exact commands and exact expected output, specifically so gaps like this get caught by a human with Docker Desktop running rather than assumed away.

**Aug 19, 2026 — then we wrote the contract for every HTTP endpoint before writing a single one of them.** Eight OpenAPI 3.1 YAML files went in, one per service, each covering every endpoint that service's functional requirements call for — auth and OTP for User, scan/nearby/BLE-resolve for Discovery, accept/decline for Connection, and so on — and every error response on every one of those endpoints `$ref`s the same `ErrorResponse` schema built in the last entry, so there's exactly one error shape across nine services instead of nine slightly different ones. This is the same "agree on the contract before the code" idea as the Kafka schemas, just applied to the HTTP surface instead of the event bus: a developer agent implementing User Service in C# and one implementing Discovery in Java are both building against the same YAML, so neither can quietly invent its own field names. Two rules mattered enough to write down explicitly rather than leave as tribal knowledge: nothing in any of these files declares a JWT `securityScheme`, because the JWT is fully consumed at the gateway and services only ever see plain `X-User-Id`/`X-User-Role`/`X-User-Gender` headers — a spec that modeled JWT auth would quietly break every future generated client into sending a bearer token nobody downstream expects; and the Discovery service's "nearby users" response schema has no `gender` field at all, by comment and by design, because the whole point of women-only mode is that gender is a server-side filter, never something broadcast back to another user. The review on this one didn't send anything back for rework, but it did surface three genuinely useful gaps — a rate-limit response using `409` instead of the more conventional `429`, a `refresh_token` field with no `/auth/refresh` endpoint to redeem it yet, and a couple of request schemas that don't reject unexpected extra fields — and rather than let those live only in a review agent's output and get forgotten by the time the affected service is actually built, they're now logged in a standing `follow-ups.md` file that future ticket creation automatically checks and folds into the relevant ticket. That's the same instinct as the `traceId`/idempotency work two entries back: a finding that isn't written down somewhere durable doesn't actually exist three weeks later.

### Phase 1 — Infrastructure

**Aug 20, 2026 — then we gave every relational service an actual schema to run against.** Five SQL Server databases got their first migration each — Flyway scripts for the three Java services (Discovery, Connection, Rating), an EF Core migration for User Service — following the same "agree on the shape before the code" instinct as the Kafka and OpenAPI contracts, just applied one layer lower, to the tables themselves. Discovery's `scan_sessions` table is the interesting one: instead of storing a stated destination as two plain floats and computing "how far apart are two points" by hand in application code (which quietly gets spherical distance wrong if you just subtract lat/lng like they're flat coordinates), it uses SQL Server's native `geography` type in a computed column, backed by a spatial index, so "find travelers heading near this point" is fast without any custom math. Getting that column to actually build correctly surfaced a real gotcha, the same kind of "looks fine, isn't" surprise as the Kafka/Zookeeper one from Phase 0: SQL Server refuses to index a computed column unless six specific session settings are all switched on first, and the tool used to hand-verify the migration (`sqlcmd`) defaults those settings differently than the JDBC driver Flyway will actually use in the running service — so a migration that visibly worked during manual testing would have failed the moment it ran for real. The review process also caught three race conditions the schema didn't originally guard against: nothing stopped two near-simultaneous OTP requests for the same phone number from creating two independent attempt counters (quietly defeating the 5-attempt lockout), nothing stopped a double-submitted rating from counting one interaction twice toward a trust score, and nothing stopped two duplicate pending connection requests reaching the same recipient. All three are now closed with unique (or filtered-unique) indexes — the database itself refusing the second write, rather than trusting application code to check first and never race itself.

**Aug 22, 2026 — then we gave Chat and Report their actual storage, not just an empty container.** MongoDB needed two things before either service could use it for real: the databases and collections themselves, and — the harder part — a database-enforced guarantee that a chat message deletes itself after a fixed window, because message expiry isn't a "nice to have" here, it's the platform's actual privacy promise, not something every future line of application code can be trusted to remember on its own. MongoDB's TTL (time-to-live) index does the deleting for us at the database layer — set `expireAfterSeconds` on a date field and Mongo's own background sweep removes the document once that many seconds have passed, no cron job or app code involved. Getting that right surfaced its own small gotcha, in the same spirit as the ZooKeeper and SQL Server ones from earlier: once a TTL index exists, MongoDB refuses to just let you re-run `createIndex` your way to a new expiry value — you have to drop the old index and recreate it, otherwise a later change to the retention window (which was already flagged as likely) would throw and silently leave the old value in place. There was also a real naming decision worth keeping: the original plan named the databases `chat_db`/`report_db`, but the actual connection strings the services already had wired up from the Docker Compose work pointed at `ChatServiceDb`/`ReportServiceDb` instead — following the placeholder names literally would have built indexes on a database nobody ever queries, so the init scripts follow the real connection strings the services actually use. Review also caught a small but real bug worth carrying forward rather than patching on the spot: the script's "env var or default" fallback used JavaScript's `||`, which treats an explicitly-set `0` the same as "unset" and silently overrides it back to the default — logged as a follow-up for whichever future task next touches Chat Service's Mongo config, rather than forgotten.

**Aug 23, 2026 — then we gave Redis a job description before any service started using it.** Redis ends up doing two completely unrelated things for this platform: caching Discovery Service's nearby-scan results so repeated scans don't re-hit SQL Server on every request, and acting as the SignalR "backplane" — the shared channel that lets Chat and Notification Service instances tell each other "deliver this message, whichever of you is holding the live socket for this user," which matters the moment either service runs as more than one instance. Rather than standing up two separate Redis containers for two unrelated jobs, one instance does both, split by Redis's own logical database indices — DB 0 for the cache, DB 1 for the backplane — the same "database per service" instinct from Phase 0, just expressed as a numbered drawer instead of a whole extra container. The config also sets a 256MB memory ceiling with LRU (least-recently-used) eviction, so the cache can't quietly grow until it OOMs the dev machine, and turns persistence off entirely — both DB 0 and DB 1 hold data that's either trivially rebuildable (the cache) or meaningless after a restart anyway (which socket belonged to which server), so there's nothing in Redis worth surviving a crash. The review on this one is what actually mattered more than the config itself: a first read of `redis.conf` looked like it should reject every connection made from another container (Redis's "protected mode" normally does exactly that when there's no password set), which would have been a real blocker the moment Discovery, Chat, or Notification Service tried to connect — but reading code isn't proof, so the review ran the actual config in a real container and connected to it from a second container, which is what actually settled it (the base image ships with protected mode already off). That same run-it-not-just-read-it pass caught two real, if smaller, gaps: a code comment claiming Redis "never leaves the dev network" that the actual port mapping contradicts, and a Redis connection string already wired up for the SignalR backplane that has no database index in it at all — meaning whoever implements Chat/Notification's real SignalR wiring will silently land in DB 0, the cache's database, unless they remember to set it. Both are logged in `follow-ups.md` against the tickets that will actually write that code, so the gap surfaces again right when it matters instead of being forgotten between now and then.

**Aug 23, 2026 — then we finished Kafka's own plumbing, not just the databases sitting behind it.** Every service's event flow — verification, connection acceptance, chat closure, ratings, trust score updates, reports — needs its channel to already exist before a single producer or consumer can use it, so the last piece standing in Phase 1's way was a script that creates all seven topics (three partitions, replication factor one, each) and runs once, automatically, the moment Kafka's own healthcheck goes green — using `--if-not-exists` so a second `docker compose up` on a machine that already has these topics is a no-op instead of a startup failure. Standing that up for real, not just writing it, surfaced the exact gotcha the Kafka service's own config had flagged and left open for this task: Kafka's client protocol connects to whatever bootstrap address you hand it only to ask "who's really in charge," then reconnects to whatever address the broker *advertises* in its answer — and that address was pinned to `localhost:9092`, correct for a human at a host terminal but meaning "myself" to any other container, including this init job and Kafka UI. Every request past the very first one would have quietly hung until it timed out. The fix was a second listener — `INTERNAL`, advertising `kafka:29092`, an address that only resolves correctly from inside the Docker network — so host tools and containers each reconnect to something that's actually the broker instead of looping back on themselves; Kafka UI's own bootstrap setting moved to match. One more small but real fix rode along: this repo checks scripts out with Windows line endings by default, and a `.sh` file bind-mounted straight into a Linux container breaks the moment its shebang line picks up a stray `\r` — so a `.gitattributes` entry now pins shell scripts to LF regardless of a developer's local Git settings, closing that off before it ever bites anyone.

**Aug 23, 2026 — then we closed out Phase 1 with the one piece that isn't infrastructure at all — it's a script for the humans, not the containers.** Every service so far assumes a contributor's own machine already has the right JDK, .NET SDK, Node, and Docker installed, because Docker only pins the runtime version *inside* a container — it says nothing about what an IDE, a debugger, or a fast local `mvn test` run outside Docker actually uses. So a one-shot PowerShell script now bootstraps Scoop — a Windows package manager that, unlike a normal `.msi` installer, unpacks everything under the user's own profile folder instead of `Program Files`, which is exactly why it needs no admin rights at all — and uses it to install JDK 21 and IntelliJ Community, while only checking (never installing) .NET, Node, and Docker, since those really do need admin to install and the script has to stay honest about that limit rather than pretend it can do the impossible. Running it for real surfaced the same kind of "looks right, isn't" gap every earlier infrastructure entry in this phase has hit: the script decided whether JDK 21 was already installed by asking "does typing `java` resolve to version 21 right now," but on a machine that already had an older Oracle Java install, Windows' own PATH ordering always resolves `java` to that older install's PATH entry first, no matter what Scoop puts on the user's own PATH behind it — so the script could install JDK 21 correctly every time and still never recognize its own success, reporting "installing" again on every single re-run instead of "already installed." The fix was to stop asking PATH what's true and start asking Scoop's own install record instead — the same distinction as checking a warehouse's own inventory list instead of glancing at whatever happens to be sitting on the loading dock, which could belong to someone else entirely. That's the same idempotency instinct that runs through this whole phase, just showing up somewhere unexpected: a Kafka topic script re-run, a MongoDB TTL index, and now a developer's own laptop all need the same discipline — check the one place that's actually authoritative, not a side effect that something else could be quietly shadowing.

### Phase 2 — API Gateway (.NET)

**Aug 26, 2026 — then we put one door in front of the whole system before writing a single business endpoint.** Without a gateway, the Angular PWA would need to know all eight backend addresses directly, and every future cross-cutting concern — JWT checks, rate limits — would have to be built eight separate times instead of once. So the first piece of Phase 2 was standing up a YARP reverse proxy: a .NET 9 host whose entire job is reading a route table out of `appsettings.json` (eight prefixes, one per service — `/user`, `/discovery`, `/connection`, and so on) and forwarding a matched request to the right container, streaming the response straight back. The routing lives entirely in config, not in C# — adding a ninth service later is a JSON entry, never a code change, which is the Open/Closed Principle showing up in a very literal way. Two things worth remembering surfaced while building this: the ticket's own file paths were stale — it assumed a fresh `src/api-gateway/` folder, when T001 had already scaffolded the real project at `src/services/api-gateway/` — and the ticket's downstream port table (8081 for User Service, 8082 for Discovery, and so on) turned out to describe the *host*-published ports from Docker Compose, not what the gateway itself needs to dial. Every container actually listens on port 8080 *inside* the Docker network regardless of which host port Compose maps it to outside — so every cluster destination in the config uses `:8080`, not the ticket's literal numbers, the same "container-internal port vs. host-mapped port" distinction that trips up a lot of first Docker Compose setups. No Dockerfile was written yet — none of the other .NET services have one either, so that's staying deferred to its own dedicated ticket rather than inventing a convention nobody else follows yet. Review didn't send this back for rework, but it did surface something worth sitting with: every downstream service's own port (8081-8088) is *also* published directly to the host right now, which means once the next entry's JWT validation lands at the gateway, a request sent straight to a service's own port would completely skip it — the gateway only actually guards anything if it's the *only* reachable door. That's logged as a follow-up against the JWT and rate-limiting work specifically so it gets decided on purpose rather than discovered by accident later.

**Aug 28, 2026 — then we decided who's actually allowed to walk through that one door.** A gateway that routes requests to the right service isn't a security boundary by itself — it needs to also check who's asking before it forwards anything. The ticket as originally written said to validate Google's Sign-In token directly against Google's own public keys on every request. That doesn't actually work: Google's token only ever carries Google's own fields (email, name, a Google-specific ID) — it has no idea what "role" or "gender" means for this app, because those live in our own database, not Google's. So the real design has to be two-step: `user-service` (not built yet) validates the Google token exactly once, at login, then issues its *own* signed token carrying our own claims — and the gateway validates *that* token on every later request instead. The remaining decision was how the gateway checks a signature it didn't create itself: a shared secret between the two services, or `user-service` holding a private key and publishing only the matching public key for the gateway to fetch. We went with the public-key approach — the private key never leaves `user-service`, ever, and the gateway only ever holds a value that can check a signature, not produce one — the same shape as the JWKS caching this ticket's own design already called for, just pointed at our own service instead of Google's. Once validated, the token itself gets thrown away — the gateway converts it into three plain headers (`X-User-Id`, `X-User-Role`, `X-User-Gender`) and strips the original token before forwarding, so none of the other eight services ever touch a JWT or a cryptographic key at all; they just read three strings off the request. Review put this through three full adversarial passes before approving it, and each one found something real: the public-route bypass list (login, OTP) was written against the paths `user-service` itself expects, not the paths the gateway actually receives with its `/user` prefix still attached — meaning login would have locked itself out forever, since the request never had a token yet to present. Then, once a real token could be built and tested against the code, a .NET library default silently renames short claim names to long legacy ones before this project's code ever gets to read them — every genuinely valid token would have been rejected as "missing claims," which is a much scarier failure than it sounds, because nothing about that code looks wrong on a read-through; it only breaks once a real signed token flows through it. A second library default separately refused to fetch the signing key at all, because it defaults to requiring HTTPS and the internal Docker Compose network has no TLS between services — a deliberate tradeoff, not a security gap, since that traffic never leaves an isolated private network. And the last pass, run against a real running gateway with real forged tokens rather than just reading the code, found that a garbled token (not cryptographically invalid, just malformed) threw an exception type outside what the code was built to catch, crashing into a bare 500 with a leaked stack trace instead of a clean rejection — closed with one final catch-all that fails closed on anything not already handled, rather than trusting an itemized list of "here's every way I know this can break" to stay complete forever.

**Aug 29, 2026 — then we decided how many times the same client gets to knock before the gateway stops answering.** A JWT check answers "who is this," but says nothing about "how often are they allowed to ask" — without a limiter, a single buggy retry loop or a script brute-forcing OTP codes could exhaust the SMS budget or spam every other user with connection requests, and every one of the eight downstream services would otherwise have to reinvent this same protection on its own. So the gateway got .NET's built-in rate limiter wired in as one more cross-cutting concern living in exactly one place: a global sliding-window ceiling — 100 requests a minute, keyed by IP — that applies to every route with zero opt-in, plus two narrower fixed-window policies that only apply where a route explicitly asks for one: ten connection requests a minute per user, and five OTP sends per ten minutes per phone number, each keyed to whichever dimension actually represents that endpoint's abuse risk rather than one counter pretending "IP" means the same thing everywhere. A fourth policy got added after the first pass had already shipped: Google sign-in turned out to be a public route for the same chicken-and-egg reason OTP is — there's no token yet to validate — but unlike OTP it had no policy of its own, so a login flood was really a JWT-minting flood on user-service hiding behind the much looser global ceiling; caught in review, closed with the same per-IP fixed-window shape as the other two. Getting the plumbing underneath those four policies right surfaced two more of its own real surprises, the same "passes on paper, breaks for real" shape every earlier phase entry in this story has hit: the one shared object that both makes the accept/reject decision and answers "how many are left" for the `X-RateLimit-Remaining` header has to be the *exact same instance* in both places, and an attempt to fetch it early via a hand-built second `BuildServiceProvider()` call quietly constructed a second, disconnected container instead — the header would have silently stopped appearing on every response, fixed by resolving the registry from the request's own DI scope at request time instead of trying to grab it before the real container even exists. Separately, that registry started out as a bare in-memory dictionary keyed by whatever a client sends as a partition key — a phone number, an IP — meaning an attacker could grow it forever just by rotating fake values on every request; closed by moving it onto a memory cache with expiry sized to each policy's own window, so an unused partition's limiter gets evicted, and disposed a few seconds after that (not immediately, so a request that's still mid-read never gets its limiter yanked out from under it) instead of living forever.

**Aug 29, 2026 — then we gave the gateway a way to actually run without anyone's laptop needing the .NET SDK installed.** Every other piece of infrastructure in this story so far comes up with one `docker compose up`; the gateway itself couldn't, because nothing had ever written its Dockerfile. That Dockerfile is the first multi-stage build in the repo, and it's deliberately the template every later .NET service (User, Chat, Notification) will copy: one stage on the full SDK image compiles and publishes the app, a second stage starts fresh from a much smaller ASP.NET runtime image and copies in only the compiled output — the compiler, the NuGet cache, the source tree itself, none of it survives into what actually ships. That split is why the final image measured 91MB against a 200MB budget instead of carrying the SDK's own 800MB+ along for the ride. Standing it up for real surfaced the same "passes on paper, breaks for real" shape as nearly every earlier entry in this story: the container built cleanly and started, but Docker's own healthcheck — `curl -f http://localhost:8080/health`, run from inside the container itself, with no Authorization header at all — got rejected with a 401 by the gateway's own JWT middleware from two entries back, because that middleware runs in front of every dispatched request regardless of textual order in `Program.cs`, including a liveness probe that was never a user and never carried a token to begin with. Docker Compose read that 401 as "still not ready" forever, meaning nothing declaring `depends_on: api-gateway: condition: service_healthy` would ever have started either. The fix was a narrow, exact-match exemption — only `GET /health`, nothing broader — kept deliberately separate from the existing pre-auth allowlist for login/OTP, since "this caller isn't a user at all" and "this user doesn't have a token yet" are different reasons to skip validation and conflating them risks the wrong route quietly inheriting the wrong exemption later. Review didn't just read that fix and trust it — it rebuilt the image, brought the container up for real, and fired six adversarial variations at the new bypass (a trailing slash, path traversal, a POST to the same path, different casing) to confirm nothing broader than that one exact route could sneak past the gateway's own front door.

### Phase 3 — User Service (.NET)

**Aug 30, 2026 — then we gave User Service an actual body to go with the schema Phase 1 already gave it.** T006 had left behind entity classes, a `DbContext`, and a generated migration sitting on disk, completely unused — `Program.cs` was still the default template, nothing in the running app knew `AppDbContext` existed. So this piece wired it in for real: `AppDbContext` registered in the DI container, three separate repositories (`IUserRepository`, `IOtpRepository`, `IIdentityVerificationRepository`) instead of one combined interface — the same "don't force a caller to depend on methods it'll never call" idea behind `IChatRoomRepository`/`IMessageRepository` being split later, just landing here first — and a plain `GET /health` that deliberately never touches the database, so Docker Compose's healthcheck answers "is the process alive," not "can it currently reach SQL Server," the same liveness-vs-readiness distinction the gateway's own health endpoint drew two entries back. The actual interesting problem wasn't the wiring itself, it was a naming mismatch nobody had caught yet: `.env` defined the connection string as `USER_DB_CONNECTION`, but the EF Core tooling from T006 was already looking for an environment variable named `ConnectionStrings__UserDb` — ASP.NET Core's own convention for "double underscore means nested config key" — and nothing bridged the two, so both `dotnet ef database update` and the running container would have failed with "connection string not set" the moment either was tried for real. The fix was one line in `docker-compose.yml` re-exposing the human-named variable under the name the framework actually listens for, so `.env` stays the single place a developer edits a password. Review didn't send this back for rework, but it did catch something worth carrying forward: the guard that's supposed to fail loudly on a missing connection string only checks for `null`, not an empty string — and the one compose file used alone in production/CI has no built-in safeguard against a blank value the way the dev-only override file does. That's logged as a follow-up against T016, the next ticket to touch this same file, rather than patched here on a ticket that was otherwise already signed off. One more thing changed after review, driven by wanting the interface layer to be easy to read as its own thing: the three repository interfaces moved into their own `Repositories/Interfaces/` subfolder, separate from the EF Core classes that implement them — now the standing layout for every future .NET service.

**Aug 30, 2026 — then we built the piece every other ticket in this phase has been waiting on: an actual way to sign in.** Until this landed, User Service could store a schema but had no way to turn "I signed in with Google" into an identity anything else on the platform could trust — the gateway's own JWT validation from Phase 2 had nothing to fetch at its JWKS endpoint, so every authenticated request in the whole system would have failed closed. The flow: Google's own client-side sign-in hands the Angular app an ID token directly (no server redirect involved), the app posts that token to `/auth/google`, and the endpoint validates it against Google's tokeninfo endpoint exactly once — checking not just that the token is genuinely Google's, but that it was minted for *this* app specifically (the `aud` claim), since tokeninfo alone happily returns 200 for a token issued to any Google-integrated app a user has ever signed into, not just this one. Past that one validation call, Google's token is discarded entirely; everything downstream runs on the platform's own RS256-signed JWT, built with an RSA keypair that only ever leaves this one class as its public half, exposed at `/.well-known/jwks.json` for the gateway to fetch and cache — the producer half of the contract Phase 2's gateway already built the consumer half of. A brand-new user gets `status = incomplete` and `gender = Unspecified` baked into that very first token, deliberately, so Discovery Service (much later) has an unambiguous flag for "not ready to appear in a scan yet" instead of defaulting to something that looks ready.

Right after this landed, one architecture-level decision got revisited across the whole .NET side rather than patched locally: the four .NET services had been building on ASP.NET Core's Minimal API style (`app.MapPost`, static endpoint classes) since Phase 2, but learning that style *and* Spring Boot's very different `@RestController` style for the five Java services at the same time was slowing the actual learning down, not adding to it. So this ticket's endpoint — and every future .NET ticket's skill file, ticket spec, and phase manifest — switched to MVC Controllers instead: `AuthController.cs`'s `[ApiController]` class with constructor-injected dependencies maps onto Spring Boot's `@RestController` + `@Autowired` almost one-for-one, which was the entire point. Nothing about the gateway, EF Core, or the RSA/JWKS logic changed underneath — this was purely about how an HTTP request finds its handler code. Review didn't send this ticket back for rework, but it did leave one real gap on the table rather than patch it invisibly: `user-service` still has no global exception-handling middleware, so two near-simultaneous sign-ins for the same brand-new Google account can both pass the "does this user exist" check before either writes — the database's own unique index on `GoogleId` correctly stops the second row from ever being created, but the losing request currently gets an unhandled exception instead of a clean error response. That's logged against the next ticket to touch this file rather than fixed here, the same "write it down so it surfaces on purpose, instead of being forgotten" instinct as every earlier gap in this story.

**Aug 31, 2026 — then we gave the platform its second real trust boundary: proving a phone number, not just an email.** Google sign-in only proves someone controls an email address; nothing stops a user from typing in a stranger's phone number on the profile step. So this ticket added `POST /auth/otp/send` and `POST /auth/otp/verify` to User Service: a 6-digit code goes out over Twilio's REST API (called directly over `HttpClient`, no SDK package, the same "one call doesn't need a whole dependency" reasoning as `GoogleTokenValidator`'s raw call to Google's tokeninfo endpoint), and the phone only counts as verified once the caller proves they received it. Only the code's SHA-256 hash is ever persisted — the plaintext exists nowhere but Twilio's request and a local variable for the seconds it takes to send it. A wrong guess increments a per-phone failure counter with its own rolling window (`otp_attempts`), and the 5th failure inside 10 minutes locks the phone out for 15 — a business-rule lockout that's deliberately separate from the gateway's own request-rate limiter from T013, because they defend different things: the gateway throttles *asking* for a code (Twilio cost), this lockout throttles *guessing* one (brute force), and neither endpoint's guard can see the other's traffic. Getting the concurrency right needed both patterns this project had only used once before: a `RowVersion` optimistic-concurrency column on `otp_attempts` (SQL Server auto-bumps it on every write; EF Core folds it into the `UPDATE`'s `WHERE` clause) stops two near-simultaneous wrong guesses from clobbering each other's increment and quietly evading the lockout, and a filtered unique index on `Users.Phone` (`WHERE PhoneVerifiedAt IS NOT NULL`) stops the same phone number from ever being verified on two different accounts at once — both closed after review surfaced the exact races on paper, the same "found before it shipped" discipline as the Phase 1 schema work. One correctness bug slipped through initial implementation and only surfaced when actually walking the idempotency logic afterward: the original "is this a retry" check reused the code's full 5-minute validity window, so a user whose text genuinely never arrived had no way to force a new one for up to 5 minutes. Fixed by splitting it into two separate windows — a 30-second `ResendCooldownSeconds` that only absorbs an accidental double-tap, independent of `CodeExpiryMinutes` (5 minutes), which still governs how long a code can be submitted. Two loose ends from earlier entries got closed here too, not deferred again: `GlobalExceptionHandler` (`IExceptionHandler`) now catches every unhandled exception with the same `{code, message, traceId}` envelope every other error path already promises — the exact gap the last entry logged instead of fixing — and the gateway's public-route bypass list, which had wrongly included the two OTP routes since T013 on the assumption that no JWT exists yet for them (true for Google sign-in, never true for OTP — a caller only ever reaches these two routes after Google sign-in already produced a token), now requires a JWT like every other authenticated route, which is what lets `OtpController` read `X-User-Id` the normal way instead of needing to decode anything itself.

**Where that leaves things right now (as of Aug 31, 2026):** Phases 0, 1, and 2 are fully done. Phase 3 (User Service) now has sign-in, phone verification, and a consistent error-handling story end to end — Google OAuth, RS256 JWT issuance, and OTP send/verify with brute-force lockout are all live. Next up: profile CRUD (T018, which will also need to reissue a fresh JWT the moment a user's gender or status changes mid-session, since a signed token can't be edited after the fact), identity verification (T019), and the `user.verified` Kafka event (T020) that finally unblocks Discovery Service.

## Concepts I can explain cold because of this

- **Monorepo** — one repository, many services, so a cross-service change is one atomic commit instead of coordinating several repos.
- **Polyglot services** — .NET and Java coexist because each service picks whatever runtime suits its job; there's no shared runtime dependency forcing a single language.
- **Database per service** — physically expressed here as separate folders now, separate schemas later; no service is ever allowed to query another's tables directly.
- **Event-Driven Architecture** — Kafka topics are named as past-tense facts (`connection.accepted`), not commands. A producer publishes a fact and has zero knowledge of who's listening or what they'll do about it.
- **Schema-first design** — the contract for a message is written and agreed on before any handler code exists, so producer and consumer can't quietly disagree about a field.
- **Idempotency via `event_id`** — every event carries a UUID specifically so a consumer can recognize "I've already handled this one" and safely ignore a duplicate delivery, which Kafka's at-least-once guarantee makes inevitable.
- **Outbox Pattern (set up now, implemented later)** — the plan is for services to write their outgoing event to their own database in the *same transaction* as the business change, then have a background relay publish it to Kafka — so the DB write and the event can never split apart.
- **Polyglot contract** — a shared shape (like the error envelope) is defined once in a language-neutral schema, and each language's implementation is checked against that schema independently, rather than one language's code being treated as the "real" version the other copies. It's why the C# record needs explicit `[JsonPropertyName]` tags to match — its default serializer casing differs from Java's — while the Java record needs none.
- **Shared library over copy-paste (DRY)** — instead of five Java services each writing their own error-handling class and slowly drifting apart, one Maven module (`shared-java-lib`) holds it once, and every service adds it as a dependency instead of re-implementing it.
- **Infrastructure as Code** — the entire local dev environment (SQL Server, MongoDB, Kafka, Redis, Kafka UI) is one version-controlled Docker Compose file; anyone reproduces it with one command instead of following a wiki page of manual setup steps.
- **Healthchecks as dependency gates** — `depends_on` in Compose doesn't just wait for a container to exist, it can wait for `condition: service_healthy` — the difference between "the process started" and "the process can actually take a request," which is what stops, say, a database-init job from racing a database that's still booting.
- **KRaft (Kafka without Zookeeper)** — modern Kafka runs its own leader-election and metadata storage internally via Raft consensus instead of outsourcing that job to a separate Zookeeper cluster; what used to require keeping two systems in sync is now just one.
- **API-first / Contract-first design (OpenAPI)** — the HTTP surface of every service is written down as a spec before any endpoint code exists, the same idea as schema-first Kafka contracts but applied to request/response shapes instead of event payloads; every developer agent implements *against* the spec instead of inventing endpoint shapes as they go.
- **Schema Migration (Flyway / EF Core)** — every schema change is a versioned, checked-in file rather than a manual `ALTER TABLE` someone ran once and forgot to write down; Flyway and EF Core each track what's already been applied so the same migration can never silently re-run or run out of order.
- **Geospatial Indexing** — storing a location as SQL Server's native `geography` type (instead of two plain numbers) means "how far apart are these two points" is computed correctly on a sphere and can be indexed for fast nearby-search, instead of every caller reimplementing (and likely getting wrong) the distance math themselves.
- **Race-safety via unique constraints (TOCTOU)** — "check if a row exists, then insert if not" has a gap between the check and the insert where two near-simultaneous requests can both pass the check and both insert — a **unique index** closes that gap by making the database itself reject the second insert, rather than trusting application code to never race itself.
- **TTL Indexes (Automatic Lifecycle Management)** — a MongoDB index type that tells the database itself to delete a document once a given number of seconds have passed since a timestamp field, so time-based data expiry (like the chat privacy retention window) is enforced by the database, not by application code someone could forget to write.
- **Cache-Aside** — on a request, check the cache first; on a miss, fetch from the real source of truth (SQL Server) and store the result in the cache before returning it, so only the first request pays the full cost and every request after it (until the entry expires or gets evicted) is served from memory instead.
- **Logical Database Separation** — one Redis (or SQL) server process can host several numbered, independent databases at once; using separate indices for unrelated data (a rebuildable cache vs. live connection state) keeps them from colliding without needing a second server just to keep them apart.
- **Bounded Resource Management (LRU eviction)** — capping how much memory a cache is allowed to use, and telling it to quietly discard the least-recently-used entry once it hits that cap, instead of either growing without limit (risking an out-of-memory crash) or rejecting new writes outright once full.
- **Idempotent Operations** — checking an authoritative record of what's actually true (a package manager's own install manifest) before acting, instead of an observable side effect that something else could be quietly shadowing (what a shell's PATH happens to resolve right now) — the difference between a script that settles into "nothing to do" on a second run and one that thinks it needs to act forever.
- **Guard Clauses** — check-and-return-early at the top of a step instead of nesting the real work inside an `if`; every step in the dev-setup script checks current state first and only falls through to the install branch when the check genuinely fails, so adding a new tool to check never means threading another level of nesting through the ones already there.
- **API Gateway** — a single entry point sits in front of every downstream service, so cross-cutting concerns (routing here, JWT and rate limiting next) get built once instead of duplicated across eight services; because routing is entirely config-driven, adding a ninth service later is a config entry, not a code change.
- **JWKS (asymmetric token validation)** — the service that issues a signed token publishes only its *public* verification key at a well-known endpoint; anyone checking a token's signature fetches and caches that key, but only the issuer ever holds the private key that could actually forge one — so a completely different process (the gateway) can verify identity without ever being trusted with the ability to create it.
- **Fail-closed exception handling at a security boundary** — listing every specific failure you can currently name and catching just those isn't enough for code that guards the whole platform; it also needs a final catch-all that rejects anything unrecognized, because an *unhandled* exception at a security boundary is worse than a clean rejection — it can crash into a leaked stack trace instead of just saying no.
- **Partitioned Rate Limiting** — "rate limit" isn't one global counter, it's a family of counters, each keyed to whatever dimension actually represents abuse risk for that specific endpoint: an IP for broad traffic shaping, a user ID for per-account throttling, a phone number for an SMS-cost-bearing one. Mixing the keys up (partitioning a per-user policy by IP, say) quietly defeats the whole point of picking a narrower key in the first place.
- **Sliding vs. Fixed Window Rate Limiting** — a fixed window resets its count cleanly at a boundary (simple to reason about, fine when the key space is already narrow, like one phone number), while a sliding window smooths that same count across the whole window continuously, closing the gap where a client could otherwise burst right at the reset instant. Which one to use is a choice about the abuse shape being defended against, not a performance tradeoff.
- **Multi-Stage Docker Build** — one stage carries the full compiler/SDK toolchain needed only to *produce* a compiled binary; a second, separate stage starts fresh from a much smaller runtime-only image and copies in just that compiled output. Nothing needed to build the app — the compiler, the source tree, the package cache — ships in the image that actually runs in production.
- **Repository Pattern + Dependency Inversion** — a repository hides "how is this data actually fetched" behind a plain interface (`IUserRepository`, not `UserRepository` or `AppDbContext` directly), and every caller depends on that interface, never the concrete EF Core class. Splitting one interface per aggregate (User, OTP, identity verification) instead of one fat combined interface means a caller that only needs OTP lookups never even sees a `User`-shaped method — and a unit test can substitute an in-memory fake without spinning up SQL Server at all.
- **Optimistic Concurrency (RowVersion)** — instead of locking a row for the whole read-modify-write cycle, every write includes the version value it read; the database (via a `rowversion`/`timestamp` column that auto-increments on every write) only accepts the write if that value still matches what's currently stored. If two updates race, the loser's `WHERE RowVersion = @old` clause matches zero rows and EF Core throws `DbUpdateConcurrencyException` instead of silently overwriting the winner's change — the same "version stamp" idea as a shared doc refusing to save over someone else's newer edit.
- **Brute-force Protection (Account Lockout)** — after N failed attempts inside a rolling time window, reject every further attempt outright for a fixed cooldown, rather than letting an attacker keep guessing indefinitely. The failure count is scoped to a window, not a lifetime total, so old unrelated typos from weeks ago don't quietly stack toward today's lockout.
- **Saga Compensation (chained conditions)** — a status that depends on several independent async steps only advances once every one of them is true; each step that completes checks the others rather than assuming it's the last one needed, so the order the steps happen in doesn't matter — only that all of them eventually do.
