# ShareConnectSave

## TL;DR

A travel companion discovery platform — verified travelers nearby heading the same way find each other, chat briefly, then the platform gets out of the way once they've met. Built as a learning vehicle for polyglot microservices: Java + .NET services talking only through Kafka events, each owning its own database, tied together with Saga/Outbox, SignalR, and an Angular PWA. Currently early — Phase 0 (foundation & contracts) is done, starting Phase 1 (infrastructure) of 14 phases.

## What this is

ShareConnectSave is a travel companion discovery platform — think of it as helping verified travelers who happen to be heading the same way find each other nearby. It only handles discovery, matching, and a temporary chat window; it deliberately stays out of ride booking, payments, and tracking. Once both people mark **Met Successfully**, the chat closes and the platform's job is done.

I'm building this primarily to *learn*, not just to ship — it's a real excuse to get hands-on with distributed microservices across two languages (Java and .NET), Kafka as an event bus, the Saga/Outbox pattern, SignalR, BLE, and an Angular PWA. Everything below is written the way I'd explain it out loud, so I can walk through it cold in an interview.

## How it's put together

The system is nine services behind a single API gateway. An Angular PWA talks to a YARP gateway, which fronts eight microservices — a mix of .NET (User, Chat, Notification) and Java/Spring Boot (Discovery, Connection, Rating, Report, Admin). Each service owns its own database; nobody reaches across into another service's tables. Services don't call each other directly for anything asynchronous — they publish events onto Kafka and react to what other services publish. Realtime stuff (chat messages, live notifications) rides over SignalR with a Redis backplane so it can scale across multiple instances.

The reason for this shape: it's a deliberately "textbook" microservices setup so that every classic distributed-systems problem — data ownership, eventual consistency, retries, duplicate delivery — shows up on purpose and gets solved on purpose, rather than avoided by keeping everything in one app.

## The story so far

### Phase 0 — Foundation & Contracts

**Jul 6, 2026 — we started with the skeleton.** Before any real code could exist, every service needed a place to live. So the first piece of work was scaffolding the whole monorepo: a folder per service (four .NET minimal API projects, five Spring Boot projects, one Angular app), stub Docker Compose entries for each, and shared tooling (`.editorconfig`, `.gitignore`) that works across both the .NET and Java worlds. Nothing in here has business logic yet — it's purely "the folders exist, the projects compile." The point of doing this first and doing it deliberately is that it makes the architecture visible from day one: separate folders per service is the physical manifestation of "database per service" and of keeping a polyglot stack (Java + .NET side by side) from turning into a tangled mess.

**Jul 10, 2026 — then we defined how services would talk to each other, before writing any of the code that actually talks.** Since Kafka is how all seven "reactive" services communicate, we wrote a JSON Schema contract for every one of the seven event types the platform produces (`user.verified`, `connection.accepted`, `chat.closed`, and so on), plus a README explaining who produces each event, who consumes it, and the partition/retention settings. This is "schema-first design" — agreeing on the exact shape of a message *before* either the producing service or the consuming service has a single line of handler code, so a .NET team and a Java team can't silently drift apart on what a field means. Every one of those schemas also carries a mandatory `event_id`, which is the seed of idempotency: because Kafka only guarantees "at least once" delivery, every consumer will eventually need to check "have I already processed this exact event_id?" before acting on a message — otherwise a redelivered message could double-charge a trust score update or reopen a closed chat.

**Aug 15, 2026 — next we agreed on how every service fails, not just how it succeeds.** Nine services behind one gateway means nine chances to invent nine different error shapes — one service returns `error`, another `message`, a third forgets to include anything traceable, and the Angular client ends up with nine special cases just to show "something went wrong." So before writing a single endpoint, we wrote one error contract: `{ code, message, traceId }`, defined once as an OpenAPI schema, with a C# record and a Java record both checked against that same schema independently rather than copying JSON shape from each other by convention. The Java side also got its first shared library, `shared-java-lib` — one `GlobalExceptionHandler` that every Java service will depend on instead of writing its own, so a decision made today about how validation errors look can't quietly drift five different ways across Discovery, Connection, Rating, Report, and Admin. The `traceId` field is the other half of the idea: it's read from the current OpenTelemetry trace context, never invented, so a user-visible error can later be pulled up in Jaeger as the exact request that failed — a fabricated ID would just be a dead end.

**Aug 16, 2026 — then we actually stood up the infrastructure the last three entries were building toward.** Docker Compose now brings up SQL Server, MongoDB, Kafka, Redis, and Kafka UI, all gated behind healthchecks so nothing tries to connect before its dependency can actually take a request — a one-shot init job creates one database per service the moment SQL Server reports healthy, so "database per service" is enforced by which connection string each service is handed, not just by convention. Getting it actually running (not just written) surfaced two real surprises no ticket predicted: ZooKeeper 3.5+ silently ignores its own `ruok` health-check command unless it's explicitly whitelisted, and — the bigger one — Kafka 4.0, which `bitnami/kafka:latest` now ships, removed ZooKeeper support entirely in favor of KRaft, a mode where Kafka manages its own cluster metadata and leader election internally instead of outsourcing that job to a second coordination system. So the original plan (a standalone Zookeeper container) was dropped in favor of Kafka running on its own as a single-node metadata quorum — which, not coincidentally, is also how Kafka is actually deployed in production today. That discovery only happened because we started running a real manual QA checklist after each review instead of trusting that code which reads correctly also runs correctly; the review step now writes one automatically, with exact commands and exact expected output, specifically so gaps like this get caught by a human with Docker Desktop running rather than assumed away.

**Aug 19, 2026 — then we wrote the contract for every HTTP endpoint before writing a single one of them.** Eight OpenAPI 3.1 YAML files went in, one per service, each covering every endpoint that service's functional requirements call for — auth and OTP for User, scan/nearby/BLE-resolve for Discovery, accept/decline for Connection, and so on — and every error response on every one of those endpoints `$ref`s the same `ErrorResponse` schema built in the last entry, so there's exactly one error shape across nine services instead of nine slightly different ones. This is the same "agree on the contract before the code" idea as the Kafka schemas, just applied to the HTTP surface instead of the event bus: a developer agent implementing User Service in C# and one implementing Discovery in Java are both building against the same YAML, so neither can quietly invent its own field names. Two rules mattered enough to write down explicitly rather than leave as tribal knowledge: nothing in any of these files declares a JWT `securityScheme`, because the JWT is fully consumed at the gateway and services only ever see plain `X-User-Id`/`X-User-Role`/`X-User-Gender` headers — a spec that modeled JWT auth would quietly break every future generated client into sending a bearer token nobody downstream expects; and the Discovery service's "nearby users" response schema has no `gender` field at all, by comment and by design, because the whole point of women-only mode is that gender is a server-side filter, never something broadcast back to another user. The review on this one didn't send anything back for rework, but it did surface three genuinely useful gaps — a rate-limit response using `409` instead of the more conventional `429`, a `refresh_token` field with no `/auth/refresh` endpoint to redeem it yet, and a couple of request schemas that don't reject unexpected extra fields — and rather than let those live only in a review agent's output and get forgotten by the time the affected service is actually built, they're now logged in a standing `follow-ups.md` file that future ticket creation automatically checks and folds into the relevant ticket. That's the same instinct as the `traceId`/idempotency work two entries back: a finding that isn't written down somewhere durable doesn't actually exist three weeks later.

### Phase 1 — Infrastructure

**Aug 20, 2026 — then we gave every relational service an actual schema to run against.** Five SQL Server databases got their first migration each — Flyway scripts for the three Java services (Discovery, Connection, Rating), an EF Core migration for User Service — following the same "agree on the shape before the code" instinct as the Kafka and OpenAPI contracts, just applied one layer lower, to the tables themselves. Discovery's `scan_sessions` table is the interesting one: instead of storing a stated destination as two plain floats and computing "how far apart are two points" by hand in application code (which quietly gets spherical distance wrong if you just subtract lat/lng like they're flat coordinates), it uses SQL Server's native `geography` type in a computed column, backed by a spatial index, so "find travelers heading near this point" is fast without any custom math. Getting that column to actually build correctly surfaced a real gotcha, the same kind of "looks fine, isn't" surprise as the Kafka/Zookeeper one from Phase 0: SQL Server refuses to index a computed column unless six specific session settings are all switched on first, and the tool used to hand-verify the migration (`sqlcmd`) defaults those settings differently than the JDBC driver Flyway will actually use in the running service — so a migration that visibly worked during manual testing would have failed the moment it ran for real. The review process also caught three race conditions the schema didn't originally guard against: nothing stopped two near-simultaneous OTP requests for the same phone number from creating two independent attempt counters (quietly defeating the 5-attempt lockout), nothing stopped a double-submitted rating from counting one interaction twice toward a trust score, and nothing stopped two duplicate pending connection requests reaching the same recipient. All three are now closed with unique (or filtered-unique) indexes — the database itself refusing the second write, rather than trusting application code to check first and never race itself.

**Where that leaves things right now (as of Aug 20, 2026):** Phase 0 (foundation & contracts) is done, and Phase 1 (infrastructure) has its first piece in place — SQL Server schemas for User, Discovery, Connection, and Rating services, geospatially indexed and concurrency-safe. Still to come in Phase 1: MongoDB setup for Chat/Report, Redis config for the discovery cache and SignalR backplane, Kafka topic initialization, and the JDK dev-setup script. Phase 2 (API Gateway) starts once Phase 1 wraps up.

## Concepts I can explain cold because of this

- **Monorepo** — one repository, many services, so a cross-service change is one atomic commit instead of coordinating several repos.
- **Polyglot services** — .NET and Java coexist because each service picks whatever runtime suits its job; there's no shared runtime dependency forcing a single language.
- **Database per service** — physically expressed here as separate folders now, separate schemas later; no service is ever allowed to query another's tables directly.
- **Event-Driven Architecture** — Kafka topics are named as past-tense facts (`connection.accepted`), not commands. A producer publishes a fact and has zero knowledge of who's listening or what they'll do about it.
- **Schema-first design** — the contract for a message is written and agreed on before any handler code exists, so producer and consumer can't quietly disagree about a field.
- **Idempotency via `event_id`** — every event carries a UUID specifically so a consumer can recognize "I've already handled this one" and safely ignore a duplicate delivery, which Kafka's at-least-once guarantee makes inevitable.
- **Outbox Pattern (set up now, implemented later)** — the plan is for services to write their outgoing event to their own database in the *same transaction* as the business change, then have a background relay publish it to Kafka — so the DB write and the event can never split apart.
- **Polyglot contract** — a shared shape (like the error envelope) is defined once in a language-neutral schema, and each language's implementation is checked against that schema independently, rather than one language's code being treated as the "real" version the other copies. It's why the C# record needs explicit `[JsonPropertyName]` tags to match — its default serializer casing differs from Java's — while the Java record needs none.
- **Shared library over copy-paste (DRY)** — instead of five Java services each writing their own error-handling class and slowly drifting apart, one Maven module (`shared-java-lib`) holds it once, and every service adds it as a dependency instead of re-implementing it.
- **Infrastructure as Code** — the entire local dev environment (SQL Server, MongoDB, Kafka, Redis, Kafka UI) is one version-controlled Docker Compose file; anyone reproduces it with one command instead of following a wiki page of manual setup steps.
- **Healthchecks as dependency gates** — `depends_on` in Compose doesn't just wait for a container to exist, it can wait for `condition: service_healthy` — the difference between "the process started" and "the process can actually take a request," which is what stops, say, a database-init job from racing a database that's still booting.
- **KRaft (Kafka without Zookeeper)** — modern Kafka runs its own leader-election and metadata storage internally via Raft consensus instead of outsourcing that job to a separate Zookeeper cluster; what used to require keeping two systems in sync is now just one.
- **API-first / Contract-first design (OpenAPI)** — the HTTP surface of every service is written down as a spec before any endpoint code exists, the same idea as schema-first Kafka contracts but applied to request/response shapes instead of event payloads; every developer agent implements *against* the spec instead of inventing endpoint shapes as they go.
- **Schema Migration (Flyway / EF Core)** — every schema change is a versioned, checked-in file rather than a manual `ALTER TABLE` someone ran once and forgot to write down; Flyway and EF Core each track what's already been applied so the same migration can never silently re-run or run out of order.
- **Geospatial Indexing** — storing a location as SQL Server's native `geography` type (instead of two plain numbers) means "how far apart are these two points" is computed correctly on a sphere and can be indexed for fast nearby-search, instead of every caller reimplementing (and likely getting wrong) the distance math themselves.
- **Race-safety via unique constraints (TOCTOU)** — "check if a row exists, then insert if not" has a gap between the check and the insert where two near-simultaneous requests can both pass the check and both insert — a **unique index** closes that gap by making the database itself reject the second insert, rather than trusting application code to never race itself.
